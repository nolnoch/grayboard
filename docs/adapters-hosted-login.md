# Hosted adapter login

```doc-meta
owns: a hosted adapter's sign-in, grant store, refresh and the lock rule
invariants: static mode (OpenCode V2 and hosted core's pi, omp and Claude Code) comes only from the launcher's environment, needs a pinned issuer, and treats a 401 as the end of the run; hosted core's static mode never reads, writes, refreshes or revokes a person's grant store; an adapter never resends a refresh token whose outcome is unknown, it revokes it; every hosted-core cross-process exclusion is a kernel-released lock, never taken over; a root's delivery runs only while its process holds that root's delivery lock
code-pointers: adapters/opencode-v2/src/binding.ts and lifecycle.ts (static mode), adapters/hosted-core/src/static.ts (hosted core static mode), adapters/hosted-core/src/login.ts, adapters/hosted-core/src/storage.ts, adapters/hosted-core/src/lock.ts, adapters/hosted-core/src/offer.ts, src/shared/endpoint.ts, src/shared/signin.ts
companions: server-oauth.md (the authorization server and built-in clients these adapters sign in to), adapters-hosted.md (the adapters themselves), server-hosted-mcp.md (the MCP endpoint the grant reaches)
```

**Adapter login and the lock rule** (#430). An adapter signs in with loopback OAuth and PKCE S256 under its built-in client and keeps its grant in one store per resource and client id under its state dir (`adapters/hosted-core/src/login.ts`, `adapters/hosted-core/src/storage.ts`; 0600 in a 0700 dir, written atomically); a login mints a new `epoch`, which is part of the enrollment's `configHash`, so a new login (possibly another account) is a credential drift. The resource, the MCP URL the tool proxy dials and the discovered issuer must be canonical HTTPS, or HTTP only on `localhost`, `127.0.0.1` or `[::1]`, with no credentials, query or fragment (`canonicalEndpoint`, `src/shared/endpoint.ts`; `grayboard setup-opencode` applies it plus stricter rules of its own, and `setup`/`refresh-adapters` apply it to pi's and omp's URL). Every cross-process exclusion is a kernel-released lock (`adapters/hosted-core/src/lock.ts`: a `node:sqlite` connection holding `BEGIN EXCLUSIVE` on the lock file, since neither Node nor Bun has `flock`): the kernel drops it when the holder dies, so nothing goes stale by age and nothing is ever taken over. A refresh holds `<store>.refresh.lock` across read-store, request and write-store, so N processes sharing a store send one refresh; while another process holds it, a still-valid access token serves at once (the SDK's request timer is already running), and only an expired token, or the one a 401 just rejected, waits for the lock: a waiter that gets it returns the token the holder wrote or refreshes itself, and one whose deadline passes with no usable token reports a retryable "refresh in progress" (`RefreshInProgress`, retried like an outage without spending the retry budget). The holder writes `pending` before its request and clears it only where the token provably wasn't spent: a failure known to come before the request was sent (refused, unresolvable, unroutable, a connect timeout), or grayboard's own refusal from before its token transaction (`invalid_client`, which is `ServerOutdated`; `temporarily_unavailable` on a 503 or a 429, an outage that spends no budget). `invalid_grant` means the token is dead: a new login, never a retry. Anything else (a TLS failure, a lost response, a timeout, another status, an invalid 200 body, a holder that died with `pending` set) is an unknown outcome and is never sent again, because the server revokes the whole grant on any reuse of a spent refresh token with no grace window: the adapter revokes that token (audited `oauth.revoked`, not a replay) and asks for a new login, recording a printable cause (never a body or a token) and whether the grant was revoked or stays queued. The next login, successful refresh or logout sends queued revokes again; one still failing then is recorded as `revoke_queued`. One sign-in flow runs per store at a time (`<store>.login.lock`); a concurrent `login()` waits and, once it holds the lock, shares the store's grant if it is live and otherwise fails rather than starting a second flow. The holder writes its authorization URL to `<store>.login.url` (unlinked when it takes the lock and again once the browser answers, before its loopback callback closes, so only a waiter's read already in flight can show a link whose callback is gone; a write or unlink that throws is a `diagnostic` with operation `login_link`, not a failed flow), and a waiter reads it only after each failed lock try (`acquire`'s `onBusy`), bounded (`readSmallJson`: an open that follows no symbolic link and doesn't block, a regular file only, at most 8 KiB, so a link to a device, a FIFO or a huge file planted there can't stall the wait or open a device, #596), so a crashed holder's leftover is read at most in the instant before the next holder unlinks it. Each distinct URL that passes `signInUrl` (`src/shared/signin.ts`, the shape the Claude Code hook accepts) and has the resource's origin goes to the waiter's own `present`, unawaited (a rejection, the plugin's decline, ends the wait with that error); a rejected one, or a link file it can't read or parse, is said once per flow, naming the check and origin, never the file's text, as a `login_link` diagnostic, which the Claude Code plugin keeps in its log and out of tool results (#592). Opening it in either process completes the holder's flow, and the waiter shares the grant. The URL carries `state` and the S256 challenge, never the verifier; a reader of the 0700 store dir already reads the tokens. An automatic sign-in (`login(signal, true)`: it started because a token request found no grant) also returns on any live grant under the lock, including one that landed before its own first read of the store, which the epoch comparison can't see; it then resolves `"current"` rather than `"signed in"`, and the adapter's sign-in record (`adapters/hosted-core/src/offer.ts`) says nothing and keeps its last outcome, while its `current` hook restarts delivery under that grant at once rather than on the credential watch's next tick (#596); an explicit login (pi `/login`) still runs a flow unless another process's landed while it started. A sign-in that can't take the refresh lock to commit revokes its new grant instead of writing it. Two processes on one raw session would share one lease and both admit every item (`delivery_open` returns the live capability for the same session and ownership), so a root's delivery runs only while its process holds that root's delivery lock (`tryDelivery`, `adapters/hosted-core/src/storage.ts`; `RootDelivery` takes it, the Controller doesn't), and tools-only otherwise. While another process holds it (`DeliveryHeldElsewhere`), `bind` and `unbind` are refused, since the binding is the holder's. A lock that can't be opened at all (not BUSY) is said and runs tools-only with no waiter (its polling would fail the same way each time) and no held claim, so `bind` and `unbind` still work; a resume tries the lock again.

## OpenCode V2 static mode

A service's OpenCode run signs in with a run token, not a browser (#270 D3; the credential and its mint: `server-oauth.md` §2 Service credentials). The launcher sets `GRAYBOARD_AUTH=static`, the pin `GRAYBOARD_ISSUER` (HTTPS only, and otherwise hosted core's issuer rule, `issuerEndpoint` in `src/shared/endpoint.ts`, vendored: the endpoint rule (no credentials, query or fragment, nor anything `new URL` would read past), and only a string the server's own issuer rule (`oauthPublicUrl`) can advertise, which is exactly `new URL`'s serialisation of it, with any explicit default port the server keeps and no trailing slash, which the server strips (`https://host`, never `https://host/`); so a pin hosted core refuses, one `new URL` rewrites (case, `https:host`, empty userinfo, a numeric or IDN host) or one ending in `/` fails at launch, not later as a metadata mismatch, #1321, #1326), optionally `GRAYBOARD_PRINCIPAL` (the service whose token may auto-enroll) and the token `GRAYBOARD_RUN_TOKEN`, which the native entry takes as `Authorization: Bearer {env:GRAYBOARD_RUN_TOKEN}` (OpenCode substitutes `{env:}` in config files). `staticMode` and `pluginOptions` (`adapters/opencode-v2/src/lifecycle.ts`) read the mode, pin and principal from the environment only: plugin options come from any config layer, a repository's `opencode.json` included, so none of them turns it on or sets its pin. Bun loads `.env` files from the working directory into the environment at startup, so a dotenv file there that names any of the four (`=` or `:`, optional `export`) refuses the mode. Unset `GRAYBOARD_AUTH` with no run token is OAuth; a lone pin or principal is ignored, but a run token without the mode is a refused mode with hosted core's text (#1313), since a launcher that set one meant static, and an OAuth user's shell that exports one for another client (the Rust example's static path) must unset it. Any other value, or a missing or malformed pin, is a refused mode: every capture, and every read of the entry, fails with `identity` and the refusal whatever the entry's shape, and it never falls back to OAuth. Unlike hosted core, it doesn't compare the exec-time environment, so a variable set after exec by anything other than a working-directory dotenv file goes unseen.

- **Shape.** `Binding.endpoint` (`adapters/opencode-v2/src/binding.ts`) takes exactly an enabled HTTPS remote entry with `oauth: false`, one `Authorization` header that is `Bearer` plus 16 to 512 visible characters, and no grayboard authority header (identity, lease, client); OAuth mode still refuses that shape, so static authority exists only in static mode.
- **Pin.** The entry's origin must be the issuer's, and the server's protected-resource metadata for the entry's path, fetched with redirects refused and no token, must name the entry's URL as `resource` and the issuer among `authorization_servers` (`vouch`, once per URL per process). The issuer is the launcher's word; the metadata binds it to the entry's URL. This guards who can enroll a root: the `whoami` that decides auto-enroll, and every plugin wire, reach only the pinned server. It doesn't protect the token, which OpenCode has already sent to whatever URL the entry names before any plugin code runs.
- **Enrollment.** Constant connection and client IDs (`static`, `service-credential`), and a `configHash` over the URL, the other headers and a SHA-256 fingerprint of the token: a new token drifts the root, as a new login does in OAuth mode. Nothing stores the token; the only stored value is the fingerprint of a rejected one.
- **A 401 ends the run.** Client credentials mint no refresh token, so `unauthorized` records the token's fingerprint and throws `AccessExpired` with `login_required`, which the Controller pauses on with no retry and no host refresh (only `expired` waits for one); `refresh` returns false, and `token` refuses the rejected token from then on. The pause says the launcher must start a new run with a fresh token.
- **Auto-enroll.** On a root's `session.created`, after any configured bind, the plugin captures the entry (which runs the pin check), asks `whoami` over its own connection with no session key, so the question leaves no hosted session behind, and enrolls the root only when `principal_kind` is `service` and, if the launcher set `GRAYBOARD_PRINCIPAL`, `principal` is that service (else an entry carrying another service's token, from a repository config, would enroll as that service). The enrollment's own capture must read the entry `whoami` checked (`Binding.expectChecked` compares `configHash`), so a token swapped in by a config reload between the two is refused, not enrolled unchecked. Not an agent approving itself (principle 10): the launcher set the mode, the pin and the token, and the kind is the server's, which a user's token can't claim. Grayboard starts nothing (principle 7): the launcher started OpenCode and its session. A user's token, or a server that reports no kind, leaves the root unenrolled for `/grayboard-enroll`. A static run has no person to enroll by hand, so an attempt that fails on an outage is retried on a capped backoff, 250 ms doubling to 8 s, 8 times (#1250), with the root's record `retrying` (code `server_unreachable`) meanwhile. An outage is unreachable, a timeout, a 5xx or 429, or whoami's `rate_limited` or `internal_error` error result; at the pin check's metadata fetch, the run's first request, it throws `ServerUnreachable` rather than the pin refusal and isn't cached, so a restarting server never reads as a pin mismatch. A refusal (a 4xx metadata answer, metadata naming another issuer, any other whoami error result, a wrong kind or principal) stands. Retries that run out leave the root `unenrolled` with the outage's code and a message telling the operator to start a new run once the server answers. Close stops the retries promptly, aborting an in-flight attempt's pin check and `whoami` as well as a wait (#1285), and records the root `unenrolled` (`server_unreachable`) before its flush, since nothing resumes a retry after a restart and a saved `retrying` would claim one; nothing records after close returns. The session's end stops them with the root recorded `unenrolled`. Children never enroll.
- **Static mode trusts the opened repository and the agent as much as the launcher.** Nothing in the plugin can keep the token from them. OpenCode 2.1.4 loads `opencode.json(c)` and `.opencode/` from the working directory and every directory above it, unless its SDK host sets `project: false`; `OPENCODE_CONFIG_DIR` replaces only the global layer. A later layer's entry of the same name replaces the launcher's whole, and every layer gets `{env:NAME}` and `{file:PATH}` substitution, so a repository config can send the token anywhere (`{file:/proc/self/environ}` reads the whole environment, whatever the variable is called) before the plugin refuses the entry. A repository's plugins and local MCP servers, and the agent's own shell, read the environment too. So a per-run config dir and an unguessable variable name do not prevent the leak. An untrusted repository needs isolation: an SDK host with `project: false` (as `tests/static-host.ts` runs), or a sandbox whose network reaches only the grayboard server and the model provider. What bounds a leak: the credential's `token_seconds` set to about the run's length, and the launcher revoking the run token when the run ends (`/oauth/revoke`, `server-oauth.md` §2), plus a service per trust class with only the boards it needs. Closing replay needs sender-constrained tokens (unbuilt).
- **Setup.** `grayboard setup-opencode` and `setup` never write a static entry and leave one alone: it isn't a recognized Grayboard entry, so `setup`'s guard skips it and `setup-opencode` refuses unwritten (`src/cli/opencode-setup.test.ts`). The launcher writes its own per-run config.

## Hosted core static mode

pi, omp and the Claude Code plugin run as a service on a run token too (#1243): the same credential, mint and variables as OpenCode's (#1300: one launcher contract, no aliases), and no config entry, since hosted core holds the token itself. The launcher sets `GRAYBOARD_AUTH=static`, the pin `GRAYBOARD_ISSUER`, the token `GRAYBOARD_RUN_TOKEN` and optionally `GRAYBOARD_PRINCIPAL`. `staticMode` (`adapters/hosted-core/src/static.ts`) reads them from the process environment only; the adapter's `config.json` still names the resource. `StaticLogin` implements `SignIn` (`login.ts`), the one seam `HostedClient`, the Controller and `RootDelivery` see, so nothing below the host knows which mode it runs.

- **Turning it on.** Unset `GRAYBOARD_AUTH` with no run token is OAuth; a lone pin or principal is ignored, but a run token without the mode is a refused mode, since a launcher that set one meant static. A refused mode never falls back to OAuth: every token request throws the refusal, the host says it (pi's and omp's status, the plugin's instructions), and nothing offers a sign-in. The repository checks run first, so a refusal names the file. Any of the four whose value differs from the exec-time environment (`/proc/self/environ`, as omp's `readLaunchEnv` reads it) refuses the mode: that catches Bun's dotenv autoload (the plugin and omp run on Bun) and omp's own project `.env` loading whatever grammar their parsers take (`KEY: value` included), and also omp's home and agent-dir `.env` files, which is stricter than needed and harmless. Where `/proc` can't be read, a dotenv file in the working directory naming one (`=` or `:`, optional `export`) refuses. For the plugin, so does a `.claude/settings.json` or `settings.local.json` in `CLAUDE_PROJECT_DIR` or the working directory (both, since the project dir is itself a variable) with one as a key anywhere, read with `JSON.parse` so an escaped key reads as Claude Code reads it; an unreadable or unparseable file refuses too. Claude Code puts those files' `env` into the plugin's exec environment, so the exec-time comparison can't see them. pi (Node) loads neither, and the same rules apply anyway. The user's own `~/.claude/settings.json` isn't the repository's, so it is not checked.
- **Before the token is sent.** The first token request checks the pin as OpenCode's does (the resource's origin is the issuer's; the protected-resource metadata, fetched with no token and redirects refused, names the resource and lists the issuer), then asks `whoami` over a wire with no session key, so it starts no hosted session, and requires `principal_kind` `service` and, when `GRAYBOARD_PRINCIPAL` is set, that service. A person's token is refused: static mode is for services, and a person signs in with OAuth. The verdict is single-flighted per `StaticLogin`; a refusal is kept, an outage (`ServerUnreachable`: unreachable, 5xx, 429, `rate_limited`, `internal_error`) isn't, so a restarting server never reads as a bad pin.
- **A 401 ends the run.** Whichever request meets the revoke: one landing after a call's admission draws the server's 401 too (`server-hosted-mcp.md` §1, #1312). No refresh exists, so the first 401 records the token's fingerprint in a process-wide set and throws `AccessExpired` with `login_required`, whose action is `NEW_RUN`: the Controller pauses with no retry, a start's `resume` or `enroll` included (a sign-out there pauses the root as the run loop's does; a refresh-only `expired` doesn't), a tool call answers that text, and every later token request in the process (pi's `/new` builds a new runtime) throws before sending anything.
- **Nothing a person signs in with is touched.** `login()` and `logout()` throw, pi's and omp's `/grayboard login` and `logout` say there is nothing to do there (the launcher revokes the token), the plugin's logout command returns before reading `grants/` (exit 0 in a valid static run; in a refused one it says the refusal, that nothing was signed out, and exits 1, so a repository `.env` can't make a person's logout a silent no-op), and startup and call-time sign-in offers are skipped. A grant store already in the state dir is left byte-identical: no read, refresh or revoke.
- **Delivery state.** The delivery lock and session file are keyed `service-credential:<built-in client id>`, never a person's key, so a static run and a person's session on one machine never share a lock. The enrollment's `configHash` covers the resource, pin and principal, not the token; nothing under the state dir holds the token.
- **The server sees the credential's client.** Its hosted rows carry the `svc_…` client ID; `peer_list` shows the harness (`pi`, `omp`, `claude-code`) named by the built-in client ID the wire's client info declares (`server-sessions.md`, #1298), and `BUS_LAUNCHER=1` makes a service session a launcher for its own service's requests only (`delegation.md`, #1299).
- **Trust.** As for OpenCode: the agent's shell, repository plugins and local MCP servers read the environment, and `/proc/<pid>/environ` keeps the initial block, so nothing in the adapter keeps the token from the opened repository or the agent. The controls are the credential's `token_seconds` about the run's length, the launcher's revoke at run end, a service per trust class, and isolation for an untrusted repository.
