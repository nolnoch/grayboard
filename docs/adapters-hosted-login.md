**Adapter login and the lock rule** (#430). An adapter signs in with loopback OAuth and PKCE S256 under its built-in client and keeps its grant in one store per resource and client id under its state dir (`adapters/hosted-core/src/login.ts`, `adapters/hosted-core/src/storage.ts`; 0600 in a 0700 dir, written atomically); a login mints a new `epoch`, which is part of the enrollment's `configHash`, so a new login (possibly another account) is a credential drift. The resource, the MCP URL the tool proxy dials and the discovered issuer must be canonical HTTPS, or HTTP only on `localhost`, `127.0.0.1` or `[::1]`, with no credentials, query or fragment (`canonicalEndpoint`, `src/shared/endpoint.ts`; `grayboard setup-opencode` applies it plus stricter rules of its own, and `setup`/`refresh-adapters` apply it to pi's and omp's URL). Every cross-process exclusion is a kernel-released lock (`adapters/hosted-core/src/lock.ts`: a `node:sqlite` connection holding `BEGIN EXCLUSIVE` on the lock file, since neither Node nor Bun has `flock`): the kernel drops it when the holder dies, so nothing goes stale by age and nothing is ever taken over. A refresh holds `<store>.refresh.lock` across read-store, request and write-store, so N processes sharing a store send one refresh; while another process holds it, a still-valid access token serves at once (the SDK's request timer is already running), and only an expired token, or the one a 401 just rejected, waits for the lock: a waiter that gets it returns the token the holder wrote or refreshes itself, and one whose deadline passes with no usable token reports a retryable "refresh in progress" (`RefreshInProgress`, retried like an outage without spending the retry budget). The holder writes `pending` before its request and clears it only where the token provably wasn't spent: a failure known to come before the request was sent (refused, unresolvable, unroutable, a connect timeout), or grayboard's own refusal from before its token transaction (`invalid_client`, which is `ServerOutdated`; `temporarily_unavailable` on a 503 or a 429, an outage that spends no budget). `invalid_grant` means the token is dead: a new login, never a retry. Anything else (a TLS failure, a lost response, a timeout, another status, an invalid 200 body, a holder that died with `pending` set) is an unknown outcome and is never sent again, because the server revokes the whole grant on any reuse of a spent refresh token with no grace window: the adapter revokes that token (audited `oauth.revoked`, not a replay) and asks for a new login, recording a printable cause (never a body or a token) and whether the grant was revoked or stays queued. The next login, successful refresh or logout sends queued revokes again; one still failing then is recorded as `revoke_queued`. One sign-in flow runs per store at a time (`<store>.login.lock`); a concurrent `login()` waits and, once it holds the lock, shares the store's grant if it is live and otherwise fails rather than starting a second flow. The holder writes its authorization URL to `<store>.login.url` (unlinked when it takes the lock and again once the browser answers, before its loopback callback closes, so only a waiter's read already in flight can show a link whose callback is gone; a write or unlink that throws is a `diagnostic` with operation `login_link`, not a failed flow), and a waiter reads it only after each failed lock try (`acquire`'s `onBusy`), bounded (`readSmallJson`: an open that follows no symbolic link and doesn't block, a regular file only, at most 8 KiB, so a link to a device, a FIFO or a huge file planted there can't stall the wait or open a device, #596), so a crashed holder's leftover is read at most in the instant before the next holder unlinks it. Each distinct URL that passes `signInUrl` (`src/shared/signin.ts`, the shape the Claude Code hook accepts) and has the resource's origin goes to the waiter's own `present`, unawaited (a rejection, the plugin's decline, ends the wait with that error); a rejected one, or a link file it can't read or parse, is said once per flow, naming the check and origin, never the file's text, as a `login_link` diagnostic, which the Claude Code plugin keeps in its log and out of tool results (#592). Opening it in either process completes the holder's flow, and the waiter shares the grant. The URL carries `state` and the S256 challenge, never the verifier; a reader of the 0700 store dir already reads the tokens. An automatic sign-in (`login(signal, true)`: it started because a token request found no grant) also returns on any live grant under the lock, including one that landed before its own first read of the store, which the epoch comparison can't see; it then resolves `"current"` rather than `"signed in"`, and the adapter's sign-in record (`adapters/hosted-core/src/offer.ts`) says nothing and keeps its last outcome, while its `current` hook restarts delivery under that grant at once rather than on the credential watch's next tick (#596); an explicit login (pi `/login`) still runs a flow unless another process's landed while it started. A sign-in that can't take the refresh lock to commit revokes its new grant instead of writing it. Two processes on one raw session would share one lease and both admit every item (`delivery_open` returns the live capability for the same session and ownership), so a root's delivery runs only while its process holds that root's delivery lock (`tryDelivery`, `adapters/hosted-core/src/storage.ts`; `RootDelivery` takes it, the Controller doesn't), and tools-only otherwise. While another process holds it (`DeliveryHeldElsewhere`), `bind` and `unbind` are refused, since the binding is the holder's. A lock that can't be opened at all (not BUSY) is said and runs tools-only with no waiter (its polling would fail the same way each time) and no held claim, so `bind` and `unbind` still work; a resume tries the lock again.
