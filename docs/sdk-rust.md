## 1. Transport and wire

`sdk/rust/grayboard` is a second client of this contract, for services rather than harnesses: modern protocol only, raw JSON-RPC over HTTP (not `rmcp`, whose client would need a custom transport for the per-request lease header, the re-read bearer and the 429 rule). hosted-core's wire is its reference: `scripts/record_rust_fixtures.ts` records the requests `wire.ts` sends for each operation the crate implements into `sdk/rust/schema/wire/requests.json`, the Rust test `requests_match_the_reference_clients_recording` compares the crate's own requests to it, and `tests/integration/rust_fixtures.test.ts` re-records under `bun test` and fails on drift, so an MCP SDK bump that moves the envelope fails without cargo (the fixture found that a notification carries no `Mcp-Method`). Its transport rules follow `wire.ts`: a body-driven 429 (`rate_limited`) retries, up to 8 attempts with the token re-read, and a 401 retries once after the credential replaces its token; nothing else retries. A plain-text 429 is capacity. A `tools/call` that times out or loses its connection after its connect is `OutcomeUnknown`, never retried, since a repeated write doubles; so is a 502, 503 or 504 answering one, since a gateway can answer after the server acted (a read gets `Unreachable`). The connect timeout (5 s) is shorter than the request timeout (10 s), so a blackholed endpoint is `Unreachable`, and the request timeout also bounds the credential's own calls: a credential that gives no token within it, or fails transiently (`AuthError::retryable`), is `Unreachable`, since nothing was sent; a terminal credential failure is `Auth`. Refusal codes, suggested names and a holder are kept only when well-formed, as `wire.ts` `subscriberError` keeps them. A dropped `Session` only cancels its requests, its delivery stream's included, so nothing releases the lease; the server keeps the session, and its names, until the lease lapses (30 s) or, with no lease, the idle sweep. A listen stream has an ack timeout and a 15 s idle timeout (three missed keepalives), never a total-body timeout, and never reconnects on its own. Cargo isn't in the root suite or the pre-push hook: `scripts/e2e.sh rust-sdk` runs fmt, clippy, the crate's tests against a scripted endpoint, `examples/roundtrip.rs` against an in-process server as a service minting its own token (§5, `tests/integration/rust_sdk.test.ts`), and the conformance suite through the Rust driver (§4).

## 2. The delivery stream

`Session::deliveries()` (`sdk/rust/grayboard/src/delivery.rs`) ports the lease protocol of `Controller.run` (`adapters/hosted-core/src/controller.ts`) as one spawned task per stream, feeding a one-slot channel; the harness-host parts (approval, guard, drift, rotation grace, children, diagnostics) aren't ported. A change to `controller.ts`'s delivery rules must name its Rust counterpart: only `delivery_tests.rs` (a test per rule below, against a stateful scripted bus) and the example catch drift. Differences from the controller follow from handing items to a caller instead of admitting them inline:
- One item is out at a time, the next only after its `receipt()` lands, since the server receipts direct items only as an in-order prefix of unread; so the in-process dedup state is that one item, not a 100-key set.
- The lease renews in the background while the caller holds an item; the controller has no renew between admission and receipt (#845).
- A `Delivery` dropped without `receipt()` is a failed acceptance (a failure, and the item is shown again).
- Lease losses count with an item out too (the controller exempts losses inside an item, whose admission is brief), so a lease that never comes back can't keep a held item reopening forever.
- `stable_id` hashes no issuer: `delivery_open` returns none, and an endpoint has one.

The subscriber connection outlives leases, so the task clears `X-Grayboard-Lease` before every `whoami`, `bind` and `delivery_open`, and closes each lease's listen stream (its `notifications/cancelled`) before anything that follows: one sent after `session_end` would start a new session under the same ID. `delivery_release` ends the session on the server (`store.end`), so every release (a dropped stream, `end()`, `receipt_capacity` recovery) is followed, if delivery goes on, by rebinding the remembered holds with `create: false`; a second stream on the same `Session` starts after the dropped one's release. The bind rule lives in `call_raw`: `bind`/`unbind` pause the stream, run, refresh the remembered holds from the subscriber `whoami` (after every `bind`/`unbind`, stream or not, since a later stream rebinds them), and resume; an `unbound: true` or alias-lost result on another call restarts it, though not while a bind holds it paused. Unbinding the last hold idles the stream until the next `bind`, giving up a held item; a dropped `Session` ends an idle stream.

| Rule | Reference |
|---|---|
| Open: `whoami`; if nothing is held, bind the remembered holds with `create: false`; if holds differ from the remembered ones, stop (`holds_changed`); an invalid `whoami` (a child session) stops at once | `controller.ts` open, `model.ts` `bindingOf` |
| `whoami` reports `alias_lost`: drop those holds; if none remain, stop (`alias_lost`) | `controller.ts` |
| `delivery_open`: validate `capability` (43 url-safe chars), `ownership`, `bind_gen`, `expiresAt`, an identity naming the first hold (another identity reopens once, then stops: `identity`); send the capability as `X-Grayboard-Lease` | `model.ts` `leaseOf` |
| Listen on `grayboard://inbox`, required in the honored filter; a hint only marks the inbox dirty; the first read is unconditional; a full page (100) means read again; no client cursor | `wire.ts`, `controller.ts` |
| Per item: check `ownership`/`bind_gen`/`address` against the lease (`identity`), `delivery_renew`, hand over, renew every interval until `receipt()`, then `delivery_receipt({ ids: [id] })` | `controller.ts` |
| After a reopen, an item out keeps its handle under the same `ownership:bind_gen:id` key once the new lease's read shows it, and an accepted one goes straight to its receipt; under another key, or not on a full page, the handle is `DeliveryLost` and the item comes again; absent from a short page, its receipt landed | `controller.ts` |
| `stable_id`: `msg_` + SHA-256 of `[1, principal, resource (the endpoint), address or null, item ID, session ID]` | `model.ts` `stableID` (v4, with issuer) |
| Renew every 10 s (TTL 30 s, `src/server/hosted.ts`); an idle renew re-reads the inbox; a healthy renew resets the loss and outage counts | `controller.ts` |
| Stream closed or unreachable: reopen from `whoami`, backoff `min(8 s, 250 ms * 2^n)`, no limit | `controller.ts` |
| Lease lost (`not_found`/`unbound` on `delivery_open`, `delivery_*` or an inbox read): reopen; a fourth loss without a healthy renew stops (`lease_lost`) | `wire.ts`, `controller.ts` |
| An item shown a ninth time (hand-overs and reconfirmations), or 8 other failures in a row: stop (`retry_exhausted`, naming the item) | `controller.ts` |
| `alias_held`, `identity_unknown`, terminal credential (`Auth`) and scope errors: stop at once with that error; a transient credential failure is `Unreachable`, the row above (§5) | `controller.ts` |
| `receipt_capacity`: `delivery_release`, then reopen (server side: `src/server/mcp-resources.test.ts`) | `controller.ts` |
| Admission-throttled reopen: wait `max(retry_after_ms, min(8 s, 500 ms * 2^n))`, 8 tries of the transport's own 8 attempts, then the transport's `RateLimited` | `controller.ts` |
| Close (`end()`, or the stream dropped): `delivery_release`, then (`end()`) `session_end` | `controller.ts` |

A stop is one terminal `Err` before the stream ends, delivered even through a pause or restart while the channel is full. A delivery receipt is not `dm_ack`. Renew interval and backoff units are `Timeouts` fields. The example (`examples/roundtrip.rs`) is a queue worker: bind, `board_subscribe` push, take a work item and a DM from the stream, receipt both, reply in the item's thread, `dm_ack` the DM, end; with `GRAYBOARD_RUN_TOKEN` (static mode's run-token name, #1300) in place of the client ID and secret it uses `StaticBearer`; `tests/integration/rust_sdk.test.ts` posts only once the Rust session is subscribed with an open lease, then asserts on server state.

## 3. Typed tools

`sdk/rust/grayboard/src/tools.rs` has one argument struct per tool the crate sends (every native tool, and the subscriber tools the delivery stream and `end()` send; the stream builds its requests from them too) and a typed method on `Session` per native tool, each wrapping `call_raw`, so `bind` and `unbind` keep the bind rule (§2). A struct mirrors its tool's input schema field for field: `Option` is an optional property, left out when `None` (`skip_serializing_if`), and `deny_unknown_fields`. Where the schema says `number` the struct may narrow to an unsigned integer (IDs, limits, `ttl_minutes`); `dm_inbox`'s `days` stays `f64`, since a fractional day is valid. Results: a refusal is `Error::Refusal` with the server's code; a JSON value (`structuredContent`, else the first text block) is read into the tool's result struct; the five unit tools (`board_subscribe`, `claim_release`, `claim_watch`, `dm_retract`, `peer_status`) take any non-refusal result as success, whatever its text (today `"ok"`, `"ok: …"`, `claim_release`'s `"released …"` or `dm_retract`'s `{}`), so a reworded confirmation isn't drift; `dm_ack` alone reads a bare `"ok"` or `"ok: …"` as a full ack, and no value with any other text as `InvalidResponse`; text blocks after the first are `Reply::notices`. Two non-refusals look like failures and are results: `claim_take` on a key someone else holds (`ClaimTaken::Held`) and a partial `dm_ack` (`Acked::not_found`).

How a schema change fails CI:
- A `src/core/tools.ts` change fails `tests/integration/hosted_core_snapshot.test.ts` (root suite, no cargo) until `bun scripts/snapshot_native_tools.ts` rewrites the snapshots, `sdk/rust/schema/{native,subscriber}-tools.json` included (descriptions stripped, so an instruction-text edit never moves the SDK).
- The rewritten snapshot then fails `argument_structs_match_the_schema_snapshot` (`tools_tests.rs`, `scripts/e2e.sh rust-sdk`): per tool, property names, required set, primitive types (`null` dropped: `Option<T>` is optional, not `T | null`), enum values and item shapes of the struct's schema (`schemars`, a dev-dependency only) must equal the snapshot's, and a snapshot tool with no struct fails. The subscriber tools the crate never sends are named in `NOT_SENT` (`session_register`), so a new subscriber tool fails until someone decides. `serialized_samples_validate_against_the_snapshot` serializes every struct with all fields set and with only the required ones and validates each against the snapshot's `inputSchema`, so a serde rename fails on `additionalProperties: false`. Its validator is a small in-file one for the keywords the snapshots use and fails on any other, so a snapshot that starts using a new keyword can't pass unchecked (`pattern` alone is accepted unchecked).
- No tool declares an `outputSchema` (every session would pay for it in `tools/list` on every start, principle 2; a follow-up measures that cost first), so result structs are tolerant readers: optional and defaulted fields, unknown fields kept in `extra`, `call_raw` as the backstop. Their contract is a recording: `bun scripts/record_rust_responses.ts` writes one real result per native tool into `sdk/rust/schema/responses/`, times, session IDs and the server version normalized to stand-ins of the same JSON type, `bind`/`unbind` prose to a placeholder and each run of string instruction lines to one (an instruction that stops being a string is still drift); `tests/integration/rust_responses.test.ts` re-records under `bun test` and fails on drift or a native tool with no recording; `every_recorded_response_reads` reads each through its typed method's own reader (`Typed::read`). One recording reaches one server branch, so a field the server adds only on another (`whoami`'s `alias_lost` after a revocation, `unbound` and `candidates`; a send's `wakes: false`; a bounce's `kind`) is typed from the server source instead, and `whoami`'s, which delivery depends on, are checked by a fake-server unit test.
- Rejected: build-time codegen (`typify`): an added optional argument compiles clean, so a schema change wouldn't fail CI, and generated names would become public API.

## 4. The conformance driver

The conformance suite (`tests/conformance/`, #926) states each scenario once and runs it under every driver; the Rust SDK is a third, `hosted/rust`, beside `local` and `hosted`. `Driver.label` names a driver in test names and skip lines, while `mode` stays `"hosted"` for the Rust one, so mode-tagged scenarios apply as written.
- `sdk/rust/conformance-driver` (a workspace member, `publish = false`) speaks JSON lines on stdio, one process per bus: `{"id","op":"peer","peer","url","issuer","client_id","secret","session"}` opens a session in push mode as the service whose credential that is (every peer shares one `ClientCredentials`, made from the first peer's fields), binds `peer` with `create: true` and opens its lease; `{"id","op":"call","peer","tool","args"}` answers `{"id","result":<raw CallToolResult>}` from `call_raw`, refusals included, so `outcome()` in `tests/conformance/driver.ts` reads it unchanged; `{"op":"close"}` ends every session and exits 0, or 1 if any end failed (the TS side then throws with its stderr). A failure outside the tool (transport, a refused peer bind) answers `{"id","error"}`, which the TS side throws with. Requests may be pipelined and are answered by id; one peer's calls run one at a time.
- The lease follows `hostedDriver()`: after a successful `bind` or `unbind` whose answer's `name` isn't null, the driver reopens it with `delivery_open` and `set_lease`. The SDK reopens a lease itself only under `deliveries()`, which the driver doesn't open: a stream renews per item and reads the inbox, and its release ends the session, none of which the TS hosted driver does.
- `rustDriver()` joins `DRIVERS` only when `GRAYBOARD_RUST_DRIVER` names the built binary. Each bus is a compiled server (`dist/grayboard-server`) as a `ServerProcess`; an admin creates the service `conformance` and one credential through the admin routes, and the driver's peers are sessions of that service sharing one `ClientCredentials` (§5), so nothing seeds the store and the run doesn't depend on its shape (the Postgres cutover, #807). Handles come back qualified by the service (`conformance/`) and are stripped as `hostedDriver()` strips the email. Every scenario passes with service principals as the peers: no scenario depends on the principal being a user. `scripts/e2e.sh rust-sdk` builds the driver and the server and runs the suite.
- Conformance covers `call_raw` (its `bind`/`unbind` path included), the transport and the envelope against the compiled server; no scenario reads deliveries, so the delivery stream is covered by `delivery_tests.rs` and the example (§2).
- Rejected: porting scenarios to Rust (two copies drift, #926).

## 5. Credentials

`Credential` (`credential.rs`) is two boxed `Send` futures, `token` and `unauthorized`, the shape of hosted-core's `AuthProvider`, so `Client` holds an `Arc<dyn Credential>` and the delivery task can be spawned. `StaticBearer` is a fixed token, a 401 terminal. `ClientCredentials` is a service credential (#270; the mint: `server-oauth.md` §2 "Service credentials"):
- The caller pins the issuer: the metadata (RFC 8414, read once) must name it exactly, and the token and revocation endpoints must be on its origin, which must be the endpoint's. Both URLs must be HTTPS, or HTTP to a loopback host, so the secret never crosses a network in the clear. Why pinned rather than discovered from the protected-resource metadata: the secret goes wherever the metadata points, so a server that could name another issuer could collect it.
- The mint is `grant_type=client_credentials` with the client ID and secret form-encoded in the Basic header (`client_secret_basic`, RFC 6749 §2.3.1; reqwest marks it sensitive) and `resource` = the MCP endpoint. The answer carries no refresh token, so renewal is another mint.
- One token is cached and shared by every clone, so several `Client`s on one credential stay under the server's per-credential mint bucket and unexpired-token cap. Concurrent callers wait on one mint (a `tokio::sync::Mutex` held across it).
- Re-minted at 80% of its lifetime (clamped to 366 days, the server's ceiling), timed from the request's start: the server closes a listen stream when its token expires, so the delivery stream's reopen must find a fresh one. A renewal that fails keeps serving the current token until it expires.
- `unauthorized` re-mints once: a rejection of a token already replaced is answered `Ok` with no mint, and a rejection of the replacement fails that request and drops it, so the next `token` mints afresh. This bounds a server that rejects every token to two mints per request, which its bucket then throttles.
- A 429 (`slow_down` from the mint bucket or cap, or the token route's own limit, whose `Retry-After` is honoured up to 60 s), a 5xx, an unreachable server or a malformed answer back off: 1 s doubling to 60 s. With no usable token, `token` waits out a backoff of up to 2 s itself, since the transport bounds it by the 10 s request timeout; a longer one fails the request at once. These failures are transient (`AuthError::retryable`) and the transport surfaces them as `Error::Unreachable`, so the delivery stream rides out an authorization-server outage around a token's expiry as it does a server outage, reopening without limit. `invalid_client` (a revoked or expired credential or secret, a disabled service), any other non-success status (a 4xx, or a redirect: redirects are never followed), an issuer mismatch or a server without the grant are terminal (`Error::Auth`, which stops the stream): the credential is dead and every later call fails with that text without asking the server.
- The secret is kept out of `Debug` output and every error; only the server's OAuth `error` code is quoted, capped (`server_text`). `credential_tests.rs` checks both, the wire, the cache, renewal, backoff and the terminal cases against a scripted authorization server.
- `revoke()` ends the current token at the revocation endpoint with the same Basic auth (the server revokes only its own credential's token), so a run's token ends with the run; the example calls it after `Session::end`. The token is out of service from the call's start, so a later `token` mints anew; a failed revocation keeps it pending, and the next `revoke` retries it rather than answering `Ok` with nothing sent.
- A credential's `source` picks the session key the server reads; the SDK always sends `io.github.nolnoch.grayboard/sessionID`, so it needs a `generic` credential (an `opencode` one reads `ai.opencode/sessionID`, so the SDK's session IDs would go unread and its sessions get only the unbound reads). `tests/integration/rust_sdk.test.ts` asserts the session row under the generic key, the example's credential as its client, the binding `<service>/w-1` and the revoked token (#929 criterion 4).
- Not built: browser PKCE, refresh rotation, a grant store (no Rust caller is a person; principle 12).
