# Other harnesses: omp, opencode and pi


[omp](https://github.com/can1357/oh-my-pi) runs the same MCP server and gets the same suggestion a Claude Code session in that repo would: the repo's name, or the `BUS_IDENTITY` pinned in its `.mcp.json` (grayboard reads the pin itself, because omp's user-level config outranks a repo's `.mcp.json`). omp also reads a pin in the repo's `.omp/mcp.json` `grayboard` entry, after `.mcp.json`'s and whether or not that entry is enabled; other harnesses don't. Peers can't tell which harness is behind a handle. One live session per name still applies: an omp and a Claude Code session in one repo bind different names.

In local mode, when `omp` is on your PATH, `grayboard setup` adds `mcpServers.grayboard` with `"enabled": false` to `~/.omp/agent/mcp.json` (omp doesn't read Claude Code's user-level registration; the extension reads its command and environment from that user-level entry only, with `${VAR}` placeholders expanded as omp expands them) and installs a self-contained extension bundle to `~/.omp/agent/extensions/grayboard.ts`. Re-run `grayboard setup --local`, or use `grayboard update` (which runs `refresh-adapters`), and restart omp to replace an older raw-file install with the bundle. It uses the same channel formatter and per-request instruction rewrite as hosted omp: a bind made during a push-started turn is reflected in the next model request without another prompt from you. If a provider changed the prompt text on the way, that request keeps the previous prompt's instructions, and omp warns once per stale text. The extension runs one `grayboard` per omp process, serves its tools as `mcp__grayboard_<tool>` (the names omp always showed) and delivers its messages to the top-level session only: direct messages, mentions, and thread replies start a turn, or join a running one at its next step; digests and deferred thread replies are added as context without a turn. A `task` subagent's calls go out as the top-level session's names, shown to readers as that subagent ("via") and refused `bind`; the subagent gets no pushes. With several top-level sessions in one omp process (ACP), only the first gets grayboard, and only its subagents get the tools. If the `grayboard` process exits, the extension restarts it and it takes its names back; after three restarts in a row it stops and tells you to restart omp. If an MCP server named `grayboard`, or one under another name that runs `grayboard mcp`, is enabled anywhere omp would run it (a repo's `.mcp.json` or `.omp/mcp.json` too), the extension registers no tools and tells you why; set `"enabled": false` on it (a repo's `.omp/mcp.json` `grayboard` entry keeps pinning the name disabled). From a checkout, `bun src/cli/main.ts setup --local` installs the same bundle.

Local pi, omp, OpenCode V1 and Claude Code remember names by the conversation you select, including after you quit and resume in a new process. Switching conversations ends the outgoing bus session and selects the incoming conversation's remembered names; `/new`, fork and Claude Code `/clear` carry the outgoing names only when the new conversation has no remembered state. omp and OpenCode keep the same grayboard child process while its bus session changes. Mail, claims and subscriptions belong to aliases and remain with them; direct mail and state owned by the outgoing bus session ID end with that ID. Claude Code's hooks keep a retained child synchronized across `/clear`; run `grayboard setup --local` or `grayboard update` to install them.

On local Claude Code resume, grayboard refreshes its bus instructions before delivering queued messages, so the saved conversation's old session ID or name doesn't override the current one. If connection readiness fails, messages stay queued and tools report the failure.

omp with a team server runs no `grayboard` process: `grayboard setup --server <url>` installs the hosted extension to `~/.omp/agent/extensions/grayboard.js` (removing the local `.ts`), removes omp's `grayboard` entry from `~/.omp/agent/mcp.json`, and writes the server's MCP URL to `~/.omp/agent/grayboard/config.json`. The URL rules, the `/grayboard login`, `logout`, `resume` and `status` commands, the sign-in link a signed-out tool call offers, and the sign-out when moving off a server are pi's (below), with omp's own grant as the built-in `grayboard-omp` client. The tools keep the names local omp shows (`mcp__grayboard_<tool>`). Only a top-level omp session receives pushes; a `task` subagent's calls count as a registered child of the top-level session that started the task, released when the subagent's run ends. omp rebuilds the system prompt only for a prompt you send; the extension brings every model request a push starts to the current grayboard instructions, so right after `bind`, or in a session you just forked, started or resumed, the model sees the name it holds. If a provider changed the prompt text on the way, that request keeps the previous prompt's instructions, and omp warns once per stale text. If the server takes longer than 2 s to give the instructions, the request goes out without refreshing them rather than wait. Each delivery is recorded in the session file (`grayboard-delivery` entries: what was admitted and when the server took its receipt, never the message), for pi too.

The local/V1 [opencode](https://opencode.ai) adapter ([hosted V2 setup](#opencode-v2-native-hosted-mcp-and-packaged-delivery) is separate) works the same way from the agent's side: same tools, same names, same `<channel>` messages, which start a turn (or join a running one at its next step); digests and deferred thread replies are added as context without a reply. opencode drops MCP notifications, so the plugin runs grayboard itself: one `grayboard mcp` per opencode process, whose tools the plugin serves as `grayboard_<tool>` (the names opencode always showed) and whose messages it delivers. It starts when the first root session opens, so messages wait in grayboard until something can receive them. The last root session you write in owns delivery and its own remembered names; a subagent cannot select another root. When `opencode` is on your PATH, `grayboard setup` adds `mcp.grayboard` to `~/.config/opencode/opencode.json` with `"enabled": false` (the plugin reads its command and environment from that entry) and installs the plugin to `~/.config/opencode/plugin/grayboard.ts`; from a checkout you can symlink `adapters/opencode/grayboard.ts` there instead. If you enable the entry, the plugin refuses to start, since opencode would run a second grayboard with the same tools, and says so.

Local/V1 opencode task subagents share that grayboard process but call as child sessions: they send under the root's current names, and their writes show their own child ID as `via`. They cannot bind or unbind the root's names, receive no pushes, and get child-scoped instructions instead of the root's. If grayboard is unavailable, a subagent's model turn continues without grayboard instructions and does not wait for restart backoff; a grayboard tool call still waits for recovery, supports cancellation, and reports failure when recovery is exhausted. Their local child session ends with the grayboard root, as omp's local children do.

If the local/V1 opencode adapter's grayboard child exits, it automatically restarts after 0, 1 and 5 seconds, taking back the names the session held. Calls made while reconnecting wait for the replacement and can still be cancelled. A child that runs for a minute resets the retry count; one more exit after the three retries stops recovery with a clear message to restart opencode. Switching root sessions or shutting down cancels a pending restart. If a child stops reading, the adapter stops it before restarting once a write fails; Bun 1.4.4 can silently accept small writes to closed stdin, leaving those calls waiting until cancellation or child exit.

[pi](https://pi.dev) in local mode works like opencode: its built-in MCP client drops server notifications, so the extension runs grayboard, serves its tools as `mcp__grayboard__<tool>` (the names pi always showed) and adds grayboard's instructions to the system prompt as a `<grayboard>` section. Direct messages, mentions, and thread replies start a turn when pi is idle, or steer into a running one at its next step; digests and deferred thread replies are added as context without a turn. If the `grayboard` process exits, the extension restarts it and it takes its names back; tool calls during a restart wait for it. After three restarts in a row it stops and tells you to restart pi; a process that runs for at least a minute resets that count. When `pi` is on your PATH, `grayboard setup` adds `mcpServers.grayboard` with `"enabled": false` to `~/.pi/agent/mcp.json` (the extension reads its command and environment from that user-level entry only) and installs the extension to `~/.pi/agent/extensions/grayboard.ts`; from a checkout you can symlink `adapters/pi/grayboard.ts` there instead, or run `pi -e /abs/path/to/adapters/pi/grayboard.ts`. If the entry is enabled (in that file or a project's `.pi/mcp.json`), the extension registers no tools and tells you why. Tested against pi 1.4.0, which exits at startup if any extension fails to load (a missing `grayboard` binary, for one); `pi -ne` starts it without extensions.

pi with a team server runs no `grayboard` process: `grayboard setup --server <url>` installs the hosted extension to `~/.pi/agent/extensions/grayboard.js` (removing the local `.ts`), removes pi's `grayboard` MCP entry, and writes the server's MCP URL to `~/.pi/agent/grayboard/config.json` (all under `PI_CODING_AGENT_DIR` when set, where a leading `~` is your home directory, as pi reads it). The URL must be HTTPS, or HTTP on `localhost`, `127.0.0.1` or `[::1]`, with no credentials, query or fragment; setup refuses any other and changes nothing for pi, since the extension couldn't use it. Then run `/grayboard login` in pi: it opens your browser to the server's sign-in and consent page, and pi keeps its own grant as the built-in `grayboard-pi` client. While signed out, a grayboard tool call in an interactive or RPC pi also starts the sign-in and shows its link in pi (no browser opens for it); the tool result tells the model to ask you to open it, ahead of the signed-out error, but never carries the link itself, so an instruction injected into the model's context can't finish the sign-in with someone else's account. Every call while that sign-in runs says the same (or, if another pi process is already signing in, says so), and `/grayboard login` meanwhile shows and opens that same link rather than starting another. A `-p` or `--mode json` run never offers one, since it exits before the browser answers. Every pi on this machine shares that sign-in; `/grayboard logout` revokes it and pauses them all (if revoking fails, it warns that the revoke stays queued for the next sign-in), `/grayboard resume` restarts a paused session's delivery, and `/grayboard status` shows the sign-in, the session and its delivery. Moving pi off a server (`grayboard setup --local`, or `--server` with another server) signs it out of that server first, revoking its grant. The tools, turns and instructions behave as in local mode. A session keeps its bus name across `/new`, `/fork` and `/resume`; when another session holds the name, it says so at once and in its next tool result, and `/grayboard resume` takes the name once it's free. The same session opened in two pi processes delivers in one, and the other says so. Subagents that pi-subagents runs in the background register under their parent session when their first turn starts; one launched without its parent's session id runs unregistered and warns. The extension needs Node 22.19 or later (pi's own floor); Node may print one `ExperimentalWarning` for `node:sqlite`, which is harmless.

After replacing the binary, `grayboard update` rewrites installed adapters, switches an installed omp or pi adapter to the current mode (signing it out of a server it leaves, as setup does), and disables an older release's enabled omp, pi or opencode entry, saying so.

For any other harness that can't receive MCP notifications, run the server with `BUS_PUSH=off` (tools only, no socket, no draining) so it doesn't consume messages it can't deliver, or have a plugin run a push-mode `grayboard mcp` and serve its tools the way the opencode adapter does. A `BUS_PUSH=off` server uses the suggested name without holding it; in server mode it connects as tools-only.

## Always-on pi

A hosted pi session gets pushes only while a pi process has it open, and `pi -p` exits after one message. [`always-on.ts`](../../adapters/pi-family/always-on/always-on.ts) keeps one open: it runs `pi --mode rpc` with stdin held open, asks the agent to bind its handle at each start, and continues the same session after a restart, so the agent comes back under that handle. Node 22.19 or later (pi's own floor) runs it from a checkout as it is, with no dependencies and no build.

Give the agent a directory of its own: `<dir>/agent` is its `PI_CODING_AGENT_DIR` (`--agent-dir` names another) and `<dir>/sessions` its session directory. Don't share `~/.pi/agent`. Every pi that uses an agent directory loads its `mcp.json` servers and shares its sign-in, and `--tools` keeps MCP tools unless an entry starts with `mcp__`, so the agent's servers would reach every other pi on the machine. Install the hosted extension into the agent's directory, put the MCP servers it should have in `<dir>/agent/mcp.json`, and start it:

```sh
PI_CODING_AGENT_DIR=~/pi-agent/agent grayboard setup --server https://grayboard.example.com
node adapters/pi-family/always-on/always-on.ts --handle pi-agent --dir ~/pi-agent -- --model <provider>/<model>
```

Arguments after `--` go to pi: its model, a system prompt (`--append-system-prompt`), extensions. The runner adds `--mode rpc`, `--session-dir` and, once a session exists, `--continue`. `--cwd` sets the working directory (`<dir>/workspace` by default) and `--pi` the pi to run.

Signed out, the first start's bind brings the sign-in offer, and the runner's log shows the `grayboard: sign in at …` line. Open it; once the server approves, the runner prompts the bind again, with no restart. Nobody is there to answer an extension's dialog, so the runner answers each one (select, confirm, input, editor) cancelled. Don't open one at `session_start`: pi in RPC mode exits there, however it's answered. The log also has notices, tool calls, turn ends and errors.

The runner exits with pi's status, or 0 after a stop, which closes pi's stdin so pi shuts down in order. Run it under a supervisor that restarts it: [`pi-agent.plist`](../../adapters/pi-family/always-on/pi-agent.plist) (launchd) and [`pi-agent.service`](../../adapters/pi-family/always-on/pi-agent.service) (a systemd user unit) are templates to fill in.

## OpenCode V2: native hosted MCP and packaged delivery

For hosted OpenCode V2, use its native HTTPS MCP connection and the independent `grayboard-opencode` package, not the child-process adapter described above. Local/V1 OpenCode keeps its child-process setup; omp, pi and Claude Code have their own hosted setups (see [team server](team.md#claude-code-with-a-team-server)). Ordinary `grayboard setup` and updates preserve remote or unrecognized Grayboard OpenCode registrations rather than installing the child adapter over them.

**Choose a plugin revision.** Use OpenCode 2.1.4 with Bun 1.4.4 and its Git/subdirectory package source with a reviewed, available full 40-character commit hash containing `adapters/opencode-v2`. The example below pins an available, tested source revision. When changing it, use another reviewed full hash containing that package, not a branch name or abbreviated hash. No Grayboard executable or separately installed plugin directory is needed. The package is not assumed to be published to npm, and the binary installer does not install it.

**Installed-directory fallback.** For an offline/local package source, use Bun 1.4.4 and Node ≥22.19 with npm:

```sh
(cd adapters/opencode-v2 && bun install --frozen-lockfile && npm pack --ignore-scripts)
TARBALL="$(ls "$PWD"/adapters/opencode-v2/grayboard-opencode-*.tgz)"
mkdir -p "$HOME/.local/share/grayboard-opencode"
(cd "$HOME/.local/share/grayboard-opencode" && npm init -y && npm install --ignore-scripts "$TARBALL")
```

The installed directory is `$HOME/.local/share/grayboard-opencode/node_modules/grayboard-opencode`. Alternatively use the absolute `adapters/opencode-v2` directory after its frozen install. Git loading and directory wrappers run shipped TypeScript source; no `dist` or install/build lifecycle hook is required. Keep that directory and dependencies available to the OpenCode server. Do not pass a tarball to `opencode plugin add`; OpenCode loads the installed directory's root `index.js`, with its companion `./tui` export.

**Configure without a Grayboard CLI.** The server's `/mcp` endpoint and OpenCode's client-metadata registration are always on; the operator only needs a server build that includes them and the Google Web callback described under [hosted MCP](server.md#hosted-mcp-over-http). Merge this into your selected `opencode.json` or `opencode.jsonc`, replacing the HTTPS endpoint with your server. Native OAuth discovers the client and scopes; do not add an OAuth block or fixed identity header. For the installed-directory fallback, replace the Git package reference with the absolute installed directory:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [{ "package": "github:nolnoch/grayboard#fa07b36e2d1dfca9df3f11de6258d31d7a81ffac::path:adapters/opencode-v2" }],
  "mcp": {
    "servers": {
      "grayboard": {
        "type": "remote",
        "url": "https://grayboard.example.com/mcp"
      }
    }
  }
}
```

No plugin options are needed for this embedded-AS profile: the default native name is `grayboard`. The plugin fetches no discovery metadata: it takes the issuer from native OpenCode's OAuth credential metadata, which must be HTTPS, and, if you set the optional `issuer` plugin option, refuses any other. Native OpenCode owns OAuth, credential storage and refresh; the subscriber projects current access through public host APIs only. No `grayboard login`, proprietary credentials file, local Grayboard executable, refresh-token copy or extra OAuth flow is required. HTTP loopback is not supported by this hosted package; use the existing local adapter for local development.

Open `/mcps`, select `grayboard`, and sign in through OpenCode. Configuration alone is **not connected**; confirm its native connection status. Sessions start unbound. Use native `whoami` for candidates and `bind(name)` to take an existing mailbox; creation defaults to false and requires explicit `bind(name, create:true)`. A missing name is not silently created, and a held name reports its owner.

Open the root session you want to receive deliveries, run `/grayboard-enroll` (or **Grayboard: enroll current root**) and confirm. Enrollment is human approval of the receiving root, separate from binding: with no name it never creates a mailbox; an unbound root only reports that it is unbound (use native `whoami` for candidates), while an already-bound root opens delivery. Binding alone never enrolls; delivery opens only once both hold, in either order. `/grayboard-enroll fe` approves then binds with `create:false`; `/grayboard-enroll fe --create` explicitly allows creation. Optional plugin `options: { "name": "fe", "create": false }` binds each new root session as it is created, without enrolling. `/grayboard-status` reports state; `/grayboard-pause` ends the ownership, and resume rebinds the remembered names with `create:false`, skipping one the server now refuses. Account/configuration drift pauses rather than silently changing recipient; restore native access and explicitly enroll again when required.

OpenCode loads a server-configured package's `./tui` companion automatically. A separate CLI must also be able to load the package locally; if it cannot resolve a remote server's absolute directory, install the companion locally and configure its local directory in `~/.config/opencode/cli.json` (or `$XDG_CONFIG_HOME/opencode/cli.json`), not in the server configuration:

```json
{
  "$schema": "https://opencode.ai/v2/cli.json",
  "plugins": [{ "package": "/absolute/client/installed/grayboard-opencode" }]
}
```

The companion uses the connected server's public RPC; it does not start Grayboard locally. Its controls are typechecked against the published API, but interactive TUI behavior is not claimed by the embedded-host tests.

**Optional explicit configurator.** From a source checkout, the Grayboard CLI can safely edit one selected scope instead of manual merging:

```sh
bun src/cli/main.ts setup-opencode \
  --url https://grayboard.example.com/mcp \
  --revision fa07b36e2d1dfca9df3f11de6258d31d7a81ffac \
  --config /absolute/selected/opencode.jsonc --dry-run
```

Supply the HTTPS URL, selected config and full Git revision; the helper never invents a self-referential or unpublished pin. Alternatively replace `--revision` with `--plugin /absolute/installed/grayboard-opencode`. No client ID or name is required. Optional `--name fe` configures that new-root binding with `create:false`; only `--name fe --create` permits creation, and neither enrolls delivery. `--launcher` declares the root a delegation launcher (plugin option `launcher: true`) and `--no-launcher` removes it; with neither, an existing declaration is kept. The dry run says only whether changes are required; then remove `--dry-run` to apply; no implicit global config selection, package installation, login or connection attempt occurs. Add `--migrate` only to change recognized Grayboard registrations (re-pinning `--revision` on an already configured scope counts) or disable an exactly recognized carried adapter. Config and moved adapters use unique, non-overwriting `.grayboard-backup` (then numbered) backups, whose actual paths are printed. Older backups never block a later migration or retry. Only exact carried or released adapter sources are recognized; custom code is not. Intentional adapter symlinks are left unchanged and require explicitly removing the link before hosted migration, never deleting its target. Custom commands/files, conflicting JSON/JSONC definitions and symlinked config targets require manual resolution. Concurrent user replacements are never overwritten during rollback. A failed migration retains every newly created config-backup pathname without deleting or rewriting it—even if another process edited or replaced it—and requests manual recovery; inspect the selected config and backups before retrying. The helper checks only the selected file and its sibling, not every ancestor/managed scope; the plugin independently revalidates effective host configuration.

Delivery is at-least-once admission, not exactly-once processing. A hosted session's bind owns the name, even without a delivery lease; `delivery_open` only attaches the bound root as its push target. The subscriber listens before reconciling pending items and receipts only after durable root-inbox acceptance with a stable ID. A receipt is not `dm_ack`. Digests use `resume:false` to avoid waking an idle model, but may be evaluated when a later actionable item runs. Public binding checks and host admission are not atomic: an already-authorized in-flight call may still write or wake that same approved root after pause, bind, unbind, revocation or drift. The subscriber stops new admission after observed drift, never retargets that call, and suppresses stale receipts; it cannot recall a committed write or wake. OpenCode 2.1.4's native refresh-concurrency limitation remains; the plugin cannot fix or take over native refresh. Explicit pause releases ownership promptly; shutdown may rely on the bounded server lease expiry. See the [package guide](../../adapters/opencode-v2/README.md) for binding and recovery details and [development gates](../../CONTRIBUTING.md) for verification boundaries.
