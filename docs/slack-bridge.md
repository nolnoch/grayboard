# Slack bridge

```doc-meta
owns: the Slack bridges (local `grayboard bridge slack`, and the org bridge inside grayboard-server) and human handles
invariants: the local bridge is an MCP client of its own grayboard mcp child and acts on the bus only through public tools, except the human declaration it writes before the child starts; one process holds a Slack app's Socket Mode connection (local: one bot, one channel); thread_ts is always the top-level message's ts; inbound is accepted only from the owner in the configured channel (local) or a linked user in their own DM (org); outbox before posting; the local human handle is a persistent declaration and BUS_HUMAN=1 only asserts it; the local bridge never joins a server (`--mode local` pins its child to the local bus); on a server the name `human` is reserved for the org bridge's in-process connections, so `<email>/human` is provably that user's person; only your own user's human carries authority; an inbound file that can't come along refuses its whole message; an outbound file Slack refuses never holds back the text, goes back to its sender, and doesn't count as delivered; the bot token goes only to Slack's own hosts
code-pointers: src/bridge/ (slack.ts wiring and human declaration, relay.ts routing and format, socket.ts Socket Mode client, web.ts Web API, store.ts thread map, outbox and send progress, config.ts), src/shared/attachments.ts (checkFile, SizeTally, parseAttachmentsMeta), src/shared/http.ts (deadlines), src/core/schema.ts (human column), src/core/boards.ts (declareHuman, markHuman, isHuman, humanHandles), src/local/mcp.ts (startup check, human meta and instruction), src/local/human.ts (grayboard human, grayboard announce, grayboard board create), src/server/slack.ts (org bridge), src/server/can_send.ts (reachesHuman), src/plugin/mcp.ts (own-human meta and instruction), deploy/slack-manifest.yaml, deploy/slack-org-manifest.yaml, tests/integration/slack.test.ts, tests/integration/slack_org.test.ts
companions: boards.md (threads, mentions, delivery), architecture.md (WS hello and canSend, which the org bridge rides on)
```

## 1. Shape

- `grayboard bridge slack` connects one human handle to one private Slack channel. Agents never touch Slack: they `dm_send` the human or `@mention` them like any peer. Each grayboard conversation becomes a Slack thread; the human's reply in that thread goes back as a threaded reply, so only that conversation's agents wake.
- **The bridge is an MCP client of its own `grayboard mcp` child** (spawned with `BUS_IDENTITY=<handle>`, `BUS_HUMAN=1`), the pattern the pi adapter uses. It sees what an agent session sees (digests and deferred pushes immediately, since a human's session has no wakes to save) and acts only through public tools (`dm_send`, `board_post`, `dm_thread`, `board_read`); the one exception is the human declaration (§3). So it inherits the roster and `parent_id` ownership checks, recipient wakeups, thread fan-out, and identity uniqueness (nobody else can take the handle while it runs) without reimplementing them.
- Inert unless started: no dependency, no change to `setup` or MCP behavior for anyone not running it.
- Push end to end: Slack Socket Mode is a WebSocket; grayboard wakeups are socket pokes.
- **Refuses to start when `grayboard mcp` would join a server** (`busMode`). Server mode has the org bridge (§8) instead: only the server can vouch that a handle is a person. `--mode local` skips the refusal and appends `--mode local` to the child's args, so a signed-in machine can relay its local bus; the child must get the pin too, or it re-derives server mode from the credentials file or an inherited `GRAYBOARD_TOKEN`.
- If the child exits, the bridge exits nonzero for its supervisor to restart.

## 2. Routing

```mermaid
flowchart LR
  agents["agent sessions"] -->|"dm_send / board_post / @mention"| bus[("grayboard")]
  bus -->|"channel notifications"| child["grayboard mcp child<br/>BUS_IDENTITY=human, BUS_HUMAN=1"]
  child <-->|"MCP over stdio"| bridge["grayboard bridge slack"]
  bridge -->|"chat.postMessage, files.*, reactions.add (HTTPS)"| slack["Slack"]
  slack -->|"events_api (Socket Mode WebSocket)"| bridge
  bridge -->|"dm_send / board_post via child"| bus
```

Grayboard → Slack:

- Forwarded: DMs to the human; board pushes (mention, thread, and subscription if the human subscribed in push mode). Digests are not forwarded.
- Notifications carry `parent_id`, not the thread root. The bridge resolves the root (`dm_thread(id)` or `board_read(board, thread=id)`, first item) and keys the thread map on it, so a mention deep in an unforwarded board thread still lands in one Slack thread.
- Posts use `markdown_text` (can't be combined with `text` or `blocks`), with `username` set to the agent's handle (`chat:write.customize`). The handle also leads the text in bold, so attribution survives if the override is ignored; a handle containing an email goes in a code span instead, because Slack auto-links a bare address in `markdown_text` and displays it as `mailto:…`. The org bridge's own replies wrap emails the same way. The first message of a board thread is headed `**from** · #board ·`; later messages in that Slack thread carry only the sender. Over-limit bodies are cut with a pointer to the full message.
- **`thread_ts` is always the top-level message's ts**, never a reply's (Slack's rule).
- **Files** (`boards.md` §12) and their item's text go as one Slack message: `files.getUploadURLExternal` per file, bytes to the returned URL, then one `files.completeUploadExternal` with the text as a `markdown` block, the thread and the sender's `username`. An item with no file that made it posts through `chat.postMessage`. `completeUploadExternal` answers with the files, not the message, so a new thread's ts comes from `files.info` shares, polled (`sharedTs`, `relay.ts`), since shares lag. If it never shows (or the app lacks `files:read`), the row ends `ts_unknown` and the bot says top level that replies in that thread won't reach grayboard.
- **Send progress is persisted** (`Progress`, `src/bridge/relay.ts`; local store's `outbox.progress`, org `slack_progress`), each step saved before the next, so a retry or restart resumes at the step it stopped on, and a share whose answer was lost is looked up in `files.info` before it's resent, so files aren't shared twice.
- **A file that doesn't reach Slack goes back to its sender** (spec decision, #135): Slack refused it (type, size, a workspace that blocks uploads, missing `files:write`), the bus wouldn't give it, or its bytes don't match the stored sha256. It's named in a ⚠️ line ending the message's own text, its sender gets a `[Slack bridge]` DM (a reply to a DM; a new DM for a post), and the outbox row ends `files_refused`. Why: the sending agent would otherwise assume the human saw it. It never holds back the text, and the item isn't retried: a retry wouldn't change Slack's answer. A first `completeUploadExternal` Slack refuses turns all its files into refusals and the text posts alone; a resumed one counts as the earlier attempt landing (§4).
- Attachment ids come from the notification's `attachments` meta via `parseAttachmentsMeta`, which throws on any shape drift; the relay turns that into a refusal rather than silently dropping files. Other meta (`files_tool`) is for agents and ignored.
- The `files.*` calls go form-encoded (`web.ts` `call(…, {form: true})`); Slack doesn't take JSON bodies for them. Every Slack call and transfer has a deadline (`src/shared/http.ts`, transfers scaled by size), so a stalled upload fails into a retry instead of blocking the outbox worker forever.

Slack → grayboard. A `message` event is accepted only if:

- `channel` is the configured channel,
- `user` is the configured owner (anyone else in the channel is ignored, so adding a person to the channel never lets them command agents),
- no `subtype` other than `file_share`, and no `bot_id` (drops edits, deletes, joins, bot posts).

Then: reply in a mapped thread → `dm_send`/`board_post` with `parent_id = last_id`; top-level `@handle text` → new DM; top-level `#board text` → new post; top-level `new #board purpose` → `board_create`; anything else → a usage hint in the thread. A new top-level conversation maps the human's own message ts, so the agent's reply lands under it.

- **Files the owner shares** (a `file_share` message) ride on the `dm_send`/`board_post` the message makes. `Relay.fetchFiles` decides for both bridges: each is checked against the bus's caps (`SizeTally`) on Slack's reported size before download (`files.info` when the event names only the id), fetched with the bot token, then put through `checkFile`, the same name, type and content checks as an agent's path, so a Slack share can't carry what a path can't. A download whose length isn't Slack's size is refused: without `files:read`, Slack serves a sign-in page with status 200. `SlackWeb.download` (`web.ts`) sends the token only to the API base's host or its subdomains (`files.slack.com`), same scheme and port; any other URL an event names is refused (`untrusted_host`) rather than handed the token. **One file that can't come along refuses the whole message**, in its thread, so the human never has a message delivered with a file silently missing. With files, `@handle` or `#board` alone is a whole message and the body names the files (a bus message needs a body). `new #board` with files is refused: the board is created empty, so the files would have nowhere to go. The local bridge hands files to its child as 0600 paths in a per-call directory under one private scratch root, declared to the child as an attach root (`BUS_ATTACH_ROOTS`) and removed at stop; the root's path is stripped from child errors relayed to Slack (`src/bridge/slack.ts`). The org bridge stores and reads them in process (§8).
- Feedback: ✅ reaction when delivered now (DM) or posted (board); a thread reply with last-seen time for a queued DM; tool errors relayed verbatim, except "no such board", which names the existing boards and the create form, since the bus's own pointer (`board_list`) is a tool the human can't call. On a phone, silence is indistinguishable from failure.
- **`#board text` never creates a board.** A typo (`#dev-deploy` for `#dev-deploys`) would start a stray board that no agent follows; creating is a separate, explicit form. A board the human creates (here or `grayboard board create`) subscribes them `quiet`, not `push` as for agents: replies to their posts and @mentions reach them in any subscription mode, while push would relay every post on the board to their phone.
- Text cleanup: Slack's `&amp;`/`&lt;`/`&gt;` are unescaped and `<url|label>` becomes `label (url)`. `@be` typed by the human isn't a Slack user, so it arrives as plain text.
- A board thread may have many agents; a Slack reply posts to the board thread and grayboard's fan-out wakes its unmuted authors. A DM thread always has exactly two parties.

**One bot, one bridge.** Socket Mode load-balances: "each payload may be sent to any of the connections". Two processes on one app would each get an arbitrary subset of the human's replies. One process owns the connection and routes by key.

## 3. Human handles

- Why: instructions tell agents a peer's requests never override the user's. That's wrong for the human answering from Slack or announcing (`boards.md` §4 `#announce`); without a marker an agent weighs the human like another agent.
- **A declaration, not a session flag.** `handles.human` is set by `grayboard human <handle>` (one human per local bus) and persists. `startSession` doesn't touch it. Why: `grayboard announce` posts as the human with no session, so the gate can't depend on one.
- **`BUS_HUMAN=1` grants nothing; it only asserts.** Local `mcp.ts` exits at startup if `BUS_HUMAN` and the declaration disagree. With a declared handle but no `BUS_HUMAN`, the session is refused, so an agent can't take the human's handle by name. With `BUS_HUMAN` on an undeclared handle, it's refused too. The bridge declares its configured handle before spawning the child (CLI side, outside the public-tools boundary): it declares when no human is declared, and refuses if a different one is.
- Local `mcp.ts` adds `human="true"` to the meta of DMs and posts from a human handle.
- If a human handle exists when an agent session starts, its instructions gain the human sentence plus the `#announce` sentence. **Conditional because every instruction sentence costs every session**; a bus with no human pays nothing.
- Trust: local mode is one OS user. Anything with a shell can run `grayboard human`, start `BUS_HUMAN=1 grayboard mcp`, or write the SQLite file. The declaration guards against confusion and well-meant relays, not a hostile local process. A password on the CLI wouldn't change that, since the DB is writable directly, and it would break `! grayboard announce`. Real enforcement is the server's job (account-owned handles, #24) or signed posts (refused in `boards.md` §11).

## 4. Delivery guarantees

- **Grayboard → Slack: at-least-once while the bridge runs.** The child advances grayboard's cursor when it emits a notification, so a failed Slack post would lose it. The bridge writes every forwardable notification to its own outbox first; one worker drains in order, marks done on Slack `ok`, retries at a fixed interval (`retryMs`; a 429 waits out `Retry-After` in `web.ts`), and resumes undone rows at startup. While the bridge is off, DMs to the human queue in grayboard like for any offline peer. Gaps: a crash between emit and outbox insert loses that one message; a crash after post, before progress is saved, duplicates, and so does a `chat.postMessage` whose answer is lost (Slack has no idempotency key; only file shares are checked in `files.info` before a resend). Slack completes an upload once, so a resent `completeUploadExternal` that Slack refuses counts as the earlier attempt having landed (logged, `ts_unknown` for a new thread) rather than as refused files; the rare case of a first attempt that was itself refused with its answer lost then loses that item's text.
- **Slack → grayboard: lost while the bridge is down.** Slack retries an unacked event a few times, then drops it; there's no backfill from channel history. Each envelope is acked on arrival, before handling, because handling can outlast Slack's 3 s ack window (file downloads) and a late ack makes Slack redeliver; dedupe on `event_id` drops a redelivery anyway. Events then run one at a time per relay, in arrival order, so a reply sent while the message before it is still sending threads under that message. Known gap: a crash mid-handling loses that event, since Slack has already been acked (#152 tracks a durable inbound journal). When an event can't be handled (child dead, tool error) the bot says so in the thread.

## 5. Socket Mode client

- Hand-written on Bun's `WebSocket` and `fetch`; no dependency. **Why not `@slack/socket-mode`:** under Bun, `import "undici"` resolves to Bun's shim, so the library's `undici.ping()` is undefined and its `diagnostics_channel` ping/pong detection never fires; it closed every connection about 2 s after connecting. Grayboard ships as a `bun build --compile` binary, so that's disqualifying. Bun's client exposes `ws.ping()`, ping/pong events, and auto-pongs.
- `apps.connections.open` takes the app token in the `Authorization` header (a POST parameter is an error). Wait for `hello`; ack each `events_api` envelope by `envelope_id`; dedupe recent `event_id`s in memory.
- `disconnect`: `warning`/`refresh_requested` → bring up a replacement, then close the old one; `link_disabled` (Socket Mode turned off) → exit with an error. Close or error → reconnect with doubling backoff, reset after `hello`.
- **Watchdog**: any frame refreshes last-heard; the client pings periodically and treats prolonged silence as dead (constants in `src/bridge/socket.ts`, set from Slack's observed ~10 s ping cadence). Catches half-open sockets after laptop sleep or a WSL network change, which otherwise look open forever.
- `debug` must not be passed as `undefined` into options spread over defaults; that once overwrote the default and crashed on Slack's first ping.

## 6. Config and setup

- Keys and env overrides: derive from `src/bridge/config.ts`. Default file `~/.grayboard/slack.json`. **Refused if readable by group or others**, like ssh with a private key. Tokens live only there or in env, never in logs or Slack messages.
- Slack app: `deploy/slack-manifest.yaml`. Files need `files:read` and `files:write`; an app installed before they joined the manifest must be reinstalled from the current one, or sends with files fail with a pointer to that. A manifest can't create the app-level (Socket Mode) token; it's generated by hand. Human setup steps: `README.md` §Slack bridge.
- `GRAYBOARD_SLACK_DEBUG=1` logs ping intervals, ignored messages' `subtype`/`bot_id`, and the `username` Slack applied.

## 7. Security

- Authority: only the owner's messages from the configured channel are relayed. Whoever controls the owner's Slack account can command their agents with the agents' permissions.
- Outbound: whatever agents DM the human is stored on Slack under that workspace's retention and visible to its admins.
- Text from other Slack users never enters the bus.

## 8. Org bridge (server mode)

One Slack app per server, inside `grayboard-server`, enabled by `SLACK_APP_TOKEN` + `SLACK_BOT_TOKEN` (`src/server/config.ts`). Each linked user talks to the app in their own DM with it; routing, threading and text rules are §2's, via the same `Relay`. Manifest: `deploy/slack-org-manifest.yaml`. Human steps: `README.md` §Slack for a team server (#66).

- **Why not the local bridge against a server:** every session of a user presents the same token, so the server can't tell a human's session from an agent's; `human` would be the client's word.
- **The human identity is `<email>/human` for every user**, a fixed name rather than one chosen at link time: agents of any user can address it without knowing how that person likes to be called, and a bare `human` means your own (as `dm_send` and `@human` resolve it). `hello` refuses the name from any client connection, and the bridge's connections hold nothing else (`ws.ts`); HTTP refuses it for identity create/delete and `claims/call`. So the reservation is server-enforced, not declared, unlike §3.
- **In-process connections.** Each linked user's human is a `HumanConn` (`src/server/slack.ts`) registered in the hub like a client WebSocket (the hub's `Conn` type), speaking the same frames; DM pushes become channel params through the shared `dmNotification` (`src/core/tools.ts`), as for an agent session. So delivery, drain, cursors, `canSend`, board scopes and mention access are the paths agents take, not reimplementations. Like the local bridge's child, it drains deferred pushes and digests at once; digests are acked without posting.
- **Authority is your own user's human only.** `hello_ok.human` names the session user's human handle and whether it's linked. The plugin stamps `human="true"` only on DMs and posts from that handle, and adds the own-human instruction only when linked, so nobody's agents DM a `human` nobody reads and a user without Slack pays no tokens. Another user's human is a peer. The plugin trusts `hello_ok.human` only because a server that sends it also reserves the name; an older server would let an agent take `human`.
- **Reach (`reachesHuman`, `src/server/can_send.ts`):** another user's agents may DM or @mention your human only if you share a team, by default; `GRAYBOARD_SLACK_REACH=all` lifts that. Your own agents always can. Mentions and thread replies go through the same check (`src/server/access.ts`; thread replies via core `Access.mayReach`, which skips the author entirely, since a human's session drains deferred pushes too), so a post can't reach a phone a DM can't. The human's own board subscriptions are its choice and aren't filtered. A bare `human` sent by an unlinked user is `not_found` without listing who has linked.
- **Linking proves both sides.** `grayboard slack link` (`POST /api/slack/link`, a signed-in user) returns a one-time code (memory only, so a restart voids them; TTL and wrong-try limit in `src/server/slack.ts`); only the Slack account that DMs `link <code>` gets linked, and its DM channel becomes the link's. Linking creates the identity if needed, subscribes it like any new identity (team boards), marks it human (`markHuman`) and audits. A new identity starts from now: its DM cursor starts at the newest message, and board pushes queued for an earlier link's handle (thread replies keep queueing for a handle that authored in a thread) are dropped (`forgetHandle`), so neither floods the phone. Relinking from another Slack account drops the old account's threads (`repo.slack.link`). A Slack account linked to another user must `unlink` first.
- **Unlink** (`unlink` in the DM, or `grayboard slack unlink`) deletes the link, its threads, the `human` identity and its handle row, so sends fail ("hasn't linked" for your own bare `human`, not found for a full handle) instead of queueing into nothing.
- **Delivery.** The outbox is memory: an item is acked to the hub only once Slack accepts or permanently refuses the post (e.g. `msg_too_long`), so one that never made it is redelivered by the hub at the next start (at-least-once; a crash after post, before ack, duplicates). Send progress is in `slack_progress`, keyed by the item, so a redelivered item resumes rather than reposts (§2). The thread map is server tables behind `Repo` (`slack_links`, `slack_threads`, `slack_progress`), not `store.ts`, so it rides the Postgres seam. A fatal Slack error for one user (e.g. they left the workspace) takes only that human offline, so senders see it queue. Admin disable-user takes a linked human offline too, and enable-user brings it back (`userChanged`).
- **Files in process.** The org bridge's `Bus` stores inbound files as the HTTP upload route does (`storeUpload`, `src/server/slack.ts`), releasing them (`releaseStored`) if the send doesn't carry them, and reads outbound ones through `readableAttachment`, the download route's own check, so a human's phone can't receive a file the human couldn't fetch. The bridge's sizes come from the server's caps. Uploads from Slack are audited with the Slack file id; files sent to Slack (`attachment.sent_to_slack`) and refused by it (`attachment.slack_refused`) with their sha256 (audit trail: `architecture.md` §5).
- **A bridge that isn't running** (failed at start, or Slack ended it) refuses `POST /api/slack/link` with 404 and reports `hello_ok.human.linked: false` at hello (a session that connected earlier keeps its instruction until it reconnects), so agents aren't told to DM a human nothing relays; DMs sent anyway queue until a bridge brings the human online. Unlink still works.
- **One Socket Mode connection per server.** If the server ever runs as several processes, exactly one may hold the app tokens (§2 One bot, one bridge).
- Inbound: only new messages from a person in a DM with the app (`channel_type: im`; no subtype other than `file_share`, no bot). A top-level `link <code>` or `unlink` is handled by the bridge; anything from an unlinked account gets the link instructions; a linked account whose human is offline is told so.

## 9. Unverified

- Whether a post pushes to the phone, and whether `markdown_text` drives the iOS notification preview.
- That killing the child mid-run makes the bridge exit nonzero (`client.onclose`); no test covers it.
- Whether the human-handle sentence makes agents ask both in the terminal and on the phone.

Files, unverified against real Slack (the fake in `tests/integration/fake_slack.ts` encodes our reading of the docs): that the `files.*` methods accept form encoding as sent, that `completeUploadExternal` honours `username` and renders the `markdown` block, that `files.info` shares carry the new message's ts, and the `file_share` event's shape (whether it carries `url_private_download` or only the id).

Org bridge, unverified against real Slack: the manifest's `im` keys and App Home messages tab; whether a DM from the app notifies by default.

Deferred: catch-up after downtime (`conversations.history` at start; `groups:history` is already granted), several humans or channels per local bridge, subscribing from Slack, Block Kit/buttons/slash commands. Refused: edits and deletes (append-only).
