A fleet is a queue board, `<name>-tasks`, on which the factory is one lane, with the agent it runs every task with: config `fleets: [{"name": "sim", "agent": "researcher"}]`, or `{"name": "app", "profile": "code"}` to run under a profile's agent and tool lists (`factory-children.md` §1). Anyone who can see the board posts a task with plain `board_post`, and the core's rotation (`boards.md` §3, queue boards) hands each top-level post to exactly one lane. Interactive sessions that subscribe are lanes too.

- **Sync at start and on reload** (`syncFleets`, `adapters/factory/factory.ts`): a missing board is created as `kind: "queue"`; an existing queue board is subscribed in push mode; a fleet whose board exists as a broadcast board is refused with a log line (every post there would read as a task). Any other queue board the factory is a lane on is left: a lane that ignores its deliveries holds each claim for the full TTL.
- **A task** is a top-level post on a joined board, delivered by the rotation or by an @mention. Replies in its thread are its conversation, not tasks, apart from thread commands (`factory-children.md` §1). The requester is the poster; locally every handle is the same OS user, as with a delegation. The agent is the fleet's, never resolved from the post's text.
- **The `taken` reply acks the claim** (a queue reply by the holder releases it), so the 30-minute TTL never redelivers a running task; a crash mid-run is reported interrupted (`factory.md` §5), as for a delegation. The store's `(source, id)` key (post ids are one sequence across boards) makes a redelivery spawn nothing.
- **No agent:** a task from the rotation is passed on with `claim_release`, which offers it to the next lane; an @mention holds no claim, so its poster gets `[factory] declined: …`.
- Replies go in the post's thread with `board_post`, so they wake the poster and the thread's participants.

**Fan-out.** The model judges; the module's code orchestrates. A fleet task's run gets one more instruction: when the task splits into 2 to `maxSubtasks` (default 5) independent parts better run in parallel, reply with only a plan, a four-backtick block with the info string `factory-plan` holding `{"subtasks": [{"title", "task"}]}`; otherwise do the task. Most tasks are done in that one run, so a simple task costs one run and no board. A fleet with `"fanout": false` never gets the instruction.

- **A plan** (`parsePlan`, `adapters/factory/fanout.ts`) posts each subtask on the fleet's work board, `<fleet>-work` (#665), naming the task it's part of (`subtask 1/3 for fe's post 7 on #sim-tasks: …`), then says so in the task's thread with the subtasks' post ids. A work board holds many trees' posts, so `status`, a stop by cancel, deadline or budget, and a failed review name this tree's post ids too (#668). The work board is one standing broadcast board per fleet, opened on the fleet's first fan-out with the factory's own subscription muted (concurrent fan-outs share one open), so it can be bridged or subscribed to once, and `board_list` doesn't grow with each fan-out. It's the durable, visible record: anyone may read, subscribe or comment. It isn't a queue: the core never hands a poster its own post (`queueLanes`, #284), so a queue the factory posts on could never reach the factory. Each subtask runs here, on the worker pool, as the fleet's agent (in a project, the profile the plan names; see Projects below) with no fan-out instruction (a subtask never fans out again), in its own directory unless the fleet's mode is `shared` (`factory-children.md` §1), and its outcome goes in its thread. The triage instruction tells the planning run which: a subtask's agent starts without the planner's files unless they share a directory.
- **Synthesis:** once every subtask has an outcome, done or failed, the fleet's agent runs once more on the original task with each outcome (the first 16K characters of each) and, outside `shared` mode, read access to each subtask's directory; its answer goes in the original thread.
- **Rounds** (#658, `maxRounds` in limits, `factory.md` §7; default 1). With more than one, the synthesis is the lead's review: it may answer, or plan another round in the triage's format, while the tree has rounds left; the last review only combines, and a plan it returns is its answer. A review also only combines when a quarter of the tree's remainder would be under the grant floor or the deadline is under two `timeoutMs` away (`factory.md` §7), so a tree near its limits still answers rather than stops. `maxRounds` is at most 10, which bounds the digest's earlier rounds. A later round posts on the same board (`subtask 2.1/3: …`) and says `fanned out, round 2` in the task's thread. Each review starts fresh: its prompt is a digest the code builds from the store (the task, the lead's notes, earlier rounds' outcomes in one line each, the latest round's in full), so a long tree can't grow one conversation past its context. Each outcome in the digest is fenced as data: a review's plan may route work to a profile with tools the subtask that wrote the outcome lacked, so a subtask (or a page it fetched) is a new source of plans, which the review must judge rather than relay; the project's profile set still bounds what runs. In worktree mode, a round's subtasks branch from the lead's `HEAD`, so the review is told to commit what the next round builds on before it plans.
- **Notes.** With rounds on, the lead (triage and each review) may end any reply with a four-backtick `factory-notes` block. The code splits it off before reading a plan or question, keeps it on the request (4K cap; each replaces the last) and puts it in the next review's digest. It's the lead's working memory across fresh runs and never reaches the thread. A notes block not at the reply's end is text.
- **An unusable plan** (bad JSON, a count outside 2 to `maxSubtasks`, an empty field) fails the task with the reason; nothing is posted. The store admits the subtasks and marks the task waiting in one transaction, after every post landed, so a crash leaves both or neither. A post that fails partway fails the task, naming the posts already made (#638); they stay on the work board and none of them runs.
- A plan is the whole reply: one that only quotes a plan block (documenting the format, say) is an answer. A subtask over 60 KiB fails the plan before anything is posted. A queue board named `<fleet>-work` would hand the subtasks to other lanes, so a fleet whose sync finds one doesn't fan out (its tasks run whole, and the log says so; renaming the fleet gives it a work board), and one made after the sync fails the plan before anything is posted. A broadcast board of that name, made by anyone, is used as is, and its existing subscribers see every subtask's text. A tree that fanned out on a `task-<post id>` board before #665 keeps posting there.
- The work board stays, as do the `task-<post id>` boards releases before #665 opened: the core has no board archive or delete (#635).

**Projects** (#645). A project is a fleet whose plans may give each subtask to a different profile: `projects: [{"name": "app", "lead": "plan", "profiles": ["plan", "code", "docs"], "repo": "/srv/app"}]`. Its board is `app-tasks`, as a fleet's; a project and a fleet can't share a name. The lead profile triages each task, runs any subtask that names no profile, and synthesizes. When a project has more than one profile, the triage instruction lists them, each with its agent and tools, and a subtask names one with `"profile"`; the subtask's post on the work board says which (`subtask 1/3 (code): …`). A plan naming a profile outside the project fails before anything is posted, so no plan widens what runs. A project's `repo`, when given, replaces its profiles' for worktree mode, so every part of one task works on the same checkout; the profiles' other fields apply as in `factory-children.md` §1. A fleet with a profile is a project of one: its plans may name only that profile. `fanout` works as on a fleet.

**Reload.** `SIGHUP` re-reads the config. Fleets, projects, profiles, the limits (`factory.md` §7) and the global `tools`, `allowedTools`, `budgetUsd`, `busTools`, `mirrorClaims`, `workdir` and `repo` take effect for every run that starts after it, and the board sync runs again: a new fleet's board is created or joined, and a removed one's is left. A run already going keeps what it started with. A queued task whose fleet or project is gone, or a queued subtask whose profile its project no longer lists, fails without a run, rather than run under other lists. A config that doesn't load is logged and the running one stays. The fields that shape the bus session, the runner or the worker pool (`RESTART_ONLY`, `adapters/factory/main.ts`) need a restart; a reload that changes one logs that the running value stays.
- **Mentions:** a fleet's replies and subtask posts carry model output, which a poster can steer, and an `@handle` in them wakes that handle as from the factory. Locally every handle is the same OS user, so this reaches no one the poster couldn't mention directly; a hosted factory must neutralise mentions first.
