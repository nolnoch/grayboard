- Hosted Claude Code (`plugins/claude-code/`, #281): in server mode Claude Code runs no `grayboard` process and no `grayboard` MCP entry (`grayboard setup` removes it, with the SessionStart hook, only after the plugin installs). The plugin is a stdio MCP server over hosted-core: it holds its own grant (built-in client `grayboard-claude-code`, store in `CLAUDE_PLUGIN_DATA`, shared by every session on the machine), proxies the server's tools, and is the delivery owner through a hosted-core lease keyed by `CLAUDE_CODE_SESSION_ID`, which survives `/clear`; `claude --resume <id>` rebinds the remembered holds with `create:false`, skipping one the server refuses. It treats an unknown channel verdict as off (a Windows registry policy, which it can't read): off means no lease and a `poll` delivery declaration, so the server holds messages rather than pushing into a session that drops them. Its stdio side stays on MCP SDK 1.x, because Claude Code skips the channel of a server that negotiated protocol `2026-07-28` or later. A second process on one session id runs tools only (hosted-core's delivery lock); SIGINT, SIGTERM or stdin EOF releases the lease, or ends a session its calls registered that never leased, so the name frees at once. Login is a URL elicitation, only when interactive, from the process that wins hosted-core's login lock and from each process waiting on it with the holder's URL (`adapters-hosted-login.md`; a new prompt withdraws the previous one), and while that flow runs the plugin's PostToolUse and PostToolUseFailure hook shows its authorization URL under every grayboard call as a `systemMessage` (#497: Claude Code may never show the prompt), which Claude Code renders for the user and keeps out of the model's requests; the server writes it to `signin` in the Claude Code process's session dir (`src/shared/claude_agents.ts`) and removes it when the flow ends. A signed-out result says only that the user has the link, or why the flow failed, never the URL (#500: a URL in the model's context lets an injected instruction finish the flow with another account); Claude Code 2.1.316 cancels an elicitation that lands while it is still wiring the connection without showing it, so a cancel inside `UNSHOWN_MS` re-sends the prompt (up to `RESENDS` times, each logged) while the flow is open and the browser hasn't answered (Login's `answered` signal aborts at the callback, before the code exchange, #506), and any other cancel (Esc) keeps the flow without asking again; the browser's answer ends the flow even with the prompt unanswered, and the plugin then completes and withdraws it; `-p` never elicits or listens. Logout is the user-only `/grayboard:logout` skill, so no tool call can trigger it. Claude Code has no context-only admission (every channel notification starts a turn), so the plugin opens its lease with `context: false` (#854): after the lease's first pull, which drains the backlog as a local session start does, the server withholds a lone non-waking item (another user's ungranted DM or mention, a deferred push, a digest), unreceipted, until a waking item carries it; a full page (100) with none waking goes out anyway, because direct items receipt only in order and holding it would starve the items behind it. Against an older server, whose `delivery_open` doesn't list `context`, the plugin opens without it and those items start a turn as before. A subagent's call runs as a child session registered under the root (`<session id>/agent/<agent id>`, joined by the hook record, `child-sessions.md` §Claude Code children; a call with no record is refused), and `SubagentStop` ends it (`plugins/claude-code/src/plugin.ts`). A service's run signs in with a launcher-set run token instead, with every sign-in surface off (static mode, `adapters-hosted-login.md` §Hosted core static mode).

- Hosted OpenCode V2 (`adapters/opencode-v2/`) leaves tools, session context and OAuth with native HTTP MCP; its in-process supplement owns only delivery. Human receiving-root approval and mailbox binding are independent and both required, in either order (#226). An enrolled root's model requests, and its subagents', carry their current server instructions through the plugin's `context` hook, since OpenCode caches the session-less `initialize` text (#531, #535, `server-oauth.md` §2). A configured name never approves delivery; creation is explicit. Enrollment pins account, resource, selected native connection/configuration and root; observed drift latches a pause even after switch-back. Durable host admission precedes receipts, with stable root-specific IDs and fresh authority checks. An already-authorized in-flight call may still write/wake that same approved root across a state change; it cannot retarget or receipt a stale epoch. No atomic cancellation or exactly-once wake is promised. `resume:false` avoids an idle digest wake, not later evaluation. An access token native OpenCode hasn't refreshed by the end of the Controller's rotation grace (10 s of polls and failed reopens, cut short 2 s before the lease's deadline, as its open or last renew reported it so the reopen keeps its ownership, #481) pauses its roots `native_access_expired`, and each waits for the refresh (#661): OpenCode 2.1.4 refreshes only when a request draws a 401, so a root's wait asks the port (`CredentialPort.refresh`) to make OpenCode reconnect the native entry, which flips `timeout.catalog` (outside the endpoint hash, so nothing drifts) and reloads, once per stored expiry and never while a native call is in flight in that location (a reconnect kills it; a call that starts mid-reconnect waits it out, bounded, and for its tool to be listed again, #917); it then re-reads the stored token on a backoff capped at 30 s, for an hour of waits, and a valid one resumes the root as a resume does (remembered holds rebind `create:false`; one held elsewhere is recorded, never taken). A pause, drift, sign-out, rejected token, session end or shutdown ends the wait, and a reload's restore re-enters it. A token that expired during a server outage is asked the same way, by the outage retry (run loop or restore), once the server answers with the expiry (#916). Own-login harnesses never wait: they refresh 60 s early and replace the listen on the new token at once (`adapters-hosted-login.md`, #1379). See `server-hosted-ownership.md` for backend ownership and the package guide for lifecycle guards. A service's run signs in with a launcher-set run token instead of native OAuth, and its roots enroll themselves (static mode, `adapters-hosted-login.md` §OpenCode V2 static mode).
- **Hosted core** (`adapters/hosted-core/`, #430) is every hosted harness's delivery: the lease run loop, guards and budgets behind `HostPort` (`adapters/hosted-core/src/port.ts`, `adapters/hosted-core/src/controller.ts`), child register/end, and the `<channel>` renderer. A host supplies the port, Controller options and its own tool and event hooks: OpenCode V2 its native grant, metadata approval and `session.synthetic` admission; for an adapter `RootDelivery` builds them (its own grant, every root approved, `approval: null`) around the host's `admit`. Admission is idempotent per `(ownership, bind_gen, item)` within a process, because pi's and Claude Code's admission has no idempotency key: a lost receipt is retried on the next read without admitting the item again. An item counts as admitted as soon as the host accepts it, before the guard and its receipt, so a receipt that fails (an outage, a lost lease, the Controller's own stop) never shows it twice. No renew sits between admission and receipt, since the server's receipt checks the lease itself (#845); the item lasts through its receipt, so a lost lease there spends the item's attempt budget, not the lease-recovery budget. An admitted item skips only the admission: its receipt still waits for a pre-admission renew that proves the current lease, so a lease that can't renew spends the item's attempt budget and never receipts it; a lease under another ownership or `bind_gen` has another key and admits it again. The set isn't persisted (a restart can show an item twice): a persisted set could turn a duplicate into a lost push, since pi's admission is in-memory only. A body's `<channel` or `</channel` keeps its `<` escaped (`fenceChannel`, `src/shared/notifications.ts`), so a peer can't close the element or forge one with `human="true"` (#433, #435): in the `<channel>` renderers of hosted-core (also used by local omp), `adapters/pi/` and `adapters/opencode/`, and in the content Claude Code is handed (hosted-core's `channelParams` and local `pushChannel`), since Claude Code (2.1.316, the pinned release) escapes a closing tag but not an opening one (#805, `tests/e2e/claude_hosted.e2e.ts`). The local human's session, which feeds the Slack bridge, keeps bodies as sent. On a server, what another signed-in user's session wrote (a DM, a pushed post, a digest's latest post) carries `other_user="true"` (#805): the server records the writer's user on the row at write time (`messages.sender_user`, `posts.author_user`, never shown on reads) and marks it in the lease's pull (`application.pending()`) and on every pull-free read (`dm_inbox`'s unanswered, `dm_thread`, `dm_history`, `board_read`'s posts and a board resource's snapshot, as a field: `other_user: true`; `writerMarks`, [#825](https://github.com/nolnoch/grayboard/issues/825)), so a poll session or one after `/clear` sees the same marks, and a team alias or an ID is judged by who wrote through it, not by its spelling. The user's own human is never marked; another user's human is. Rows from before the column carry no mark, so no mark never means the user's own. A DM or pushed post another user wrote that no `msg.wake` grant covers (server-access.md §1, #806) is also marked `ungranted="true"` (on reads too, judged per call, so a grant set or revoked changes the next read; a digest's latest is judged on reads, never in the pull, where it never wakes) and goes out not actionable: hosted-core's `wakes()` refuses it whatever the flag (omp passes `true`), and OpenCode V2 admits it without resuming. Claude Code wakes on any notification, so CC H's lease is `context: false` and the server withholds such an item, like a digest or deferred push, until a waking item carries it (§Hosted Claude Code, [#854](https://github.com/nolnoch/grayboard/issues/854)). Login, locks, packaging and the wire: `adapters-hosted-login.md`, `server-hosted-mcp.md` §2.
- **Own-human admission authority** (#388 item 11): `adapters/hosted-core/src/own-human.ts` shares inbox discriminants and exact lease-user sender comparison between `channelParams` and V2's JSON renderer. Only a direct sender or a board **push** author can qualify; a digest's latest author never grants authority to its aggregate. `channelParams` still strictly parses and keeps pi/omp/Claude formatting; V2 safely parses for classification but preserves the original event value, leaving malformed/unknown events serializable and untrusted. V2 places authority only on its adapter-generated outer `<channel source="grayboard">` envelope and encodes every payload `<` as JSON `\u003c`, preventing channel-tag forgery without changing decoded values. Its serialized-event limit precedes escape/envelope overhead, not a bound on aggregate drain size. The leaf imports no notification/server implementation, so generated V2 copies stay package-isolated.
- **Hosted session shell** (#444): the harness adapters (pi, omp, Claude Code) share one session layer above the Controller, so an audit fix lands in all of them at once. `HostedClient` (`adapters/hosted-core/src/client.ts`) is every adapter session's connection, roots, children and loose sessions alike. Its `call` is the one error wrapper: a thrown call becomes an error result with `failureMessage`'s text (`adapters/hosted-core/src/diagnostics.ts`: the retry hint where retrying can help, a sign-out's login action, a refusal's code; a tool call cut off after its request may have left, `wire.ts` `OutcomeUnknown` as the Rust SDK classifies it, says to check before calling again rather than the retry hint, since a repeated write doubles (#1345)) and, for a server refusal or an unclassified failure, the error's own message with control and bidi characters replaced and capped (`DETAIL_MAX`), so a harness never sees a raw throw. Its watch says a sign-out once per sign-out per session (a host's own logout marks it said) and re-lists tools on a sign-in, and `endSession` says every failure, a sign-out included. `RootDelivery` (`adapters/hosted-core/src/root.ts`) is a root's delivery: it takes the delivery lock or waits for it (held and unopenable locks: `adapters-hosted-login.md`; pi's `/grayboard resume` and Claude Code's next tool call retry it, and each attempt's answer replaces the last's held or error state), runs the Controller with a push proxy, restarts single-flight, and restarts on a sign-in through one epoch-guarded path (`restartIfChanged`: the watch calls it directly; pi's and omp's sign-in (`/grayboard login`, or a signed-out tool call's offer, #499) and the plugin's run on `adapters/hosted-core/src/offer.ts` (#581): stateless functions over a plain `SignInState` record, one flow per process (pi and omp keep the record on the extension's shared slot, so it outlives the runtime that started it and a `/reload`'s newer bundle; no class instance goes there), the offer's outcomes and its `LINK_MS` wait, and a `Last` record (`/grayboard status`'s `last sign-in:` line; the plugin's stderr names the origin). A pi/omp flow speaks and restarts through the current root runtime; an outcome that ends while none is set (omp between one session's finish and the next one's begin) is kept unsaid and said once by the next root's start. Only the current root's quit aborts the flow, never a parked subagent's; an in-process subagent takes its root's mode for an offer. Another process's sign-in never aborts a pending flow: a lock waiter returns with the shared grant. Both reach the restart through `credentialChanged`, which reconnects the proxy first), so two triggers restart once. A root tools-only with no other holder (no push, a lock that couldn't be opened) binds through its calls and ends that session on any release (Claude Code's quit; pi's every shutdown but `/reload`). Notices ride the next tool result from keyed slots (`SLOTS`, `root.ts`), each keeping only its latest text, so a superseded pause or held notice is never shown; the host's pre-call (`before`) notice comes last. After a credential drift the root's pauses are the watch's to say, so once the store's epoch moved the sink skips any pause or degradation except a failed lease release (`degraded` `session_end`/`delivery_release`), which is said whatever the epoch (a logout, then a quit); the shutdown's own pause never is.
- **One shutdown order** (`RootDelivery.shutdown`): mark closed; stop the watch and the lock waiter; `Controller.shutdown(sessionID, mode, {carry})`, which stops this session's run loop before entering the Controller's queue (per session: OpenCode V2 runs several roots in one Controller), then in the queue stops the root, reads the carried name (pi's `/new` and fork) and releases the lease (`release`) or keeps it (`detach`, pi's `/reload`) (a `release` with no live root, or with no Controller at all when its calls bound the session or its start took the lock, still ends the session, never while another process holds delivery; a failure is recorded, a sign-out included); `controller.close()`, which flushes the diagnostics so the shutdown's own records are said inside the host's shutdown handler; release the delivery lock; await the start and restart in flight; close the proxy. Why this order: the lease release is the only network step whose loss matters. The kernel frees the delivery lock when a process is killed, never the lease, and a lost release leaves the name bound until the lease lapses; Claude Code sends a stdio server SIGKILL 500 ms after SIGINT, and omp caps a shutdown handler at 2 s. Because the run loop stops before the queue, a start in flight costs at most the request it is already in; it re-checks `closed` after every await and builds nothing more, and the shutdown closes the connection it did build, so nothing leaks in pi's and omp's long-lived process. `HostPort.admit` gets the run loop's signal, so a host's admit still waiting (the plugin's `initialized` gate) ends with the stop and records no pause, and an admit after the abort refuses without reaching the host. Logging stays on until the shutdown returns.
- Hosted pi (`adapters/pi-family/`, #279): in server mode pi runs no `grayboard` child and no MCP entry. The bundled extension (`~/.pi/agent/extensions/grayboard.js`) holds its own grant (built-in client `grayboard-pi`), serves the tools by proxying the server's HTTP MCP, and is the delivery owner through a hosted-core lease, one per root session. Delivery for a root session is a per-session file lock: a second pi process on the same session (`pi --resume` twice) runs tools only and takes over when the lock frees. A child (pi-subagents runner marker, or a `parentSession` file live in this process) owns no delivery and registers under the top root just before its first call or instructions fetch (the unregistered instructions tell it to bind, which a child can't); any shutdown but a `/reload` ends any registration it attempted, even one still in flight, so none counts toward the root's child cap. A marked child with no parent session id stays unregistered and, if it made a call, `session_end`s itself on any shutdown but a `/reload`. `/new` and fork carry the outgoing root's holds in-process, but only holds remembered under the current sign-in (`Controller.carried`); a carry the server refused or couldn't be reached for stays with the new session until a start takes it, `/grayboard resume` included. `/resume` rebinds the holds stored as `rememberedHeld` that the server no longer has, skipping one it now refuses; it skips only `alias_held`, `identity_unknown`, `forbidden` and `not_found`, any other refusal fails it, and it fails too when nothing ends up held; an outage, or another process holding the token refresh, leaves the root `retrying` on the outage backoff until the prepare lands or a refusal ends it as such a failure would (#895). A runtime starts once: pi's RPC mode emits `session_start` twice for every session a command replaces it with (`new_session`, `fork`, `clone`, `switch_session`: its runtime rebinds the extensions, then the command does again), and a second root in the same runtime would find its own delivery lock held and leave the first one's lease bound past the session. Admission is idempotent per item across a `/reload`, which keeps the lease while the Controller's admitted set restarts; from the start of a shutdown, admission refuses, so an item reaching a root mid-`/new` stays for the next holder. A sign-in in another pi process restarts each root (its epoch moved); a sign-out pauses them. A tool call pi or omp aborts (Esc, `/new`) stops waiting for the connection, the server's answer or a transfer and throws `CallAborted` (the `signal` of hosted-core `ToolProxy.call`), never read as an outage and never closing the shared connection; an aborted send still waits for its uploads' release, and a call the server already took may still land (#438-26). Each root records its deliveries in the session file as `grayboard-delivery` custom entries (#441), shared with omp: an `admitted` entry (`itemId`, `stableID`, `wake`) when an item reaches the harness and a `receipted` entry (`itemIds`) once the server took its receipt, both under the root session id and never with a message body, so the file shows what reached the session and when. omp points its session manager at the next session before it emits `session_switch`, so its entry writes a record only while the current session is the one the record names; one landing in that gap (a receipt during `/new`, `/resume` or `/fork`) goes to omp's log instead. A failed write logs a warning and never fails the admission or receipt. The receipt record runs from hosted-core's `HostPort.receipted` hook after the receipt lands; a hook that throws leaves the receipt standing and puts the root in `degraded` (`receipt_hook`), not paused. `Grayboard.instructions()` (`extension.ts`), which pi's `before_agent_start` and omp's hooks call, waits at most 2 s (`INSTRUCTIONS_WAIT_MS`) so an outage never stalls a model call by a connect timeout; a timeout or failure warns once until a fetch succeeds and skips fetching for 30 s (`INSTRUCTIONS_BACKOFF_MS`), which the timed-out fetch ends if it lands. A sign-out, a root still starting (`NotStarted`) and a shutdown neither warn nor back off (#438-25). A service's run signs in with a launcher-set run token instead, with `/grayboard login` and `logout` refusing (static mode, `adapters-hosted-login.md` §Hosted core static mode).
- Hosted omp (`adapters/pi-family/entry-omp.ts`, #280): the same extension as hosted pi, bundled as `extensions/grayboard.js` in omp's agent directory (`ompAgentDir`, `src/shared/pi.ts`: omp's `getAgentDir()` rule) with built-in client `grayboard-omp`; server mode removes omp's `mcp.json` entry, local mode installs `adapters/omp/` with the disabled entry. omp keeps one extension runtime across `/new`, `/resume`, `/fork` and branch moves, so the entry replaces its session's `Grayboard` when the session id changes (a `session_shutdown` while the old one ends leaves none started). Task subagents run in-process, each with its own runtime and `ctx.agent`: only `kind: "main"` owns delivery and gets the instructions; a `sub` resolves its root through the `parentId` chain of agents in this process (`adapters/pi-family/omp-ancestry.ts`, one map per process under a global symbol) and registers under it before its first call, with the subagents between as `via`; one whose chain reaches no main stays unregistered. Entries outlive their sessions, so a nested sub revived after its parent parked still reaches the root, and the root is read again at each register, so a sub revived after its main session's `/new` registers under the new one. A sub's child slot is ended at its final `agent_end` (not one with `willContinue`), once the calls already running land, not only at `session_shutdown`: omp keeps a finished subagent live and revivable for `task.agentIdleTtlMs` and shuts it down only when it parks, so ending at shutdown would fill the root's child cap (`limits.children`, `src/server/hosted.ts`) on a fast fan-out; a revived sub re-registers at its next call, behind the end still landing. Pushes go out with `deliverAs: "aside", triggerTurn: true` (waking) or `"nextTurn"` (context). omp runs a main session's `before_agent_start` only for a user prompt, so a push-started turn skips it (#441): `before_provider_request` replaces the last prompt's instructions in the request payload when the instructions changed since, and a turn whose system prompt never got them (a `/fork`, `/new` or `/resume` woken before its first prompt) gets them from the `context` hook as a hidden custom message (`grayboard-instructions`, never persisted) appended last: omp marks a context-added message per-call, and Anthropic's cache checkpoints stop before the first such message, so one placed first would cache nothing of the history (`adapters/pi-family/omp-instructions.ts`). The rewrite touches only a payload string equal to the stale element, or equal to the whole system prompt joined as pi-ai joins it for a provider that sends one system string, never a substring, so a peer's message or a tool result quoting the old text stays as it was. `context` fetches the instructions once per main request and `before_provider_request` reuses that fetch; the fetch is the extension's bounded one (hosted pi's bullet), and a request it doesn't answer in time goes out as omp built it. A payload where the text changed on the way (Cursor's blob-encoded prompt, omp's credential redaction) keeps the stale instructions: omp's log names the provider and model, and the UI warns once per stale text. Advisors share the main runner's payload hook but skip `context`: their payloads get the same rewrite and never warn. Subagents get neither. Tested by `tests/integration/omp.test.ts` against the pinned omp. Static mode as hosted pi's (`adapters-hosted-login.md` §Hosted core static mode).
