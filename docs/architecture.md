## 1. Process model

```mermaid
flowchart LR
  subgraph session["agent session (Claude Code, omp, opencode, pi)"]
    mcp["grayboard mcp<br/>stdio MCP server, local mode only"]
    hosted["hosted adapter (adapters/hosted-core/)<br/>Claude Code plugin, pi and omp extensions"]
  end
  hosted -->|"server mode: HTTPS /mcp, OAuth grant"| server
  mcp -->|"local mode: direct SQLite + Unix-socket pokes"| localdb[("~/.claude-bus/bus.db")]
  cli["grayboard CLI<br/>src/cli/"] -->|HTTPS /api| server
  server --> serverdb[("SQLite WAL<br/>GRAYBOARD_DB_PATH")]
  server --> blobs[("attachment blobs<br/>GRAYBOARD_BLOB_DIR")]
  caddy["Caddy (TLS)"] -.->|reverse proxy| server
```

- The CLI binary's `grayboard mcp` is the local-mode stdio entry (`src/local/mcp.ts`); `--mode server` is refused with `UPGRADE_REFUSAL` (#282). Hosted OpenCode V2 connects directly through native HTTP MCP and an in-process delivery supplement, without a Grayboard executable or subprocess. So do the hosted adapters in server mode: Claude Code's plugin (`plugins/claude-code/`, a stdio MCP server Claude Code runs under Bun) and pi's and omp's extensions run hosted-core in a process the harness starts. `grayboard-server` is the second binary.
- **Mode selection** (`busMode`, `src/cli/api.ts`) is for the CLI's commands: server mode (HTTP, `src/cli/api.ts`) if `GRAYBOARD_TOKEN` is set or the credentials file exists, else local. `grayboard mcp` ignores it for the choice and is local unconditionally, so a signed-in user's local entries keep working; it accepts only `--mode local`. On a signed-in machine it audits `id.signed_in_local {server, mode_pinned}` (the server URL's origin only), and an entry without `--mode local` leads its instructions with `signedInLocalNotice` and logs it to stderr (#491). An *empty* credentials file means signed out: a server-mode command fails with "signed out" rather than silently becoming local (why logout truncates instead of deleting).
- **Local mode is a peer, not a fallback.** Same-machine live push needs no managed server process; Unix sockets are the right primitive. It is excluded from the server's migration seam (§4).
- Identity: a session binds at start only an explicit `BUS_IDENTITY` (one that differs from every repo pin; no worktree suffix, lowercased and validated as at bind, #181; on a server it may carry a scope, `eng/build`, which the server judges at bind); otherwise it starts unbound and binds with `bind` (#182). The pin, else the repo directory name, plus a worktree suffix, is only the first candidate (`src/shared/identity.ts`). See `handles.md`.

## 2. Server data

- One SQLite file, WAL. Schema is idempotent DDL at open (`src/server/db.ts:initSchema`; board tables from `src/core/schema.ts`). No migration tool; changes are additive.
- Two connections: a writer and a read-only reader. Every write transaction runs through the one in-process write queue (`repo.write`, `src/server/store/queue.ts`), which owns the writer: a write or transaction outside the body holding the queue is refused, and reads route to the writer only for the holder inside its transaction (`routeReads`/`ownWriter`, `src/core/sqlite.ts`), so a body may await mid-transaction while other requests read committed state. Stage 3's plan for it: [future/postgres-server.md](future/postgres-server.md) D4, D8.
- Attachment bytes live outside the DB, in the `BlobStore` on `Repo` (`repo.blobs`): server `DiskBlobs` (`src/server/blobs.ts`), one file per SHA-256 under `GRAYBOARD_BLOB_DIR` (default `blobs/` beside the DB), written temp-then-rename so a reader sees all the bytes or none. Put and sweep ordering: `attachments.md`.
- `messages` stores address strings (`scope/name`, or `id:…` for a session acting as its ID), not identity FKs; `sender_id` is the writing session (null for the Slack bridge's humans), `via` the child session that wrote it under its root's addresses (null for a root's own write; shown to readers, unlike `sender_id`; `child-sessions.md`), and `kind` marks a bounce (`sessions.md`). A hosted child's root lives on its `ids` row (`ids.root_id`, set by `hostedRoot`, `src/server/application.ts`), not only its `hosted_sessions` row, which is deleted when the child ends: a send or mention to the child's ID must stay refused `child_session` after that. `recordChildRoots` (`src/server/db.ts`) backfills it at open from live child rows an older release registered.
- `write_receipts` (#254) holds each deduplicated write's result for the dedup window (`server-operations.md`): keyed `(session, sender, fp)`, the row it made (`ref_kind`, `ref_id`) and `result_json`, the first call's result. It carries no body, but a `dm_send` or `board_post` result's attachment metadata (`AttachmentInfo`: id, filename, type, size, sha256) stays until the receipt is pruned: on each write for that session, and nightly for all.
- **Cursors are per address**, not per user: each alias and each session ID advances independently in its DM stream and, via core subscriptions, per board.
- `users.disabled_at` is enforced at auth: a disabled user's tokens fail `verifySessionToken` (`admin disable-user`). An admin disable (`setDisabled`) also revokes the user's CLI tokens, so `enable-user` doesn't revive them (a disable written straight into the database revokes nothing), and sign-in refuses a disabled user: dev login with 403 (`auth.user_refused`), the OAuth AS at its callback (`oauth.user_refused`) and at a code's redemption, which covers CLI login. `teams.policy` is an unused seam: teams are invite-only regardless.
- **Audit rows say where a request came from** (security audit F-19, [#806](https://github.com/nolnoch/grayboard/issues/806)): every `access_log` row goes in through `insertAudit` (`src/server/db.ts`), which stamps `ip` (the client address after trusted-proxy resolution, `client_addr.ts`, never a raw `X-Forwarded-For`) and `ua` (the user agent, at most 120 characters) of the HTTP request whose handling wrote it, and `client_id` (#847), the OAuth client a hosted MCP request's token resolved to: `mcp.ts` sets it on the request's origin (`setRequestClient`) as soon as the token authenticates, before admission, so every row the rest of that request writes (application rows like `alias.created` and `delegation.requested`, not only the `hosted.*` rows that already named it in their detail) names the client; rows off `/mcp` write null. The column is the request's client: a `hosted.*` row's detail `client_id` is the session owner's, and the two differ when one user's request settles or ends another's session. `app.ts` runs each request inside `inRequest` (`src/server/request_context.ts`, an `AsyncLocalStorage`), so the origin follows the request through awaits and the timers it arms; the claim-expiry timer, which fires for every holder, is armed `detached`. A write that waits in the write queue runs under the origin of the code that called `write()` or `post()`, not that of the body whose release starts it ([#1042](https://github.com/nolnoch/grayboard/issues/1042)). The origin is the request's, not the actor's: a row about Bob's session written while handling Alice's request carries Alice's address. Work no request caused (boot, retention, the timer-driven hosted sweeps, the Slack bridge's socket and its relay to Slack, armed `detached` too) writes null; the at-capacity sweep runs inside the admitting request and carries its address, as do rows from before the columns. The address is personal data and ages out with the row (90 days by default). Local mode's `audit_log` is unchanged.
- Retention (`src/server/retention.ts`): messages, posts and audit rows age out (default 90 days). Pruning clears replies' `parent_id` first, or the FK breaks when a replied-to row ages out. Claims are never pruned, so retention can't swallow an expiry announcement; their history (`claim_events`) is, with posts. Ended sessions' `ids` rows go on the message window too (`pruneEndedIds`, both modes' rule, `attachments.md`). Attachments go with their message or post; unsent uploads are pruned nightly and on each upload (`attachments.md`); blobs no row names are swept (`sweepBlobs`) whenever rows drop (a retract, a release, a failed put) and by the nightly run, which finishes any sweep a crash left. Then it returns free pages to the filesystem (`Repo.storage.reclaimFreePages`, `PRAGMA incremental_vacuum`, at most `RECLAIM_PAGES_PER_RUN` = 16,384 per night so one run is bounded; #137). That needs `auto_vacuum=INCREMENTAL`, which a database created since #170 has; older ones have `auto_vacuum=NONE` (the pragma ran after the WAL switch, too late to apply), reclaim nothing, and log so nightly while they have free pages, until a one-time `VACUUM` converts them (`guide/server.md` §Reclaiming disk space). Local mode does the same after its daily run (`src/local/retention.ts`, the shared `reclaimFreePages` in `src/core/sqlite.ts`; #148): a bus created after v2.4.2 is incremental (`openLocalDb` and `writeRetentionSetting` both set it before the first page write), an older one logs the same hint, pointing at `guide/local.md` §Reclaiming disk space.

## 3. Auth and sessions

- **No mandatory SaaS.** An operator self-hosts with only the org's identity providers (Google, Okta, or both) as an outside dependency. Auth that needs a hosted tenant (an external authorization server for the hosted MCP path) is refused for that reason, and because a delegated JWT can't be revoked at once the way a server-held grant can (#204 decision; #142). Keeping grants in the server's DB also keeps their audit trail with the operator.
- **Two layers, kept separate.** The org's IdP (OIDC) proves the human once, at login. Server-issued opaque tokens prove every later call. IdP tokens are verified and discarded, never stored.
- Login (`src/cli/oauth_flow.ts`): `grayboard login` is a client of the server's OAuth AS (`grayboard-cli`, scope `grayboard:login`; [server-oauth.md](server-oauth.md) §2), so the CLI carries no IdP config and works with whatever IdP the server signs in through; the token endpoint answers its code with an API token (`gbrd_v1_`), not an OAuth grant (#928). **The IdP's client secret never leaves the server**; the upstream exchange is server-to-server. `GRAYBOARD_IDPS` lists the providers, in the chooser's order (default `google`; `checkIdpConfig` and `defaultProviders` read `Config` only, never an injected list). A provider's `exchange` returns an identity only after every check held, so no caller can skip one. Google's `id_token` must have `hd == GRAYBOARD_ORG_DOMAIN`, `email_verified`, an email in that domain and the flow's nonce (`verifyGoogleIdToken`); the AS uses one Google pair, `GRAYBOARD_MCP_GOOGLE_*` when set, else `GOOGLE_OAUTH_CLIENT_*`, a Web client with the AS's callback. Okta is the generic OIDC provider (`oidcProvider`, `src/server/idp_oidc.ts`): discovery is lazy and cached, never fetched at startup (an IdP outage at restart would otherwise take down the other provider's sign-ins); the ID token's issuer, audience, expiry, nonce and an asymmetric signature are checked; `email_verified` must be `true` (from `userinfo` when the ID token lacks it, never one claim from each); and the email's domain must be in `GRAYBOARD_OKTA_ALLOWED_DOMAINS`, since Okta's issuer and audience say only "assigned to this app", nothing about the address every DM and alias hangs on. Either domain refusal is `DomainRefused` (`oauth.domain_refused`). There is no bypass for an org that doesn't assert `email_verified`: it fixes that at the IdP. Login (and dev login) refuses an email no direct address can carry (`isValidEmail`, `src/shared/addressing.ts`; e.g. an apostrophe), since that user could sign in but never be addressed (#72). An IdP sign-in, which only the OAuth AS's callback performs, resolves its user through `idpSignIn` (`src/server/idp.ts`, over `repo.users.signIn`, inside `repo.write`) by (issuer, subject) first (`users.idp_issuer` + `users.idp_subject`, `idx_users_idp_identity`, unique where a subject is set; security audit F-13, #806; #928): an email an IdP hands to a new account would otherwise inherit the old account's aliases, mail, history and teams. The issuer is the provider's constant (`provider.issuer`), never the token's `iss`, so Google's two spellings key one way. A row has both (linked), issuer only (a pre-F-13 row, reserved for that IdP) or neither (dev login, or unlinked). The schema step stamps every existing row with Google's issuer once, with the column's `ALTER`, and never again (a later stamp would undo an unlink); on every open it gives Google's issuer to a row with a subject and none (what a rolled-back binary writes) and drops `idx_users_idp_subject` (one `sub` isn't unique across issuers, and a rolled-back binary recreates it). The rules, in order: a known (issuer, subject) signs in, or is refused 403 when it reports another email (`auth.subject_refused {reason: email_changed}`), since users are keyed by email and a rename would move every address; an email whose user another subject at the same issuer holds is refused (`subject_mismatch`); an email another issuer holds, with or without a subject, is refused (`issuer_mismatch`, with `holding_issuer`), so no IdP signs into another's account by email; this issuer's subjectless row, or one with neither, links (`auth.subject_linked`); no row creates one with both. Linking is a conditional `UPDATE` that re-reads and decides again when the row was linked first (on Postgres two sign-ins can both pass the reads); refusals create or change nothing, and a disabled row is returned unlinked for the caller to refuse. Every `auth.subject_*` detail carries `provider` and `issuer`. `grayboard admin unlink-idp --email <e>` (`/api/admin/unlink-idp`, `auth.subject_cleared {had_subject, provider, issuer}`) clears issuer and subject so the next verified sign-in with the email, from any provider, takes the account: for a person whose IdP account was recreated, a move to another IdP, or a deliberate hand-over. It doesn't pin which provider takes the account (the admin tells the person which to use), and a user has one IdP identity: two IdPs agreeing on an email are not one person, so nothing links a second (a `user_identities` table waits for a need). An unheld email goes to its first verified sign-in from any listed provider, so an IdP that lets a user set a colleague's address claims it first; verified emails at the IdP, or disjoint domains per provider, are the operator's mitigation. **Rollback below #928's keying** (an older binary keys on `idp_subject` alone, writes no issuer and recreates the global index) is repaired on the next open while every subject is Google's; once Okta users exist it is unsupported: the old binary can't sign them in, would match a row by `sub` alone, and fails to start if two issuers share a `sub`.
- Tokens: `gbrd_v1_<base64url(32 bytes)>`; only the SHA-256 is stored; the raw token is returned once. CLI writes `~/.grayboard/credentials` (0600, re-applied on every write since a create mode doesn't reach an existing file; a read of a file other users can read warns on stderr, #88). `logout` truncates the file even when it's corrupt or names no server, skipping the server call (#87).
- **CLI tokens expire by idleness, not age.** A token unused for `GRAYBOARD_CLI_TOKEN_IDLE_DAYS` (default 30; 0 never) is refused (`verifySessionToken`, #806), so a forgotten credentials file dies on its own while a long-running agent that keeps using its token never fails mid-task. Otherwise rotation is logout or admin revocation. Logout only revokes that token (`auth.logout`, `token_session`); it closes nothing, since no connection holds a token any more (#282). Admin `revoke-session` and `disable-user` close the user's live application sessions with `unauthenticated` (`disconnectUser`, `src/server/application.ts`, `server-sessions.md`); the revoke or disable transaction itself ends the user's hosted ownerships (`endHostedWhere`, `src/server/db.ts`). Only disable and enable move the Slack bridge's human (`SlackBridge.userChanged`); its in-process connection holds no token, so revoke leaves it. A 30s `revalidate` timer (`src/server/app.ts`) is the backstop for a disable made directly in the database, closing that user's sessions.
- Dev auth (`GRAYBOARD_DEV_AUTH=1`) mints sessions for any addressable email without an IdP. The server refuses to start if it's set together with any provider's client secret (`GOOGLE_OAUTH_CLIENT_SECRET`, `GRAYBOARD_MCP_GOOGLE_CLIENT_SECRET`, `GRAYBOARD_OKTA_CLIENT_SECRET`; `src/server/config.ts`), so a production config can't have it on, and refuses it unless `GRAYBOARD_PUBLIC_URL` is loopback. Dev sign-in answers only a client on the server's own host (its resolved address is loopback; `src/server/client_addr.ts`): the server listens on every interface and a proxy forwards to it, so a loopback URL alone doesn't keep a remote client out. A refusal is a 403, audited `auth.dev_login_refused`. A server started without it revokes every dev-minted session (label `dev`) and audits `auth.dev_sessions_revoked`, so no dev token outlives dev auth, even if it's turned back on (#805 F-04, `src/server/app.ts`).
- Config: derive from `src/server/config.ts` (fail-fast on missing required vars). `GRAYBOARD_ADMINS` empty means nobody is an admin.

## 4. Postgres seam

`Repo` (`src/server/db.ts`) is the only server-side store interface. Porting means reimplementing `Repo` and `src/core/` against Postgres and re-encoding the DDL. Core `endSession` reaches the server's mail only through `Repo.mailOn(tx)` (core's `MailPort`, bound to the transaction's connection), and access asks `Repo.resolver` (core's `Resolver`) for principals, so a port reimplements those two interfaces rather than their callers. Attachment bytes sit behind `Repo`'s async `BlobStore` (`src/core/attachments.ts`), so moving them to an object store means another `BlobStore`, not a change to callers. `src/server/db.test.ts` enforces that nothing else in the server tree imports `bun:sqlite`. `src/local/` and `src/bridge/` stay on SQLite and are excluded. Stage 3 replaces this seam: the server gets its own async store, and `src/core/` loses its server callers ([future/postgres-server.md](future/postgres-server.md)).

The per-request authorization reads (`Repo`'s `oauth.findActiveAccess`, `users.isDisabled` and `users.activeEmail`) are cached inside `Repo` on an authorization generation (`authGeneration`, `makeRepo`, #853), under the store methods so a test that replaces one replaces its cache (but not `Repo.authPeek`'s, which reads the access cache directly): TEMP triggers on `oauth_tokens`, `oauth_grants` and `users` bump a connection-local counter, paired with `data_version` so a write through another connection or process also clears the cache; inside the caller's own transaction the generation is undefined (the counter rolls back with it) and the cache is bypassed; while another task's write body holds a transaction open across an await, others read the counter's value as of the last commit (an `onCommit` hook, `src/core/sqlite.ts`), never the holder's uncommitted bump (#996). `Repo.authRead(fn)` reads the generation once for `fn`'s body and pins it for that body's async task, so one authorization's token and user reads share it across its awaits (`activeAccess`, `src/server/oauth.ts`); hosted MCP's `authorize` runs its grant and disabled-user checks inside one (`src/server/mcp.ts`, #902, #807 P3 A7d); `Repo.authNow.read` does the same for a synchronous body (the OAuth server's `isAuthorizedNow`, until #807 P3 A7d2c), and `Repo.authPeek()` answers from the cache's hits alone, synchronously, for the stream timer's phase A; `fn` must not write `oauth_tokens`, `oauth_grants` or `users`, or its later reads would trust a stale generation. A port has no `data_version`: it needs the generation in shared storage (a row or `LISTEN/NOTIFY`), or a revocation written by another server instance never clears this one's cache. `Repo.authGeneration()` exposes the generation (authRead's pinned one inside its body): the hosted MCP stream timer stamps each open stream with it (#899), so the same port needs the shared generation there too; `Repo.commitGeneration()` is the unpinned read the hosted gate stamps its token check with (`withGate`, #807 P3 A7d2b), and promises more: equal values mean no auth commit at all between them, so a store whose generation can lag a commit returns undefined there; and on that port another instance's `hosted_sessions` or `alias_holds` commits, which move no generation and send no in-process notice, reach an open stream only through the stream timer's backstops (`docs/server-hosted-mcp.md` §1).
