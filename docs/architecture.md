## 1. Process model

```mermaid
flowchart LR
  subgraph session["agent session (Claude Code, omp, opencode, pi)"]
    mcp["grayboard mcp<br/>stdio MCP server, local mode only"]
    hosted["hosted adapter (adapters/hosted-core/)<br/>Claude Code plugin, pi and omp extensions"]
  end
  hosted -->|"server mode: HTTPS /mcp, OAuth grant"| server
  mcp -->|"local mode: direct SQLite + Unix-socket pokes"| localdb[("~/.claude-bus/bus.db")]
  cli["grayboard CLI<br/>src/cli/"] -->|HTTPS /api| server
  server --> serverdb[("SQLite WAL<br/>GRAYBOARD_DB_PATH")]
  server --> blobs[("attachment blobs<br/>GRAYBOARD_BLOB_DIR")]
  caddy["Caddy (TLS)"] -.->|reverse proxy| server
```

- The CLI binary's `grayboard mcp` is the local-mode stdio entry (`src/local/mcp.ts`); `--mode server` is refused with `UPGRADE_REFUSAL` (#282). Hosted OpenCode V2 connects directly through native HTTP MCP and an in-process delivery supplement, without a Grayboard executable or subprocess. So do the hosted adapters in server mode: Claude Code's plugin (`plugins/claude-code/`, a stdio MCP server Claude Code runs under Bun) and pi's and omp's extensions run hosted-core in a process the harness starts. `grayboard-server` is the second binary.
- **Mode selection** (`busMode`, `src/cli/api.ts`) is for the CLI's commands: server mode (HTTP, `src/cli/api.ts`) if `GRAYBOARD_TOKEN` is set or the credentials file exists, else local. `grayboard mcp` ignores it for the choice and is local unconditionally, so a signed-in user's local entries keep working; it accepts only `--mode local`. On a signed-in machine it audits `id.signed_in_local {server, mode_pinned}` (the server URL's origin only), and an entry without `--mode local` leads its instructions with `signedInLocalNotice` and logs it to stderr (#491). An *empty* credentials file means signed out: a server-mode command fails with "signed out" rather than silently becoming local (why logout truncates instead of deleting).
- **Local mode is a peer, not a fallback.** Same-machine live push needs no managed server process; Unix sockets are the right primitive. It is excluded from the server's migration seam (§6).
- Identity: a session binds at start only an explicit `BUS_IDENTITY` (one that differs from every repo pin; no worktree suffix, lowercased and validated as at bind, #181; on a server it may carry a scope, `eng/build`, which the server judges at bind); otherwise it starts unbound and binds with `bind` (#182). The pin, else the repo directory name, plus a worktree suffix, is only the first candidate (`src/shared/identity.ts`). See `boards.md` §3.

## 2. Server data

- One SQLite file, WAL. Schema is idempotent DDL at open (`src/server/db.ts:initSchema`; board tables from `src/core/schema.ts`). No migration tool; changes are additive.
- Attachment bytes live outside the DB, in the `BlobStore` on `Repo` (`repo.blobs`): server `DiskBlobs` (`src/server/blobs.ts`), one file per SHA-256 under `GRAYBOARD_BLOB_DIR` (default `blobs/` beside the DB), written temp-then-rename so a reader sees all the bytes or none. Put and sweep ordering: `boards.md` §12.
- `messages` stores address strings (`scope/name`, or `id:…` for a session acting as its ID), not identity FKs; `sender_id` is the writing session (null for the Slack bridge's humans), `via` the child session that wrote it under its root's addresses (null for a root's own write; shown to readers, unlike `sender_id`; `boards.md` §3 Child sessions), and `kind` marks a bounce (`boards.md` §3). A hosted child's root lives on its `ids` row (`ids.root_id`, set by `hostedRoot`, `src/server/application.ts`), not only its `hosted_sessions` row, which is deleted when the child ends: a send or mention to the child's ID must stay refused `child_session` after that. `recordChildRoots` (`src/server/db.ts`) backfills it at open from live child rows an older release registered.
- `write_receipts` (#254) holds each deduplicated write's result for the dedup window (§4): keyed `(session, sender, fp)`, the row it made (`ref_kind`, `ref_id`) and `result_json`, the first call's result. It carries no body, but a `dm_send` or `board_post` result's attachment metadata (`AttachmentInfo`: id, filename, type, size, sha256) stays until the receipt is pruned: on each write for that session, and nightly for all.
- **Cursors are per address**, not per user: each alias and each session ID advances independently in its DM stream and, via core subscriptions, per board.
- `users.disabled_at` is enforced at auth: a disabled user's tokens fail `verifySessionToken` (`admin disable-user`). `teams.policy` is an unused seam: teams are invite-only regardless.
- Retention (`src/server/retention.ts`): messages, posts and audit rows age out (default 90 days). Pruning clears replies' `parent_id` first, or the FK breaks when a replied-to row ages out. Claims are never pruned, so retention can't swallow an expiry announcement; their history (`claim_events`) is, with posts. Ended sessions' `ids` rows go on the message window too (`pruneEndedIds`, both modes' rule, `boards.md` §12). Attachments go with their message or post; unsent uploads are pruned nightly and on each upload (`boards.md` §12); blobs no row names are swept (`sweepBlobs`) whenever rows drop (a retract, a release, a failed put) and by the nightly run, which finishes any sweep a crash left. Nothing reclaims free DB pages (#137): the monthly vacuum hook is empty. A database created since #170 has `auto_vacuum=INCREMENTAL`, which only tracks free pages until something runs `PRAGMA incremental_vacuum` (not exposed through `Repo`); older ones have `auto_vacuum=NONE` (the pragma ran after the WAL switch, too late to apply) until a one-time `VACUUM` converts them.

## 3. Auth and sessions

- **No mandatory SaaS.** An operator self-hosts with only the org's identity provider (Google) as an outside dependency. Auth that needs a hosted tenant (an external authorization server for the hosted MCP path) is refused for that reason, and because a delegated JWT can't be revoked at once the way a server-held grant can (#204 decision; #142). Keeping grants in the server's DB also keeps their audit trail with the operator.
- **Two layers, kept separate.** Google OIDC proves the human once, at login. Server-issued opaque tokens prove every later call. Google tokens are verified and discarded, never stored.
- Login (`src/cli/oauth_flow.ts` → `src/server/auth.ts:exchangeGoogleCode`): PKCE over a loopback redirect. The CLI bootstraps client ID and org domain from public `GET /api/auth/config`, so developers need no OAuth config. **The client secret never leaves the server**; the code exchange is server-to-server. The `id_token` must have `hd == GRAYBOARD_ORG_DOMAIN` and `email_verified`. Login (and dev login) refuses an email no direct address can carry (`isValidEmail`, `src/shared/addressing.ts`; e.g. an apostrophe), since that user could sign in but never be addressed (#72).
- Tokens: `gbrd_v1_<base64url(32 bytes)>`; only the SHA-256 is stored; the raw token is returned once. CLI writes `~/.grayboard/credentials` (0600).
- **CLI tokens never expire.** A long-running agent must not fail mid-task. Rotation is logout or admin revocation. Logout only revokes that token (`auth.logout`, `token_session`); it closes nothing, since no connection holds a token any more (#282). Admin `revoke-session` and `disable-user` close the user's live application sessions with `unauthenticated` (`disconnectUser`, `src/server/application.ts`, §4); the revoke or disable transaction itself ends the user's hosted ownerships (`endHostedWhere`, `src/server/db.ts`). Only disable and enable move the Slack bridge's human (`SlackBridge.userChanged`); its in-process connection holds no token, so revoke leaves it. A 30s `revalidate` timer (`src/server/app.ts`) is the backstop for a disable made directly in the database, closing that user's sessions.
- Dev auth (`GRAYBOARD_DEV_AUTH=1`) mints sessions for any addressable email without Google. The server refuses to start if it's set together with `GOOGLE_OAUTH_CLIENT_SECRET` or `GRAYBOARD_MCP_GOOGLE_CLIENT_SECRET` (`src/server/config.ts`), so a production config can't have it on.
- Config: derive from `src/server/config.ts` (fail-fast on missing required vars). `GRAYBOARD_ADMINS` empty means nobody is an admin.

### Embedded authorization boundary

`src/server/app.ts` mounts `src/server/oauth.ts` on the same listener before the retained HTTP router; only the new hosted MCP boundary adopts its OAuth principal. CLI and API token authentication stays independent. Google proves an account, never authorizes a downstream client: upstream state, PKCE and verified ID-token nonce are separate from downstream state, PKCE and explicit one-use consent. A supplied upstream callback issuer must exactly match the pinned Google authorization-server issuer before exchange or state consumption; the optional callback parameter is not an alternative ID-token issuer policy. Pending browser flows intentionally fail across process restart; issued codes and grants survive through `Repo.oauth`.

The AS's HTTPS Google callback requires a Google Web application registration with that exact callback. Its optional dedicated Google client pair (`src/server/config.ts`, selected in `src/server/oauth.ts`) preserves the retained CLI's Desktop-client loopback profile; without the override, the AS uses the primary pair for deployments already configured with a Web client. Authorization, code exchange and ID-token audience verification use one selected pair consistently. Neither upstream Google client is a downstream MCP client registration, and development auth refuses either Google client secret.

Public clients register through HTTPS Client ID Metadata Documents; operator registrations remain available for pinned public or confidential clients. `src/server/oauth-cimd.ts` validates the exact client ID, registered redirects and public-client authentication before consent. All DNS answers must be public unicast; the HTTPS connection pins one validated address while retaining TLS hostname verification. Redirects are not followed. Bounded fetches, coalescing, concurrency, positive/negative caches and the `/oauth/*` rate limits bound metadata abuse. Dynamic client registration is not exposed without a demonstrated supported-client requirement.

Redirects match their registration except ephemeral ports on registered HTTP loopback callbacks; host, scheme, path and query remain exact, including the distinction between localhost and literal addresses. Code redemption binds the actual selected redirect including its port. Confidential authentication does not waive PKCE. Protected-resource discovery advertises tools and delivery so one native grant can support both; scopes have no hierarchy. Missing resource selects the single configured resource server, but an explicitly wrong or empty resource fails, and code exchange and refresh preserve the original audience binding.

The configured public base is the exact issuer identifier, including any explicit default port; `iss` must never be URL-normalized. The resource identifier is separately URL-serialized to one canonical audience, so default-port spelling cannot fragment client resource bindings; alternate spellings are not additional audiences. Redirects, metadata and Origin checks derive from configuration; request Host and forwarding headers never select them. Prefix-preserving and prefix-stripping proxies can forward OAuth routes, but must also forward the RFC well-known path-insertion locations. Production requires HTTPS; the only HTTP issuer exemption is explicit loopback development. Opaque HttpOnly cookies are hash-only capabilities, not signed identity claims. Browser session rotation, request/browser/session binding, one-use CSRF and mandatory same-Origin consent precede atomic code issuance. The remote completion page is an ordinary registered HTTPS callback for full-URL paste, not an out-of-band grant, and never redeems codes; a CIMD client can't register a redirect on the AS's own origin, so only operator-registered clients use it.

OAuth extension parameters are ignored only after bounded syntax, encoding and duplicate checks; they never become stored bindings or redirect fields. Empty OAuth values are omitted only after duplicate checks; omitted scope never expands beyond persisted consent. Nonempty credentials and grant bindings still belong only in their prescribed locations; Basic authentication cannot be mixed with a nonempty body client ID. Authorization errors redirect with state and exact issuer only after an unambiguous registered client/redirect pair and valid state are established; malformed or untrusted requests stay local, and database exceptions never become client redirect errors.

Authorization codes and refresh tokens consume atomically with their successor records. Recognized code or refresh replay commits whole-family revocation; a concurrent loser can therefore invalidate the legitimate winner. Clients must single-flight refresh and reauthorize after ambiguous results, not retry old credentials. Stable grants retain original refresh permissions; each access token records its actual requested subset. Scope omission on refresh restores original permissions, not merely the previous access subset. Access revocation is individual; refresh revocation is family-wide; the retained `/api/auth/logout` touches no OAuth grant or browser session. Disable and admin all-session revocation invalidate OAuth grants so reenable cannot resurrect them. Lifetimes derive from `src/server/oauth-types.ts` (`OAUTH_TTL`), clamps from `makeOAuthStore` (`src/server/db.ts`); spent lineage outlives sliding expiry through the absolute family deadline.

Consumers must authenticate every HTTP method and revalidate the actual access hash and deadline, not only the grant ID, before dispatch and during long-lived delivery. `isAuthorized` covers individually revoked access as well as disabled users and revoked grants. Database failures propagate from authentication and become generic server errors on AS HTTP operations, never invalid-grant guesses or successful revocations. Closing this service clears its bounded ephemeral maps and housekeeping timer and closes the CIMD resolver (aborting in-flight fetches) only; server shutdown first cancels MCP exchanges and contexts, then closes OAuth before callers close the database. Rate limits key by the auth gate's client address (`src/server/client_addr.ts`, so a trusted proxy's `X-Forwarded-For` counts), check the address bucket before the global one, and spend neither until both pass, so one address can't drain the org-wide bucket. Token and revocation posts have their own address bucket of the same size and spend it, with the global one, only when a request carrying grant material (a code, refresh token or revocation token, or an Authorization header) is refused with a 4xx; a foreign Origin, a malformed request or one with no grant material fails before client authentication (so before any CIMD fetch), uncharged and unaudited, so a cross-site form post can't lock an address out of token refresh (#283). Every other `/oauth/*` route spends on entry.

### Hosted MCP

`src/server/mcp.ts` serves HTTP MCP through the official SDK 2 handler and native sessionful HTTP transport, directly against the typed application the org bridge also calls; the local stdio path remains independent. Modern listeners have separate SDK buses: URI filtering on a shared bus is not principal isolation, and the SDK's capability-only listen probe does not authorize URIs. The boundary authorizes canonical board URIs or a subscriber's lease-bound inbox before acknowledgment and rechecks actual access, visibility and lease epoch before hints and periodically while connected. Catalog-change notifications and idle channels are not advertised. Hints are nonconsuming; stream loss requires re-listening and durable reconciliation, not event replay.

A supported initialized HTTP session binds user, grant and role, not its initialization access token or a static mailbox header. Each POST carries its own mapped source metadata. Legacy GETs inherit only the context pinned by the initializing POST or the latest authorized subscription; incompatible source registrations are refused within that legacy protocol session. Every later method and callback uses its current HTTP exchange. A GET watching resources keeps its own access and lease snapshot: fresh access may continue the same protocol session but cannot upgrade it. An idle GET (one watching nothing) is re-authorized in place by the next subscribing POST under the same binding (§Legacy GET streams). Subscription registration is authorized by the current POST and acknowledged without requiring a retry. An incompatible GET retires; recovery must authenticate a new GET with its own live access and the registered lease before receiving hints. Unexpected storage faults during that check remain internal errors, not successful registrations. Release or replacement cannot reuse an old inbox epoch. Both HTTP disconnect and SDK request cancellation must be checked: the native legacy transport's cancellation signals are independent. Non-owning contexts follow their request or stream, not the capability-probe server instance. Bounded registries and idle retirement prevent disconnected protocol sessions from becoming permanent application contexts. `src/server/mcp-streams.ts` owns bounded original-body reads and SDK byte forwarding, awaiting source cancellation and reader release without an unread Request tee; shutdown closes sources before OAuth and persistence.

Native callers receive agent tools and authorized board snapshots; an explicit subscriber role selects binding/session and private delivery controls with its lease-bound inbox (`src/server/mcp-resources.ts`). The role is not authentication. A subscriber refusal carries only its domain `code`, plus validated `known` names on `identity_unknown` and the plain-text `holder` (the account's other session, bounded, no control or bidi characters) on `alias_held` (`domainData`); exception text never crosses. Exactly one grant per harness installation and server: the host's (OpenCode V2) or the adapter's (pi, omp, Claude Code), never both. `whoami` reports the current session binding, not a static identity resource. OAuth success alone binds no mailbox and never grants human authority. Anyone holding a user's OAuth token can act as any of that user's hosted sessions: the hosted session ID is routing and attribution, not a capability (#229 tracks hardening). Lease capabilities remain in a private header, never a resource URI. Authenticate each request's actual access independently of the lease's grant-liveness predicate: fresh access of the same grant may continue a lease, while revoked or expired access may not invoke it. Lease identity must match the selected request identity before any read, renewal or mutation; do not renew as an identity check. Storage faults in resource or lease request authorization remain redacted internal errors, not credential refusals; that failed check alone neither destroys an established lease nor renews it, issues items or advances receipts. Background authorization deliberately fails closed and retires watches or leases, with cleanup exceptions isolated from timers and committed mutations; continuity through an ongoing storage outage is not guaranteed.

A supplied Origin must match the configured public URL's origin, never a request-derived host; absent Origin remains valid for native clients. Invalid, opaque or non-origin URL values are rejected before authentication or application context creation. Every method requires a live OAuth access token with the selected role's scope; proprietary session tokens have no fallback on this path. Authentication precedes identity selection, repeats in the SDK factory, and rechecks the actual access token before dispatch. Explicit OAuth refusals in the factory or after awaited identity selection retain their original HTTP challenge through request-local propagation before the response returns to the listener; SDK error bodies are cancelled when replaced. Cancellation and shutdown do not become credential challenges, and storage exceptions remain internal errors. Once a response has returned to the listener, later dispatch refusal is an MCP tool error or stream termination, not a retroactive HTTP status change. Individual access revocation, family revocation, expiry and user disable therefore cannot be bypassed by an earlier discovery or initialization. Missing or invalid credentials advertise both source scopes in the protected-resource challenge so URL-only native discovery obtains one tools-and-delivery grant; a valid delivery-only token still receives insufficient scope on the native role, not permission to invoke agent tools. The authenticated grant's client alone selects the source mapping (below); arbitrary identity headers never bind a name. Stable IDs hash length-prefixed user, client and raw source values, not access credentials. The accepted routing trust boundary is the authenticated account: a token holder can name another raw source under that same client, not another user's session (#226, #229). Missing or unmapped context permits only the shared unbound reads; explicit bind creates a mailbox only with `create: true`, and never `human`. Each HTTP exchange holds a non-owning application context until completion or cancellation, including a still-open SSE response; a persistent SDK instance resolves callbacks against the current exchange, never an initialization closure. Shutdown closes outstanding streams and instances. These contexts neither acquire delivery ownership, reset the owner's status, nor advance delivery cursors. Binding holds the mailbox through the application's shared holder map; delivery open adds a separate push session without becoming a competing holder. Quota and publication remain inside the owning gate, with authorization/cancellation rechecked after awaits; failed post-open admission releases only the exact new capability, never a successor. HTTP resource and delivery services close before OAuth and database shutdown. Concurrent readers therefore cannot steal an existing harness's pushes.

A 1 s timer (`src/server/mcp.ts`) rechecks each open stream's access and closes one that fails. A close of a stream bound to a hosted session ID is audited once as `hosted.stream_closed` with `reason` (`access_expired` at the token's expiry, else the refusal's code, else `failed`), `role` and `ownership` (#472). Not audited: a stream with no session ID and a stream its client already closed. The close leaves the delivery lease alone: a subscriber that reopens with refreshed access inside the lease TTL keeps its ownership, which is why an adapter whose host refreshes only at expiry waits for that refresh instead of pausing (`adapters/opencode-v2/README.md` §Delivery safety).

**Legacy dormancy** (#476). A legacy-protocol (2025-11-25, `Mcp-Session-Id`) session whose access token expires while its grant stays active is not retired: the timer puts it to sleep. A dormant session closes its GET stream (audited as `hosted.stream_closed`) and releases its admission slot; its transport, `McpServer`, sid, binding and subscriptions stay. It holds a `dormant` slot instead, bounded by the legacy limits; none free drops it with reason `capacity`. The next request on that sid with refreshed access for the same binding rehydrates it (admission again, 429 when full). A request for another binding gets 404 so its client re-initializes, and drops the session only when it comes from the session's own user under a new grant (`grant_changed`); a stranger's guess leaves it to the idle reclaim. A DELETE drops it without admission (`deleted`). The timer drops a dormant session whose grant ended (`grant_ended`), that has seen no request for 60 s since dormancy or its last request, with none in flight (`idle`), or whose check threw (`failed`); server close drops the rest (`shutdown`). Each transition is audited as `hosted.legacy_dormant`, `hosted.legacy_rehydrated` or `hosted.legacy_dropped` (`reason`, `dormant_ms`), keyed by a random per-session `ref`, never the sid. Revocation and other refusals still retire a legacy session unaudited.

**Legacy GET streams** (#431). A legacy session's standalone GET writes `: keepalive` (the SDK's keepalive comment) as its first bytes, so its headers flush at once instead of waiting for the first hint or the 5 s keepalive; omp's native client abandons a GET whose headers take over 1 s. Why a comment and not the 2025-11-25 priming event: that event carries an event ID, which invites a `Last-Event-ID` resumption, and no event store backs this transport. A legacy GET with no watched resource is idle: it carries nothing a binding governs, so a bind change doesn't close it (`idle`, `src/server/mcp.ts`). An unbound GET (an initialize without `_meta`, a session ID never bound, a subscriber without a lease) therefore stays open, where it used to end at the first hosted change; omp never reopens it. An idle GET receives nothing, so `peer_list` doesn't show its session among the user's unbound sessions (`ApplicationSession.listed`). The next `resources/subscribe` attaches it (`attach`): its context is selected again from the subscribing POST, whose `_meta` routes it and whose headers carry the current token and any lease, while the GET's own signal keeps its lifetime. The attach charges no second hosted admission: the POST paid it. A refusal there, or the GET closing meanwhile, ends the GET so its client recovers, as an incompatible GET always has, and the subscription stays registered; a fault fails the subscribe with an internal error rather than registering it. A protocol session's subscribes and unsubscribes run one at a time, so the one-session-context rule holds across the attach's await.

**Source mapping** (#414). `oauth.authenticate` resolves the grant's client to one `_meta` source key, `OAuthPrincipal.sourceKey` (`sourceKeyFor`, `src/server/oauth-config.ts`): OpenCode's CIMD client maps `ai.opencode/sessionID`; the built-in clients (below) and an operator client (`GRAYBOARD_OAUTH_CLIENTS`) with `sessionSource: true` map `io.github.nolnoch.grayboard/sessionID`; every other client, every other CIMD client included, is unmapped and gets the unbound reads only. A mapped client ignores the other key; a missing or invalid value leaves the request unbound (reads still run), and `bind`/`delivery_open` refusals name the client's own key. `sourceContext` (`src/server/hosted.ts`) is the one mapping for `_meta`, child registration and the byte routes. Why opt-in: a CIMD client gets both scopes on user consent, so mapping every client would let a consent-phished client bind names, send DMs and take delivery as the victim; the operator config is the trust decision. `sessionSource` is refused on any `https:` client ID, OpenCode's included: CIMD resolves only `https:` IDs and a grant keeps only the client ID string, so a grant consented under a metadata document never turns write-capable because an operator later registers the same ID. It is also refused on a client ID over `SESSION_FACT_MAX` (`src/shared/protocol.ts`): `harnessFor` labels an operator client's sessions with its exact ID, and `registerId` would cut a longer one. Config is read at startup, which logs the opted-in IDs and the built-in ones. Removing `sessionSource` unmaps the client's requests after restart (writes stop; its tokens keep reads until they expire) but ends none of its hosted sessions: bound roots keep their names until the lease deadline, an idle probe or a competing bind, since `sweep` idle-ends only unnamed rows. To end them at once, revoke the grants or disable the user.

**Built-in clients** (#429). Public clients defined in code (`BUILTIN_CLIENTS`, `src/server/oauth-config.ts`), reserved as the constant IDs of the hosted adapters (#279, #280, #281). Each is `none`-auth with refresh and both scopes, redirects only to `/callback` on `127.0.0.1` or `[::1]` (not `localhost`) on any port (`matchesRedirect`, RFC 8252), maps the generic key, and takes its harness label from the same table. They join the AS client map ahead of operator clients, so the consent page shows no "Unverified client" line (the local-callback line still shows), and AS metadata lists their IDs as `grayboard_builtin_clients` (an RFC 8414 §2 extension) so an adapter can detect an older server before it opens a browser. Why in code: operator registration would be a manual step on every server, and CIMD can't carry them: a CIMD ID must be the https URL of its own `application/json` document (`src/server/oauth-cimd.ts`), which raw.githubusercontent.com (`text/plain`) can't serve and this repo has no Pages site for. Trust matches OpenCode's CIMD client, whose document is loopback-only too: a consent-phished code lands on the victim's own machine, so exploiting it needs code already running there, including another local user on a multi-user host, since binding a loopback port needs no privilege (RFC 8252 §7.3, §8.1). Map membership is load-bearing: token refresh and revocation authenticate the client through the map (`clientAuth`, `src/server/oauth.ts`) and refresh needs its `allowRefresh`, while write capability and the harness label come from the code table (`sourceKeyFor`, `harnessFor`). The CIMD same-origin redirect check applies only to fetched clients. Built-ins can't be disabled per server: an operator entry reusing one of their IDs stops startup (`parseOAuthClients`). Before #429 an operator client could hold one of these IDs, and a grant keeps only the client ID string, so its grants would turn into a built-in's (write-capable, refreshed with no secret). The first start that knows the built-ins, once the config parses and before it serves, therefore revokes every grant and drops every unredeemed code under their IDs, audits each grant as `oauth.builtin_client_grant_revoked`, and records the cutover in `server_state` (`revokePreBuiltinGrants`, `src/server/db.ts`). Later grants under these IDs are the built-ins' own and survive restarts; because it runs once per database, a later downgrade that registers one of these IDs again isn't caught on the next upgrade.

**Delivery declaration** (#429). A generic-key client may send `_meta["io.github.nolnoch.grayboard/delivery"] = {mode: "push" | "poll", source}` beside its session key on any native request (`deliveryDeclaration`, `src/server/hosted.ts`; `source` format: `DELIVERY_SOURCE`). It selects a bound session's `initialize` instructions (`hostedBoundInstruction`; an unbound session gets `hostedUnboundInstruction` whatever it declares) and the bind result text. `push`: the channel lines (`channelInstructions`, `src/core/tools.ts`) carry the declared `source`, the tag the client renders, and the bind result has no delivery note: a push client must open delivery right after bind and report its own failure. `poll`: `initialize` keeps the polling line, both texts add `POLL_NOTE`, and neither carries channel lines. Absent (any bound session that sends none, OpenCode's included): a bind result with `DEFAULT_CHANNEL_SOURCE` channel lines and the `delivery_open` note; the `initialize` text follows the ownership's lease (#531): open, those channel lines; none, the polling line and the same note. Why: a push client forwards the server's text verbatim, so the text must match the delivery the session actually has. A malformed declaration refuses the request (HTTP 400 `bad_request`) before admission, never falling back to text for the wrong delivery. Only a generic-key principal's declaration is read, so an OpenCode session always gets the absent text, and the subscriber role ignores it. It changes text only: it grants nothing, so nothing audits it. Local sessions pass `DEFAULT_CHANNEL_SOURCE` through `boundInstructions` (`src/core/bindings.ts`); it must equal the MCP entry name `grayboard setup` writes, since Claude Code sets a pushed tag's `source` from the server's configured name.

**Hosted core** (#430). `adapters/hosted-core/` is the one client-side implementation of hosted delivery and attachment transfers for every harness, and of the tool proxy for the harnesses without native MCP tools (OpenCode V2 keeps native tools and transforms its attachment surface; its delivery and admission rules: `boards.md` §9). For the harness adapters (pi, omp, Claude Code) it also holds the session shell above the Controller (#444; `adapters/hosted-core/src/client.ts`, `adapters/hosted-core/src/root.ts`; `boards.md` §9); a host keeps its sign-in presentation, its instructions text, its own session roles and an item's rendering and delivery (`admit`). Its wire (`adapters/hosted-core/src/wire.ts`) sends the port's session key on every request made for a session and the port's delivery declaration when it has one (OpenCode V2 declares none); the proxy's shared native connection is made for no session. The vendored wire carries its own copy of the delivery key, since it can't import `src/` (`tests/integration/hosted_core_wire.test.ts` fails on drift). A refusal of `server/discover` or `initialize` with any non-OK status other than 401, 403, 429 or a gateway status surfaces as `ConnectRefused` with the server's status and body, since the SDK reports it only as failed version negotiation. OpenCode installs `adapters/opencode-v2` from a Git subdirectory, which can't reach a sibling package, so `adapters/opencode-v2/src/core/` is a generated copy of its hosted-core modules and their shared attachment dependencies (`scripts/sync_hosted_core.ts`); edit the original source and regenerate, never the copy. `tests/integration/hosted_core_sync.test.ts` fails on drift and on any other module present in both packages. Grant storage and refresh remain native; attachment transforms call the original native send tools and reuse `HostedAttachments` for byte transfers (#578). Before login the proxy serves `adapters/hosted-core/src/native-tools.json`, a committed snapshot of the server's native `tools/list`, so a native tool change ships with a regenerated snapshot (`bun scripts/snapshot_native_tools.ts`; `tests/integration/hosted_core_snapshot.test.ts` fails on drift); after login each new native connection re-lists, since the server declares `listChanged: false`. The `adapterBundle` macro (`src/cli/adapters.ts`) bundles `adapters/pi-family/entry-<harness>.ts` into the CLI binary at compile time, as a `bun build` subprocess because Bun refuses `Bun.build` inside a macro; `setup`/`refresh-adapters` (`installPiFamily`, `src/cli/cli.ts`) write pi's and omp's bundles in server mode (removing the local `.ts` and the MCP entry; a server URL `canonicalEndpoint` refuses fails before anything of that harness's changes, since the extension would refuse it too, and `setup` goes on to the other harnesses and exits 1) and the local adapter in local mode (removing the `.js` and `config.json`; a local refresh recreates a missing entry for pi, whose adapter reads its command there, and for omp only when leaving a hosted install). Leaving a server (local mode, another server) first signs the harness out of it through hosted-core's `Login`, revoking its grant, so no grant outlives the config that named it. `refresh-adapters` skips a harness when either file is a symlink; `setup` replaces it. omp's bundle keeps `@oh-my-pi/pi-coding-agent` external (omp resolves it to the running host). An adapter must load hosted-core bundled `--target node` (pi runs under Node), so hosted-core and every repo module it imports carry no Bun API: hosted-core typechecks with `types: ["node"]`, and `tests/integration/hosted_core_bundle.test.ts` bundles its entries and refuses any `Bun.` or `bun:sqlite` reference.

**Claude Code plugin children** (#551; the record mechanism: `boards.md` §3 Claude Code children). The plugin's hooks (`plugins/claude-code/hooks/hooks.json`, run as `bun dist/hook.js`, built by `scripts/build_claude_plugin.ts`) write records under `CLAUDE_PLUGIN_DATA`; `plugin.ts` takes the one named by a call's `claudecode/toolUseId`, comparing the dir's start time with its own parent's, read once at startup. A subagent's call goes to `RootDelivery.call(tool, args, {child})` with the raw id `<sessionID>/agent/<agent_id>`; the ancestry callback (`root.ts`) accepts only a child the host passed under its own root. A push session's proxy registers it through the Controller's `beforeCall`; a tools-only session's poll proxy has no hooks, so `RootDelivery.call` registers the child itself (`children.ts` `register`) before each of its calls, as the Controller does: a registration remembered across calls would outlive a root the server ended, and the child's next call would make it a root of its own. `endChild` ends it. `SubagentStop` writes `ended/<agent_id>`, which the plugin watches (fs.watch) and also drains on every child call, and turns into the child's end on either path (the server's idle sweep ends only roots, so an unended child lasts until its root does); locally nothing ends a child but its root (`boards.md` §3 Local children). A missing record is refused by the plugin and logged to its stderr (Claude Code's MCP log): the server never sees the call. The plugin always ships its hooks, so it has no not-installed state.

**Adapter login and the lock rule** (#430). An adapter signs in with loopback OAuth and PKCE S256 under its built-in client and keeps its grant in one store per resource and client id under its state dir (`adapters/hosted-core/src/login.ts`, `adapters/hosted-core/src/storage.ts`; 0600 in a 0700 dir, written atomically); a login mints a new `epoch`, which is part of the enrollment's `configHash`, so a new login (possibly another account) is a credential drift. The resource, the MCP URL the tool proxy dials and the discovered issuer must be canonical HTTPS, or HTTP only on `localhost`, `127.0.0.1` or `[::1]`, with no credentials, query or fragment (`canonicalEndpoint`, `src/shared/endpoint.ts`; `grayboard setup-opencode` applies it plus stricter rules of its own, and `setup`/`refresh-adapters` apply it to pi's and omp's URL). Every cross-process exclusion is a kernel-released lock (`adapters/hosted-core/src/lock.ts`: a `node:sqlite` connection holding `BEGIN EXCLUSIVE` on the lock file, since neither Node nor Bun has `flock`): the kernel drops it when the holder dies, so nothing goes stale by age and nothing is ever taken over. A refresh holds `<store>.refresh.lock` across read-store, request and write-store, so N processes sharing a store send one refresh; while another process holds it, a still-valid access token serves at once (the SDK's request timer is already running), and only an expired token, or the one a 401 just rejected, waits for the lock: a waiter that gets it returns the token the holder wrote or refreshes itself, and one whose deadline passes with no usable token reports a retryable "refresh in progress" (`RefreshInProgress`, retried like an outage without spending the retry budget). The holder writes `pending` before its request and clears it only where the token provably wasn't spent: a failure known to come before the request was sent (refused, unresolvable, unroutable, a connect timeout), or grayboard's own refusal from before its token transaction (`invalid_client`, which is `ServerOutdated`; `temporarily_unavailable` on a 503 or a 429, an outage that spends no budget). `invalid_grant` means the token is dead: a new login, never a retry. Anything else (a TLS failure, a lost response, a timeout, another status, an invalid 200 body, a holder that died with `pending` set) is an unknown outcome and is never sent again, because the server revokes the whole grant on any reuse of a spent refresh token with no grace window: the adapter revokes that token (audited `oauth.revoked`, not a replay) and asks for a new login, recording a printable cause (never a body or a token) and whether the grant was revoked or stays queued. The next login, successful refresh or logout sends queued revokes again; one still failing then is recorded as `revoke_queued`. One sign-in flow runs per store at a time (`<store>.login.lock`); a concurrent `login()` waits and, once it holds the lock, shares the store's grant if it is live and otherwise fails rather than starting a second flow. The holder writes its authorization URL to `<store>.login.url` (unlinked when it takes the lock and again once the browser answers, before its loopback callback closes, so only a waiter's read already in flight can show a link whose callback is gone; a write or unlink that throws is a `diagnostic` with operation `login_link`, not a failed flow), and a waiter reads it only after each failed lock try (`acquire`'s `onBusy`), bounded (`readSmallJson`: a non-blocking open, a regular file only, at most 8 KiB, so a FIFO or a huge file planted there can't stall the wait), so a crashed holder's leftover is read at most in the instant before the next holder unlinks it. Each distinct URL that passes `signInUrl` (`src/shared/signin.ts`, the shape the Claude Code hook accepts) and has the resource's origin goes to the waiter's own `present`, unawaited (a rejection, the plugin's decline, ends the wait with that error); a rejected one, or a link file it can't read or parse, is said once per flow, naming the check and origin, never the file's text, as a `login_link` diagnostic, which the Claude Code plugin keeps in its log and out of tool results (#592). Opening it in either process completes the holder's flow, and the waiter shares the grant. The URL carries `state` and the S256 challenge, never the verifier; a reader of the 0700 store dir already reads the tokens. An automatic sign-in (`login(signal, true)`: it started because a token request found no grant) also returns on any live grant under the lock, including one that landed before its own first read of the store, which the epoch comparison can't see; it then resolves `"current"` rather than `"signed in"`, and the adapter's sign-in record (`adapters/hosted-core/src/offer.ts`) says nothing and keeps its last outcome; an explicit login (pi `/login`) still runs a flow unless another process's landed while it started. A sign-in that can't take the refresh lock to commit revokes its new grant instead of writing it. Two processes on one raw session would share one lease and both admit every item (`delivery_open` returns the live capability for the same session and ownership), so a root's delivery runs only while its process holds that root's delivery lock (`tryDelivery`, `adapters/hosted-core/src/storage.ts`; `RootDelivery` takes it, the Controller doesn't), and tools-only otherwise. While another process holds it (`DeliveryHeldElsewhere`), `bind` and `unbind` are refused, since the binding is the holder's. A lock that can't be opened at all (not BUSY) is said and runs tools-only with no waiter (its polling would fail the same way each time) and no held claim, so `bind` and `unbind` still work; a resume tries the lock again.

Hosted admission charges a separate per-user request bucket after OAuth authentication but before source-session or alias lookup, not the bind limiter (§4, #189, #226). Request-local application contexts resolve stable grant-client source sessions; charging each request against the bind limiter's budget would let ordinary fleet tool traffic starve binds. The hosted defaults support sustained fleet requests with bounded burst headroom. Defaults: `src/server/rate_limit.ts`; overrides: `src/server/config.ts`. A refusal is a typed MCP error with HTTP 429 and Retry-After, never dispatches the tool, and recovers after refill; arbitrary application or storage errors never become throttles. Request-local refusal state stays with its exchange, including concurrent refreshed legacy requests. Hosted and bind refusal audit streaks remain independent, as do live-state quotas.

Unexpected-failure diagnostics use code-owned catch-site provenance and bounded exchange context, never exception messages, stacks, causes or arbitrary properties (`src/server/diagnostics.ts`, #386). From the error they take only its class and a SQLite- or errno-shaped `code`, each matched against a bounded pattern and read as data descriptors so no getter or `toString` runs. Root throwing locations are deliberately unavailable: even plausible source frames can contain credentials. SDK error callbacks and surrounding catches share exchange-local deduplication; clients get generic unexpected-error text, while factory authentication loss remains HTTP 401. The Slack bridge follows the same provenance and generic-reply boundary.

Durable hosted ownership history is separate from live source-session rows (`src/server/hosted-types.ts`, `Repo.hosted`). A hosted session holds several names (#451): `bind` and `unbind` (`src/server/hosted.ts`) run `application.bindNow` and `application.unbind` on a session rebuilt from the root's holds (`hostedSession`), inside the root's one transaction; they preserve ownership, children, status and claims (claims stay with their address, `boards.md` §3); a bind that adds a hold or an unbind that releases one bumps the generation and closes delivery. A refused bind's `refused` binding row is written after the transaction rolls back (`hostedRefused`). The last `unbind`, or a revocation of the last hold, clears the lease deadline: the root is unbound but owning, and the sweep leaves it to the idle window. A revocation releases only the revoked hold, through the hosted store's transaction so the lease closes at once. HTTP has no frame, so that transaction keeps the loss (`hosted_alias_lost`, #453) for two readers. The agent's reader takes it once: the root's next native `whoami` (as `alias_lost`) or tool result, a refusal included, appends the plugin's notice (`aliasLostNotice`, `src/core/bindings.ts`; audited `hosted.alias_lost_notified`) and marks the result with `_meta["io.github.nolnoch.grayboard/alias_lost"]` (`GRAYBOARD_ALIAS_LOST_META`, `src/shared/session_meta.ts`), on which the adapter's proxy drops its cached instructions. The Controller's reader is reported, not taken: every subscriber `whoami` carries `alias_lost` until the root's next `delivery_open` takes the reported entries (audited `hosted.alias_lost_seen`), so a resume or a reopen that lost a `whoami` answer still learns it; the Controller drops those holds from what it rebinds, keeps receiving under the rest instead of pausing and shows the loss on its status line, and a `delivery_open` refused because the primary went between its `whoami` and the open retries once. A `bind` of the lost alias clears both readers' entries for it. A child's calls take none (pi probes a child with `whoami`), nor do `bind` and `unbind` results; an ownership end drops it. Old-name DMs never move; a DM to the root's own ID is pushed without an address, and an alias DM carries its address, which the client checks against its holds. A bind refuses a name any other session holds with `alias_held` naming the holder; a contending hosted root whose lease deadline has passed, or that was never leased and is idle past the window, is ended instead. Child registration is depth one, under ordered root/child writer gates and one immediate transaction; a child uses its root's effective name, cannot bind or control delivery, and can end only itself. Root end removes descendants atomically. A child idle past the window (no request of its own, and no `session_register` of it) is parked by the sweep (`hosted_sessions.parked_at`, audited `hosted.child_parked` against the root, #566): `Repo.hosted.all()` leaves parked rows out, so they count against neither the root's `MAX_CHILDREN` nor the user's and global rows, while `get` and `children` still see them. Its next request, or its root's `session_register` of it, makes it active again under the root's current grant (`unpark`, audited `hosted.child_unparked`), admitted against the same limits as a registration; a refusal leaves it parked. A refused registration, convert or unpark for the root's child limit says local mode's `childCapacity` text (#584). A root keeps at most `MAX_CHILDREN` parked children: past that, the sweep that parked them releases the oldest parked (by `parked_at`, then last activity, then ID) in the same transaction, audited `hosted.child_released` with `reason: "evicted"`; an evicted child that calls again starts as a root, as an ended one does. No idle check ends or parks a session with a call running (#584): the server counts in-flight calls per session ID in memory, a child's call counting for its root too (ending a root deletes its children), and the sweep's root end and child park and `bind`'s idle-contender end all skip a counted row (the bind probe needs no skip: it runs alone on the root's gate, after the root's calls drain); lease expiry and a disabled user still end it. A call's end touches the row and its root again, if both are still as the call found them, so the idle window runs from the call's end. Neither an exchange's selection (`snapshot`, which every MCP request runs before its tool) nor its `session_end` unparks it, so ending one is never refused for capacity, and a resource read leaves it parked. Why server-side: pi and omp cache a child's registration, so a deleted row's next call would start an ownership of its own (#523). Children take no restart credit (#423): they hold nothing, and an outage past the window parks them all, each unparked on its return. Registration is server audit, not a fabricated name-binding event. Hosted source IDs register an `ids` row against the authenticated principal (`hostedRegister`; another principal's row is `id_collision`) without claiming a reusable session-key proof; its harness fact is `harnessFor` (`src/server/oauth-config.ts`): `opencode` for OpenCode's client, a built-in's own label, else the opted-in client's exact ID, which `peer_list` shows and `match.harness` filters. A child attributes writes to its own ID while sharing the root's mailbox. Alias holds follow durable ownership and rebuild before requests after restart; releasing ownership drops the hold (`released`, detail the end reason), not the source ID's history: a source ID is stable, so it never ends through `endSession` (`disconnectUser` skips hosted-owned IDs), and its mail isn't bounced nor its claims released. ID status stays with that source across bind and unbind, while a mailbox's queue opt-out stays with the alias.

Only successful bind, delivery open or root registration moves the ownership's grant attachment. Ordinary same-account/client writes under another grant are audited without attaching it. Attached-family revocation and disable end the ownership, descendants and name binding atomically; post-commit invalidation closes memory state before another request. A lease's durable deadline survives disconnect and restart: timely reopen retains ownership and status, while expiry releases exactly once without needing a contender. Never-leased owners use the contender-only idle rule. Server shutdown drops memory delivery but leaves durable deadlines, auditing each dropped capability as `hosted.lease_detached`; it is not explicit session end. Lease and idle clocks stop while the server is down (#423, `creditDowntime` in `src/server/hosted.ts`): start credits the gap since the last heartbeat to each root's live lease deadline or not-yet-idle clock, except a disabled user's. A lease deadline is capped at one TTL past now and an idle clock at now, so a stale heartbeat (a rollback to a release without it, or failing heartbeat writes while renewals succeed) can't let a dead owner hold its name longer. A gap within two heartbeats is indistinguishable from a live server or a concurrent opener and earns nothing; the credit commits with the new heartbeat, so it applies once. Each change is audited as `hosted.lease_restart_credit`, and every start, credited or not, as actorless `server.started`.

Tools, byte transfers, pending reads and receipts take the effective root's BindGate reader; bind, registration, end, grant attachment, delivery open and release take its writer; delivery renew takes the reader. Gates retire only after active and queued callers finish. Cross-process writers require more than a process-local gate: native effects reselect authority and exact root generation/name/child relation inside their effect transaction; receipt authority, issued-prefix validation and cursor updates share one immediate transaction. Database state commits before holder publication, without an intervening await. Native effects and audits stay inside that transaction; live DM/board payloads, observer invalidations and wakeups wait for its outermost successful commit (`src/core/sqlite.ts:afterCommit`). Nested savepoint success only transfers effects to the parent; rollback discards them. Use `db.transaction`, not raw SQL transaction boundaries. Postcommit sink failure cannot fail or roll back the durable operation, and failed board publication leaves no phantom inflight receipt. Lease capabilities and issued batches capture ownership, generation, grant and name; stale receipt, renewal, release or delayed cleanup cannot mutate a successor or advance its cursors. A canceled open cleans up only unaccepted state created by that attempt; successful reuse fences older cleanup and preserves existing notification hooks. Receipts acknowledge durable host admission only, not DM handling. `dm_ack` remains separate.

Live-session admission is bounded transactionally per account, globally and per root (`src/server/hosted.ts`), including unbound contexts and restart-restored rows. Refusal cannot attach a new grant. Unbound idle roots and their descendants retire without a contender; bound never-leased ownership keeps its contender-only rule. These are live-state limits, not an audit-retention policy.

HTTP tool attachment arguments are uploaded `attachment_ids`, not paths on either machine. Attachment byte URLs derive from protected-resource discovery's canonical resource and the attachment id (`src/server/mcp-attachments.ts`); these URLs contain no bearer or lease capability. Byte requests use the same resource-bound tools grant and source mapping as tools: the grant's client selects the key, never the request (#226, #208 item 9). MCP carries the value under the client's `_meta` source key; raw byte routes require `X-Grayboard-Session`, the canonical `encodeURIComponent` of that same raw source session, mapped through the same `sourceContext`. The header is routing context, not a mailbox or credential, on the same token trust boundary as tool metadata. Byte requests do not enter the JSON-RPC factory or acquire delivery ownership. A registered child resolves to its root. Missing, unmapped or unbound context cannot transfer private bytes or mutate uploads; clients unable to send the header fail closed. The optional identity query only asserts the effective bound name (403 on mismatch). The retained attachment API remains session-authenticated; neither credential type grants the other's routes. The hosted endpoint does not offer a local-file download tool. SDK schema validation precedes application dispatch, and unexpected operation errors are redacted rather than exposing storage details.

The endpoint's discover and initialize results publish the server's attachment caps (`GRAYBOARD_ATTACHMENT_MAX_BYTES`, `GRAYBOARD_ATTACHMENT_MAX_TOTAL_BYTES`) as the one experimental capability, `io.github.nolnoch.grayboard/attachments` = `{file, total}` in bytes (`ATTACHMENT_LIMITS_CAPABILITY`, `src/shared/attachments.ts`); no channel capability is advertised, since hosted HTTP has no push (#430). hosted-core's tool proxy checks local files against it before any upload and derives `attachment_get`'s download deadline from its per-file cap (`transferTimeoutMs`); it falls back to `DEFAULT_ATTACHMENT_LIMITS` only when the server publishes no such capability (a server older than #430), and refuses a malformed one.

OpenCode V2 attachment transforms (`adapters/opencode-v2/src/transfer-tools.ts`) preserve the native tool namespace and already-uploaded IDs, add local paths to send tools and register the local save tool in that same namespace. They use the host location for relative paths, not the plugin process cwd. A path send checks the namespaced host permission once, then calls the server tool over a shared sessionless native wire with the caller's session key: invoking the host's native execute would prompt a second time after a once-only approval. The wire caches its published capabilities until endpoint/grant replacement or connection failure; callers never share source-session metadata. `HostedAttachments` (`adapters/hosted-core/src/attachments.ts`) owns upload cleanup, authorized HTTP transfer and verified downloads for both these transforms and `ToolProxy`; shared path validation is vendored from `src/shared/attachments.ts`, never reimplemented. Each transfer pins a native grant projection and each byte request rechecks it; the plugin cannot refresh or retarget that captured grant.

## 4. Application sessions

`src/server/application.ts` owns sessions (`ApplicationSession`: hosted MCP and the bridge's humans), their holds, delivery ownership, operations and typed delivery sinks; `src/server/hosted.ts` and `src/server/mcp.ts` reach it for every agent, `attachHuman` for the bridge. A session is not an authenticated user or a transport connection: only a delivery owner counts as online, and tools-only callers never drain pending items.
- **The WSS transport is gone** (#282). `/ws` keeps one unauthenticated refusal handler for pre-removal `grayboard mcp --mode server` clients (`src/server/ws_refusal.ts`): it answers a hello carrying `proto: 2` with `upgrade_required` (`UPGRADE_REFUSAL`, the hello's `req_id`) and a hello without `proto` with `bad_request` (`PROTO_REFUSAL`, the 1.x refusal), closes on any other frame, and has no session, hub or database. Why not a 410: Bun's WebSocket gives a client no status or body for a non-101, so every release treated it as a network blip and reconnected forever; only a frame reaches a 2.x client's fatal-refusal path, and a 1.x client's from 1.10.0 on. The upgrade matches by header on any path and needs no token. It is bounded because nothing authenticates it: `idleTimeout` (with `sendPings` off: Bun's default pings keep a silent client's socket open past it), `maxPayloadLength` and a per-address open-socket cap (`MAX_REFUSAL_SOCKETS`, 429 at the upgrade). Each refusal logs one stderr line per address a minute, the only trace of which clients still dial it, behind the address gate (`authGate.refuse`) like every route. It never charges the auth gate: a restarted 2.x fleet would otherwise see 429 at its `/api/whoami` probe and loop on "rate limited" instead of reaching the refusal. A client with a revoked token waits for a new token at that probe and never sends a hello.
- **A hosted request's model and effort are the session's latest** (#364). `sessionContext` reads `GRAYBOARD_MODEL_META`/`GRAYBOARD_EFFORT_META` from any client's `_meta` (display facts that grant nothing): a non-string is `bad_request` with a message naming the key (logged `session_meta`, as a malformed delivery declaration is), and `cleanFact` drops format characters (`\p{Cf}`), folds to one line, stores NFC and cuts length, so `match` compares what a reader sees. `rowFor` compares them with the session's `ids` row on every gated request and `hostedFacts` writes and audits (`id.facts_changed`, before and after, `why: request`) only on a change. Each fact has three states on the wire (#558): a string is the value, an empty string is "the host has none" and clears the stored one (audited like any change), and an absent key is "unknown" and keeps it, so a client that sends nothing (OpenCode's native client, a release before #558) never clears one, and the hot path stays one read. An empty string meant nothing before #558 (both hosted-core and the server dropped it), so the meaning is additive. A new ownership of a stable source ID overwrites with its first request's facts, null when absent, so a resumed session never shows the last ownership's model; that overwrite is audited `why: ownership`. A legacy GET or DELETE routes by its creating POST's `_meta` with the facts removed (`withoutFacts`), since replaying them would revert the latest. "Latest" is the order the server processes requests, not the order a client sent them: two in flight across a model switch can land either way, and the next request heals it. A child row keeps its own facts; `peer_list` shows the root holder's. hosted-core sends them on every request for the session that request names, reading the host's provider per request (`HostedClientOptions.facts`, `HostPort.facts`; `SessionFacts` fields are a string, `null` for none, sent as `""`, or absent for unknown) so a mid-session switch lands on the next one; the native wire is shared across sessions, so the provider takes the session ID. pi and omp report `ctx.model` as `provider/id` (none without one) and the thinking level, only for the session their runtime currently shows (omp repoints `ctx` at the next session before ending the old one, so the old one's end request must not carry the next one's model; a child's process reports its own; omp's `inherit` is none). `HostedClient` says a provider failure once per session. The OpenCode v2 plugin notes each session's model from its `context` hook (`providerID/id`, the variant as effort, none without one, since `Model.Ref.variant` is unset for the model default; compaction, title and generate requests have their own hooks and don't re-note it; an LRU bounded by `FACTS_LIMIT`, `adapters/opencode-v2/src/lifecycle.ts`), so a root restored after a restart reports nothing until its next model request and sends it on its own wires (subscriber, temporary, the instructions fetch). The Claude Code plugin's MCP child has no in-process source, so its hooks relay the root's facts (#545, measured on 2.1.316): SessionStart's `model` and PostModelSwitch's `to_model` (which runs only once the user confirms the switch; PreModelSwitch runs before that dialog and isn't used) are written to `model` (a full ID such as `claude-opus-5-5`; `to_model` is the ID as given to `/model`), and the root's grayboard PreToolUse `effort.level` (the `CLAUDE_EFFORT` env var keeps the start-time value and isn't a source) to `effort`; a root PreToolUse without one (a model without effort) writes an empty `effort` (none, a clear on the wire, #558), PostModelSwitch removes `effort` (unknown until the next root call, so the server keeps the last level rather than clearing and restoring it), and a SessionStart other than `clear` removes both before writing the model, so a new process never inherits a reused pid's facts. Each is a whole file in the #551 per-process dir (`src/shared/claude_agents.ts`, plugin hook only), checked to `SESSION_FACT_MAX` so the server stores what the hook wrote; the plugin's provider reads both per request for its root, after the same start-time check the records use, at most `SESSION_FACT_MAX + 1` bytes of a regular file opened without following a link or waiting on a FIFO, reads an empty file as none and a missing one as unknown, and leaves out a malformed or unreadable file (said once per fact) while sending the other. No hook names a subagent's model, so a child session reports none. The facts are harness-asserted in a same-user directory: any same-user process can write any session's facts, so a forged file misreports that session's display model or effort and grants nothing (the records' boundary, `boards.md` §3, and #229's). Known limits: the model reaches the server with the first request after SessionStart's hook (the bind or first call); a model change without PostModelSwitch (an automatic fallback) shows at the next SessionStart; an `/effort` change (no hook fires) shows at the next grayboard call, as does the effort after `/clear` or a model switch (SessionStart carries none, so the server shows the last level until then); and the hook says nothing (it must never block a call), so a fact it failed to write (a full disk, a Claude Code build without PostModelSwitch) leaves the last one standing with no signal. Audit rows are bounded only by the per-request hosted limit, on the client's own row. A client sets facts only on its own row (`rowFor` fences user and client); that any holder of the token can act as the user's sessions is the accepted #229 boundary.
- **A hosted root's suggested name is its first request's** (#443). `sessionContext` reads `GRAYBOARD_SUGGESTED_META` from any client's `_meta`: a hint that grants nothing, normalized by `normalizeIdentityName` (a bare name, lowercased); a non-string is `bad_request` naming the key, and a string that isn't a name, or is `human`, is no suggestion (as local mode treats it). `rowFor` stores it on the root's `hosted_sessions.suggested` at insert and never updates it (the store's update lists its columns), so a later request's suggestion changes nothing and a new ownership of the same source ID takes its own; a child's is null. The ownership's `hosted.ownership_started` audit records it as `suggested` (#522), so the trail says why a session was offered a name. Every unbound root's candidate list (`initialize` instructions, `whoami`, the last `unbind`) passes it to `candidates()`, which offers it first while no session holds it (`fresh` when the alias doesn't exist yet). hosted-core sends it on every wire (`SUGGESTED_META`, the `HostedClient`/`HostPort` `suggested` provider, #522), since whichever request reaches `rowFor` first fixes it: the Claude Code plugin and pi/omp send local mode's `sessionIdentity(env, cwd)` (the pin or the repo's name, with the worktree suffix) for the root only. OpenCode V2 sends none yet (#696), so its roots offer only the user's free names.
- **Where hosted differs from the removed WSS on purpose** (#463). A name's `last_seen` is its last request before `delivery_release`, not the release (hosted has no close frame). A refusal from a native board, claim or DM tool is `error: <message>` text, so a caller branches on the message; only `bind` and `unbind` return a structured `{code, message}`, because the adapters branch on those codes. `bind "human"` refuses `forbidden` with `HUMAN_RESERVED`, the code and text `bindNow` gives, whichever entry the bind came through. `whoami` carries `id` and `principal` beside the holds. Write dedup (`dedupWrite`) is the application's, so a hosted write replays as an AppSession one does; `tests/integration/write_dedup.test.ts` forces the lost-answer window on a hosted session and the rest on AppSession.
- **Leftover sessions end once at start.** Every unended session that no hosted ownership holds (a WSS session an earlier run left) ends through `endSession` with `why: wss_removed` (`endIds`, `src/server/application.ts`), since only a hello could re-attach one. Hosted-owned IDs are the hosted store's to end.
- **Binds are rate-limited per user** (#210, `RateLimiter`, `src/server/rate_limit.ts`): a token bucket per user (sizes: `src/server/config.ts`, `GRAYBOARD_HELLO`, named from when a hello spent it too), spent by every `bind` and checked before anything reads or writes the database. Over it, a bind gets `rate_limited` with `retry_after_ms` (the wait until a token is back). Why: a bind creates its alias lazily, so a client looping on it could load the server and mint rows without bound. The Slack bridge's in-process connections are exempt. A run of refusals lasts until the user's bucket is full again, seen by the next bind or by the 30s limiter sweep (`sweepLimits`, `src/server/app.ts`, which drops refilled buckets); ending it at any accepted bind would let a loop just faster than the refill start a run, and an audit row, at every refusal. Each run logs one line and writes one audit row when it starts (`hello.rate_limited`, detail: the tripping session ID, the alias it bound, and `retry_after_ms`) and one of each with its count when it ends (`hello.rate_limit_ended`, detail `{refused}`).
- **Authentication failures are rate-limited per client address** (#240, `AuthGate`, `src/server/auth_gate.ts`, on the same `RateLimiter`): every presented token the server refuses with 401 on the MCP or `handleHttp` path (the OAuth AS and OAuth byte routes answer before charging) and every call to a sign-in route (`signInRoute`, `src/server/http.ts`, one table that both dispatches and decides charging; charged on entry because the exchange awaits Google; a disabled route, such as dev-login with dev auth off, dispatches to 404 uncharged) spends a token from the address's bucket. An HTTP 401 is charged on the MCP or `handleHttp` response when the request carried a bearer token (`chargeRefusedToken`), so a protected or unknown path with a bad token costs one, while the public routes, dispatched before `requireAuth`, cost nothing unless they are sign-in routes. A request with no token costs nothing: a web page can make a browser send one cross-origin (an `<img>`), but can't attach `Authorization` without a CORS preflight, so charging them would let any page lock out everyone behind its viewer's NAT. For the same reason a sign-in route takes only `Content-Type: application/json` (`isJsonRequest`) and answers anything else 415 `unsupported_media_type`, uncharged: a cross-origin form post needs no preflight, a JSON one does. While it's empty, `fetch` answers every request from the address, `/healthz` included, with 429 `{code: "rate_limited", message, retry_after_ms}` and `Retry-After` (whole seconds, at least 1), before anything reads the database. 403s, 404s and the 429s themselves cost nothing, and valid authenticated traffic never touches a bucket: a check allocates nothing, so the map holds only addresses that have failed, dropped by the 30s sweep once refilled, and capped at 10,000 (past the cap a new address is neither charged nor refused, with a log line and an `auth.rate_limit_full` row at most once a minute; a flood spread across addresses belongs at the network edge). Why failures only: a lookup that succeeds is bounded by legitimate use and the bind limit, and charging only failures keeps a stale-token client behind a shared NAT from blocking its neighbours until it has failed the whole burst; hosted-core stops retrying a refused token, which keeps it from getting there. The address (`src/server/client_addr.ts`) is the peer, normalised (Bun reports an IPv4 peer as `::ffff:a.b.c.d`), or when the peer is in `GRAYBOARD_TRUSTED_PROXIES` (default loopback) the first untrusted `X-Forwarded-For` entry walking from the right, with a port or brackets stripped; a walk that runs out of entries, or meets one that doesn't parse, keys by the last address it trusted, and the first unparsable entry per process is logged, since it puts that proxy's clients in one bucket. A peer Bun can't report keys to the shared bucket `unknown`, never skipping the gate. IPv4 keys by address, IPv6 by /64. The resolved address is also `auth.login`'s `ip`. A run of refusals has the bind limit's streak semantics, with `auth.rate_limited` (actor null, target the key; its detail carries the refused request's full address and `last_failure`, the charge that emptied the bucket, so a stale-token fleet reads differently from a scan) and `auth.rate_limit_ended` (`{refused}`) rows and a log line each. The start hook runs before the refusal is counted, so a failed audit write leaves no run without its row; `sweepLimits` (its own 30s timer in `startServer`) runs both limiters' sweeps, each catching per bucket.
- **The Slack bridge's humans** attach in-process through the application's trusted bridge method (`attachHuman`, `src/server/application.ts`) with no key, so no network client reaches that path. A human gets no ID (its session ID is the literal `human`), no `ids` row or end; it holds `<email>/human` (a newer bridge attachment for the user supersedes it) and its writes carry no `sender_id`. With `human` refused in every `bind` and `writes_as`, `<email>/human` is provably that user's person. The session facts (`helloOkFields`, `src/server/application.ts`) tell every hosted session its user's human handle and whether it's linked (`slack-bridge.md` §8).
- Adapter authority derives from that reserved structured sender, compared against the authenticated **lease** user's human, never a body claim or OAuth sign-in alone. Shared classification and V2's JSON envelope boundary: `boards.md` §9; real attachment/model-admission proof: `adapters/opencode-v2/tests/host.ts` (`human-authority`).
- **`bind`** (`src/server/application.ts` `bind`; a hosted session's own tool calls `bindNow`, skipping only the holder probe because `hosted.ts` clears stale contenders itself, §Hosted MCP) adds an alias to the session's holds (`boards.md` §3; up to `MAX_HOLDS`); The result carries `held`, every hold oldest first, and `restored {verified, detail}` when the call claimed continuity. **`unbind`** removes one and answers `{alias, released, held, left?}` (`released: false` for one not held; `left`: the claims that stay with it); it spends no limiter token, since it creates nothing. A bare name is the caller's own person scope; `scope/name` needs `mayActIn` (§5); `human` is refused in every scope, since `canSend` treats any `*/human` as a person's phone. The alias is created lazily (audited `{lazy: true, session}`) unless `create: false`, which refuses a never-seen name with `identity_unknown` carrying `known` (the closest names). An alias another session holds is `alias_held` naming the holder and its place; there's no takeover. A hosted root holding it is probed first (#402): a never-leased one idle past the hosted window ends and frees the alias (the contender-only idle rule, §Hosted MCP); a live one is `alias_held`. An alias in use by another principal's session (held, or written as by a tools-only session) is exclusive (#284 S8; `aliasUser`, `src/core/bindings.ts`): that principal's bind, `writes_as` and HTTP `?as=` are `alias_held`, while the user's own tools-only sidecars and `?as=` share it (#182). An identity any session uses can't be deleted, or a second session could bind the name while the first still acts as it. After a bind the server drains the alias's mail and boards. A `meta` the server refuses (`parseAliasMeta`) logs a `refused` binding event. Revoking one team alias drops only that hold; the rest and the primary rule stand.
- **Binding events** (`binding_events`, `boards.md` §3) come from `bind`, session end, revocation and hosted binds and ownership ends: `bound` (detail `restored after end of session <id>` for a verified `previous_key`, else the `… not verified` reason; only a verified one inherits the predecessor's status, #211. `restored_from` names a public ID any client can present, so it's logged `restore claimed from <id>, not verified` and proves nothing; `previous_key` is the ended session's secret, so it proves descent, #259), `refused` (a bind's, or a hosted `writes_as`'s; a retry loop's repeats share one row, `boards.md` §3), `released` on an `unbind`, a session end or an access revocation (details: `logBinding` callers). A hosted bind and unbind log through `bindNow` and `unbind`, except a refused bind's row, written after its rollback (`hostedRefused`); a hosted ownership's end writes `released` with its end reason for every hold directly (hosted store `end`, `src/server/db.ts`). The Slack bridge's human logs under the literal session `human`: `bound` when it attaches, `released` (`connection closed`) when it closes; a superseding attachment logs only its own `bound`.
- **Tools-only sessions** are never pushed to and aren't in the registry or online. A hosted root declaring `writes_as` (`hostedWritesAs`, `src/server/application.ts`) names an alias judged like a bind target and created lazily but never held, and reads and writes only as that alias (its address set is `[writes_as]`); its `ids` row has `writes_as` set, so a send to its ID is refused `no_delivery`, and its `bind` is refused. Why a hosted bind holds without delivery: holding nothing let two sessions bind one name (#182 audit 2).
- **Unbound hosted MCP sessions read only** (`src/server/hosted.ts`): a hosted session ID is routing, not a capability (#229), so an unbound hosted session doesn't act as its ID. The application allowlists `UNBOUND_READS` calls and refuses all named operations, including receipts, with `unbound`; transports cannot bypass that gate. Such a session takes no `alias_holds` row; live read-only application sessions supply its presence (`peer_list` `unbound_sessions`, the caller's own user only), and its board visibility is judged as its user (`seer`, `src/server/application.ts`).
- **Address set** (#284 S8): a session reads as its holds plus its ID (a hosted child: its root's holds plus the root's ID, never its own, and its writes carry its ID as `via`; `hostedSession`, `boards.md` §3 Child sessions) and writes as its primary (`boards.md` §3), unless `as` or a reply default picks another address; the registry is keyed by address. `as` and the reply default are resolved before `prepareSend` (bare-peer resolution and `canSend` are per acting address) and before the dedup fingerprint. History, inbox and thread match any address in the set; an `ack` advances each message's own recipient address's cursor, a retract acts as the address that sent the message, and `board_ack` acknowledges on each address. **Drain at bind and delivery open**: DMs after each address's cursor (`mailbox_cursors`, keyed by address; seeded once from 1.x `cursors`, as `aliases` is from 1.x `identities`, and neither old table is read after), then pending board items. Drain doesn't advance cursors; only `ack` does (`MAX(existing, new)`, so out-of-order acks can't regress). Board items: the session keeps an in-flight set, keyed per post with the addresses it went to, so an `unbind` drops that alias's items and a later `bind` of it re-drains them; `board_ack` acks in the core. A new session starts empty, so unacked items resend. At-least-once for both.
- **Delegation** (`delegate {persona, task, context?, to?}`, #184): the server resolves the target — `to` through the same resolution as `send`'s recipient (`resolvePeer`), then both modes of targeting (explicit and auto-pick) restricted to the requester's own user — and delivers the payload as a pending DM through the ordinary send path. The payload fences persona/task/context inside a four-backtick JSON block the launcher's instruction says is data; the body's header is never authority (the DM's sender is, and it must be the launcher's own user). Every outcome is audited: `delegation.requested` (target: the launcher; detail `{requester, via: explicit|auto|human_fallback, message_id}`) or `delegation.refused {reason}`, each with `child` when a child session made the call (`boards.md` §3 Child sessions) (on the hosted path, which runs a tool call in one transaction, the refusal's row is written after that transaction unwinds via `ApplicationSession.afterRollback`, so it survives the rollback, #452); `handle.launcher_set {on}` against the session ID (locally, once per session that owns delivery, under its ID). The reply carries `to` and, on the degrade path, `human_fallback` added (`DelegateOk`). A hosted session is a launcher when its requests declare it (#473): `_meta["io.github.nolnoch.grayboard/launcher"]: true`, which `sessionContext` reads from a built-in client only (a third-party client can't claim the user's delegation requests; a non-boolean is `bad_request` naming the key; `false` and absence are the same). Any request of a root's ownership that declares it turns `ids.launcher` on (`rowFor` → `hostedDeclareLauncher`, #520), whether the request starts the ownership (a new ID, or a new ownership of a stable source ID) or comes later: OpenCode's native client starts an ownership with no plugin `_meta`, and the plugin's subscriber wire declares it afterwards. A tools-only root, which can't receive pushes, and a child are never one. `handle.launcher_set {on: true}` is audited under the session ID when the flag actually turns on, so once per ownership; a later `false` or absence changes nothing, and the ownership's end clears it (`hosted.end`, with `writes_as`), audited `handle.launcher_set {on: false, ownership, reason}` when it was on (#532), so a resumed session that no longer declares one isn't a launcher. A `session_end` request's declaration doesn't count: its end would clear the flag in the same request. The launcher instruction rides the session's initialize text and its bind and unbind results from the stored flag (`hostedLauncher`), so the text matches what routing does. hosted-core sends the key on every wire when the host declares it: `HostedClient`'s `launcher` option for its proxy wire, and `HostPort.launcher` for the Controller's (subscriber, temporary, child registration). The Claude Code plugin and pi/omp set it from `BUS_LAUNCHER=1`; the OpenCode v2 adapter from its plugin option `launcher: true`, since its settings are plugin options. OpenCode's native client sends `initialize` with no session key and caches its text for the process, so its agents would only ever see the unbound text; the OpenCode v2 plugin's `context` session hook (`adapters/opencode-v2/src/instructions.ts`, #531) instead rebuilds grayboard's `<server>` entry in every primary request of an enrolled root that isn't paused with that root's current `initialize` text, fetched over a native wire that names the root (refetched when the root's state, holds or ownership change, or after a native `bind`/`unbind`). That carries the launcher instruction whether the name came from a native bind before enrollment or the plugin's configured `name`. The hook never rejects (OpenCode puts no timeout on it and a rejection fails the step): it waits 2 s and otherwise keeps the last text; an outage or token rollover keeps the last text without refetching until the next change, a sign-out clears it, and a failure lands on the root's own diagnostic record (operation `instructions`). Server text is indented under the frame, so it can't close the entry. A subagent of such a root gets the same rewrite with its own `initialize` text, the server's child text (`hostedChildInstruction`, #535): `Controller.childRoot` resolves its ancestry once (at `session.created`, which also starts the fetch so the first request needn't wait out registration and connect; a resolved path is kept, and only a failure resolves again; it's a lookup, not a route, so ending a session the server never saw sends nothing), and its native wire runs under the root's enrollment after `Controller.enlist` registers it, since an unregistered session key would start an ownership of its own; a refused registration fetches nothing and is the fetch's `instructions` failure, not a `child_register` one that would degrade the root, and a child that ended while its registration was in flight ends the row it made. Every such subagent holds a child row, which counts against the root's child capacity until it idles past the window and is parked (#566). A child's wire never declares a launcher. Its cached text follows the root's: any invalidation of the root refetches it, its failure lands on the root's record, and `session.deleted`/`archived` drops it. The compaction summarizer, title and other generations have their own OpenCode hooks, so they keep OpenCode's own text. A server that held WSS launchers keeps their `ids.launcher` rows: an offline alias is never a delegation target (`online()` gates both resolutions), and once a hosted session binds the alias, `LAUNCHER_SQL` follows the alias to that session's own flag.
- **DM send**: body non-blank and ≤ 64 KiB (`checkBody`, `src/core/boards.ts`, shared with local mode). A bare name resolves to the acting address's own scope's alias of that name (`ownScope`: an alias's scope, or an ID's principal), else the one alias anyone has with it; ambiguity is `not_found` naming the candidates (`resolvePeer`). A send to an `id:` is checked inside the write's transaction (`assertDeliverableId`), so it can't race that session's end: an ended, tools-only or child-session ID is refused, never queued: core's `Undeliverable` carries `not_found`, `id_ended`, `no_delivery` or `child_session`, which `coreRefusal` sends as the error's code (the same code and text local mode shows), as it does for an `@id:` mention a post is refused for. `team:<name>` recipients are rejected: teams are reached by posting to their board. `history`'s peer resolves the same way (`resolvePeer`). `parent_id` must be a message the sender sent or received, and the recipient must be its other party (`replyPeer`; `bad_request` otherwise, `boards.md` §7). DM visibility is one check, `participant` (`src/server/db.ts`), shared by send's parent check, `thread`, and attachment reads; a DM you're not in reads as missing. `canSend` (§5) gates every DM. `attachment_ids` names uploads (§5 Attachments) to bind in the message's transaction.
- **Append writes are deduplicated** (#254, `src/server/write_dedup.ts`): `send`, `delegate` and `call`'s `board_post` run through `dedupWrite`. The retry this catches comes from the model after a lost answer, and no harness gives the original call and the re-call a shared identifier (per-harness evidence in #254 §1; a client's `req_id` is a per-process counter), so the server fingerprints the call: `sha256(canonicalJson({tool, session, sender, args}))`, with `sender` the resolved acting address, `session` the session's ID (so sibling subagents writing under one name don't collapse; a hosted source ID is stable across a restart, a local process's is not) and `args` as the server resolved them (the recipient's full handle, the normalized board, attachments by blob digest, since every attempt uploads afresh under new ids; `delegate`'s persona, task and context as given and `to` resolved to its full handle or null, taken before resolution picks a launcher). A repeat within `WRITE_DEDUP_WINDOW_MS` on the hub's clock (`opts.now`) whose row still exists returns the stored result with `replayed {first_at, ref}` and a `note` naming the target and `resend: true`, and writes only a `request.replayed` audit row: no push, wake, outbox fan-out or delegation resolution. `resend: true` writes again and audits `request.resent`. The lookup, the write, the receipt and the audit row are one IMMEDIATE transaction (`repo.atomic`; the write callback's type refuses a promise, so nothing awaits between the lookup and the write), so a throw leaves no receipt. `attachment.bound` is audited inside the fresh write's transaction. Pushes and wakes wait for the outermost successful commit, only for a fresh write; savepoint success cannot publish rolled-back effects. A replay drops the retry's own unsent uploads in its transaction (`dedupWrite`'s `onReplay`; `attachment.released` with `reason: replayed`; blobs swept after the commit): nothing will bind them, and they'd hold unsent quota until the prune. The receipt stores the payload, not the framing, so a replay is answered in the current call's own envelope. A `board_post` runs `checkPostAccess` (board visible, parent on it, announcements human-only: the checks `post()` makes) before the fingerprint, so a repeat from a caller who has since lost the board is refused, not replayed (#296); `dm_send` runs its send checks the same way in `prepareSend`, except that an `id:` recipient's deliverability is checked in the write itself, so a repeat after that session ended still replays. Exempt: the Slack bridge's humans (`session.human`, `writeOnce` in `src/server/application.ts`), whose repeated line is two sends. `delegate`'s inner send isn't deduplicated as a `dm_send`, or a later plain `dm_send` of the same body would replay the delegation. Accepted false positives, each answered `replayed` rather than silently: a deliberate identical repeat in the window, and a second identical post to a queue board. `testPause("write:after-commit")` sits between the commit and the answer, where a lost answer happens.
- `call {tool, args}` runs the shared core dispatch (`src/core/tools.ts`) as the address `boardActor` resolves (`as`, else `boards.md` §3's board pick, else the primary), with its address set and session ID, so claim renew, release and ack match any address in the set; `CoreError` becomes `bad_request`. The returned wake list is pushed to connected handles immediately.
- Handlers run inside one try/catch in the transports (`src/server/mcp.ts`), so a throw becomes a generic error answer instead of a hung call.
- A 30s `revalidate` timer (`src/server/app.ts`) re-checks every live session's user (disabled in the database with no route to say so) and aliases (`revalidate`, `src/server/application.ts`, §5). The registry is per process; a hosted session's lease and ownership are durable (§3), so a restart loses only memory delivery, and clients re-drain from durable cursors.

## 5. Access and authorization

- **`canSend`** (`src/server/can_send.ts`) is the policy seam for DMs: pure, synchronous, takes the sending address (an alias or an ID) and a tagged target, returns `{allow}` or `{allow:false, code, reason}`. Its one rule today: another user's `human` is reachable only by their teammates' addresses, and by a team alias only when they're a member of that team (`reachesHuman`, `GRAYBOARD_SLACK_REACH`; `slack-bridge.md` §8). The one call site is the DM path in `application.ts`.
- **`canAdmin`**: only emails in `GRAYBOARD_ADMINS`. Gates every `/api/admin/*` route, and team member management when the caller isn't a member.
- **Board access is enforced in the core**, through the `Access` policy the server installs at open (`src/server/access.ts`), evaluated for the acting address through `repo.resolver` (`src/core/resolver.ts`): an ID acts for its principal, a person alias for its user, a team alias for its team; an address with no principal sees nothing. `scope NULL`: anyone signed in. `scope team:<name>`: that team's aliases and its members' addresses, for list, read, post, subscribe, mentions and pushes. A session bound to `eng/x` acts as eng: it sees eng's boards, not its binder's other teams', so a team alias can't carry one team's content into another's. A board you can't see reads as "no such board". Queued items for a handle that lost access are dropped at delivery.
- **Who may act in a scope is one check**, `mayActIn(repo, principal, scope)` (`src/server/access.ts`), keyed by principal, never by email: a user acts in its own person scope and in its teams' scopes; service scopes and principals are refused until #270. It decides `bind`, `writes_as` and board team access. It holds for the life of a hold, not only at bind: `accessChanged(principal)` (`src/server/application.ts`; HTTP team leave and remove call it through `SessionHooks`, `src/server/http.ts`) re-checks every alias that principal's unended sessions hold or write as. A holder loses the alias (hold released, `alias.revoked` with the acting user as actor, null for the `revalidate` backstop, and the session's principal in the detail) and acts as its ID; a tools-only writer has nothing left to act as, so its session ends. A hosted root's hold is released through the hosted store, and the root is told on its next native result (§Hosted MCP). `revalidate()` repeats the check over every session every 30s as a backstop. Why: otherwise a removed member keeps the team's boards and mail for the session's life.
- **Teams** (`src/server/teams.ts`, routes in `src/server/http.ts`): a team is an access group whose board is `#<team>`. Users and teams share one `principals` namespace (#284): creating a team inserts its row in the same transaction, and a name another principal holds is refused (409). Invite-only: any member or admin adds or removes by email; anyone can leave. Add requires the person to have signed in once (a user row). Add subscribes all their person-scope aliases in digest mode; remove unsubscribes. Team and board names share one namespace.
- **Non-members get 404, not 403**, for a team's member routes and roster, so a private team's existence doesn't leak. Admins acting on a team they're not in are audited with `as_admin: true` (the path for an empty team). `POST /api/teams/:name/join` is always 403, kept so older CLIs get a pointer to `team add`.
- Distributed mentions (`resolveMention`, `src/server/access.ts`; grammar: `boards.md` §4): a name resolves only among aliases that can see the board (`canSee`) and that `reachesHuman` allows the author to reach. Anything unresolved, or unable to see the board, isn't pushed and returns in `unresolved`.
- **Attachments** (`src/server/http.ts` attachments section, `src/server/attachments.ts`): the MCP process checks paths (`boards.md` §12) and the body (`checkBody`), so a refused body uploads nothing, then uploads each file over HTTP as the call's `as`, else the session's primary (`?as=`); a send binds an upload made as any address of the sending session by its user (`bindAttachments`, `uploader_principal`): a team alias can pass to another member, and its holder's unsent uploads don't go with it, whether the next holder would send, download or delete them (#367); `dm_send` and `board_post` carry only the returned ids. If the send fails, hosted-core's tool proxy releases its uploads (`DELETE /api/attachments/<id>`, unsent uploads of that address and user only), so a refused send doesn't hold the user's quota until expiry. A send binds its files all or none, so when every release answers 404 the send landed and only its answer was lost: the tool reports it sent (`SendLanded`, `sendWithUploads`, `src/shared/attachments.ts`, shared with hosted-core's tool proxy) rather than failing, so the agent doesn't send it twice. Bytes stay out of tool arguments: a file would travel base64-inflated inside the JSON call.
- **Upload limits.** The upload re-checks size and sniffs type from the bytes, since a client's checks are the client's word. `storeUpload` is the one store path, for the HTTP route and the org bridge's in-process sends alike, so both pay the same quotas, checked in the insert's transaction: a user's unsent bytes (twice the per-message total, `unboundCap`) and stored bytes sent or not (`GRAYBOARD_ATTACHMENT_USER_QUOTA_BYTES`), so neither abandoned uploads nor a heavy sender can fill the disk. The caps have ceilings and must nest (file ≤ total ≤ quota), else startup fails (`src/server/config.ts`). Before reading a body, an upload reserves its declared length in `UploadGate` (`src/server/uploads.ts`: server-wide room is FIFO; a user at their own cap waits without holding up other users; dropped if the request aborts), so concurrent uploads can't each buffer a full body in memory; hence no `Content-Length` → 411. The body must then arrive within `transferTimeoutMs` of its length (`readUploadBody`) → 408, so a trickling client can't hold its reservation. The request body cap is the per-file cap plus `MAX_BODY_BYTES` (`maxRequestBodySize`, `src/server/app.ts`), not Bun's 128 MB default.
- **Attachment reads.** A download is served only to an address that can read the carrier (`readableAttachment`, shared with the org bridge), with `nosniff`, `no-store` and `Repr-Digest` (RFC 9530 sha-256), which hosted-core's tool proxy checks against the bytes before saving (a missing one fails the check); anything else is 404, as for hidden boards. OAuth byte requests require a mapped, bound nonhuman source context, validate configured Origin before authentication, and recheck actual access, effective root binding and carrier visibility after the asynchronous blob read. Upload insertion and release deletion fence the same authority inside their write transaction; download authorization and response construction share a transaction after the read. Bytes are buffered before the response; authorization cannot retract bytes after headers commit.
- **OAuth upload boundaries** (`src/server/http.ts`, `src/server/attachments.ts`): revalidate after quota waits and body reads, around storage and before replying. If access, ownership or cancellation changes while a put is pending, release only that identity's newly created unbound upload; a concurrent successful bind must survive cleanup. Guarded uploads own the original body without request cloning or an implicit tee; source cancellation and reader unlock complete before their gate reservation or operation is released. Pre-body refusals also await source cancellation. Shutdown aborts waiters and awaits operations before OAuth teardown or caller DB close. Release checks authorization around its asynchronous sweep; a committed release cannot be undone by subsequent revocation. Unexpected storage faults remain redacted server errors, never inferred token failures; blob sweeping retains the existing retry-on-retention policy.
- **Every attachment's lifecycle is audited** with its SHA-256 and where it went; a download is logged only after the blob read, so a failed read isn't logged as one; a failed read or write is logged as `attachment.download_failed` / `attachment.upload_failed` with the error. A blob swept between the read check and the read answers 404 (`BlobMissing`, `src/core/errors.ts`). Other faults return redacted internal errors: the retained router delegates to `Bun.serve`'s `error` handler (`src/server/app.ts`), which logs the stack and answers a bare `{code: "internal"}` 500, while the OAuth byte router maps them directly. Neither uses Bun's default dev page, which can expose the message when `NODE_ENV` is unset (the prod unit sets none). A leaked file can be traced to who stored, sent and fetched it. Derive the events from `writeAudit(` calls naming `attachment.` (`src/server/`).
- Claims are org-wide: key, holder and note are visible to anyone signed in; `claim_list` hides the board name of an announcement on a board you can't see. `GET /api/claims` (for `grayboard claims`) authenticates a user, not a handle, so it omits board names entirely.
- **Retained HTTP routes acting as an address resolve it one way** (`ownAddress`, `src/server/http.ts`), for claims and attachments: a bare name is the caller's own person scope; an alias must be in the caller's scope or a team's it belongs to, and exist (else `unknown_identity`, 404, rather than created lazily as a bind does, so a mistyped name in a script can't act as a fresh alias); `human` is 403 in any scope (claims are for agents; the bridge's human stores files in-process); an `id:` must be the caller's unended session, so nothing uploads or claims as an ended one.
- `POST /api/claims/call` (for `grayboard claim`) runs a claim tool as an address `ownAddress` accepts, with that address's holder's address set when the holder is the same principal (`addressSet`, #360: an alias's CLI releases a claim its session took as its ID; refuses `args.as`), and passes the core's wake list to the same `wake` the WS tool path uses, so a CLI claim change is delivered like a tool call's.

## 6. Postgres seam

`Repo` (`src/server/db.ts`) is the only server-side store interface. Porting means reimplementing `Repo` and `src/core/` against Postgres and re-encoding the DDL. Core `endSession` reaches the server's mail only through `Repo.mail` (core's `MailPort`), and access asks `Repo.resolver` (core's `Resolver`) for principals, so a port reimplements those two interfaces rather than their callers. Attachment bytes sit behind `Repo`'s async `BlobStore` (`src/core/attachments.ts`), so moving them to an object store means another `BlobStore`, not a change to callers. `src/server/db.test.ts` enforces that nothing else in the server tree imports `bun:sqlite`. `src/local/` and `src/bridge/` stay on SQLite and are excluded.

## 7. Build and deploy

- `bun build --compile` produces self-contained binaries (Bun runtime bundled). Every target cross-compiles on Linux runners (only the darwin-arm64 binaries suite runs on macOS); a native dependency that can't cross-compile would break that. Release process: `AGENTS.md` §Releasing.
- Every compile the repo runs (builds, CI, tests) runs from a throwaway cwd: `bun build --compile` stages a `.<hash>-00000000.bun-build` file in its cwd that survives when the bun binary is read-only (oven-sh/bun#14020). Shell builds (`package.json`, `.github/workflows/release.yml`) go through `scripts/build_scratch.sh`, which needs absolute paths; `tests/support/build.ts` spawns its compile in a temp dir. A new compile path does one or the other.
- Binaries reach a machine verified (#162): the release job signs `SHA256SUMS` (first line `# grayboard <tag>`) with an ECDSA P-256 key held only by the reviewer-gated `release` environment, writing `SHA256SUMS.sig` as `<key id> <base64 DER>`. `install.sh` (openssl) and `grayboard update` (`src/shared/release_verify.ts`, WebCrypto) verify the signature with a key from their own embedded list, require the tag line to equal the tag they resolved, and check each binary against both its `SHA256SUMS` line and the API's `sha256:` digest and run the CLI's `--version` against the tag before replacing anything; install.sh moves no binary until every binary passes. Both refuse a tag that isn't `vX.Y.Z[-pre]` before it reaches a URL or file name (a signed SUMS can't smuggle `../`), and both bound every download (curl connect and stall limits; `src/shared/http.ts` deadlines in update), since a stalled origin would otherwise hang an install forever. The API digest alone isn't the trust root: GitHub computes it from whatever asset is uploaded, so whoever can replace the asset changes both, and a mirror serves both. The key list is compiled in with no runtime override, since an env var that adds a trusted key is the bypass; `assets/release-keys/<id>.pem` is canonical and `scripts/release_keys.ts sync` generates `src/shared/release_keys.ts` and install.sh's key block (a test holds all three equal). Tests sign with openssl-made test keys swapped in by `tests/support/build.ts`'s `onLoad` plugin (CLI) and `tests/support/release_keys.ts` `testInstallSh` (install.sh), never `--define` or env, so every real build carries the real list. Known gap: a mirror can freeze clients on an old signed release (#308). A `GRAYBOARD_RELEASES_URL` mirror serves `SHA256SUMS(.sig)`, the API paths with digests, the download paths and the `releases/latest` redirect.
- `deploy/grayboard.service` runs `/usr/local/bin/grayboard-server` with `EnvironmentFile=/etc/grayboard/env`. `deploy/Caddyfile` terminates TLS for one host (placeholder `grayboard.example.com`); WS upgrade passes through.
- The deploy files ride the same trust root (#311): release.yml copies `deploy/grayboard.service`, `deploy/Caddyfile` and `deploy/backup.sh` into the release as `deploy-grayboard.service`, `deploy-Caddyfile` and `deploy-backup.sh` (the `deploy-` prefix keeps them out of the `grayboard-*` binary glob), lists them in the signed `SHA256SUMS` and attests them. With `INSTALL_SERVER=1` on a host with `systemctl`, `install.sh` verifies each against its `SHA256SUMS` line and the API digest, like a binary, before it replaces anything. Placement is staged, then committed: every destination is made writable, staged beside itself and backed up before any file is renamed into place or any binary replaced, so a refusal leaves the machine as it was; then the deploy files are renamed, systemd is reloaded, and only then are the binaries moved, so a failed reload leaves the old release serving. The backup script goes beside the binaries as `grayboard-backup` and is replaced like one (it's configured by environment only); the unit and the Caddyfile belong to the operator once placed (a source-mode `ExecStart`, the real hostname; a Caddy package ships its own Caddyfile), so a copy that differs from the release's is kept and named unless `GRAYBOARD_DEPLOY_REPLACE=1` (old copy kept as `<file>.prev`, or `<file>.prev.<UTC time>` when one exists), and a symlink there is never replaced. A unit systemd defines outside the unit directory is left alone. A reload happens when the run wrote the unit or systemd reports it changed on disk; a brand-new unit is not started (no env file yet). `install.sh`'s header lists the overrides.
- The inspector (`scripts/inspect.ts`) ships as the release binary `grayboard-inspect-<target>` (#608) and `install.sh`'s server install replaces it with `grayboard-server`. It reads the server's tables directly, so a build from another commit drifts silently: a pre-#284 build kept reading the retired `handles` table, and its "last seen" froze at the migration. The binaries suite runs the compiled inspector against the compiled server's database.
- A deploy is checked by version, not liveness: `/healthz` returns `package.json`'s version (`src/server/http.ts` `healthz`), and `grayboard-server --version` answers before `loadConfig`, so it runs without the server env. A running process keeps the old binary until restarted, so `install.sh` with `INSTALL_SERVER=1` restarts the `grayboard` unit when its `ExecStart` is the installed binary and it isn't stopped, then polls loopback `/healthz` until it reports the installed tag, else exits 1 with a rollback to `grayboard-server.prev`. The unit is `Type=simple`, so `systemctl is-active` right after a restart passes even for a binary about to crash; only `/healthz` proves the start. The version on unauthenticated `/healthz` is public by design: releases are public and the operator's remote check needs it.
- `deploy/backup.sh`: `sqlite3 .backup` to S3, then `aws s3 sync --delete` of the blob directory. The DB alone isn't a backup: attachment rows name blobs it doesn't hold. The mirror runs after the snapshot so every blob the snapshot names is copied; restoring an older snapshot's blobs needs bucket versioning (noncurrent-version expiry matching the lifecycle rule), since the mirror's `--delete` removes blobs the server swept. Retention is an S3 lifecycle rule, not the script.
- The Claude Code plugin ships from this repo's marketplace (`.claude-plugin/marketplace.json`), not as a release asset (#281). Marketplace installs run no build step, so `plugins/claude-code/dist/grayboard.js` is a committed bundle (`scripts/build_claude_plugin.ts`; a root test rebuilds and diffs it), and its manifest `version` equals `package.json`'s, since Claude Code keeps an install on a version until it changes. The entry is a Git-subdirectory source pinned to a tag's `ref` and commit `sha` (a relative-path source can't take a ref); `plugins` stays empty until the first release containing the plugin, since any earlier tag would be a broken install. The release's `plugin-pin` job writes the pin (`scripts/pin_claude_plugin.ts`) only once the release is immutable, so the pinned tag can never move, after checking the tag's commit is the run's; it pushes branch `plugin-pin/vX.Y.Z` rather than opening a PR, because a `GITHUB_TOKEN` PR or push starts no workflow, so the ruleset's required checks would never run on it. Since the pin lands after the release, `grayboard update` runs the plugin step even when the CLI is already current, and compares the marketplace's pin (the catalog in the marketplace checkout), the installed plugin (`claude plugin list --json`) and the CLI: a pin older than the CLI means its PR hasn't merged yet, and an installed plugin other than the pin fails the run (#511). Versions compare in semver order through one comparator (`versionOrder`, `src/cli/update.ts`), which `update` uses too, so a pre-release updates to its release. On a PR whose only change is the marketplace file, `test.yml`'s `scope` job routes the required `test` check to the pin check (marketplace tests; `pin_claude_plugin.ts verify`, which requires the file to be byte for byte the base's re-pinned to a newer release through the same `versionOrder`; then the pinned tag is an immutable release whose commit is the pinned `sha`) and passes `skip` to `hosted.yml`, whose `Hosted required` accepts a skipped matrix only then; a failed `scope` fails `test` rather than skipping it, since a skipped required check counts as passed.
- Operator steps (host, DNS, OAuth client, env file, updates): `docs/guide/server.md`.
