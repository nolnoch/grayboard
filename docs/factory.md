# The factory module

```doc-meta
owns: the opt-in factory module (orchestration outside the core): boundary, how it reaches the bus, request authority, headless spawn, its store
invariants: the module imports nothing in the repo beyond itself and adapters/hosted-core/src/client.ts, and nothing in src/ or adapters/hosted-core/src/ imports it; it reaches the bus only through grayboard's public surface (a `grayboard mcp` child and the MCP tools); it acts on a delegation only when the channel sender is the payload's requester; one request key (source, id) spawns at most once, across restarts; a run cut by a crash is reported interrupted, never re-run; a scratch or worktree run's directory is its tree's, removed only after the store prunes the tree's request; a run's transcript is the operator's only (0600) and goes once its run's row has; children never share its push channel, inherit no harness session, and read none of the operator's settings, hooks or MCP servers; its store keeps its own retention and never writes to boards; it is a queue lane only on its configured fleets' task boards and sharing fleets' share boards, and a fleet task's agent comes from the config, never the post; a fan-out's plan is parsed by the module's code, its board is broadcast unless its fleet shares (then the fleet's share queue, posted by a second session), and a subtask never fans out again; a shared subtask's outside outcome counts only from a `shareWith` handle and reaches a synthesis fenced as data; a review sees earlier rounds only through the digest the code builds from the store, never a resumed conversation, and a lead's notes are never posted; a parked question is answered only by the requester or your user, holds no worker slot, and never parks forever
```

## 1. Why it exists

Principle 7 (`boards.md` §1, #288) keeps the core to addresses, mailboxes, boards, claims and presence. Users without an orchestrator still want a process that takes delegated work and runs it with no harness UI open. The factory is that process, in this repo but isolated (#293): an opt-in module that coordinates *through* grayboard as an outside orchestrator would, so moving it out later is mechanical. Design credit: the #293 series (#300, #309, #313, #314, #320, #321) gave the `FactoryBus` seam, the delegation parser and the roster design.

## 2. The boundary

- Lives in `adapters/factory/`, entry `main.ts`. Nothing in the default install, build or release references it; it starts only when its entry is run.
- `scripts/check_factory_isolation.ts` (run by `tests/integration/factory_isolation.test.ts`) refuses both directions: `src/` or `adapters/hosted-core/src/` importing the module, and the module importing any repo file beyond itself and `adapters/hosted-core/src/client.ts` (#282 decision A7). npm packages aren't repo files, so the MCP SDK is allowed.
- No core tables, tools or instruction text. A missing hook is answered by a core event or an opaque reference (principle 7), never a core feature.

## 3. How it reaches the bus

The module is its own session's harness, as the local Slack bridge is (`src/bridge/slack.ts`): it spawns `grayboard mcp --mode local` with `BUS_IDENTITY` and `BUS_LAUNCHER=1`, push on, and drives it over stdio with the MCP SDK client. Deliveries arrive as `notifications/claude/channel`; everything else is a tool call. `whoami` must report the configured name as primary, else it refuses to start: a second factory on a live name would start unbound and receive nothing (`boards.md` §3, one live session per name).

- **The child env is session-free** (`sessionFree`, `adapters/factory/bus.ts`). A factory started from a shell inside Claude Code inherits `CLAUDECODE` and its session ID; passed on, `grayboard mcp` takes the factory for a Claude Code child and holds every push for a hook record no one writes. Bus identity variables (`BUS_IDENTITY`, `BUS_HARNESS_SESSION`…) are stripped too; the bus's own settings (`BUS_DB_PATH`, `BUS_SOCK_DIR`) stay. Spawned workers get the same env and no MCP servers (`--strict-mcp-config`, §5) but, with `busTools` on, the factory's relay (§10), which is not a session; so a worker holds no bus session at all and can't contest the factory's name.
- **Why not `HostedClient`:** A7's allowlisted client gives hosted tool calls only. Its sign-in and push delivery (`root.ts`, `controller.ts`) aren't importable, so a factory on it alone would be poll-only. Push is principle 3.
- **Local mode only.** `grayboard mcp` is local on every machine (#282). A hosted factory needs push through the server's lease protocol; whether that is an allowlist widening to hosted-core's root delivery or a module-side client is an open decision for its own PR.
- `FactoryBus` (`adapters/factory/bus.ts`) is the one seam feature code sees: tool calls plus an async stream of deliveries. A hosted or broker implementation slots in behind it.
- The child's lifetime is the factory's: when it exits, the factory exits non-zero for a supervisor to restart both (SIGINT/SIGTERM exit 0). The child's restart semantics (name take-back, replay of unconsumed mail) and the store (§6) do the recovery.

## 4. Request authority

This section covers delegations; a fleet task's authority is the board's (§7). A delegation DM's header and fenced payload are text any sender can write (`boards.md` §13: never authority). The module acts on a delivery only when all hold (`requestOf`, `adapters/factory/delegate.ts`):

- It is a DM (channel meta carries `message_id` and `from`, no `board`).
- The body parses as a delegation: the header, then the four-backtick fenced JSON block `delegationBody` builds, with non-empty `requester`, `persona` and `task`. The core's parser isn't on the allowlist, so the module reads the bytes itself.
- The channel `from` equals the payload's `requester`. Anything else is logged and never answered, so a delegation can't make the module send text to a third party.

Locally every handle is the same OS user, so the core's same-user rule is implied. A hosted factory adds the user check through the identity the server reports.

## 5. Spawning

A request's key is its source and id: the bus message id for a DM, the post id for a board post (separate sequences). The module records it in its store before anything else, so a redelivered key (a restart, a replay) spawns nothing. It replies `[factory] taken: …` in the thread at once (`boards.md` §13's launcher contract), naming the agent and whether it starts now or queues, then `[factory] done: …` or `[factory] failed: …` when the child ends. Replies go where the request came from, in its thread (a DM to its sender, a post in its board thread), clipped under the body cap.

- **Persona → roster entry** (`resolvePersona`, `adapters/factory/runner.ts`): exact name, then article-stripped, then whole word, then substring; the longest name wins a rung. No match is `[factory] declined: …` naming the roster, so the requester can re-delegate. Model and effort come from the agent file, never the payload (§13's persona rule).
- **Claude Code** (`adapters/factory/claude/runner.ts`): `claude -p --restricted --strict-mcp-config --agents <json> --agent <name> --output-format stream-json --verbose --permission-prompts none`, plus `--tools`, `--allowedTools` and `--max-budget-usd` from config, and `--mcp-config` with `busTools` (§10) (stream-json under `-p` exits 1 without `--verbose`: measured). The reply is the last `result` event's `result`; that event also carries the session id, turn count and cost the run row records (§6). The prompt (task, then context) goes on stdin, never argv, so a task starting with `-` isn't a flag. `--permission-prompts none` denies any prompt nothing would answer, so an unattended child can't hang on one. The roster is Claude Code's own: `$CLAUDE_CONFIG_DIR/agents` (or `~/.claude/agents`), then the working directory's `.claude/agents`, which wins on a name. The module reads the file and passes the agent inline, with only its body, `description`, `tools` (a comma list) and `model`: restricted mode hides file agents, and a field like `permissionMode` never reaches the child. Claude Code is the only runner so far; pi, OpenCode and Cursor runners would implement the same `Runner` interface (#243, #266, #265).
- **Children are unattended code with tools, and the operator's settings don't reach them.** Without `--restricted`, a user `settings.json` rule allowing `Bash` lets a headless child run the shell (measured on the pinned Claude Code, `tests/e2e/factory_claude.e2e.ts`, e2e `claude-local`). Restricted mode ignores user, project and local settings files (allow rules, hooks), drops the shell and WebFetch unless `--tools` names them, and confines the file tools to the working directory; `--strict-mcp-config` drops every MCP server. Managed settings still apply. The config's `tools` sets what a child has (absent: restricted mode's default) and `allowedTools` what runs without a prompt (default none); a shell needs `Bash` in both. Those are the global lists, for delegations and for fleets without a profile. A **profile** (#643) names an agent and its own lists, each falling back to the global one: `profiles: [{"name": "code", "agent": "coder", "tools": ["Bash", "Read"], "allowedTools": ["Bash"]}]`. A fleet gives `profile` or `agent`, not both; its tasks and their subtasks run under its profile's lists, read from the config as it is at run time, and a task whose fleet has left the config fails without a run rather than fall back to the global lists. The factory acts on any delegation its own user's sessions send.
- **Working directories** (`adapters/factory/workdir.ts`, #641). Restricted mode confines the file tools to a child's working directory, so the directory is the run's file boundary; a shell, when `tools` grants one, isn't confined by it. The config's `workdir` picks the mode (a profile's `workdir` overrides it, and `repo` likewise):
  - `scratch` (default): each request is a tree with its own directory, `$FACTORY_DATA_DIR/trees/<seq>/main` (`seq` is the request's store row), and each fan-out subtask gets `trees/<seq>/<subtask seq>`. Parallel subtasks can't overwrite each other, and no task sees another's leftovers.
  - `worktree`: the same layout, each directory a detached git worktree of `repo`: the request's from `repo`'s `HEAD`, a subtask's from its request's worktree's `HEAD`, so subtasks start from what the planning run committed. All share `repo`'s object store, so the synthesis run can merge their commits. `worktree` without `repo` is a config error; a `repo` that isn't a git checkout fails the run, nothing spawned. Worktree calls run one at a time.
  - `shared`: every child runs in `cwd` (default `$FACTORY_DATA_DIR/work`, never `$HOME`: there a child could read `~/.ssh`). For read-only profiles; parallel children see each other's files.
  - A request's synthesis run (§7) runs in `main` with the tree added (`--add-dir`, which restricted mode's confinement includes: measured, `tests/e2e/factory_claude.e2e.ts`), and its prompt names each subtask's directory.
  - Project agents are read from `cwd`'s `.claude/agents` in every mode.
- **Budgets** (#649). `budgetUsd`, global or per profile (the profile's wins), passes as `--max-budget-usd`; absent, no cap. Claude Code checks it after each turn, so a run can pass it by up to one turn's cost. A stopped run fails with the spend in its reply and is recorded as `budget`. It caps one run; a tree's and a day's caps are §9's, and a run's `--max-budget-usd` is the least of all of them.
- **Bus capability (§13).** A child holds no bus connection: the module relays its result, which §13 counts as the parent relaying, and with `busTools` its reads (§10).
- Concurrency is capped by config; requests over the cap wait in the store in arrival order. Each child runs in its own process group with a timeout; on expiry or shutdown the group is killed and the failure is recorded. On a timeout the thread gets it at once; on shutdown the bus is already gone, so the factory waits (up to 15 s) for running children's outcomes to be stored and the next start sends them. A child that outlasts that wait is reported interrupted at the next start. A failure while taking a delivery or running a request fails that request only; the loop goes on.

**Thread commands** (#651). A reply in a request's thread whose whole body is `cancel`, `retry` or `status` (case-insensitive; leading @mentions and trailing punctuation ignored) is a command, read by code, never a model. Any other reply is chatter unless it answers a parked question (§8). The `taken` reply says where to send one.

- **Where.** A command answers the request itself or any reply the factory sent for it (taken, fanned out, the outcome, a command's answer): the store records the id of each (§6). A command on someone else's reply in the thread, or in a subtask's thread on the work board, is ignored. On a board, a reply to the bare task post wakes only its author, so the factory gets it with its next delivery; a reply to one of the factory's posts, or one that @mentions it, wakes it now. The answer goes in the command's own thread.
- **Who.** `cancel` and `retry`: the requester or your user (a delivery with `human="true"`, which only the bus sets). `status`: anyone on a board, where the thread is public; in a DM, the same two as the others, since a DM thread is its parties' only. Anyone else gets a one-line refusal.
- **At most once.** A command's key (source, id) is recorded before it acts, so a replay doesn't cancel, retry or answer twice.
- **cancel.** Queued or asking: finishes `[factory] cancelled: …` without a run. Running: its child's process group is killed and the run ends `cancelled`; a cancel between the slot and the spawn spawns nothing. Fanned out: queued and asking subtasks finish cancelled, running ones are killed, and the request finishes cancelled and never synthesizes. Finished: says so.
- **retry.** Finished requests only: the same persona or fleet, task and context, admitted as a new request keyed by the command and answered in its thread (on a board, still the original poster's request; in a DM, the command's sender's, the only other party in that thread). Queued, running, asking or fanned out: says to cancel first.
- **status.** Queued with its position; running with the agent and elapsed time; asking with the question's first line and how long it has waited; fanned out with the tree's subtask post ids, how many of the current round's subtasks finished and how many are asking, and the round when `maxRounds` is over 1 (§7); finished with its outcome's first line. Then the turns and cost of the tree's finished runs so far.
- **Load.** The factory's `peer_status` is `N running, M queued`, with `, K asking` when questions are parked, or `idle`, set when it changes, so `peer_list` shows it.

## 6. The store

SQLite in the module's data directory (`FACTORY_DATA_DIR`, default `~/.grayboard-factory`), separate from the bus database. It keeps what a restart needs: each request's key, reply route and state and, once finished, the reply text until it's sent. A store an earlier factory wrote gets newer columns by guarded `ALTER TABLE` at open. At start, a request left running finishes as interrupted (re-running it unasked could repeat side effects the dead child already had); nothing else is lost (#642). A fanned-out request stays waiting and its queued subtasks, which never started, run as before; a subtask that was running counts as finished, interrupted, so its task still synthesizes, with the interruption among the results (§7). Unsent replies are resent; the resend repeats hourly. Replied rows are pruned past the retention, default 30 days: the key must outlive any replay of its message. After each prune, any tree under `trees/` whose request's row is gone is removed, worktrees included (`git worktree prune` in their repository), so a directory never outlives its record and a crash between the two leaves only a directory the next pass removes.

**Runs and transcripts** (#649). Each child is a `runs` row (a fanned-out request has its triage's and each review's): agent, start and end, exit code, outcome (`ok`, `failed`, `timeout`, `budget`, `interrupted`, `cancelled`, `deadline`), its grant (`granted_usd`, §9) and, from its final event, session id, turns and cost. A row left open at start ends as `interrupted`. Cost is the run's own: a resumed run's final event reports its session's running total (measured on the pinned Claude Code), so the runner subtracts what the session's earlier runs cost (§8). Its stream goes to `runs/<run id>.jsonl` as it arrives, one file per run, a resume's included; a request's runs are deleted in the same transaction as the request, and a transcript whose row is gone is removed in the same pass as trees. A transcript holds whatever the child read and wrote, so the data directory is 0700 and each transcript 0600, set at open whatever the umask.

**Questions** (#652). An asking row keeps its question, whether it's addressed to your user, when it was asked and escalated, the answer that resumes it, and the count of questions it asked (`question`, `ask_human`, `asked_at`, `escalated_at`, `answer`, `asks`), all added by guarded `ALTER`.

**Claims** (#669). `claims` holds each tree claim (tree, key, holder, note, taken at, and the bus key when mirrored, §10); liveness comes from the holder's row (§10), and a prune removes claims whose holder is gone.

**Threads and commands** (#651). `threads` maps the id of each reply the factory sent to its request's row, so a thread command finds its request; `commands` holds each command's key once it has acted. Both are deleted with their request.

## 7. Fleets

A fleet is a queue board, `<name>-tasks`, on which the factory is one lane, with the agent it runs every task with: config `fleets: [{"name": "sim", "agent": "researcher"}]`, or `{"name": "app", "profile": "code"}` to run under a profile's agent and tool lists (§5). Anyone who can see the board posts a task with plain `board_post`, and the core's rotation (`boards.md`, queue boards) hands each top-level post to exactly one lane. Interactive sessions that subscribe are lanes too.

- **Sync at start and on reload** (`syncFleets`, `adapters/factory/factory.ts`): a missing board is created as `kind: "queue"`; an existing queue board is subscribed in push mode; a fleet whose board exists as a broadcast board is refused with a log line (every post there would read as a task). Any other queue board the factory is a lane on is left: a lane that ignores its deliveries holds each claim for the full TTL.
- **A task** is a top-level post on a joined board, delivered by the rotation or by an @mention. Replies in its thread are its conversation, not tasks, apart from thread commands (§5). The requester is the poster; locally every handle is the same OS user, as with a delegation. The agent is the fleet's, never resolved from the post's text.
- **The `taken` reply acks the claim** (a queue reply by the holder releases it), so the 30-minute TTL never redelivers a running task; a crash mid-run is reported interrupted (§6), as for a delegation. The store's `(source, id)` key (post ids are one sequence across boards) makes a redelivery spawn nothing.
- **No agent:** a task from the rotation is passed on with `claim_release`, which offers it to the next lane; an @mention holds no claim, so its poster gets `[factory] declined: …`.
- Replies go in the post's thread with `board_post`, so they wake the poster and the thread's participants.

**Fan-out.** The model judges; the module's code orchestrates. A fleet task's run gets one more instruction: when the task splits into 2 to `maxSubtasks` (default 5) independent parts better run in parallel, reply with only a plan, a four-backtick block with the info string `factory-plan` holding `{"subtasks": [{"title", "task"}]}`; otherwise do the task. Most tasks are done in that one run, so a simple task costs one run and no board. A fleet with `"fanout": false` never gets the instruction.

- **A plan** (`parsePlan`, `adapters/factory/fanout.ts`) posts each subtask on the fleet's work board, `<fleet>-work` (#665), naming the task it's part of (`subtask 1/3 for fe's post 7 on #sim-tasks: …`), then says so in the task's thread with the subtasks' post ids. A work board holds many trees' posts, so `status`, a stop by cancel, deadline or budget, and a failed review name this tree's post ids too (#668). The work board is one standing broadcast board per fleet, opened on the fleet's first fan-out with the factory's own subscription muted (concurrent fan-outs share one open), so it can be bridged or subscribed to once, and `board_list` doesn't grow with each fan-out. It's the durable, visible record: anyone may read, subscribe or comment. It isn't a queue: the core never hands a poster its own post (`queueLanes`, #284), so a queue the factory posts on could never reach the factory. Each subtask runs here, on the worker pool, as the fleet's agent (in a project, the profile the plan names; see Projects below) with no fan-out instruction (a subtask never fans out again), in its own directory unless the fleet's mode is `shared` (§5), and its outcome goes in its thread. The triage instruction tells the planning run which: a subtask's agent starts without the planner's files unless they share a directory.
- **Synthesis:** once every subtask has an outcome, done or failed, the fleet's agent runs once more on the original task with each outcome (the first 16K characters of each) and, outside `shared` mode, read access to each subtask's directory; its answer goes in the original thread.
- **Rounds** (#658, `maxRounds` in limits, §9; default 1). With more than one, the synthesis is the lead's review: it may answer, or plan another round in the triage's format, while the tree has rounds left; the last review only combines, and a plan it returns is its answer. A review also only combines when a quarter of the tree's remainder would be under the grant floor or the deadline is under two `timeoutMs` away (§9), so a tree near its limits still answers rather than stops. `maxRounds` is at most 10, which bounds the digest's earlier rounds. A later round posts on the same board (`subtask 2.1/3: …`) and says `fanned out, round 2` in the task's thread. Each review starts fresh: its prompt is a digest the code builds from the store (the task, the lead's notes, earlier rounds' outcomes in one line each, the latest round's in full), so a long tree can't grow one conversation past its context. Each outcome in the digest is fenced as data: a review's plan may route work to a profile with tools the subtask that wrote the outcome lacked, so a subtask (or a page it fetched) is a new source of plans, which the review must judge rather than relay; the project's profile set still bounds what runs. In worktree mode, a round's subtasks branch from the lead's `HEAD`, so the review is told to commit what the next round builds on before it plans.
- **Notes.** With rounds on, the lead (triage and each review) may end any reply with a four-backtick `factory-notes` block. The code splits it off before reading a plan or question, keeps it on the request (4K cap; each replaces the last) and puts it in the next review's digest. It's the lead's working memory across fresh runs and never reaches the thread. A notes block not at the reply's end is text.
- **An unusable plan** (bad JSON, a count outside 2 to `maxSubtasks`, an empty field) fails the task with the reason; nothing is posted. The store admits the subtasks and marks the task waiting in one transaction, after every post landed, so a crash leaves both or neither. A post that fails partway fails the task, naming the posts already made (#638); they stay on the work board and none of them runs. On a share board another lane may still be handed one, so each posted thread gets a `not run` reply saying nothing waits for it.
- A plan is the whole reply: one that only quotes a plan block (documenting the format, say) is an answer. A subtask over 60 KiB fails the plan before anything is posted. A queue board named `<fleet>-work` would hand the subtasks to other lanes, so a fleet whose sync finds one doesn't fan out (its tasks run whole, and the log says so; renaming the fleet gives it a work board), and one made after the sync fails the plan before anything is posted. A broadcast board of that name, made by anyone, is used as is, and its existing subscribers see every subtask's text. A tree that fanned out on a `task-<post id>` board before #665 keeps posting there.
- The work board stays, as do the `task-<post id>` boards releases before #665 opened: the core has no board archive or delete (#635).

**Sharing** (#636). A fleet with `"share": true` and a `shareWith` list of handles puts its subtasks, every round's (#658), on a queue board of their own, `<fleet>-share`, instead of `<fleet>-work`, so the rotation hands each to one lane: the factory's own, another factory on that fleet, or a subscribed session. Scratch-mode fleets only: an outside lane's files can't reach the synthesis yet (#677). Projects can't share: a routed subtask must run under its profile.

- **Two sessions.** The rotation never hands a poster its own post (`queueLanes`), so a second session, `<identity>-share` (`posterName`, `adapters/factory/main.ts`), posts the subtasks and is pushed their thread replies as author; it never subscribes in push, or it would be a lane holding other factories' claims. The factory's own session is a lane on `<fleet>-share` (`syncFleets`), so a subtask handed to it runs here and its `taken` reply acks the claim. Its own subtasks are recognized by post id in the store, never by body text; a share-board post that isn't ours is another factory's subtask and runs here whole, without fan-out, its spend counted against the fleet (`fleetSpent`). The poster session starts only with the process: a reload that makes the first fleet share is refused, one that adds a second is taken. The poster isn't a launcher, so no delegation lands on a session that reads only board threads. Either session ending stops the factory.
- **What counts as done.** The post asks the taker to reply at once (the queue's ack), then reply with its outcome led by `done:` or `failed:` (`outcomeOf`). An ack is not completion. The first outcome from a `shareWith` handle finishes the subtask, its row recording who (`shared_by`); anyone else's is logged and ignored, and the subtask keeps waiting. The factory's own lane isn't listed: its outcomes come from its store. The poster ignores the factory's handles, so a reply that reaches both sessions applies once. Binding an outcome to the lane that actually took the claim needs a core change and is deferred to the hosted head (#676).
- **Silence.** Before an ack the bus re-rotates the post itself. After `shareTimeoutMs` (default `timeoutMs`) with no listed outcome, the factory runs the subtask here, says so in its thread, and a later outside outcome is ignored.
- **Restart.** Pushes don't survive one, so at start, before the timeout fallback's first tick, each subtask still shared has its thread read (`recoverShared`) for an outcome that came while the factory was down. An outcome that arrives while its fan-out is still posting waits for the rows.
- **What outside lanes bypass.** The tree and daily budgets (§9) don't see outside spend. `cancel` finishes the shared subtasks in their threads and stops waiting; it can't stop a run elsewhere. The tree's deadline still closes the tree. Tree claims (#669) and questions (§8) are the factory's own runs' only.

**Projects** (#645). A project is a fleet whose plans may give each subtask to a different profile: `projects: [{"name": "app", "lead": "plan", "profiles": ["plan", "code", "docs"], "repo": "/srv/app"}]`. Its board is `app-tasks`, as a fleet's; a project and a fleet can't share a name. The lead profile triages each task, runs any subtask that names no profile, and synthesizes. When a project has more than one profile, the triage instruction lists them, each with its agent and tools, and a subtask names one with `"profile"`; the subtask's post on the work board says which (`subtask 1/3 (code): …`). A plan naming a profile outside the project fails before anything is posted, so no plan widens what runs. A project's `repo`, when given, replaces its profiles' for worktree mode, so every part of one task works on the same checkout; the profiles' other fields apply as in §5. A fleet with a profile is a project of one: its plans may name only that profile. `fanout` works as on a fleet.

**Reload.** `SIGHUP` re-reads the config. Fleets, projects, profiles, the limits (§9) and the global `tools`, `allowedTools`, `budgetUsd`, `busTools`, `mirrorClaims`, `workdir` and `repo` take effect for every run that starts after it, and the board sync runs again: a new fleet's board is created or joined, and a removed one's is left. A run already going keeps what it started with. A queued task whose fleet or project is gone, or a queued subtask whose profile its project no longer lists, fails without a run, rather than run under other lists. A config that doesn't load is logged and the running one stays. The fields that shape the bus session, the runner or the worker pool (`RESTART_ONLY`, `adapters/factory/main.ts`) need a restart; a reload that changes one logs that the running value stays.
- **Mentions:** a fleet's replies and subtask posts carry model output, which a poster can steer, and an `@handle` in them wakes that handle as from the factory. Locally every handle is the same OS user, so this reaches no one the poster couldn't mention directly; a hosted factory must neutralise mentions first.

## 8. Asking

A run that can't finish without a fact or decision only a person can give ends with a question instead of a guess (#652, `adapters/factory/ask.ts`). The model decides to ask; code parks, routes and resumes.

- **Format.** Every run but a resume gets one more instruction: reply with only a four-backtick block, info string `factory-ask`, holding `{"question": "…"}`, plus `"to": "human"` for a decision only your user can make. As with a plan (§7), the block is the whole reply, so an answer that quotes one is an answer. An unusable block (bad JSON, no question, over 8 KiB, another `to`) fails the run with the reason.
- **Park.** The row goes to `asking` and holds no worker slot. The question goes in the request's thread, a subtask's in its root request's thread (the one the requester watches), as a reply the store maps to the asking row (§6), so a reply to it finds that row. `"to": "human"` also sends it to your user at once; a send that fails is retried on the next clock check.
- **Who answers.** A free-text reply from the requester or your user (`human="true"`); anyone else's is chatter, as with thread commands (§5), which still take precedence. A reply to the question (in the thread, or to the DM your user got) answers that row; one elsewhere in the thread answers the tree's only open question, and with several open the factory asks which. A reply to a question that has since closed (answered, given up, cancelled) gets `that question is already closed`, so it isn't silently dropped. Your user's thread commands work in the DM that sent them a question, acting on its request.
- **Resume.** The answer queues the row; its next run is `--resume <session id>` (the last run's) with the answer as the prompt, so the conversation keeps its context and its directory. With no session id recorded, a fresh run gets the task, the question and the answer. A resumed run is a new run row and a new transcript, with the full timeout and budget, under the settings as they are then.
- **Clocks** (config `askEscalateMs`, `askGiveUpMs`, default 1 h and 24 h, checked every 30 s). Unanswered past the first, the question goes to your user once by DM; it's stamped escalated only when the DM went, so a failed send is retried at the next check. Unanswered for the second after that, the run resumes with "no one answered; use your judgement or fail saying what you needed". Both are measured from the stored `asked_at` and `escalated_at` against the config at check time, so a reload changes pending clocks. Your user is a declared human (`grayboard human`): only their replies carry `human="true"`, so only theirs can answer. Config `human` picks which declared handle when there are several; one that isn't declared is logged and the first in the bus's "Humans on this bus" line is used instead. With no declared human, the escalation is only logged and the give-up clock still runs, so no question parks forever.
- **Cap** (`maxAsks`, default 3, per request tree). A question past it isn't parked: the run resumes told to decide; asking again after that fails it. The cap stops a model from turning every step into a question that holds a person hostage.
- **Commands and restart.** `cancel` on an asking row finishes it without a run; `status` shows the question and how long it has waited; `retry` refuses until it's cancelled. An asking row survives a restart as it is (it has no child to interrupt) and its clocks go on from the stored times.

## 9. Limits

Spend and time caps over a whole request tree and over a day (#655), decided in code at each run's start, never asked of a model. Config only: `treeBudgetUsd`, `dailyBudgetUsd`, `deadlineMs` and `maxRounds` (§7), each on the top level, a fleet or a project; none is set by default, and `maxRounds` is 1. A fleet's tree budget, deadline and `maxRounds` replace the global ones for its tasks. Day caps stack: the global one counts every run the factory starts, a fleet's only its own board's tasks and their subtasks, plus other factories' subtasks it ran from its share board (§7).

- **Grant.** Each run's `--max-budget-usd` is the least of its per-run `budgetUsd` (§5), each day cap's remainder and the tree's remainder over its stages left. A subtask's stages are itself, its queued, asking or shared (§7) siblings and the synthesis, so parallel subtasks split the remainder and the synthesis keeps a share; a review that may plan again (§7) gets a quarter, leaving the rest for its round (at least two subtasks) and the review after it; a triage, last review or delegation run is one stage, so a triage may spend the whole tree's budget. Claude Code checks its cap after each turn, so each run, and with it the tree and the day, can pass a cap by up to one turn.
- **What counts as spent.** A run's reported cost, or its grant while it runs and when it ended without reporting one (killed, crashed): a run that dies mid-turn is charged everything it was allowed, never nothing. Open grants count, so concurrent runs can't jointly overspend.
- **A spent tree** (its remainder per stage under $0.01) stops the tree through cancel's path (§5, `stopTree`): queued and asking members finish, running ones are killed and recorded `budget`, nothing is combined; the request's thread names the cap and, when it fanned out, the work board holding the finished subtasks' outcomes and the tree's post ids there (#668).
- **A spent day** holds work instead of failing it: a held row stays queued, `taken` and `status` say whose budget is spent and about when it frees, and `peer_status` adds `(K held: daily budget spent)`. The window is the last 24 hours of run starts, rechecked at each question tick (§8, 30 s). Pruning it early would undercount, so the config refuses a day cap with `retentionMs` under a day (a reload too, against the running retention, which takes a restart). A day cap alone serializes its scope: with no `budgetUsd`, a run is granted the day's whole remainder and everything else waits until it reports what it spent. Pair a day cap with a per-run `budgetUsd`.
- **Deadline**, measured from the request's admission. A run's timeout is clamped to it; it's checked when a run would start, at each question tick (so trees parked on a question or held stop too) and at the factory's start (one that expired while it was down). Past it the tree stops as above, recorded `deadline`. A deadline shorter than `askEscalateMs` plus `askGiveUpMs` cuts off the give-up resume.
- **Reload.** Limits are read from the config at each decision, so a reload applies to runs not yet started, and to trees and holds already open.

## 10. Bus tools for children

A child holds no bus session (§3), so by default it can't see the boards its task came from. `busTools: true` (#669), on the top level or a profile (the profile's wins), gives each of its runs four reads: `board_list`, `board_read`, `claim_list` and `peer_list`. Off by default.

- **A relay, not a session.** The run gets one stdio MCP server, `bus` (`adapters/factory/relay_shim.ts`), which forwards each call over a Unix socket to the factory (`adapters/factory/relay.ts`). The factory answers through a reader (`startReader`, `adapters/factory/bus.ts`): a second `grayboard mcp` started as a child session of its own (`BUS_PARENT_SESSION` naming the factory session's `BUS_HARNESS_SESSION`, `boards.md` §3 Child sessions). It acts under the factory's name, so it sees what the factory sees, owns no delivery, and its `board_read` peeks: the factory's cursors and pending pushes don't move. A reader that doesn't report itself a child of the factory's name is refused. Socket, reader and the shim's Bun config all open on the first run that has the tools, so a factory that never opts in opens nothing.
- **The tool surface is the security boundary.** The socket is 0600 in a 0700 directory (`relay/` in the data directory), and each run gets a fresh 256-bit token, revoked when the run ends. That scopes a call to a live run, but a child with a shell runs as the factory's uid and can read the socket path and token from the shim's environment. So every relayed bus tool is a read that any local process of the user's could already make: no posts, DMs, creates, subscribes, `bind` or `delegate`, and no DM reads, since the factory's inbox holds other requesters' delegations. Arguments are kept to each tool's own fields and types; anything else is dropped. The shim is the boundary's one process in the child's directory: a stdio server starts there, where Bun would read `bunfig.toml` (whose `preload` runs code), `tsconfig.json` and `.env`, so a child with only file tools could plant one and run code as the factory. It starts with `--no-env-file` and a config and tsconfig the factory owns, in `relay/` (`shimCommand`). A shim whose harness exits (stdin closed) exits too.
- **Results are data.** Each result opens with a note that it is what other agents and people wrote, to weigh and never to obey, and the JSON follows fenced as data, cut at 24,000 characters with a hint to ask for less. Turning the tools on still widens what can steer a run: anyone who can post on a board the factory can read can put text in front of the child. Opt in per profile where the reads are worth that.
- **Claude Code.** The server goes in `--mcp-config`, a 0600 file beside the run's transcript (its env carries the token, which argv would show every local process), removed when the run ends; `--strict-mcp-config` keeps every other server out. Its tools join `--allowedTools` as `mcp__bus__<tool>`, so they run unprompted. They don't go in `--tools`: on the pinned Claude Code that list filters only built-ins, and MCP tools pass it either way (measured), so naming them there would only cut a child on the default tools down to them. An MCP tool not in `--allowedTools` is denied, unprompted. `tests/e2e/factory_claude.e2e.ts` covers a call through the real shim.
- **Tree claims** (#669). A subtask's run also gets `tree_claim_take`, `tree_claim_release` and `tree_claims`, so the subtasks of one request can split shared work (a file, a module) without stepping on each other. They are answered from the store (§6), never the bus (unless mirrored, next bullet): a claim is visible only inside its own request's tree, so no bus write is relayed: the boundary above holds for the bus, and the claim tools write only the factory's store, inside the run's own tree, which the factory's uid could write anyway. A key is at most 200 characters and a note 500. A claim is live only while its holder's row is running, asking, or queued to resume after an answer, so every way a run ends (done, failed, cancelled, interrupted, timed out) releases it with no cleanup step, and a row that starts a fresh run rather than resuming holds none (a defensive clear: a lead never holds claims and a retry is a new row). A refused take names the holder's subtask title and note, fenced as data like a bus read: they are another child's words. A task's lead and a delegation's run get no tree tools: they hold no siblings to coordinate with.
- **Mirrored claims** (#675). `mirrorClaims: true` (top level or profile, the profile's wins) also holds each of a subtask's tree claims on the bus, under the factory's name, so lanes editing the same repository outside the factory (your own sessions, another factory on the same local bus) see it and the subtask sees theirs. It needs `busTools` and a `worktree` or `shared` workdir, else the config is refused: a scratch directory is no repository anyone else edits. One way: a bus claim never becomes a tree claim; a bus holder only refuses the take, named and fenced as data.
  - **Key.** `path:<repo id>/<tree key>` (`adapters/factory/mirror.ts`), a leading `./` dropped. The repo id is `origin`'s URL without scheme, user, port or `.git`, else the main checkout's path, which every worktree of it shares: two worktrees of one repo collide, two repos don't. Lanes outside the factory interoperate by claiming the same form. A subtask whose directory isn't in git fails before spawning. Only path-shaped tree keys are mirrored (letters, digits and `. _ @ + - /`, the whole bus key at most 200 characters): a bus claim key reaches every session's startup instructions, so a child's key with whitespace or markup in it could address other agents. A mirrored run's other keys are refused, as is a second spelling of a key it already holds (`a`, then `./a`).
  - **Order.** The store first, then the bus: a sibling's or another tree's live hold refuses without touching the bus. A bus refusal or a bus that can't answer undoes the store take. The bus can't tell the factory's runs apart (one name holds them all, and a holder's re-take is a renewal), so the store also refuses a bus key another live claim already mirrors, across trees and across spellings (`a`, `./a`).
  - **Release.** A tree claim ends with its row (above), which the bus can't see, so the factory sweeps: at start (when any policy mirrors), after each mirrored run, and on the question tick when a key it last left held is no longer live (a parked run cancelled). A sweep lists `path:` claims under the factory's name and releases each one no live tree claim holds, which also clears what a crash between store and bus left. Live keys are renewed every 10 minutes with a 30-minute TTL, so a dead factory's lapse on their own.
  - **Boundary.** This is the one bus write a child can cause: a claim or release under the factory's name, on a key prefixed by the factory, with a note the factory writes (the subtask's seq), never the child's. It can't post, address anyone, or take a key outside its repository's prefix.
  - **Modes.** The factory is local-only (§2), so this guards only against lanes on the same local bus; across machines it needs a hosted head (#676).
- **Failure.** A run whose policy has the tools but whose relay can't open (or a factory built without one) fails before spawning, saying so. A reader that exits is logged and restarted on the next call.
