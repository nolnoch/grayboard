## 1. The principal

- A service is a `users` row whose `email` column holds its name (the team name rule, so never an email or a person scope) and a `principals` row of kind `service`. The kind is read with the user row (one join, `USER_SQL` in `src/server/db.ts`; no `users.kind` column), so it rides the auth cache and reaches every `AuthedUser` and policy subject. A service is never a person: no sign-in reaches its row (`signIn` refuses it, `upsertByEmail` throws), `admin` refuses it before the env list (a service named in `GRAYBOARD_ADMINS` is no admin), it holds no role and joins no team, and its hello carries no `human` handle. The generic user routes (`revoke-session`, `disable-user`, `enable-user`, `unlink-idp`) refuse kind service (400): services go through `/api/admin/services` (`grayboard admin service`), behind `admin` like every admin route. Create inserts both rows and each owner's `service_owner` binding in one savepoint, granted with the gate's authority so an admin revoked between the decision and the write creates nothing (`http:admin-service-create:before-write`), and writes `service.created`; a refused owner rolls the service back. Disable and enable are `setDisabled`, audited `auth.user_disabled`/`auth.user_enabled` with `{service: true}`; nothing deletes a service. `delete-alias` is the team route's twin. Create refuses a disabled owner (409). A service's names are seen by the service and its `service_invoke` holders (`alias.see_service`, one grant read per service scope a call touches); to anyone else mail or delegation to one reads as a missing name (`aliasHidden`, `src/server/application.ts`), except a reply in a thread with it. A `GRAYBOARD_ADMINS` entry that isn't an email is no admin and isn't listed. `disable-user` on a person names the services left with no enabled owner (`orphaned_services`, in the answer and the audit detail); their bindings stay. **Credentials** (`POST /api/admin/services/credentials` and `…/revoke`, `grayboard admin service credential add|revoke`; the OAuth side is `server-oauth.md` §2): add answers the client ID and secret once, `Cache-Control: no-store`, and refuses a disabled service (409); `rotate` adds a second secret only to a live credential of the named service (another service's client ID reads as missing) and a third live secret is refused; `revoke --secret` refuses a credential's last live secret (409: that's the credential's revoke). Each writes `service.credential_added` or `service.credential_revoked` with the admin and the service, never the secret. Disable revokes every credential's grant through `setDisabled` (no per-credential rows), and enable revives none. A service's session, lease and request-bucket caps are their own tier (`DEFAULT_HOSTED_CAPS.perService`, `DEFAULT_SERVICE_LIMITS`, `src/server/config.ts`), picked by `AuthedUser.kind` at admission with no row read, the session and lease tiers clamped under the global caps; why not raise the per-user values: they bound what one phished person's grant holds.

## 2. Invocation

- **`service.invoke`** (#270 D6): posting on a service's board (`boards.md` §3 Service boards), and `claim_take` with that board, which announces there. Decided in the post's transaction for the acting address's principal (`src/server/invoke.ts`), a team-scoped name's being the team, so it holds the right only by the team's own binding; a session's ID is judged as its session's primary, or a session bound only to `eng/w-1` would invoke through its user's direct grant whenever the post fell back to the ID. Allow: `service.own`, or `role.service_invoke` with the binding id and, through a team, the member's `team`; recorded with the post, since an invocation exercises a grant (principle 8). Deny: `role.service_invoke`, `not_found`, recorded after the rollback, answering with a missing board's exact text and code (principle 9). The grant read (`roles.invokeBinding`) is one statement driven from the holder: its own binding, else a team of the user's, lowest name first so the row names one binding every time: 1 + the user's team count probes of the unique binding index, never the service's holders (principle 13; `src/server/db.test.ts` pins the plan). Membership is read live (principle 11): `team remove` ends the right at the next check and writes no `role.revoked`. Visibility, lanes, mention resolution and `alias.see` ask the same grant, so a holder can't see more than it can invoke. Team owners can extend a team-held right by adding members (R8, accepted).
