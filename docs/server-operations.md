# Server operations

```doc-meta
owns: the server's application operations: delegation, DM send, append-write dedup, `call`, handler errors
invariants: a repeat of an append write after a lost answer never writes twice; a handler throw becomes a generic error, never a stack
code-pointers: src/server/application.ts, src/server/write_dedup.ts, src/core/delegation.ts, src/core/tools.ts, src/server/mcp.ts
companions: server-sessions.md, delegation.md, dms.md, boards.md §6 (tool surface rules)
```

- **Delegation** (`delegate {persona, task, context?, to?}`, #184): the server resolves the target — `to` through the same resolution as `send`'s recipient (`resolvePeer`), then auto-pick restricted to the requester's own user, and an explicit `to` to it or to a user it shares a `delegating` team with (#256: `resolveDelegation`'s injected `reach`, which on a server answers from a `delegate.to` decision (`authorize`) the delegate body makes before core runs, of the requester's user and the user of the session behind the address, `addressUser`; a deny writes an `authz.decision` row, and a granted target's open cap is half) — and delivers the payload as a pending DM through the ordinary send path. The payload fences persona/task/context inside a four-backtick JSON block the launcher's instruction says is data; the body's header is never authority (the DM's sender is, and it must be the launcher's own user, or another user's under a grant). Every outcome is audited: `delegation.requested` (target: the launcher; detail `{requester, via: explicit|auto|human_fallback, message_id}`) or `delegation.refused {reason}`, each with `child` when a child session made the call (`child-sessions.md`); the limits (#252: a per-user bucket keyed by email, `delegation.throttled`/`throttle_ended` targeting the user, and a per-launcher open cap) are `delegation.md`'s, with `ApplicationOptions.delegateLimit`/`delegateOpenCap` (and `Config`'s, from `GRAYBOARD_DELEGATE_BURST`/`_PER_SEC`/`_OPEN_CAP`) overriding the defaults; the bucket is checked and spent inside `writeOnce`'s write, and its streak rows, and a policy deny's decision row, are written after that transaction (on a session without an `afterRollback` of its own, a WSS one, the call collects them for its catch path, #867; `rowAfterRollback` on a refusal, written and handed to `afterRollback` on success) so neither a rollback nor hosted's outer transaction loses them (on the hosted path, which runs a tool call in one transaction, the refusal's row is written after that transaction unwinds via `ApplicationSession.afterRollback`, so it survives the rollback, #452); `handle.launcher_set {on}` against the session ID (locally, once per session that owns delivery, under its ID). The reply carries `to` and, on the degrade path, `human_fallback` added (`DelegateOk`). A hosted session is a launcher when its requests declare it (#473): `_meta["io.github.nolnoch.grayboard/launcher"]: true`, which `sessionContext` reads from a built-in client only (a third-party client can't claim the user's delegation requests; a non-boolean is `bad_request` naming the key; `false` and absence are the same). Any request of a root's ownership that declares it turns `ids.launcher` on (`rowFor` → `hostedDeclareLauncher`, #520), whether the request starts the ownership (a new ID, or a new ownership of a stable source ID) or comes later: OpenCode's native client starts an ownership with no plugin `_meta`, and the plugin's subscriber wire declares it afterwards. A tools-only root, which can't receive pushes, and a child are never one. `handle.launcher_set {on: true}` is audited under the session ID when the flag actually turns on, so once per ownership; a later `false` or absence changes nothing, and the ownership's end clears it (`hosted.end`, with `writes_as`), audited `handle.launcher_set {on: false, ownership, reason}` when it was on (#532), so a resumed session that no longer declares one isn't a launcher. A `session_end` request's declaration doesn't count: its end would clear the flag in the same request. The launcher instruction rides the session's initialize text and its bind and unbind results from the stored flag (`hostedLauncher`): initialize's only for a pushed session (declared push, or undeclared with an open lease), bind's and unbind's unless the session is declared poll (#521 4), so the text matches what routing does. hosted-core sends the key on every wire when the host declares it: `HostedClient`'s `launcher` option for its proxy wire, and `HostPort.launcher` for the Controller's (subscriber, temporary, child registration). The Claude Code plugin and pi/omp set it from `BUS_LAUNCHER=1`; the OpenCode v2 adapter from its plugin option `launcher: true`, since its settings are plugin options. OpenCode's native client sends `initialize` with no session key and caches its text for the process, so its agents would only ever see the unbound text; the OpenCode v2 plugin's `context` session hook (`adapters/opencode-v2/src/instructions.ts`, #531) instead rebuilds grayboard's `<server>` entry in every primary request of an enrolled root that isn't paused with that root's current `initialize` text, fetched over a native wire that names the root (refetched when the root's state, holds or ownership change, or after a native `bind`/`unbind`). That carries the launcher instruction whether the name came from a native bind before enrollment or the plugin's configured `name`. The hook never rejects (OpenCode puts no timeout on it and a rejection fails the step): it waits 2 s and otherwise keeps the last text; an outage or token rollover keeps the last text without refetching until the next change, a sign-out clears it, and a failure lands on the root's own diagnostic record (operation `instructions`). Server text is indented under the frame, so it can't close the entry. Only the entry in OpenCode's MCP instructions is rebuilt (#538): OpenCode joins its sources with a blank line in a fixed order (code-mode catalog, MCP instructions, references, skills, project files, built-ins, context entries), so the hook takes the MCP segment only where every paragraph before it is the catalog's, and never touches the agent prompt (`system[0]`); a project file, context entry or update message quoting a grayboard entry after another source is left as written, and skill bodies are user messages, never rewritten. A subagent of such a root gets the same rewrite with its own `initialize` text, the server's child text (`hostedChildInstruction`, #535): `Controller.childRoot` resolves its ancestry once (at `session.created`, which also starts the fetch so the first request needn't wait out registration and connect; a resolved path is kept, and only a failure resolves again; it's a lookup, not a route, so ending a session the server never saw sends nothing), and its native wire runs under the root's enrollment after `Controller.enlist` registers it, since an unregistered session key would start an ownership of its own; a refused registration fetches nothing and is the fetch's `instructions` failure, not a `child_register` one that would degrade the root, and a child that ended while its registration was in flight ends the row it made. Every such subagent holds a child row, which counts against the root's child capacity until it idles past the window and is parked (#566). A child's wire never declares a launcher. Its cached text follows the root's: any invalidation of the root refetches it, its failure lands on the root's record, and `session.deleted`/`archived` drops it. The compaction summarizer, title and other generations have their own OpenCode hooks, so they keep OpenCode's own text. Every open clears the marks no live hosted root holds (`sweepStaleLaunchers`, `src/server/db.ts`, #521 5): a pre-upgrade WSS launcher's, or a root's whose ownership ended before #532 cleared the flag at the end, which kept `peer_list` showing `launcher: true` on an offline alias that last held one; each cleared ID is audited `handle.launcher_set {on: false, reason: "stale"}`, actor its principal. A mark the sweep keeps is still gated: an offline alias is never a delegation target (`online()` gates both resolutions), and once a hosted session binds the alias, `LAUNCHER_SQL` follows the alias to that session's own flag.
- **DM send**: body non-blank and ≤ 64 KiB (`checkBody`, `src/core/boards.ts`, shared with local mode). A bare name resolves to the acting address's own scope's alias of that name (`ownScope`: an alias's scope, or an ID's principal), and only that: one only other scopes have is `not_found` naming the full handles the sender may see (`resolvePeer`; security audit F-08): a team's only to its members (`alias.see`, [#348](https://github.com/nolnoch/grayboard/issues/348)), so a name only hidden scopes hold reads as one nobody has. Mail to a team alias by its exact handle from a sender who may not see it (`teamAliasHidden`) is `not_found` with the missing name's text, unless it replies (`parent_id`) in a thread with that alias (#1014): a DM's result and `dm_inbox`'s queued list say whether it was delivered, which would show the alias exists. `msg.wake` keeps another user's alias from waking its holder. A send to an `id:` is checked inside the write's transaction (`repo.sessionEnd.refusal`, core's `undeliverableId` on SQLite), so it can't race that session's end: an ended, tools-only or child-session ID is refused, never queued: core's `Undeliverable` carries `not_found`, `id_ended`, `no_delivery` or `child_session`, which `coreRefusal` sends as the error's code (the same code and text local mode shows), as it does for an `@id:` mention a post is refused for. `team:<name>` recipients are rejected: teams are reached by posting to their board. `history`'s peer resolves the same way (`resolvePeer`). `parent_id` must be a message the sender sent or received, the recipient must be its other party (`replyPeer`), and the sender must be the party the session holds unless that party is a session ID (`replySenderError`, #530); `bad_request` otherwise, `dms.md`. DM visibility is one check, `participant` (`src/server/db.ts`), shared by send's parent check, `thread`, and attachment reads; a DM you're not in reads as missing. `msg.send` (`server-access.md` §1) gates every DM. `attachment_ids` names uploads (`server-access.md` §1 Attachments) to bind in the message's transaction.
- **Append writes are deduplicated** (#254, `src/server/write_dedup.ts`): `send`, `delegate` and `call`'s `board_post` run through `dedupWrite`. The retry this catches comes from the model after a lost answer, and no harness gives the original call and the re-call a shared identifier (per-harness evidence in #254 §1; a client's `req_id` is a per-process counter), so the server fingerprints the call: `sha256(canonicalJson({tool, session, sender, args}))`, with `sender` the resolved acting address, `session` the session's ID (so sibling subagents writing under one name don't collapse; a hosted source ID is stable across a restart, a local process's is not) and `args` as the server resolved them (the recipient's full handle, the normalized board, attachments by blob digest, since every attempt uploads afresh under new ids; `delegate`'s persona, task and context as given and `to` resolved to its full handle or null, taken before resolution picks a launcher). A repeat within `WRITE_DEDUP_WINDOW_MS` on the hub's clock (`opts.now`) whose row still exists returns the stored result with `replayed {first_at, ref}` and a `note` naming the target and `resend: true`, and writes only a `request.replayed` audit row: no push, wake, outbox fan-out or delegation resolution. `resend: true` writes again and audits `request.resent`. A repeat whose receipt names a row that's gone (retracted, pruned) writes again and audits `request.receipt_stale` (`tool`, `fp`, the stale `ref_kind`/`ref_id`, `first_at`, `session`), so a fresh write after a retract is explicit (#306). The receipt is claimed before the write (`writeReceipts.claim`: `INSERT … ON CONFLICT DO NOTHING RETURNING`, a placeholder `ref_id` 0 that the write's upsert fills); a lost claim reads the receipt that beat it, a stale one is taken over by a conditional `UPDATE` only while it still names the gone row, and a pass that neither claims nor answers prunes again and retries, three passes at most (`postgres-server.md` D3, #807 P2-2), so under READ COMMITTED of two identical calls one writes and the other replays. The claim, the write, the receipt and the audit row are one savepoint on the caller's transaction (`dedupWrite` runs in `parent.savepoint`, its write, `onReplay` and `recheck` on the savepoint's Tx), so a throw leaves no receipt. `attachment.bound` is audited inside the fresh write's transaction. Pushes and wakes wait for the outermost successful commit, only for a fresh write; savepoint success cannot publish rolled-back effects. A replay drops the retry's own unsent uploads in its transaction (`dedupWrite`'s `onReplay`; `attachment.released` with `reason: replayed`; blobs swept after the commit): nothing will bind them, and they'd hold unsent quota until the prune. The receipt stores the payload, not the framing, so a replay is answered in the current call's own envelope. A `board_post` runs `checkPostAccess` (board visible, parent on it, announcements human-only: the checks `post()` makes) before the fingerprint, so a repeat from a caller who has since lost the board is refused, not replayed (#296); `dm_send` runs its send checks the same way in `prepareSend`, except that an `id:` recipient's deliverability is checked in the write itself, so a repeat after that session ended still replays (deliverability, not authority: the first call's message was written while the session lived). A `delegate` picks its launcher inside the write, so its authority checks run again on a hit instead (`dedupWrite`'s `recheck`, in the lookup's transaction): the stored target must still be the requester's own user's or granted (`reach`, judged against the alias's current holder; a person's `human`, which no session holds, is that person's, #1030) and pass `msg.send`, or the repeat is refused as a fresh call naming that target would be (an auto-pick repeat's refusal also names the pick and `resend: true`, since a fresh call would pick again), audited `delegation.refused` and with no `request.replayed` row (#393, `docs/vision.md` principle 11); routing (online state, the open cap, the limiter) stays the first call's. Every authority check thus runs before a replay is answered, never after the lookup on a miss only, which is why #303's receipt-first lookup was declined. Exempt: the Slack bridge's humans (`session.human`, `writeOnce` in `src/server/application.ts`), whose repeated line is two sends. `delegate`'s inner send isn't deduplicated as a `dm_send`, or a later plain `dm_send` of the same body would replay the delegation. Accepted false positives, each answered `replayed` rather than silently: a deliberate identical repeat in the window, and a second identical post to a queue board. `testPause("write:after-commit")` sits between the commit and the answer, where a lost answer happens.
- `call {tool, args}` runs the shared core dispatch (`src/core/tools.ts`) as the address `boardActor` resolves (`as`, else `handles.md` §1's board pick, else the primary), with its address set and session ID, so claim renew, release and ack match any address in the set; `CoreError` becomes `bad_request`. The returned wake list is pushed to connected handles immediately.
- Handlers run inside one try/catch in the transports (`src/server/mcp.ts`), so a throw becomes a generic error answer instead of a hung call.
