# Application sessions

```doc-meta
owns: the server's application sessions: hosted request context, leftover sessions, the bridge's humans, bind, the server's binding-event sources, tools-only and unbound sessions, the address set, revalidation
invariants: another session's alias hold is never taken over (a never-leased hosted root idle past its window ends when a contender binds its name); a hosted session holds several names, and its claims stay with their address
code-pointers: src/server/application.ts, src/server/hosted.ts, src/server/app.ts, src/core/resolver.ts, src/shared/protocol.ts, src/shared/identity.ts
companions: handles.md (names, both modes), server-operations.md (the operations), server-access.md (rate limits, authorization), slack-org-bridge.md
```

`src/server/application.ts` owns sessions (`ApplicationSession`: hosted MCP and the bridge's humans), their holds, delivery ownership, operations and typed delivery sinks; `src/server/hosted.ts` and `src/server/mcp.ts` reach it for every agent, `attachHuman` for the bridge. A session is not an authenticated user or a transport connection: only a delivery owner counts as online, and tools-only callers never drain pending items.
- **The WSS transport is gone** (#282), and the server serves no WebSocket at all (#475): an upgrade on `/ws` or any path gets the ordinary 404. A v2.3.0-or-later CLI refuses `grayboard mcp --mode server` itself (`UPGRADE_REFUSAL`). An older client reads the 404 as a dropped connection and retries until its user updates it; that is accepted rather than kept behind a shim (#475).
- **A hosted request's model and effort are the session's latest** (#364). `sessionContext` reads `GRAYBOARD_MODEL_META`/`GRAYBOARD_EFFORT_META` from any client's `_meta` (display facts that grant nothing): a non-string is `bad_request` with a message naming the key (logged `session_meta`, as a malformed delivery declaration is), and `cleanFact` drops format characters (`\p{Cf}`), folds to one line, stores NFC and cuts length, so `match` compares what a reader sees. `rowFor` compares them with the session's `ids` row on every gated request and `hostedFacts` writes and audits (`id.facts_changed`, before and after, `why: request`) only on a change. Each fact has three states on the wire (#558): a string is the value, an empty string is "the host has none" and clears the stored one (audited like any change), and an absent key is "unknown" and keeps it, so a client that sends nothing (OpenCode's native client, a release before #558) never clears one, and the hot path stays one read. An empty string meant nothing before #558 (both hosted-core and the server dropped it), so the meaning is additive. A new ownership of a stable source ID overwrites with its first request's facts, null when absent, so a resumed session never shows the last ownership's model; that overwrite is audited `why: ownership`. A legacy GET or DELETE routes by its creating POST's `_meta` with the facts removed (`withoutFacts`), since replaying them would revert the latest. "Latest" is the order the server processes requests, not the order a client sent them: two in flight across a model switch can land either way, and the next request heals it. A child row keeps its own facts; `peer_list` shows the root holder's. hosted-core sends them on every request for the session that request names, reading the host's provider per request (`HostedClientOptions.facts`, `HostPort.facts`; `SessionFacts` fields are a string, `null` for none, sent as `""`, or absent for unknown) so a mid-session switch lands on the next one; the native wire is shared across sessions, so the provider takes the session ID. pi and omp report `ctx.model` as `provider/id` (none without one) and the thinking level, only for the session their runtime currently shows (omp repoints `ctx` at the next session before ending the old one, so the old one's end request must not carry the next one's model; a child's process reports its own; omp's `inherit` is none). `HostedClient` says a provider failure once per session. The OpenCode v2 plugin notes each session's model from its `context` hook (`providerID/id`, the variant as effort, none without one, since `Model.Ref.variant` is unset for the model default; compaction, title and generate requests have their own hooks and don't re-note it; an LRU bounded by `FACTS_LIMIT`, `adapters/opencode-v2/src/lifecycle.ts`), so a root restored after a restart reports nothing until its next model request and sends it on its own wires (subscriber, temporary, the instructions fetch). The Claude Code plugin's MCP child has no in-process source, so its hooks relay the root's facts (#545, measured on 2.1.316): SessionStart's `model` and PostModelSwitch's `to_model` (which runs only once the user confirms the switch; PreModelSwitch runs before that dialog and isn't used) are written to `model` (a full ID such as `claude-opus-5-5`; `to_model` is the ID as given to `/model`), and the root's grayboard PreToolUse `effort.level` (the `CLAUDE_EFFORT` env var keeps the start-time value and isn't a source) to `effort`; a root PreToolUse without one (a model without effort; a null level counts as none, an empty or malformed one writes nothing) writes an empty `effort` (none, a clear on the wire, #558), PostModelSwitch removes `effort` (unknown until the next root call, so the server keeps the last level rather than clearing and restoring it) and a root PreToolUse whose hook a confirmed switch overtook removes its own write (it `lstat`s `model` before and after, #561), so the old model's level never stands (a switch landing while Claude Code spawns the hook isn't caught; the next root call heals it), and a SessionStart other than `clear` removes both before writing the model, so a new process never inherits a reused pid's facts; only a startup SessionStart carries `model` (2.1.316: `clear` and `resume` don't), so a `/clear` keeps both files and a resumed or forked root (`--resume`, `--continue`, `/resume`, a fork) reports no model until a model switch. Each is a whole file in the #551 per-process dir (`src/shared/claude_agents.ts`, plugin hook only), checked to `SESSION_FACT_MAX` so the server stores what the hook wrote; the plugin's provider reads both per request for its root, after the same start-time check the records use, at most `SESSION_FACT_MAX + 1` bytes of a regular file opened without following a link or waiting on a FIFO, reads an empty file as none and a missing one as unknown, and leaves out a malformed or unreadable file while sending the other, saying it once, and again only after a read finds it fixed. No hook names a subagent's model, so a child session reports none. The facts are harness-asserted in a same-user directory: any same-user process can write any session's facts, so a forged file misreports that session's display model or effort and grants nothing (the records' boundary, `child-sessions.md`, and #229's). Known limits: the model reaches the server with the first request after a startup SessionStart's hook (the bind or first call); a model change without PostModelSwitch (an automatic fallback) shows at the next fresh (startup) process; an `/effort` change (no hook fires) shows at the next grayboard call, as does the effort after `/clear` or a model switch (SessionStart carries none, so the server shows the last level until then); and the hook says nothing (it must never block a call): a hook whose root fact write fails leaves its reason in `hook-error` (without the temporary's pid, so a lasting failure reads the same from every hook), which the plugin says the same way and the next hook to finish one removes; a hook that writes no fact (a subagent's call) neither sets nor clears it, and two racing root hooks can leave an older failure over a newer success until the next root call (#561); a full disk fails that write too, and a Claude Code build without PostModelSwitch fires no hook to fail, so both leave the last fact standing with no signal. Audit rows are bounded only by the two per-user hosted request buckets (tool calls and the subscriber role's, #845), on the client's own row. A client sets facts only on its own row (`rowFor` fences user and client); that any holder of the token can act as the user's sessions is the accepted #229 boundary.
- **A hosted root's suggested name is its first request's** (#443). `sessionContext` reads `GRAYBOARD_SUGGESTED_META` from any client's `_meta`: a hint that grants nothing, normalized by `normalizeIdentityName` (a bare name, lowercased); a non-string is `bad_request` naming the key, and a string that isn't a name, or is `human`, is no suggestion (as local mode treats it). `rowFor` stores it on the root's `hosted_sessions.suggested` at insert and never updates it (the store's update lists its columns), so a later request's suggestion changes nothing and a new ownership of the same source ID takes its own; a child's is null. The ownership's `hosted.ownership_started` audit records it as `suggested` (#522), so the trail says why a session was offered a name. Every unbound root's candidate list (`initialize` instructions, `whoami`, the last `unbind`) passes it to `candidates()`, which offers it first while no session holds it (`fresh` when the alias doesn't exist yet). hosted-core sends it on every wire (`SUGGESTED_META`, the `HostedClient`/`HostPort` `suggested` provider, #522), since whichever request reaches `rowFor` first fixes it: the Claude Code plugin and pi/omp send local mode's `sessionIdentity(env, cwd)` (the pin or the repo's name, with the worktree suffix) for the root only. OpenCode V2 sends `sessionIdentity({}, directory)` for the plugin's directory on every session's wire (#696), from its generated copy of `src/shared/naming.ts`; a child's is ignored, as above.
- **Where hosted differs from the removed WSS on purpose** (#463). A name's `last_seen` is its last request, not the release (`handles.md` §3). Every native tool refusal carries `structuredContent` in the subscriber role's shape (`domainData`: the code, `refused` for a core refusal, `internal_error` for a fault; #806), so a caller branches on the code, never the message. The text stays what the agent reads: `error: <message>` for board, claim and DM tools and `whoami`, and a JSON `{code, message, …}` for `bind` and `unbind`, whose code is the one `structuredContent` carries (#843). An input-schema refusal is the SDK's `Input validation error` text, with no code. `bind "human"` refuses `forbidden` with `HUMAN_RESERVED`, the code and text `bindNow` gives, whichever entry the bind came through. `whoami` carries `id` and `principal` beside the holds, on the native and subscriber roles alike; it names the holds `held`, where local `whoami` names them `aliases` (#489: a rename would break the adapters that read either). Write dedup (`dedupWrite`) is the application's, so a hosted write replays as an AppSession one does; `tests/integration/write_dedup.test.ts` forces the lost-answer window on a hosted session and the rest on AppSession.
- **Leftover sessions end once at start.** Every unended session that no hosted ownership holds (a WSS session an earlier run left) ends through `endSession` with `why: wss_removed` (`endIds`, `src/server/application.ts`), since only a hello could re-attach one. Hosted-owned IDs are the hosted store's to end.

- **The Slack bridge's humans** attach in-process through the application's trusted bridge method (`attachHuman`, `src/server/application.ts`) with no key, so no network client reaches that path. A human gets no ID (its session ID is the literal `human`), no `ids` row or end; it holds `<email>/human` (a newer bridge attachment for the user supersedes it) and its writes carry no `sender_id`. With `human` refused in every `bind` and `writes_as`, `<email>/human` is provably that user's person. The session facts (`helloOkFields`, `src/server/application.ts`) tell every hosted session its user's human handle and whether it's linked (`slack-org-bridge.md`).
- Adapter authority derives from that reserved structured sender, compared against the authenticated **lease** user's human, never a body claim or OAuth sign-in alone. Shared classification and V2's JSON envelope boundary: `adapters-hosted.md`; real attachment/model-admission proof: `adapters/opencode-v2/tests/host.ts` (`human-authority`).
- **`bind`** (`src/server/application.ts` `bindNow`, synchronous so a hosted bind runs inside its transaction; `hosted.ts` clears a stale hosted contender itself first, `server-hosted-ownership.md`) adds an alias to the session's holds (`handles.md`; up to `MAX_HOLDS`); The result carries `held`, every hold oldest first. **`unbind`** removes one and answers `{alias, released, held, left?}` (`released: false` for one not held; `left`: the claims that stay with it); it spends no limiter token, since it creates nothing. A bare name is the caller's own person scope; `scope/name` needs `alias.bind` (`server-access.md` §1); `human` is refused in every scope, since `msg.send` treats any `*/human` as a person's phone. The alias is created lazily (audited `{lazy: true, session}`) unless `create: false`, which refuses a never-seen name with `identity_unknown` carrying `known` (the closest names). An alias another session holds is `alias_held` naming the holder, and its place only when the asker is the holder's own principal (#349); there's no takeover. A hosted root holding it is checked first by the hosted service (#402): a never-leased one idle past the hosted window ends and frees the alias (the contender-only idle rule, `server-hosted-ownership.md`); a live one is `alias_held`. An alias in use by another principal's session (held, or written as by a tools-only session) is exclusive (#284 S8; `aliasUser`, `src/core/bindings.ts`): that principal's bind, `writes_as` and HTTP `claims/call` `identity` are `alias_held`, while the user's own tools-only sidecars and `claims/call` share it (#182). An identity any session uses can't be deleted, or a second session could bind the name while the first still acts as it. After a bind the server drains the alias's mail and boards. A new name past its scope's cap (`aliasCapRefusal`, #347, `handles.md`) is `bad_request`, checked before the bind's transaction so the `refused` binding event stays; `writes_as` and `POST /api/identities` check it too, each with no await between the count and the create, so concurrent creates can't overshoot. A `meta` the server refuses (`parseAliasMeta`) logs a `refused` binding event. Revoking one team alias drops only that hold; the rest and the primary rule stand.
- **Binding events** (`binding_events`, `sessions.md`) come from `bind`, session end, revocation and hosted binds and ownership ends: `bound` (no detail: a server bind carries no restore claim, and a hosted session's continuity is its ownership, `server-hosted-ownership.md`), `refused` (a bind's, or a hosted `writes_as`'s; a retry loop's repeats share one row, `sessions.md`), `released` on an `unbind`, a session end or an access revocation (details: `logBinding` callers). A hosted bind and unbind log through `bindNow` and `unbind`, except a refused bind's row, written after its rollback (`hostedRefused`); a hosted ownership's end writes `released` with its end reason for every hold directly (hosted store `end`, `src/server/db.ts`). The Slack bridge's human logs under the literal session `human`: `bound` when it attaches, `released` (`connection closed`) when it closes; a superseding attachment logs only its own `bound`.
- **Tools-only sessions** are never pushed to and aren't in the registry or online. A hosted root declaring `writes_as` (`hostedWritesAs`, `src/server/application.ts`) names an alias judged like a bind target and created lazily but never held, and reads and writes only as that alias (its address set is `[writes_as]`); its `ids` row has `writes_as` set, so a send to its ID is refused `no_delivery`, and its `bind` is refused. Why a hosted bind holds without delivery: holding nothing let two sessions bind one name (#182 audit 2).
- **Unbound hosted MCP sessions read only** (`src/server/hosted.ts`): a hosted session ID is routing, not a capability (#229), so an unbound hosted session doesn't act as its ID. The application allowlists `UNBOUND_READS` calls and refuses all named operations, including receipts, with `unbound`; transports cannot bypass that gate. Such a session takes no `alias_holds` row; its durable root row supplies its presence (`peer_list` `unbound_sessions`, the caller's own user only: `HostedStore.roots`, those holding nothing, never a tools-only root, a child or one whose only live connections are idle legacy GETs; #475), so a root with no request in flight is listed until it ends, and its board visibility is judged as its user (`ServerToolContext.principal`, `src/server/boards.ts`).
- **Address set** (#284 S8): a session reads as its holds plus its ID (a hosted child: its root's holds plus the root's ID, never its own, and its writes carry its ID as `via`; `hostedSession`, `child-sessions.md`) and writes as its primary (`handles.md` §1), unless `as` or a reply default picks another address; the registry is keyed by address. `as` and the reply default are resolved before `prepareSend` (bare-peer resolution and `msg.send` are per acting address) and before the dedup fingerprint. A request naming one address (the HTTP claim route's `as`, an attachment read) reads as that address plus the rest of its session's set only when that session is the caller's principal's; a null principal (the bridge's humans) reads as the address alone (`addressSet`, `src/core/bindings.ts`; #373). History, inbox and thread match any address in the set; an `ack` advances each message's own recipient address's cursor, a retract acts as the address that sent the message, and `board_ack` acknowledges on each address. **Drain at bind and delivery open**: DMs after each address's cursor (`mailbox_cursors`, keyed by address; seeded once from 1.x `cursors`, as `aliases` is from 1.x `identities`, and neither old table is read after), then pending board items. Drain doesn't advance cursors; only `ack` does (`MAX(existing, new)`, so out-of-order acks can't regress). Board items: the session keeps an in-flight set, keyed per post with the addresses it went to, so an `unbind` drops that alias's items and a later `bind` of it re-drains them; `board_ack` acks in the core. A new session starts empty, so unacked items resend. At-least-once for both.

- A 30s `revalidate` timer (`src/server/app.ts`) re-checks every live session's user (disabled in the database with no route to say so) and aliases (`revalidate`, `src/server/application.ts`, `server-access.md` §1). The registry is per process; a hosted session's lease and ownership are durable (`server-hosted-ownership.md`), so a restart loses only memory delivery, and clients re-drain from durable cursors.
