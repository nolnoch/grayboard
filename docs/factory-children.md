## 1. Spawning

A request's key is its source and id: the bus message id for a DM, the post id for a board post (separate sequences). The module records it in its store before anything else, so a redelivered key (a restart, a replay) spawns nothing. It replies `[factory] taken: …` in the thread at once (`delegation.md`'s launcher contract), naming the agent and whether it starts now or queues, then `[factory] done: …` or `[factory] failed: …` when the child ends. Replies go where the request came from, in its thread (a DM to its sender, a post in its board thread), clipped under the body cap.

- **Persona → roster entry** (`resolvePersona`, `adapters/factory/runner.ts`): exact name, then article-stripped, then whole word, then substring; the longest name wins a rung. No match is `[factory] declined: …` naming the roster, so the requester can re-delegate. Model and effort come from the agent file, never the payload (`delegation.md`'s persona rule).
- **Claude Code** (`adapters/factory/claude/runner.ts`): `claude -p --restricted --strict-mcp-config --agents <json> --agent <name> --output-format stream-json --verbose --permission-prompts none`, plus `--tools`, `--allowedTools` and `--max-budget-usd` from config, and `--mcp-config` with `busTools` (§2) (stream-json under `-p` exits 1 without `--verbose`: measured). The reply is the last `result` event's `result`; that event also carries the session id, turn count and cost the run row records (`factory.md` §5). The prompt (task, then context) goes on stdin, never argv, so a task starting with `-` isn't a flag. `--permission-prompts none` denies any prompt nothing would answer, so an unattended child can't hang on one. The roster is Claude Code's own: `$CLAUDE_CONFIG_DIR/agents` (or `~/.claude/agents`), then the working directory's `.claude/agents`, which wins on a name. The module reads the file and passes the agent inline, with only its body, `description`, `tools` (a comma list) and `model`: restricted mode hides file agents, and a field like `permissionMode` never reaches the child. Claude Code is the only runner so far; pi, OpenCode and Cursor runners would implement the same `Runner` interface (#243, #266, #265).
- **Children are unattended code with tools, and the operator's settings don't reach them.** Without `--restricted`, a user `settings.json` rule allowing `Bash` lets a headless child run the shell (measured on the pinned Claude Code, `tests/e2e/factory_claude.e2e.ts`, e2e `claude-local`). Restricted mode ignores user, project and local settings files (allow rules, hooks), drops the shell and WebFetch unless `--tools` names them, and confines the file tools to the working directory; `--strict-mcp-config` drops every MCP server. Managed settings still apply. The config's `tools` sets what a child has (absent: restricted mode's default) and `allowedTools` what runs without a prompt (default none); a shell needs `Bash` in both. Those are the global lists, for delegations and for fleets without a profile. A **profile** (#643) names an agent and its own lists, each falling back to the global one: `profiles: [{"name": "code", "agent": "coder", "tools": ["Bash", "Read"], "allowedTools": ["Bash"]}]`. A fleet gives `profile` or `agent`, not both; its tasks and their subtasks run under its profile's lists, read from the config as it is at run time, and a task whose fleet has left the config fails without a run rather than fall back to the global lists. The factory acts on any delegation its own user's sessions send.
- **Outside effects** (#659). What a child can change beyond this machine, by who holds the means. Without a shell, nothing: its file tools stay in its directory, so its changes stay local (in worktree mode, a branch in `repo` that a person must push or merge, Handback below); its bus tools (§2) are reads plus the factory's own store; its words reach people only in the replies the factory posts; and budgets and every other limit come from the config file, never the bus. With a shell (`Bash` in `tools`), a child runs as the factory's uid, with that user's network, git and `gh` credentials, so it can push, merge or call any API that user can. No `allowedTools` or deny rule binds it: a pattern like `Bash(git push:*)` matches one spelling of a command, and a shell has many. So the factory keeps no sensitive-action list. Give a shell only to a profile whose agent you'd trust at that uid, or run the factory as a user without push rights. A gate that binds needs the factory to hold the capability: a publish step it runs itself after a person's OK (#689, not built).
- **Working directories** (`adapters/factory/workdir.ts`, #641). Restricted mode confines the file tools to a child's working directory, so the directory is the run's file boundary; a shell, when `tools` grants one, isn't confined by it. The config's `workdir` picks the mode (a profile's `workdir` overrides it, and `repo` likewise):
  - `scratch` (default): each request is a tree with its own directory, `$FACTORY_DATA_DIR/trees/<seq>/main` (`seq` is the request's store row), and each fan-out subtask gets `trees/<seq>/<subtask seq>`. Parallel subtasks can't overwrite each other, and no task sees another's leftovers.
  - `worktree`: the same layout, each directory a detached git worktree of `repo`: the request's from `repo`'s `HEAD`, a subtask's from its request's worktree's `HEAD`, so subtasks start from what the planning run committed. All share `repo`'s object store, so the synthesis run can merge their commits. `worktree` without `repo` is a config error; a `repo` that isn't a git checkout fails the run, nothing spawned. Worktree calls run one at a time.
  - **Handback** (#683). A worktree-mode request's last reply (done, failed or cancelled; a subtask's never) names the branch its result is on, in its first line: the factory creates `factory/<board>/<post id>` (a DM's: `factory/dm/<message id>`) in `repo` at the request's own worktree's `HEAD`, when that `HEAD` has commits no branch holds. A taken name gets the commit's short id appended; both taken, the reply says it couldn't and the worktree stays until the prune. A done reply with nothing new says `no new commits, so no branch`. The branch is the requester's: the prune removes the tree's worktrees, never its branch. A tree stopped while its subtasks ran (deadline, budget, a cancel of the waiting request) hands back nothing; its worktrees stay until the prune.
  - `shared`: every child runs in `cwd` (default `$FACTORY_DATA_DIR/work`, never `$HOME`: there a child could read `~/.ssh`). For read-only profiles; parallel children see each other's files.
  - A request's synthesis run (`factory-fleets.md`) runs in `main` with the tree added (`--add-dir`, which restricted mode's confinement includes: measured, `tests/e2e/factory_claude.e2e.ts`), and its prompt names each subtask's directory.
  - Project agents are read from `cwd`'s `.claude/agents` in every mode.
- **Budgets** (#649). `budgetUsd`, global or per profile (the profile's wins), passes as `--max-budget-usd`; absent, no cap. Claude Code checks it after each turn, so a run can pass it by up to one turn's cost. A stopped run fails with the spend in its reply and is recorded as `budget`. It caps one run; a tree's and a day's caps are `factory.md` §7's, and a run's `--max-budget-usd` is the least of all of them.
- **Bus capability (`delegation.md`).** A child holds no bus connection: the module relays its result, which `delegation.md` counts as the parent relaying, and with `busTools` its reads (§2).
- Concurrency is capped by config; requests over the cap wait in the store in arrival order. Each child runs in its own process group with a timeout; on expiry or shutdown the group is killed and the failure is recorded. On a timeout the thread gets it at once; on shutdown the bus is already gone, so the factory waits (up to 15 s) for running children's outcomes to be stored and the next start sends them. A child that outlasts that wait is reported interrupted at the next start. A failure while taking a delivery or running a request fails that request only; the loop goes on.

**Thread commands** (#651). A reply in a request's thread whose whole body is `cancel`, `retry` or `status` (case-insensitive; leading @mentions and trailing punctuation ignored) is a command, read by code, never a model. Any other reply is chatter unless it answers a parked question (`factory.md` §6). The `taken` reply says where to send one.

- **Where.** A command answers the request itself or any reply the factory sent for it (taken, fanned out, the outcome, a command's answer): the store records the id of each (`factory.md` §5). A command on someone else's reply in the thread, or in a subtask's thread on the work board, is ignored. On a board, a reply to the bare task post wakes only its author, so the factory gets it with its next delivery; a reply to one of the factory's posts, or one that @mentions it, wakes it now. The answer goes in the command's own thread.
- **Who.** `cancel` and `retry`: the requester or your user (a delivery with `human="true"`, which only the bus sets). `status`: anyone on a board, where the thread is public; in a DM, the same two as the others, since a DM thread is its parties' only. Anyone else gets a one-line refusal.
- **At most once.** A command's key (source, id) is recorded before it acts, so a replay doesn't cancel, retry or answer twice.
- **cancel.** Queued or asking: finishes `[factory] cancelled: …` without a run. Running: its child's process group is killed and the run ends `cancelled`; a cancel between the slot and the spawn spawns nothing. Fanned out: queued and asking subtasks finish cancelled, running ones are killed, and the request finishes cancelled and never synthesizes. Finished: says so.
- **retry.** Finished requests only: the same persona or fleet, task and context, admitted as a new request keyed by the command and answered in its thread (on a board, still the original poster's request; in a DM, the command's sender's, the only other party in that thread). Queued, running, asking or fanned out: says to cancel first.
- **status.** Queued with its position; running with the agent and elapsed time; asking with the question's first line and how long it has waited; fanned out with the tree's subtask post ids, how many of the current round's subtasks finished and how many are asking, and the round when `maxRounds` is over 1 (`factory-fleets.md`); finished with its outcome's first line. Then the turns and cost of the tree's finished runs so far. Last, for each running row of the tree (the request's own run, or each running subtask, named by seq and title) that has called `progress` (§2), its latest note and its age, fenced as data: the note is the run's own words, and the reply goes to the bus, so a handle in it wakes no one.
- **Load.** The factory's `peer_status` is `N running, M queued`, with `, K asking` when questions are parked, or `idle`, set when it changes, so `peer_list` shows it.

## 2. Bus tools for children

A child holds no bus session (`factory.md` §3), so by default it can't see the boards its task came from. `busTools: true` (#669), on the top level or a profile (the profile's wins), gives each of its runs four reads: `board_list`, `board_read`, `claim_list` and `peer_list`. Off by default.

- **A relay, not a session.** The run gets one stdio MCP server, `bus` (`adapters/factory/relay_shim.ts`), which forwards each call over a Unix socket to the factory (`adapters/factory/relay.ts`). The factory answers through a reader (`startReader`, `adapters/factory/bus.ts`): a second `grayboard mcp` started as a child session of its own (`BUS_PARENT_SESSION` naming the factory session's `BUS_HARNESS_SESSION`, `child-sessions.md`). It acts under the factory's name, so it sees what the factory sees, owns no delivery, and its `board_read` peeks: the factory's cursors and pending pushes don't move. A reader that doesn't report itself a child of the factory's name is refused. Socket, reader and the shim's Bun config all open on the first run that has the tools, so a factory that never opts in opens nothing.
- **The tool surface is the security boundary.** The socket is 0600 in a 0700 directory (`relay/` in the data directory), and each run gets a fresh 256-bit token, revoked when the run ends. That scopes a call to a live run, but a child with a shell runs as the factory's uid and can read the socket path and token from the shim's environment. So every relayed bus tool is a read that any local process of the user's could already make: no posts, DMs, creates, subscribes, `bind` or `delegate`, and no DM reads, since the factory's inbox holds other requesters' delegations. Arguments are kept to each tool's own fields and types; anything else is dropped. The shim is the boundary's one process in the child's directory: a stdio server starts there, where Bun would read `bunfig.toml` (whose `preload` runs code), `tsconfig.json` and `.env`, so a child with only file tools could plant one and run code as the factory. It starts with `--no-env-file` and a config and tsconfig the factory owns, in `relay/` (`shimCommand`). A shim whose harness exits (stdin closed) exits too.
- **Results are data.** Each result opens with a note that it is what other agents and people wrote, to weigh and never to obey, and the JSON follows fenced as data, cut at 24,000 characters with a hint to ask for less. Turning the tools on still widens what can steer a run: anyone who can post on a board the factory can read can put text in front of the child. Opt in per profile where the reads are worth that.
- **Claude Code.** The server goes in `--mcp-config`, a 0600 file beside the run's transcript (its env carries the token, which argv would show every local process), removed when the run ends; `--strict-mcp-config` keeps every other server out. Its tools join `--allowedTools` as `mcp__bus__<tool>`, so they run unprompted. They don't go in `--tools`: on the pinned Claude Code that list filters only built-ins, and MCP tools pass it either way (measured), so naming them there would only cut a child on the default tools down to them. An MCP tool not in `--allowedTools` is denied, unprompted. `tests/e2e/factory_claude.e2e.ts` covers a call through the real shim.
- **Tree claims** (#669). A subtask's run also gets `tree_claim_take`, `tree_claim_release` and `tree_claims`, so the subtasks of one request can split shared work (a file, a module) without stepping on each other. They are answered from the store (`factory.md` §5), never the bus (unless mirrored, next bullet): a claim is visible only inside its own request's tree, so no bus write is relayed: the boundary above holds for the bus, and the claim tools write only the factory's store, inside the run's own tree, which the factory's uid could write anyway. A key is at most 200 characters and a note 500. A claim is live only while its holder's row is running, asking, or queued to resume after an answer, so every way a run ends (done, failed, cancelled, interrupted, timed out) releases it with no cleanup step, and a row that starts a fresh run rather than resuming holds none (a defensive clear: a lead never holds claims and a retry is a new row). A refused take names the holder's subtask title and note, fenced as data like a bus read: they are another child's words. A task's lead and a delegation's run get no tree tools: they hold no siblings to coordinate with.
- **Progress** (#669). Every run with the tools, lead or subtask, also gets `progress(note)`: one line on where it is, shown by `status` (§1) and posted nowhere else, so it costs no thread noise and wakes nobody. It writes only the run's own row in the store (`progress`, `progress_at`), so the boundary above holds. The factory keeps one line: control characters and line breaks become spaces, runs of whitespace one space, at most 200 characters, and each call replaces the last. A row that starts a fresh run rather than resuming starts without one, so a lead's synthesis or review doesn't show its triage's note; a resume after an answer keeps it. A call after the row has stopped running is refused like a revoked token.
- **Mirrored claims** (#675). `mirrorClaims: true` (top level or profile, the profile's wins) also holds each of a subtask's tree claims on the bus, under the factory's name, so lanes editing the same repository outside the factory (your own sessions, another factory on the same local bus) see it and the subtask sees theirs. It needs `busTools` and a `worktree` or `shared` workdir, else the config is refused: a scratch directory is no repository anyone else edits. One way: a bus claim never becomes a tree claim; a bus holder only refuses the take, named and fenced as data.
  - **Key.** `path:<repo id>/<tree key>` (`adapters/factory/mirror.ts`), a leading `./` dropped. The repo id is `origin`'s URL without scheme, user, port or `.git`, else the main checkout's path, which every worktree of it shares: two worktrees of one repo collide, two repos don't. Lanes outside the factory interoperate by claiming the same form. A subtask whose directory isn't in git fails before spawning. Only path-shaped tree keys are mirrored (letters, digits and `. _ @ + - /`, the whole bus key at most 200 characters): a bus claim key reaches every session's startup instructions, so a child's key with whitespace or markup in it could address other agents. A mirrored run's other keys are refused, as is a second spelling of a key it already holds (`a`, then `./a`).
  - **Order.** The store first, then the bus: a sibling's or another tree's live hold refuses without touching the bus. A bus refusal or a bus that can't answer undoes the store take. The bus can't tell the factory's runs apart (one name holds them all, and a holder's re-take is a renewal), so the store also refuses a bus key another live claim already mirrors, across trees and across spellings (`a`, `./a`).
  - **Release.** A tree claim ends with its row (above), which the bus can't see, so the factory sweeps: at start (when any policy mirrors), after each mirrored run, and on the question tick when a key it last left held is no longer live (a parked run cancelled). A sweep lists `path:` claims under the factory's name and releases each one no live tree claim holds, which also clears what a crash between store and bus left. Live keys are renewed every 10 minutes with a 30-minute TTL, so a dead factory's lapse on their own.
  - **Boundary.** This is the one bus write a child can cause: a claim or release under the factory's name, on a key prefixed by the factory, with a note the factory writes (the subtask's seq), never the child's. It can't post, address anyone, or take a key outside its repository's prefix.
  - **Modes.** The factory is local-only (`factory.md` §2), so this guards only against lanes on the same local bus; across machines it needs a hosted head (#676).
- **Failure.** A run whose policy has the tools but whose relay can't open (or a factory built without one) fails before spawning, saying so. A reader that exits is logged and restarted on the next call.
