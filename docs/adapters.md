# Adapters and push ownership

```doc-meta
owns: harness adapters in local mode and push ownership: the one delivery owner per handle, each local adapter, setup
invariants: exactly one delivery owner per handle; for a retained child adapter the harness's `grayboard` MCP entry is config, kept disabled
code-pointers: adapters/, src/local/mcp.ts, src/shared/claude_channels.ts, src/shared/claude_agents.ts, src/shared/claude_identity.ts, src/cli/cli.ts (setup)
companions: adapters-hosted.md (server-mode adapters), parity.md (each harness's capabilities), child-sessions.md
```

An adapter does two jobs: **tools** and **push** (harness-specific). Which capability each harness has in each mode, and the open gaps: `parity.md`.

- **Exactly one component per handle owns delivery** (holds the socket or live connection, drains, moves cursors). In a harness that drops MCP notifications, a push-mode MCP server would consume messages into a void. A harness without an adapter runs its MCP entry with `BUS_PUSH=off` (tools only), which never acquires a name. `grayboard setup` and `refresh-adapters` warn when omp's, opencode's or pi's grayboard entry is enabled without `BUS_PUSH=off` and no adapter is installed (#95). A hosted session's owner is the process holding its delivery lease (`delivery_open`; hosted-core's delivery lock leaves a second process on one raw session tools-only, `adapters-hosted-login.md`); a hosted `bind` holds the name with or without one, and with no lease DMs wait for `dm_inbox`.
- Claude Code: native `notifications/claude/channel`; the MCP server is the owner. Claude Code drops channel notifications silently unless its own gate registered the server, so every Claude-side owner evaluates one mirror of that gate (`claudeChannels`, `src/shared/claude_channels.ts`: provider, interactive entrypoint and no `-p`, feature flag and org restriction, managed `channelsEnabled` policy, and the session's `--dangerously-load-development-channels`/`--channels` list naming its exact entry; the source comment names the Claude Code version it was read from, and a pin bump re-reads it). When off, `grayboard mcp` holds its name without listening (a session that gets no pushes and binds like any other), and the off reason goes into the instructions, first tool result and stderr (`channelsOff`, `src/shared/toolguard.ts`). `grayboard mcp` treats an unknown verdict (an unreadable parent command line) as on; a process that isn't Claude Code's child is never off.

- omp (`adapters/omp/`, local mode; #523, #552, #195): setup installs a Node-target bundle with the host package external. The first main runtime owns one child process; later ACP mains receive no tools, and only descendants whose unambiguous parent chain reaches that owner serve tools. Subagents name their session under `GRAYBOARD_AGENT_META`, get no pushes or root instructions, and cannot change bindings. Owner-main `session_switch` and changed-ID `session_branch` retain the child but rotate its bus root before tools or pushes resume. Current instructions come from initialize, transition acknowledgements and tool results; the shared hosted-omp per-request rewrite/context hooks preserve push-started updates after a prompt rebuild. Unexpected child exits retain the existing bounded restart policy and restart under the current selected conversation. User-level configuration alone chooses the executable; file-backed internal URLs resolve through omp's router. `tests/integration/omp.test.ts` covers the pinned runtime.
- **Local-mode pi and omp, and local/V1 opencode: the adapter serves the tools** from its one push-mode `grayboard mcp` child. Why: with a tools-only MCP entry beside the push child, a name bound through the tools process would have to move the push process, needing a cross-process record and a control socket (#182 decision 13). At load the adapter runs `grayboard tools` (the list `grayboard mcp` would serve, in the mode it would pick, without opening the bus) and registers each tool under the name the harness showed before (pi `mcp__grayboard__<tool>`, omp `mcp__grayboard_<tool>`, opencode `grayboard_<tool>`); each call is a `tools/call` to the child, started on demand and awaited through initialize. A failing `grayboard tools` fails the load: pi then exits 1 (any extension load failure does), omp reports it as an extension load error, opencode's init throws. After initialize the adapter compares the child's `tools/list` with what it registered and logs any difference. The child's instructions go into the system prompt, replaced by `structuredContent.instructions` from any tool result: `bind`'s, or the next call's after a lost bind result or a lost name. A cancel that crosses a result on the wire requeues what the result carried (notices, instructions, a bind outcome) for the next call (`src/shared/latecancel.ts`). The adapter listens for `error` on the child's stdin: a write after the child closed its end (EPIPE) would otherwise crash the host.
- **For those child adapters, the harness's `grayboard` MCP entry is config, kept disabled** (`enabled: false`, `BUS_PUSH=off`; `grayboard setup` writes it, `refresh-adapters` disables the entry of each adapter it rewrites, so `update` moves an older release's enabled omp entry over). The adapter takes the child's command and env from it. An entry enabled anywhere would register the tools twice (pi: last registration wins; opencode: duplicate ids; omp: the same names, and a second delivery owner), so the adapter refuses: no tools, no child, and the fix reported (pi: UI notify; omp: UI notify and omp's log; opencode: `app.log` and a toast, and every call fails with it). `BUS_PUSH=off` stays on the disabled entry, so a re-enabled one never adds a second delivery owner. omp's check runs as omp's own loader resolves its config (`loadAllMCPConfigs` with `mcp.enableProjectConfig`: every source, priority, same-name shadowing, `disabledServers`, `enabledServers`) and refuses two kinds of enabled server: one named `grayboard`, whatever it runs (stdio through any wrapper, or HTTP), since its tools take the adapter's names, as pi's name rule; and one under any other name whose command, past a wrapper (`bunx`, `npx`, `pnpx`, `bun x`, `npm exec`, `pnpm dlx`, `yarn dlx`, `env`, `exec`, a shell's `-c` line), is a `grayboard` binary or package with an `mcp` argument, or the entry's own command up to `mcp`. Why any name: the disabled user entry shadows only a same-named server omp ranks lower (Claude Code's user config, a repo's `.mcp.json`), not a repo's `.omp/mcp.json` entry or one under another name. A server under another name that runs grayboard some other way (its own script) isn't recognised. An ACP session skips the check: omp loads no on-disk MCP config there, only the servers the ACP client declares (`session/new`, load, resume, fork), which arrive after the check and aren't checked (#559). For a repo's `.omp/mcp.json` `grayboard` entry with a `BUS_IDENTITY`, the notice adds that the pin still names the session once disabled (`handles.md` §2 Worktree suffix).
- pi (`adapters/pi/`): `~/.pi/agent` here means pi's agent directory as pi resolves it (`piAgentDir`, `src/shared/pi.ts`, which the adapter mirrors and a test holds equal); an empty `PI_CODING_AGENT_DIR` counts as unset, never the cwd, where a repo's `./mcp.json` could run its command (#437). It reads the user-level `~/.pi/agent/mcp.json` entry only (a project `.pi/mcp.json` can override just `enabled` and exposure); registers the tools at `session_start`, which has the cwd for the project-entry check. Injects DMs, mentions and thread replies as a turn (or steers into a running one); digests and deferred pushes as context. It passes pi's session id (`getSessionId()`) to its grayboard as `BUS_HARNESS_SESSION`, and in pi-subagents' detached runner (`PI_SUBAGENT_CHILD=1`) the launching session's id as `BUS_PARENT_SESSION`, which makes the runner's grayboard a child of that session (`child-sessions.md` §Local runner children); a foreground child that loads this extension gets its top root's id the same way, found from its header's `parentSession`, when its launching session has a session file and owns its delivery (#557); in a keyed or human pi process every session but the one holding the key or identity is its subagent, a keyed root's its child with or without a header and a human root's given no grayboard (#1075). Unexpected exits fail calls in flight and use the local omp restart policy (#559): the new child takes its names back from the name record (`sessions.md`), except a subagent's, which keeps none and restarts unbound (#1078), and calls during a backoff wait for it; exhaustion reports "restart pi to reconnect". A child that hasn't answered initialize and finished its session handshake within 30 s is killed and restarted as an exit is (omp and OpenCode V1 too). Tool calls awaiting a backoff or initialization stop waiting when aborted, so teardown can reach `session_shutdown`, which cancels a pending restart before `/new`, `/resume`, fork or quit; each session's extension instance keeps its own count. The policy is mirrored rather than imported: setup installs each local adapter as one raw file (`src/cli/adapters.ts:adapterSource`). Tested by `tests/integration/pi.test.ts` against the pinned pi.
- opencode (`adapters/opencode/`, local/V1): user-level configuration alone chooses the child executable and fixed tool list; the effective config only controls duplicate-owner refusal. Root-only `selectTarget`/`firstTarget` use SDK ancestry classification, including resumed sessions whose creation event was missed. A child cannot change the selected root and receives child-only instructions. One retained MCP child rotates its bus root on root changes; a notification captures its recipient before asynchronous host admission. `noReply` remains context-only, not a guarantee against evaluation by an already running turn. Child state ends with its root, not at resumable OpenCode idle/deletion events. OpenCode V2 does not run V1 plugins.
- **Local retained-child transition barrier** (#195; `src/local/mcp.ts`): adapter-only `grayboard/session` over existing stdio settles calls under `BindGate` and delivery before ending the outgoing root, registering/restoring the incoming root and returning current instructions. Owner/epoch guards reject stale selection; same-ID selection leaves the bus root unchanged. The adapter applies guidance then acknowledges `grayboard/session/ready` before tools/delivery resume. Adapter delivery receipts mark cursors only after admission to the stamped conversation; refused stale admission remains pending, never consumed into another root. Existing end semantics bounce direct-ID mail and end ID-owned state; alias mail, claims and subscriptions remain alias-owned (`handles.md`).
- **Claude retained-child identity** (#195; `src/shared/claude_agents.ts`, `src/shared/claude_identity.ts`): the connection-time environment is only bootstrap, stale after `/clear`. Existing PID hook records publish authoritative `SessionStart.session_id` atomically with the process-start guard. `SessionEnd(clear)` waits for live children's acknowledged pause before the host changes conversation; SessionStart rotates them through the same gate and returns current guidance. PreToolUse cross-checks the recorded conversation before dispatch. Children register their control endpoint before rereading current identity, closing the startup publication race; tools and each push also check current identity. A live failed acknowledgement is visible, not a silent watcher-based fallback.
- **Local native Claude activation and saved guidance** (#195; `src/local/mcp.ts`): pinned 2.1.316 registers its channel handler after `initialized` and the initial `tools/list` request. Write the list response, then await one standard MCP ping response before local tools/delivery proceed; real initial/fresh-resumed processes prove registration precedes that response. This is a measured pinned-runtime activation seam, not a public native admission acknowledgement. A failed/refused ping surfaces failure and leaves pending delivery points untouched; never replace it with a delay/retry or consume mail at `initialized`. Restored/changed identity publishes the complete current instructions and bus root ID as native `kind: guidance` before pending mail: Claude replays stale saved MCP instructions in transcript system context instead of replacing them with initialize's text. `tests/integration/claude_records.test.ts` deterministically holds/refuses activation; actual `tests/e2e/local_resume.e2e.ts` checks idle queued delivery and current guidance in the first resumed model context.
- Local/V1 child recovery retains the bounded restart/cancellation policy (`adapters/opencode/grayboard.ts`): stop and await a retiring owner before replacement, restart under the selected conversation, and restore its authoritative snapshot before PID carry. pi restarts its child at `session_start.reason`; fresh launches and same-process resume both select their conversation's own remembered state. `tests/integration/local_resume.test.ts` covers ordering, provenance, refusal, reaping and deterministic transition races.

- `grayboard setup` installs each harness's adapter for the mode but preserves remote or uncertain OpenCode registrations. Hosted V2 uses native configuration/package loading or explicit `setup-opencode`; human steps belong in `docs/guide/harnesses.md`.
