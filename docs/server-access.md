# Access and authorization

```doc-meta
owns: the server's access rules: the authorization seam, decision rows, wake rules, role bindings and admin, teams, mentions, attachment uploads and reads, claims visibility, retained HTTP routes
invariants: the server's authorization rules live in one set of rule bodies (policy.ts decide), writing nothing, and who may act in a scope is its principal-keyed rule, re-checked for the life of a hold; a role is a `role_bindings` row read on every decision, never cached, and `GRAYBOARD_ADMINS` emails are admins with no row; every binding change writes its audit row in its transaction; hidden teams and boards read as not found; attachment bytes cross HTTP and bind only by id
```

## 1. Authorization

- **One authorization seam** (`src/server/policy.ts`, [#806](https://github.com/nolnoch/grayboard/issues/806)): `decide(ctx, req)` holds every rule as a generator yielding its storage reads; `authorize` answers them on the caller's handle, `decidePure` the read-free verbs. Each takes a verb and subject, returning `{allow, rule}` or `{allow:false, code, reason, rule}`. The scope, team, admin and human-reach rules live only there: `src/server/policy.test.ts` fails if another source file calls the pre-seam helpers. No policy refusal decides inline ([#851](https://github.com/nolnoch/grayboard/issues/851)); refusals that aren't policy (a missing hosted session ID, malformed input, a hosted session outside the caller's root) refuse in place and leave no decision row. Verbs: `msg.send` (a DM) and `human.reach` (the same rule as a filter: mentions, thread replies); `alias.bind`, `act_as` and `scope.act` (a principal acting in a scope: a bind or `writes_as`, an HTTP `as`, visibility, the alias sweep; a bind and an `as` refuse `human`, an `as` an ownerless scope); `session.act` (an HTTP `as` naming a session ID: the caller's own, live, not a viewer's; other users', unknown and viewers' IDs read alike); `hosted.session` (a hosted MCP request reaching a hosted session row, its own, a `session_register` child's or a `session_end` target: another user's or OAuth client's reads as missing, `not_found`, though only policy refusals leave a row); `attachment.read` (a download, over HTTP or the Slack bridge: the rule is core's `canReadAttachment`, shared with local mode, named by the carrier that decided it; a refusal reads as missing and also keeps its `attachment.download_refused` row); `team.read`, `team.manage` and `team.leave` (members only: an admin can't leave a team it's not in); `admin`; `msg.wake` (a filter: whether a delivery wakes its recipient); `alias.see` (a filter: whether a principal may see that a scope's alias exists, for `peer_list` rows, name suggestions, `board_post` recipients and a DM or delegation recipient, judged for the session's ID, not its team address: a person scope to anyone, a team's to its members and its own aliases, no admin exemption, #348).
- **Decision rows** (security audit F-19): the caller that owns a requested act records it with `recordDecision` as an `authz.decision` `access_log` row: the verb, allow, the rule that decided, code and reason on a deny, the subject, and who asked (the user as actor; user, address and session ID in the detail; on `/mcp`, the row's `client_id` column names the OAuth client). Every policy deny is recorded, and so is every allow of team management, of an admin route (which names the route; a dashboard read's once per window, server-admin-dashboard.md §2) and of an admin's roster read of a team they aren't in (an exercise of admin authority, principle 8; a member's read isn't). A role-based allow names its binding (`binding`, with `role` and `scope`, in the detail), a role deny the role and scope it looked for; the rule stays a closed name, so callers compare it (`byAdmin`). Caller-chosen strings (a route, a requested team name) are clipped to 128 characters. Filter checks (board visibility, mention fan-out, a thread reply's reach, the alias sweep) record nothing. A hosted tool call's deny row is written after the call's rollback, so it survives the refusal. Delegation keeps its own `delegation.requested`/`delegation.refused` rows. Deny rows are thinned per user (`DENY_ROW_LIMIT`, burst 30, then one per 2s): a client looping on a refused act over HTTP routes no request limiter covers would otherwise write a 90-day row per request. Denies past the burst go unrecorded, and the streak's end writes one `authz.suppressed` row with the count. Inside a write body the caller's own streak row goes on the body's `Tx`; other users' refilled buckets are swept after that body commits, each row posted, so a body that fails to commit leaves their counts for the next sweep (#1436).
- **`msg.send`'s one rule today**: another user's `human` is reachable only by their teammates' addresses, and by a team alias only when they're a member of that team (rules `human.teammates`, `human.team_alias`; `GRAYBOARD_SLACK_REACH`; `slack-org-bridge.md`). It gates every DM in `application.ts` (`prepareSend`).
- **`msg.wake`** (security audit F-03, [#806](https://github.com/nolnoch/grayboard/issues/806)): sending is open, waking another user's agent needs a grant (`vision.md` principle 9). Its subjects are users, never addresses: the writer's user recorded on the row at write time and the receiving session's user. Allowed for the same user (`wake.same_user`) and for two users who share a team whose policy is `collaborative` or `delegating` (`wake.team_policy`, one indexed lookup, `teams.shareCollaborative`); denied otherwise (`wake.cross_user`), with no admin exemption, since admin is a server role, not a messaging grant. A team's policy is `open` by default and set by an owner or admin (`POST /api/teams/<team>/policy`, audited `team.policy_set` with before and after, only on a change). `writerMarks` (`src/server/application.ts`) decides per writer per call, for `application.pending()` and every pull-free read (`dm_inbox`, `dm_thread`, `dm_history`, `board_read`, a board resource's snapshot, [#825](https://github.com/nolnoch/grayboard/issues/825)), so a grant set or revoked (a member removed, the policy reset) governs the next pull or read: another user's DM or push without the grant goes out `ungranted` and not actionable (adapters-hosted.md §Hosted core), a digest in the pull never wakes anyway and carries no `ungranted`; on a read the same item is marked `ungranted`, and the instruction text every hosted session gets (`OTHER_USER_NOTE`, `src/server/hosted.ts`) says to treat it as data and not act on it without the user's approval (principle 10). The send result says `wakes: false` with a `wake_note` when the recipient is known to be such a user (the live holder's user, else a person alias's; the note names the user only when the address is their person alias, since a team alias's or ID's holder is a handle, not a user, F-12), so the sender doesn't wait on an agent that won't act; a human recipient, or a team alias or ID with no live holder, gets no such field. When either side is a service the note says no team policy changes it, a service being no team member (#1241). A post on a service's board is also judged with the post's facts (its board, the author address's principal and the reading address's): `wake.service_invoke` allows it when one side is that service and the other holds `service_invoke` on it, keyed per board so one service's grant never marks another's post; DMs between them stay mail (open question 7's default). After a revoke or a removed membership the service reads the holder's queued post `ungranted`; the holder's own pending replies drop, as from any board it can no longer see. A filter: no decision rows.
- **Role bindings** (#927, `role_bindings`, `src/server/roles.ts`): authority is a row that exists, read by an indexed lookup on every decision and never cached (principle 11), so a revoke, or a row an operator deletes by hand, governs the next request with no restart. Holder, scope and granter are `principals.id` (a user, a team or a service; never an email, and a team's name can't be reused onto its binding). The role table in `policy.ts` (`ROLES`) says which kind each role is scoped to and who may hold it; there's no `CHECK` on `role`, so a role this code doesn't know grants nothing. Grant is one `INSERT … SELECT … ON CONFLICT DO NOTHING RETURNING` whose `WHERE` re-checks the holder's kind, a `team_owner`'s membership and the granter's authority as of the write (`org_admin`, or for an owner's grant the team's `team_owner`; a bootstrap admin's needs no check), so a granter revoked after the route's decision lands nothing (403); when it writes nothing, reads after it say why (404 for a missing name or scope, 409 for a non-member, an existing binding answered 200 unchanged with no row; when those reads find the preconditions met, the grant runs once more before any refusal, since on Postgres they read newer snapshots than its statement). On Postgres every role-binding writer takes one lock first, because an in-statement re-check doesn't exclude a concurrent revoke under READ COMMITTED (`docs/future/postgres-server.md` D3). Revoke is a hard `DELETE … RETURNING`, never a soft delete (every reader would need a `revoked_at` filter), and it is the only way a binding goes: member removal deletes the binding through it. Each change writes `role.granted` or `role.revoked` in its transaction; the revoke row carries the whole binding, so an id an older decision row names resolves for as long as any row names it (ids are never reused). The foreign keys are `ON DELETE RESTRICT`: whoever adds team or service deletion revokes their bindings first, with their rows. `service_owner` (scope a service, holder a user) records who answers for a service and carries no power; the store's revoke refuses a service's last one (`LastOwner`, counted in the revoke's statement as a team's last owner is). `service_invoke` (scope a service, holder a user, a team or a service) is the right to invoke it (`server-services.md` §2).
- **Service principals, their credentials' admin side, service boards' access and `service.invoke`** (#270): `server-services.md`.
- **Per-grant list and revoke, and the IdP re-auth clock** (#930): `server-offboarding.md`.
- **`admin`**: `GRAYBOARD_ADMINS` first (`admin.env`, no read; never written to the table, so the server stays administrable with the table empty or wrong), then an `org_admin` binding (`role.org_admin`). Gates every `/api/admin/*` route, the roster of a team the caller isn't in, and team management where the caller isn't an owner; no messaging or directory power (`msg.wake`, `delegate.to`, `alias.see`, principle 9). `org_admin` grants and revokes `org_admin`, its own included (`/api/admin/roles`, `grayboard admin role`). The role list shows bootstrap emails first, with no id, signed in or not; revoking one's `org_admin` without a binding is 409. No last-`org_admin` guard: the env list is the recovery, and the revoke answer warns when no admin is left. The read-only dashboard over these routes: `server-admin-dashboard.md`.
- **Board access is one rule set** (`src/server/access.ts` `boardAccess`), async on the caller's handle, for the server's board and claim ports and its session end (`src/server/session_end.ts`); the server installs no synchronous `Access` into core (#807 P3 C10d2-a). `src/server/board-access-parity.test.ts` holds it equal to the synchronous oracle the parity tests run core under (`tests/support/sync_access.ts`). Each is evaluated for the acting address: an ID acts for its principal, a person alias for its user, a team alias for its team; an address with no principal sees nothing. `scope NULL`: anyone signed in. `scope team:<name>`: that team's aliases and its members' addresses, for list, read, post, subscribe, mentions and pushes. A session bound to `eng/x` acts as eng: it sees eng's boards, not its binder's other teams', so a team alias can't carry one team's content into another's. Its ID is judged as its session's primary (oldest hold) on every scoped board (`seerOn`, #1255), so falling back to the ID, or `as: <ID>`, doesn't reach the binder's other teams' boards either, nor another team's aliases' labels (its own team's stay visible; a person alias's labels are judged for its user, so its binder's sessions' labels still reach it); which names it may see stays its user's (`alias.see`, #348). A claim it took there before its primary moved ends for its user instead (`claims.md` Watches, #1286). So a `dm_send` or an @-mention on an org board can still carry eng content to a qa alias it may name, while no path delivers qa's board content to it: accepted (#1273), as vision principle 9 makes reading the directory and sending mail open. A board you can't see reads as "no such board". Board names are one global key, so `board_create` with a hidden board's name is refused with a visible open board's text (`board #<name> already exists`, archived or not): it reveals that the name is taken and nothing about the board (#1257, accepted). Team create on a board's name answers the same way for any board, hidden or not (409 `a board named "#<name>" already exists`). Keep secrets out of board names. Queued items for a handle that lost access are dropped at delivery.
- **Who may act in a scope is one check**, `decide`'s scope verbs (`src/server/policy.ts`), keyed by principal, never by email: a user acts in its own person scope and in its teams' scopes; a service acts in its own service scope only (`scope.own_service`), and no user, its owners included, acts in a service's scope (`scope.service`; a bind reads it as a missing scope, as a team's reads to a non-member, so the refusal doesn't say the service exists). It decides `bind`, `writes_as` and board team access. It holds for the life of a hold, not only at bind: `accessChanged(principal)` (`src/server/application.ts`; HTTP team leave and remove call it through `SessionHooks`, `src/server/http.ts`) re-checks every alias that principal's unended sessions hold or write as. A holder loses the alias (hold released, `alias.revoked` with the acting user as actor, null for the `revalidate` backstop, and the session's principal in the detail) and acts as its ID; a tools-only writer has nothing left to act as, so its session ends. A hosted root's hold is released through the hosted store, and the root is told on its next native result (`server-hosted-ownership.md`). `revalidate()` repeats the check over every session every 30s as a backstop. Why: otherwise a removed member keeps the team's boards and mail for the session's life.
- **Teams** (`src/server/teams.ts`, routes in `src/server/http.ts`): a team is an access group whose board is `#<team>`. Users and teams share one `principals` namespace (#284): creating a team inserts its row in the same transaction, and a name another principal holds is refused (409). Invite-only, managed by owners (security audit F-02: with flat membership any member could remove the creator, then bind the team names the creator lost): an owner or admin adds and removes members and makes them owners or members again; members read the roster and leave. An owner holds a `team_owner` binding on the team (#927): creating a team grants its creator one, and `team add --role owner|member` grants and revokes through the same store calls as the admin route, so a team has one store of owners. An owner is a member: the grant requires the membership, and removal or leave revokes the binding with its row. The open that creates `role_bindings` seeds a binding (`granted_by` null) for each `team_members.role = 'owner'` row and each creator still a member with a null role, once, so a revoked ownership never comes back; nothing reads `team_members.role` after it, and with no dual write a rollback to an older release reads stale roles (restore the pre-upgrade snapshot). A team with no owner is the admins' to manage. The last owner can't leave, be removed or be demoted while other members remain (`LastOwner`, counted in the store's revoke, so every writer hits it). Add and remove re-check the caller's owner or admin binding in the store's write, as a grant does, so an owner revoked after the route's decision changes no membership (403, `AuthorityLost`). Add requires the person to have signed in once (a user row), and refuses a service (#270: membership would carry the team's wakes, boards and names). Add subscribes all their person-scope aliases in digest mode; remove unsubscribes. An owner or admin deletes a team name (`POST /api/teams/<team>/delete-alias {name}`, #347), refused `alias_held` (409) while a session holds or writes as it and `not_found` for one the team doesn't have; audited `alias.deleted` with the user as actor and `{team, as_admin?}`. Team and board names share one namespace.
- **Non-members get 404, not 403**, for a team's member routes and roster, so a private team's existence doesn't leak; a member who isn't an owner gets 403 on add and remove. Teams, users and services share one name space, so team create on a taken name must refuse: it answers every holder alike (409 `the name "<name>" belongs to another user, team or service`), saying the name is taken and nothing about whether a team holds it (#1280, accepted as board names are, #1257). Admins acting on a team they're not in, by env or by binding, are audited with `as_admin: true` (the path for an empty team). `POST /api/teams/:name/join` is always 403, kept so older CLIs get a pointer to `team add`.
- Distributed mentions (`resolveMention`, `src/server/access.ts`; grammar: `boards.md` §3): a name resolves only among aliases that can see the board (`canSee`) and that `human.reach` (§1) allows the author to reach. Anything unresolved, or unable to see the board, isn't pushed and returns in `unresolved`; so does a team's alias the author can't see, pushed anyway.
- **Attachments** (`src/server/http.ts` attachments section, `src/server/attachments.ts`): hosted-core's tool proxy (`adapters/hosted-core/src/proxy.ts`, `attachments.ts`) checks paths (`attachments.md`), then uploads each file to the hosted endpoint's `<resource>/attachments` with `X-Grayboard-Session`, which the server serves through the shared attachment handlers (`src/server/http.ts`) as the session's primary (`src/server/mcp-attachments.ts` sets their `?as=`); no route takes `?as=` from a client since the session-token `/api/attachments` routes went (#475). A send binds an upload made as any address of the sending session by its user (`bindAttachments`, `uploader_principal`): a team alias can pass to another member, and its holder's unsent uploads don't go with it, whether the next holder would send, download or delete them (#367); `dm_send` and `board_post` carry only the returned ids. If the send fails, hosted-core's tool proxy releases its uploads (`DELETE <resource>/attachments/<id>`, unsent uploads of that address and user only), so a refused send doesn't hold the user's quota until expiry. A send binds its files all or none, so when every release answers 404 the send landed and only its answer was lost: the tool reports it sent (`SendLanded`, `sendWithUploads`, `src/shared/attachments.ts`, shared with hosted-core's tool proxy) rather than failing, so the agent doesn't send it twice. Bytes stay out of tool arguments: a file would travel base64-inflated inside the JSON call.
- **Upload limits.** The upload re-checks size and sniffs type from the bytes, since a client's checks are the client's word. `storeUpload` is the one store path, for the HTTP route and the org bridge's in-process sends alike, so both pay the same quotas, checked in the insert's transaction: a user's unsent bytes (twice the per-message total, `unboundCap`) and stored bytes sent or not (`GRAYBOARD_ATTACHMENT_USER_QUOTA_BYTES`), so neither abandoned uploads nor a heavy sender can fill the disk. The caps have ceilings and must nest (file ≤ total ≤ quota), else startup fails (`src/server/config.ts`). Before reading a body, an upload reserves its declared length in `UploadGate` (`src/server/uploads.ts`: server-wide room is FIFO; a user at their own cap waits without holding up other users; dropped if the request aborts), so concurrent uploads can't each buffer a full body in memory; hence no `Content-Length` → 411. The body must then arrive within `transferTimeoutMs` of its length (`readUploadBody`) → 408, so a trickling client can't hold its reservation. The request body cap is the per-file cap plus `MAX_BODY_BYTES` (`maxRequestBodySize`, `src/server/app.ts`), not Bun's 128 MB default.
- **Attachment reads.** A download is served only to an address that can read the carrier (`requestAttachment`, shared with the org bridge), with `nosniff`, `no-store` and `Repr-Digest` (RFC 9530 sha-256), which hosted-core's tool proxy checks against the bytes before saving (a missing one fails the check); anything else is 404, as for hidden boards. OAuth byte requests require a mapped, bound nonhuman source context, validate configured Origin before authentication, and recheck actual access, effective root binding and carrier visibility after the asynchronous blob read. Upload insertion and release deletion fence the same authority inside their write transaction; download authorization and response construction share a transaction after the read. Bytes are buffered before the response; authorization cannot retract bytes after headers commit.
- **OAuth upload boundaries** (`src/server/http.ts`, `src/server/attachments.ts`): revalidate after quota waits and body reads, around storage and before replying. If access, ownership or cancellation changes while a put is pending, release only that identity's newly created unbound upload; a concurrent successful bind must survive cleanup. Guarded uploads own the original body without request cloning or an implicit tee; source cancellation and reader unlock complete before their gate reservation or operation is released. Pre-body refusals also await source cancellation. Shutdown aborts waiters and awaits operations before OAuth teardown or caller DB close. Release checks authorization around its asynchronous sweep; a committed release cannot be undone by subsequent revocation. Unexpected storage faults remain redacted server errors, never inferred token failures; blob sweeping retains the existing retry-on-retention policy.
- **Every attachment's lifecycle is audited** with its SHA-256 and where it went; a download is logged only after the blob read, so a failed read isn't logged as one; a failed read or write is logged as `attachment.download_failed` / `attachment.upload_failed` with the error. A blob swept between the read check and the read answers 404 (`BlobMissing`, `src/core/errors.ts`). Other faults return redacted internal errors: the retained router delegates to `Bun.serve`'s `error` handler (`src/server/app.ts`), which logs the stack and answers a bare `{code: "internal"}` 500, while the OAuth byte router (`src/server/mcp-attachments.ts`) maps them directly and logs a hosted diagnostic line itself (`operation` `attachments.upload`/`download`/`release`, the error's class and code only, never its message, per `docs/server-hosted-ownership.md`; #1608), the cause staying in the audit row. Neither uses Bun's default dev page, which can expose the message when `NODE_ENV` is unset (the prod unit sets none). A leaked file can be traced to who stored, sent and fetched it. Derive the events from `writeAudit(` calls naming `attachment.` (`src/server/`).
- Claims are org-wide: anyone signed in sees each key, and its holder and note unless a team alias outside their teams holds it, and its note unless the claim's board is one they can't see (#1257, `claims.md`); `claim_list` hides the board name of an announcement on a board you can't see. `GET /api/claims` (for `grayboard claims`) authenticates a user, not a handle, so it omits board names entirely.
- **Retained HTTP routes acting as an address resolve it one way** (`ownAddress`, `src/server/http.ts`), for claims and attachments: a bare name is the caller's own person scope; an alias must be in the caller's scope or a team's it belongs to, and exist (else `unknown_identity`, 404, rather than created lazily as a bind does, so a mistyped name in a script can't act as a fresh alias); `human` is 403 in any scope (claims are for agents; the bridge's human stores files in-process); an `id:` must be the caller's unended session, so nothing uploads or claims as an ended one.
- `POST /api/claims/call` (for `grayboard claim`) runs a claim tool as an address `ownAddress` accepts, with that address's holder's address set when the holder is the same principal (`addressSet`, #360: an alias's CLI releases a claim its session took as its ID; refuses `args.as`), and passes the core's wake list to the same `wake` the WS tool path uses, so a CLI claim change is delivered like a tool call's.
