# Access and authorization

```doc-meta
owns: the server's access rules: the authorization seam, decision rows, wake rules, admin, teams, mentions, attachment uploads and reads, claims visibility, retained HTTP routes, rate limits
invariants: the server's authorization rules live in one pure function (policy.ts authorize), and who may act in a scope is its principal-keyed rule, re-checked for the life of a hold; hidden teams and boards read as not found; attachment bytes cross HTTP and bind only by id; authentication failures are limited per client address and charged only on a refused presented token or a sign-in call, so valid traffic never touches a bucket, and a refused token repeated on a path is answered from memory, uncharged, for 60s
code-pointers: src/server/policy.ts, src/server/access.ts, src/server/teams.ts, src/server/http.ts, src/server/attachments.ts, src/server/rate_limit.ts, src/server/auth_gate.ts
companions: boards.md (the core's Access policy), server-sessions.md, attachments.md
```

## 1. Authorization

- **One authorization seam** (`src/server/policy.ts`, [#806](https://github.com/nolnoch/grayboard/issues/806)): `authorize(repo, ctx, req)` is pure and synchronous, takes a verb and its subject, and returns `{allow, rule}` or `{allow:false, code, reason, rule}`. The scope, team, admin and human-reach rules live only there: `src/server/policy.test.ts` fails if another source file calls the pre-seam helpers. No policy refusal decides inline ([#851](https://github.com/nolnoch/grayboard/issues/851)); refusals that aren't policy (a missing hosted session ID, malformed input, a hosted session outside the caller's root) refuse in place and leave no decision row. Verbs: `msg.send` (a DM) and `human.reach` (the same rule as a filter: mentions, thread replies); `alias.bind`, `act_as` and `scope.act` (a principal acting in a scope: a bind or `writes_as`, an HTTP `as`, visibility and the alias sweep; a bind and an `as` refuse the reserved `human` name, and an `as` a scope no principal owns); `session.act` (an HTTP `as` naming a session ID: the caller's own, live and no viewer's; another user's, an unknown and a viewer's ID read alike, so a refusal never says whose an ID is); `hosted.session` (a hosted MCP request reaching a hosted session row, its own, a `session_register` child's or a `session_end` target: another user's or another OAuth client's reads as missing, `not_found`, like an ID that doesn't exist, though only the policy refusals leave a row); `attachment.read` (a download, over HTTP or the Slack bridge: the rule is core's `canReadAttachment`, shared with local mode, named by the carrier that decided it; a refusal reads as missing and also keeps its `attachment.download_refused` row); `team.read`, `team.manage` and `team.leave` (members only: an admin can't leave a team it isn't in); `admin`; `msg.wake` (a filter: whether a delivery wakes its recipient); `alias.see` (a filter: whether a principal may see that a scope's alias exists, for `peer_list` rows, name suggestions (a DM's, a mention's) and `board_post`'s recipient lists, judged for the session's ID, not the team address it acts as: a person scope to anyone, a team's to its members and its own aliases, no admin exemption, #348).
- **Decision rows** (security audit F-19): the caller that owns a requested act records it with `recordDecision` as an `authz.decision` `access_log` row: the verb, allow, the rule that decided, code and reason on a deny, the subject, and who asked (the user as actor; user, address and session ID in the detail; the OAuth client joins with [#847](https://github.com/nolnoch/grayboard/issues/847)). Every deny `authorize` makes is recorded, and so is every allow of team management and of an admin route (which names the route). Caller-chosen strings (a route, a requested team name) are clipped to 128 characters. Filter checks (board visibility, mention fan-out, a thread reply's reach, the alias sweep) record nothing. A hosted tool call's deny row is written after the call's rollback, so it survives the refusal. Delegation keeps its own `delegation.requested`/`delegation.refused` rows. Deny rows are thinned per user (`DENY_ROW_LIMIT`, burst 30, then one per 2s): a client looping on a refused act over HTTP routes no request limiter covers would otherwise write a 90-day row per request. Denies past the burst go unrecorded, and the streak's end writes one `authz.suppressed` row with the count.
- **`msg.send`'s one rule today**: another user's `human` is reachable only by their teammates' addresses, and by a team alias only when they're a member of that team (rules `human.teammates`, `human.team_alias`; `GRAYBOARD_SLACK_REACH`; `slack-org-bridge.md`). It gates every DM in `application.ts` (`prepareSend`).
- **`msg.wake`** (security audit F-03, [#806](https://github.com/nolnoch/grayboard/issues/806)): sending is open, waking another user's agent needs a grant (`vision.md` principle 9). Its subjects are users, never addresses: the writer's user recorded on the row at write time and the receiving session's user. Allowed for the same user (`wake.same_user`) and for two users who share a team whose policy is `collaborative` or `delegating` (`wake.team_policy`, one indexed lookup, `teams.shareCollaborative`); denied otherwise (`wake.cross_user`), with no admin exemption, since admin is a server role, not a messaging grant. A team's policy is `open` by default and set by an owner or admin (`POST /api/teams/<team>/policy`, audited `team.policy_set` with before and after, only on a change). `writerMarks` (`src/server/application.ts`) decides per writer per call, for `application.pending()` and every pull-free read (`dm_inbox`, `dm_thread`, `dm_history`, `board_read`, a board resource's snapshot, [#825](https://github.com/nolnoch/grayboard/issues/825)), so a grant set or revoked (a member removed, the policy reset) governs the next pull or read: another user's DM or push without the grant goes out `ungranted` and not actionable (adapters-hosted.md §Hosted core), a digest in the pull never wakes anyway and carries no `ungranted`; on a read the same item is marked `ungranted`, and the instruction text every hosted session gets (`OTHER_USER_NOTE`, `src/server/hosted.ts`) says to treat it as data and not act on it without the user's approval (principle 10). The send result says `wakes: false` with a `wake_note` when the recipient is known to be such a user (the live holder's user, else a person alias's; the note names the user only when the address is their person alias, since a team alias's or ID's holder is a handle, not a user, F-12), so the sender doesn't wait on an agent that won't act; a human recipient, or a team alias or ID with no live holder, gets no such field. A filter: no decision rows.
- **`admin`**: only emails in `GRAYBOARD_ADMINS`. Gates every `/api/admin/*` route, and team member management when the caller isn't a member.
- **Board access is enforced in the core**, through the `Access` policy the server installs at open (`src/server/access.ts`), evaluated for the acting address through `repo.resolver` (`src/core/resolver.ts`): an ID acts for its principal, a person alias for its user, a team alias for its team; an address with no principal sees nothing. `scope NULL`: anyone signed in. `scope team:<name>`: that team's aliases and its members' addresses, for list, read, post, subscribe, mentions and pushes. A session bound to `eng/x` acts as eng: it sees eng's boards, not its binder's other teams', so a team alias can't carry one team's content into another's. A board you can't see reads as "no such board". Queued items for a handle that lost access are dropped at delivery.
- **Who may act in a scope is one check**, `authorize`'s scope verbs (`src/server/policy.ts`), keyed by principal, never by email: a user acts in its own person scope and in its teams' scopes; service scopes and principals are refused until #270. It decides `bind`, `writes_as` and board team access. It holds for the life of a hold, not only at bind: `accessChanged(principal)` (`src/server/application.ts`; HTTP team leave and remove call it through `SessionHooks`, `src/server/http.ts`) re-checks every alias that principal's unended sessions hold or write as. A holder loses the alias (hold released, `alias.revoked` with the acting user as actor, null for the `revalidate` backstop, and the session's principal in the detail) and acts as its ID; a tools-only writer has nothing left to act as, so its session ends. A hosted root's hold is released through the hosted store, and the root is told on its next native result (`server-hosted-ownership.md`). `revalidate()` repeats the check over every session every 30s as a backstop. Why: otherwise a removed member keeps the team's boards and mail for the session's life.
- **Teams** (`src/server/teams.ts`, routes in `src/server/http.ts`): a team is an access group whose board is `#<team>`. Users and teams share one `principals` namespace (#284): creating a team inserts its row in the same transaction, and a name another principal holds is refused (409). Invite-only, managed by owners (security audit F-02: with flat membership any member could remove the creator, then bind the team names the creator lost): an owner or admin adds, removes and sets roles (`team_members.role`, `owner`/`member`); members read the roster and leave. A row from before roles has a null role and reads as owner only for the team's creator (`OWNER_SQL`, `src/server/db.ts`), per row, so promoting a second owner doesn't demote the creator and no backfill runs; every write since stores an explicit role. A team whose creator left before roles has no owner and is the admins' to manage. The last owner can't leave, be removed or be demoted while other members remain (`LastOwner`, checked in the write's transaction). Add requires the person to have signed in once (a user row). Add subscribes all their person-scope aliases in digest mode; remove unsubscribes. An owner or admin deletes a team name (`POST /api/teams/<team>/delete-alias {name}`, #347), refused `alias_held` (409) while a session holds or writes as it and `not_found` for one the team doesn't have; audited `alias.deleted` with the user as actor and `{team, as_admin?}`. Team and board names share one namespace.
- **Non-members get 404, not 403**, for a team's member routes and roster, so a private team's existence doesn't leak; a member who isn't an owner gets 403 on add and remove. Admins acting on a team they're not in are audited with `as_admin: true` (the path for an empty team). `POST /api/teams/:name/join` is always 403, kept so older CLIs get a pointer to `team add`.
- Distributed mentions (`resolveMention`, `src/server/access.ts`; grammar: `boards.md` §3): a name resolves only among aliases that can see the board (`canSee`) and that `human.reach` (§1) allows the author to reach. Anything unresolved, or unable to see the board, isn't pushed and returns in `unresolved`.
- **Attachments** (`src/server/http.ts` attachments section, `src/server/attachments.ts`): hosted-core's tool proxy (`adapters/hosted-core/src/proxy.ts`, `attachments.ts`) checks paths (`attachments.md`), then uploads each file to the hosted endpoint's `<resource>/attachments` with `X-Grayboard-Session`, which the server serves through the shared attachment handlers (`src/server/http.ts`) as the session's primary (`src/server/mcp-attachments.ts` sets their `?as=`); no route takes `?as=` from a client since the session-token `/api/attachments` routes went (#475). A send binds an upload made as any address of the sending session by its user (`bindAttachments`, `uploader_principal`): a team alias can pass to another member, and its holder's unsent uploads don't go with it, whether the next holder would send, download or delete them (#367); `dm_send` and `board_post` carry only the returned ids. If the send fails, hosted-core's tool proxy releases its uploads (`DELETE <resource>/attachments/<id>`, unsent uploads of that address and user only), so a refused send doesn't hold the user's quota until expiry. A send binds its files all or none, so when every release answers 404 the send landed and only its answer was lost: the tool reports it sent (`SendLanded`, `sendWithUploads`, `src/shared/attachments.ts`, shared with hosted-core's tool proxy) rather than failing, so the agent doesn't send it twice. Bytes stay out of tool arguments: a file would travel base64-inflated inside the JSON call.
- **Upload limits.** The upload re-checks size and sniffs type from the bytes, since a client's checks are the client's word. `storeUpload` is the one store path, for the HTTP route and the org bridge's in-process sends alike, so both pay the same quotas, checked in the insert's transaction: a user's unsent bytes (twice the per-message total, `unboundCap`) and stored bytes sent or not (`GRAYBOARD_ATTACHMENT_USER_QUOTA_BYTES`), so neither abandoned uploads nor a heavy sender can fill the disk. The caps have ceilings and must nest (file ≤ total ≤ quota), else startup fails (`src/server/config.ts`). Before reading a body, an upload reserves its declared length in `UploadGate` (`src/server/uploads.ts`: server-wide room is FIFO; a user at their own cap waits without holding up other users; dropped if the request aborts), so concurrent uploads can't each buffer a full body in memory; hence no `Content-Length` → 411. The body must then arrive within `transferTimeoutMs` of its length (`readUploadBody`) → 408, so a trickling client can't hold its reservation. The request body cap is the per-file cap plus `MAX_BODY_BYTES` (`maxRequestBodySize`, `src/server/app.ts`), not Bun's 128 MB default.
- **Attachment reads.** A download is served only to an address that can read the carrier (`requestAttachment`, shared with the org bridge), with `nosniff`, `no-store` and `Repr-Digest` (RFC 9530 sha-256), which hosted-core's tool proxy checks against the bytes before saving (a missing one fails the check); anything else is 404, as for hidden boards. OAuth byte requests require a mapped, bound nonhuman source context, validate configured Origin before authentication, and recheck actual access, effective root binding and carrier visibility after the asynchronous blob read. Upload insertion and release deletion fence the same authority inside their write transaction; download authorization and response construction share a transaction after the read. Bytes are buffered before the response; authorization cannot retract bytes after headers commit.
- **OAuth upload boundaries** (`src/server/http.ts`, `src/server/attachments.ts`): revalidate after quota waits and body reads, around storage and before replying. If access, ownership or cancellation changes while a put is pending, release only that identity's newly created unbound upload; a concurrent successful bind must survive cleanup. Guarded uploads own the original body without request cloning or an implicit tee; source cancellation and reader unlock complete before their gate reservation or operation is released. Pre-body refusals also await source cancellation. Shutdown aborts waiters and awaits operations before OAuth teardown or caller DB close. Release checks authorization around its asynchronous sweep; a committed release cannot be undone by subsequent revocation. Unexpected storage faults remain redacted server errors, never inferred token failures; blob sweeping retains the existing retry-on-retention policy.
- **Every attachment's lifecycle is audited** with its SHA-256 and where it went; a download is logged only after the blob read, so a failed read isn't logged as one; a failed read or write is logged as `attachment.download_failed` / `attachment.upload_failed` with the error. A blob swept between the read check and the read answers 404 (`BlobMissing`, `src/core/errors.ts`). Other faults return redacted internal errors: the retained router delegates to `Bun.serve`'s `error` handler (`src/server/app.ts`), which logs the stack and answers a bare `{code: "internal"}` 500, while the OAuth byte router maps them directly. Neither uses Bun's default dev page, which can expose the message when `NODE_ENV` is unset (the prod unit sets none). A leaked file can be traced to who stored, sent and fetched it. Derive the events from `writeAudit(` calls naming `attachment.` (`src/server/`).
- Claims are org-wide: key, holder and note are visible to anyone signed in; `claim_list` hides the board name of an announcement on a board you can't see. `GET /api/claims` (for `grayboard claims`) authenticates a user, not a handle, so it omits board names entirely.
- **Retained HTTP routes acting as an address resolve it one way** (`ownAddress`, `src/server/http.ts`), for claims and attachments: a bare name is the caller's own person scope; an alias must be in the caller's scope or a team's it belongs to, and exist (else `unknown_identity`, 404, rather than created lazily as a bind does, so a mistyped name in a script can't act as a fresh alias); `human` is 403 in any scope (claims are for agents; the bridge's human stores files in-process); an `id:` must be the caller's unended session, so nothing uploads or claims as an ended one.
- `POST /api/claims/call` (for `grayboard claim`) runs a claim tool as an address `ownAddress` accepts, with that address's holder's address set when the holder is the same principal (`addressSet`, #360: an alias's CLI releases a claim its session took as its ID; refuses `args.as`), and passes the core's wake list to the same `wake` the WS tool path uses, so a CLI claim change is delivered like a tool call's.

## 2. Rate limits

- **Binds are rate-limited per user** (#210, `RateLimiter`, `src/server/rate_limit.ts`): a token bucket per user (sizes: `src/server/config.ts`, `GRAYBOARD_HELLO`, named from when a hello spent it too), spent by every `bind` and checked before anything reads or writes the database. Over it, a bind gets `rate_limited` with `retry_after_ms` (the wait until a token is back). Why: a bind creates its alias lazily, so a client looping on it could load the server and mint rows without bound. The Slack bridge's in-process connections are exempt. A run of refusals lasts until the user's bucket is full again, seen by the next bind or by the 30s limiter sweep (`sweepLimits`, `src/server/app.ts`, which drops refilled buckets); ending it at any accepted bind would let a loop just faster than the refill start a run, and an audit row, at every refusal. Each run logs one line and writes one audit row when it starts (`bind.rate_limited`, detail: the tripping session ID, the alias it bound, and `retry_after_ms`) and one of each with its count when it ends (`bind.rate_limit_ended`, detail `{refused}`). A hosted bind spends the bucket inside its transaction, which a refusal rolls back: the run's row is written there, where a committing bind keeps it, and again after a rollback through the session's `afterRollback` (#467), so each row is written once either way.
- **Authentication failures are rate-limited per client address** (#240, `AuthGate`, `src/server/auth_gate.ts`, on the same `RateLimiter`): every presented token the server refuses with 401 on the MCP, OAuth attachment byte (#401) or `handleHttp` path (the OAuth AS routes authenticate clients by secret, never a bearer, and answer before charging, under their own OAuth limiters: per address and global, with token and revocation posts per address only (`docs/server-oauth.md`)) and every call to a sign-in route (`signInRoute`, `src/server/http.ts`, one table that both dispatches and decides charging; charged on entry; a disabled route, such as dev-login with dev auth off, dispatches to 404 uncharged) spends a token from the address's bucket. An HTTP 401 is charged on the MCP, byte-route or `handleHttp` response when the request carried a bearer token (`chargeRefusedToken`), so a protected or unknown path with a bad token costs one, while the public routes, dispatched before `requireAuth`, cost nothing unless they are sign-in routes. A request with no token costs nothing: a web page can make a browser send one cross-origin (an `<img>`), but can't attach `Authorization` without a CORS preflight, so charging them would let any page lock out everyone behind its viewer's NAT. For the same reason a sign-in route takes only `Content-Type: application/json` (`isJsonRequest`) and answers anything else 415 `unsupported_media_type`, uncharged: a cross-origin form post needs no preflight, a JSON one does. While it's empty, `fetch` answers every request from the address, `/healthz` included, with 429 `{code: "rate_limited", message, retry_after_ms}` and `Retry-After` (whole seconds, at least 1), before anything reads the database. 403s, 404s and the 429s themselves cost nothing, and valid authenticated traffic never touches a bucket: a check allocates nothing, so the map holds only addresses that have failed, dropped by the 30s sweep once refilled, and capped at 10,000 (past the cap a new address is neither charged nor refused, with a log line and an `auth.rate_limit_full` row at most once a minute; a flood spread across addresses belongs at the network edge). Why failures only: a lookup that succeeds is bounded by legitimate use and the bind limit, and charging only failures keeps a stale-token client behind a shared NAT from blocking its neighbours until it has failed the whole burst; hosted-core stops retrying a refused token, which keeps it from getting there. A client that keeps retrying anyway is answered from memory (#923): `chargeRefusedToken` keeps each 401 it sees for a presented token (status, headers and body, so `/mcp` keeps its `WWW-Authenticate`) for 60s, keyed by one SHA-256 of the path, query and `Authorization` header as sent (a fixed size whatever the client sends, and a token in another shape is another entry), at most 10,000 entries with the oldest forgotten and the expired dropped by the 30s sweep. The entry is stored before the body is read and a token already remembered isn't charged again, so requests in flight together cost one. `replayRefused`, first in `route` ahead of the limiter check, answers a remembered token with it, uncharged, with no database read, from a limited address too. So one stale token costs its address one token a minute per path and query, under the 0.1/s floor on the refill rate, while distinct bad tokens still drain the bucket. A refused token stays refused, save a disabled user's after an admin re-enables them, whose wait the 60s bounds. A valid token pays a SHA-256 and a map lookup. What stays open: tokenless requests and new sign-ins from an address another client's distinct bad tokens have limited are still refused. The address (`src/server/client_addr.ts`) is the peer, normalised (Bun reports an IPv4 peer as `::ffff:a.b.c.d`), or when the peer is in `GRAYBOARD_TRUSTED_PROXIES` (default loopback) the first untrusted `X-Forwarded-For` entry walking from the right, with a port or brackets stripped; a walk that runs out of entries, or meets one that doesn't parse, keys by the last address it trusted, and the first unparsable entry per process is logged, since it puts that proxy's clients in one bucket. A peer Bun can't report keys to the shared bucket `unknown`, never skipping the gate. IPv4 keys by address, IPv6 by /64, and an IPv6 request is also checked against, and charged to, its /48 (#274): a second limiter with its own 10,000-key cap and 4× the per-address limit (`SITE_LIMIT_FACTOR`), checked after the /64 so a request its own /64 refuses doesn't spend its /48. Since a new /64 bucket is created only by a charge, which spends the /48, a prefix rotating through its /64s holds at most about the /48's burst plus its refill over a sweep interval and a bucket's refill (240 + 4 × 31 ≈ 364 at the defaults), plus requests in flight (a refused token is charged when its response resolves, so fresh /64s whose requests overlap all pass the /48's check). So one /48 can't fill the cap and fail every later address open; about 28 /48s together can, and so can a flood that fills the /48 tier's own cap, which then charges no new /48: both are floods across prefixes, which belong at the network edge (#240 decision 6). A drained /48 refuses every /64 under it, valid tokens included, as a drained IPv4 address does its NAT, and the 429's message names the network (/48) rather than the address. A /48 is often more than one site (an ISP's /48 holds 256 customers' /56s), so a client failing from five or more /64s at once can drain it and lock out its neighbours; the refused-token memo keeps one stale-token loop from getting it there. The /48's rows are the same `auth.rate_limited`/`auth.rate_limit_ended` actions with the /48 as target; its cap row carries `tier: "site"`. The resolved address is also dev login's `auth.login` `ip`. A run of refusals has the bind limit's streak semantics, with `auth.rate_limited` (actor null, target the key; its detail carries the refused request's full address and `last_failure`, the charge that emptied the bucket, so a stale-token fleet reads differently from a scan) and `auth.rate_limit_ended` (`{refused}`) rows and a log line each. The start hook runs before the refusal is counted, so a failed audit write leaves no run without its row; `sweepLimits` (its own 30s timer in `startServer`) runs the hello, address and /48 limiters' sweeps, each catching per bucket.
