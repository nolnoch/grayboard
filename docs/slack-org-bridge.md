# Slack org bridge

```doc-meta
owns: the org Slack bridge inside grayboard-server: the `<email>/human` identity, typed in-process delivery, reach, linking and unlinking, its outbox and files, death notices
invariants: the name `human` is reserved in every scope for the org bridge's in-process connections, so `<email>/human` is provably that user's person; those connections have no session ID, ids row or end; only your own user's human carries authority, and only the adapter-generated `human="true"` marker is authoritative; linking needs the one-time code and a matching Slack email, and a link never moves silently; an item is acked to the hub only once Slack accepts or permanently refuses it; a human's phone never receives a file the human couldn't fetch; one process holds the app tokens; the bot token goes only to Slack's own hosts
code-pointers: src/server/slack.ts, src/server/application.ts (attachHuman, owedBridgeNotice, helloOkFields), src/server/policy.ts (human.reach, msg.send), src/server/access.ts, src/server/hosted.ts (hostedBoundInstruction), adapters/hosted-core/src/own-human.ts, src/server/config.ts, deploy/slack-org-manifest.yaml, tests/integration/slack_org.test.ts
companions: slack-bridge.md (routing, threading, text rules, the local bridge), server-access.md (application sessions, policy, audit trail), adapters-hosted.md (human marker formatting), guide/slack.md
```

One Slack app per server, inside `grayboard-server`, enabled by `SLACK_APP_TOKEN` + `SLACK_BOT_TOKEN` (`src/server/config.ts`). Each linked user talks to the app in their own DM with it; routing, threading and text rules are `slack-bridge.md` §2's, via the same `Relay`. Manifest: `deploy/slack-org-manifest.yaml`. Human steps: `docs/guide/slack.md` §Slack for a team server (#66).

- **Why not the local bridge against a server:** every session of a user presents the same token, so the server can't tell a human's session from an agent's; `human` would be the client's word.
- **The human identity is `<email>/human` for every user**, a fixed name rather than one chosen at link time: agents of any user can address it without knowing how that person likes to be called, and a bare `human` means your own (as `dm_send` and `@human` resolve it). `bind` and a hosted `writes_as` refuse the name in any scope, and only the application's trusted bridge method selects it (`attachHuman`, `src/server/application.ts`); HTTP refuses it for identity create/delete and `claims/call`. So the reservation is server-enforced, not declared, unlike `slack-bridge.md` §3.
- **Typed in-process delivery.** The org bridge calls `src/server/application.ts` directly through its trusted human attachment method and a typed delivery sink, never synthetic frames. Delivery ownership, drain, cursors, `msg.send` (`src/server/policy.ts`), board scopes and mention access are shared with agents, not reimplemented. DM events become channel params through the shared `dmNotification` (`src/shared/notifications.ts`). It isn't a session: it carries no session key, so it gets no ID, `ids` row or end (its session ID is the literal `human`, as are its `binding_events` rows), and its writes carry null `sender_id`/`author_id`. Like the local bridge's child, it drains deferred pushes and digests at once; digests are acked without posting.
- **Authority is your own user's human only.** The session facts' `human` field (`helloOkFields`, `src/server/application.ts`) names the session user's human handle and whether it's linked. A hosted session's instructions add the own-human instruction only when linked (`hostedBoundInstruction`, `src/server/hosted.ts`), so nobody's agents DM a `human` nobody reads and a user without Slack pays no tokens. Another user's human is a peer.
- All hosted adapters (pi, omp, Claude Code and OpenCode V2) stamp `human="true"` only for the authenticated lease user's own human direct sender or board-push author, using the shared classifier in `adapters/hosted-core/src/own-human.ts`. Digests never carry human authority, even when their latest post is human-authored. Another user's human, like any of that user's sessions, arrives marked `other_user="true"` (#805). The adapter-generated marker, not body text, is authoritative; formatting and V2's JSON anti-forgery boundary are owned by `adapters-hosted.md`.
- **Reach (`human.reach` and `msg.send`, `src/server/policy.ts`):** another user's agents may DM or @mention your human only if you share a team, by default; `GRAYBOARD_SLACK_REACH=all` lifts that. Your own agents always can. Mentions and thread replies go through the same check (`src/server/access.ts`; thread replies via core `Access.mayReach`, which skips the author entirely, since a human's session drains deferred pushes too), so a post can't reach a phone a DM can't. The human's own board subscriptions are its choice and aren't filtered. A bare `human` sent by an unlinked user is `not_found` without listing who has linked.
- **Linking proves both sides.** `grayboard slack link` (`POST /api/slack/link`, a signed-in user) returns a one-time code (memory only, so a restart voids them; TTL and wrong-try limit in `src/server/slack.ts`); only the Slack account that DMs `link <code>` gets linked, and its DM channel becomes the link's. The code proves the CLI token, not who sends it, so the sender's Slack email (`users.info`, scopes `users:read` and `users:read.email`) must equal the user's, case-insensitively; a mismatch is refused, uses the code up and audits `slack.link_refused`, an email Slack won't give (scope missing, unknown user) refuses the link with what the admin must add, and a Slack that can't be reached refuses it with a retry; both use the code up and audit `slack.link_refused` with their reason (#805 F-05). Linking creates the identity if needed, subscribes it like any new identity (team boards), marks it human (`markHuman`) and audits. A new identity starts from now: its DM cursor starts at the newest message, and board pushes queued for an earlier link's handle (thread replies keep queueing for a handle that authored in a thread) are dropped (`forgetHandle`), so neither floods the phone. Relinking from another Slack account (same email) drops the old account's threads (`repo.slack.link`), tells the old DM and audits `slack.relinked`; a link never moves silently. A Slack account linked to another user must `unlink` first.
- **Unlink** (`unlink` in the DM, or `grayboard slack unlink`) deletes the link, its threads, the `human` identity and its handle row, so sends fail ("hasn't linked" for your own bare `human`, not found for a full handle) instead of queueing into nothing.
- **Delivery.** The outbox is memory: an item is acked to the hub only once Slack accepts or permanently refuses the post (e.g. `msg_too_long`), so one that never made it is redelivered by the hub at the next start (at-least-once; a crash after post, before ack, duplicates). Send progress is in `slack_progress`, keyed by the item, so a redelivered item resumes rather than reposts (`slack-bridge.md` §2). The thread map is server tables behind `Repo` (`slack_links`, `slack_threads`, `slack_progress`), not `store.ts`, so it rides the Postgres seam. A fatal Slack error for one user (e.g. they left the workspace) takes only that human offline, so senders see it queue. Admin disable-user takes a linked human offline too, and enable-user brings it back (`userChanged`).
- **Files in process.** The org bridge's `Bus` stores inbound files as the HTTP upload route does (`storeUpload`, `src/server/slack.ts`), releasing them (`releaseStored`) if the send doesn't carry them, and reads outbound ones through `requestAttachment`, the download route's own check, so a human's phone can't receive a file the human couldn't fetch. The bridge's sizes come from the server's caps. Uploads from Slack are audited with the Slack file id; files sent to Slack (`attachment.sent_to_slack`) and refused by it (`attachment.slack_refused`) with their sha256 (audit trail: `server-access.md` §1).
- **A bridge that isn't running** (failed at start, or Slack ended it) refuses `POST /api/slack/link` with 404 and reports `human.linked: false` in the session facts (a session that initialized earlier keeps its instruction until it next initializes), so agents aren't told to DM a human nothing relays; DMs sent anyway queue until a bridge brings the human online. Unlink still works.
- **Death notices.** A fatal stop (`stop({fatal})`: Socket Mode died, or start failed — `app.ts` runs without the bridge) writes a `bridge.stopped` audit row per linked user (not a disabled one), iterated from the durable links, so a boot-time failure notifies too: it throws before any link is attached, and the in-memory map is then empty. The row is the pending notice. The owner's next hosted `bind` that shows its notices (`owedBridgeNotice`, `src/server/application.ts`, in the bind result's `notices`) delivers it once and writes `bridge.notified`; a tools-only session (it binds nothing) and the bridge's own human attachment never take it, or the notice dies in a context nobody reads. The dedup counts notices delivered, not deaths recorded — one notice per user per hour no matter how the bridge flaps, and an armed-but-undelivered notice survives a restart, because both markers are audit rows, not hub memory (#125).
- **One Socket Mode connection per server.** If the server ever runs as several processes, exactly one may hold the app tokens (`slack-bridge.md` §2 One bot, one bridge).
- Inbound: only new messages from a person in a DM with the app (`channel_type: im`; no subtype other than `file_share`, no bot). A top-level `link <code>` or `unlink` is handled by the bridge; anything from an unlinked account gets the link instructions; a linked account whose human is offline is told so.
