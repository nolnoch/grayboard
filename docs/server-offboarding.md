## 1. Revocation

- Logout only revokes that token (`auth.logout`, `token_session`); it closes nothing, since no connection holds a token any more (#282). Admin `revoke-session` and `disable-user` close the user's live application sessions with `unauthenticated` (`disconnectUser`, `src/server/application.ts`, `server-sessions.md`); the revoke or disable transaction itself ends the user's hosted ownerships (`endHostedWhere`, `src/server/db.ts`), browser sessions (#1552) and unspent codes. Only disable and enable move the Slack bridge's human (`SlackBridge.userChanged`); its in-process connection holds no token, so revoke leaves it. A 30s `revalidate` timer (`src/server/app.ts`) is the backstop for a disable made directly in the database, closing that user's sessions.
- **Per-grant list and revoke** (#930, `grayboard grants`, `/api/grants`; `/api/admin/grants` behind `admin`): a user's live OAuth grants and CLI tokens (`cli:<n>`), one revoked by id. A grant goes through `revokeGrant` (family revocation, hosted-session end), on Postgres under the grant row lock rotation takes ([server-oauth.md](server-oauth.md) §1). Each revoke also deletes the user's browser sessions (a live one skips the IdP at consent, #1552) and unspent codes, on Postgres holding the users row. Another user's id is a 404: ids don't probe. A credential's grant lists read-only; its revoke is a 409, as `admin service credential revoke` owns it. Audits `auth.grant_revoked {grant_id, client_id}` or `auth.session_revoked {token_session}`; the list carries no scopes or resource.

## 2. The IdP re-auth clock

- **Why a clock** (#930): the IdP proves a person only at sign-in ([architecture.md](architecture.md) §3), and no provider yet answers "is this user still enabled" (the status check is #930's next part; Keycloak's is #1555). Without one, a person disabled at the IdP keeps refreshing grants and using CLI tokens indefinitely. The clock bounds that to `GRAYBOARD_IDP_REAUTH_DAYS` (default 30; 0 off). The startup line `IdP re-auth:` names the window and the providers with no directory check, so an operator sees the bound they're running under.
- **`users.idp_checked_at`** is stamped by every verified sign-in, in the same write as the link or display-name update of each `signIn` path on both backends, and by dev login (`stampIdpChecked`), which has no IdP to do it. Adding the column stamps every row once (SQLite's guarded ALTER; Postgres migration 0003), so an upgrade starts each clock instead of sending everyone back through the IdP, unlinked rows included. A row a rolled-back binary links meanwhile has a null clock, which reads as due: that user signs in once more.
- **Who is due** (`reauthDue`): a person (`kind = 'user'`) whose clock is older than the window; a service principal never signs in, so it's exempt. A null clock is due with an issuer. With neither it reads as not due, so no token-holding row may get there: the upgrade stamps every row, and `unlink-idp` (`clearSubject`) keeps the clock or starts a missing one at 0 (due at once). A dev login's token is on the clock too; signing in again restamps it.
- **Where it's enforced.** A CLI token on every request (`verifySessionToken`, beside the idle check). A refresh at `/oauth/token`: the check runs after `rotateRefresh` succeeds, inside its transaction, so `invalid_grant` rolls the rotation back and the refresh token stays unspent, while a replay still commits its family revocation. The harness then signs in again through the browser. A hosted access token already issued lives out its hour; a browser session is at most 12 h old and was made by a sign-in that stamped the clock, so consent needs no check of its own.
