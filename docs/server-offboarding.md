## 1. Revocation

- Logout only revokes that token (`auth.logout`, `token_session`); it closes nothing, since no connection holds a token any more (#282). Admin `revoke-session` and `disable-user` close the user's live application sessions with `unauthenticated` (`disconnectUser`, `src/server/application.ts`, `server-sessions.md`); the revoke or disable transaction itself ends the user's hosted ownerships (`endHostedWhere`, `src/server/db.ts`), browser sessions (#1552) and unspent codes. Only disable and enable move the Slack bridge's human (`SlackBridge.userChanged`); its in-process connection holds no token, so revoke leaves it. A 30s `revalidate` timer (`src/server/app.ts`) is the backstop for a disable made directly in the database, closing that user's sessions.
- **Per-grant list and revoke** (#930, `grayboard grants`, `/api/grants`; `/api/admin/grants` behind `admin`): a user's live OAuth grants and CLI tokens (`cli:<n>`), one revoked by id. A grant goes through `revokeGrant` (family revocation, hosted-session end), on Postgres under the grant row lock rotation takes ([server-oauth.md](server-oauth.md) §1). Each revoke also deletes the user's browser sessions (a live one skips the IdP at consent, #1552) and unspent codes, on Postgres holding the users row. Another user's id is a 404: ids don't probe. A credential's grant lists read-only; its revoke is a 409, as `admin service credential revoke` owns it. Audits `auth.grant_revoked {grant_id, client_id}` or `auth.session_revoked {token_session}`; the list carries no scopes or resource.

## 2. The IdP re-auth clock

- **Why a clock** (#930): the IdP proves a person only at sign-in ([architecture.md](architecture.md) §3), and a provider without a directory check (§3) can't answer "is this user still enabled". Without one, a person disabled at the IdP keeps refreshing grants and using CLI tokens indefinitely. The clock bounds that to `GRAYBOARD_IDP_REAUTH_DAYS` (default 30; 0 off). The startup line `IdP re-auth:` names the window and the providers with no directory check, so an operator sees the bound they're running under.
- **`users.idp_checked_at`** is stamped by every verified sign-in, in the same write as the link or display-name update of each `signIn` path on both backends, and by dev login (`stampIdpChecked`), which has no IdP to do it. Adding the column stamps every row once (SQLite's guarded ALTER; Postgres migration 0003), so an upgrade starts each clock instead of sending everyone back through the IdP, unlinked rows included. A row a rolled-back binary links meanwhile has a null clock, which reads as due: that user signs in once more.
- **Who is due** (`reauthDue`): a person no status provider covers (§3): one whose issuer has no provider with `status`, whose issuer is no longer listed, or with no subject. Among those, a person (`kind = 'user'`) whose clock is older than the window; a service principal never signs in, so it's exempt. A null clock is due with an issuer. With neither it reads as not due, so no token-holding row may get there: the upgrade stamps every row, and `unlink-idp` (`clearSubject`) keeps the clock or starts a missing one at 0 (due at once). A dev login's token is on the clock too; signing in again restamps it.
- **Where it's enforced.** A CLI token on every request (`verifySessionToken`, beside the idle check). A refresh at `/oauth/token`: the check runs after `rotateRefresh` succeeds, inside its transaction, so `invalid_grant` rolls the rotation back and the refresh token stays unspent, while a replay still commits its family revocation. The harness then signs in again through the browser. Each refusal by the clock audits `auth.reauth_required {credential: "refresh" | "cli", client_id?}` with the user as target (#1558), so an operator can tell a re-auth wave (the upgrade started every clock at once, so everyone who hasn't signed in goes due on one day) from an attack: the refresh's row is written after the rotation's transaction rolls back, and both kinds are bounded to one row per user and credential kind an hour (`REAUTH_ROW_MS`, `IdpRecheck.reauthRefused`; per process). A refusal by the directory check (§3) audits `auth.idp_disabled` instead. A hosted access token already issued lives out its hour; a browser session is at most 12 h old and was made by a sign-in that stamped the clock, so consent needs no check of its own.

## 3. The IdP directory re-check

- **What it is** (#930 A2): a provider may implement `IdentityProvider.status(subject, signal)` (`src/server/idp.ts`), the directory's word on a subject it signed in: `"inactive"` only when the directory says the person is suspended, deprovisioned or gone; it throws on anything else (network, 5xx, 429, its own credential refused). A person (`kind = 'user'`) with an issuer and subject whose listed provider has `status` is covered: they're off the §2 clock and are asked again once `idp_checked_at` is older than `GRAYBOARD_IDP_RECHECK_HOURS` (default 24). Google implements `status` once the operator gives it a directory key, `oidc` once its issuer is a Keycloak realm and the operator gives it a checker client, and `okta` once the operator gives it an API service app (all below); a provider without one is named on the startup line as having no directory check.
- **Where it runs** (`createIdpRecheck`, `src/server/idp_recheck.ts`; one per server, built in `app.ts` over the providers the AS signs in with and shared by both paths). A refresh at `/oauth/token`: after client authentication, `oauth.findRefreshUser` reads the user behind a live, unspent refresh token of that client and resource, and `beforeRefresh` runs the check before the rotation's transaction, so the IdP call never holds the write queue; a token the rotation couldn't spend (a replay, a dead grant) skips it and reaches the rotation, so a replay still revokes its family. Inside the rotation, `fallbackDue` applies §2 to uncovered users only. A CLI token (`verifySessionToken`, through `SessionHooks.recheck`): a stale covered user is checked in the background (`background`, which shutdown waits for) and the token works meanwhile; past the stale bound the check blocks, as a refresh's does: active lets the token through, inactive refuses it 401, anything else answers 503 (below). Only a caller holding a live refresh token past client authentication, or a valid CLI token, reaches the IdP, so an unauthenticated post spends no directory quota.
- **Answers.** Active: restamps `idp_checked_at`. Inactive: disables the user as admin `disable-user` does, in one write (`setDisabled`, which revokes grants, CLI tokens, browser sessions and codes and ends hosted ownerships), audited `auth.idp_disabled {provider, issuer, reason, orphaned_services?}`, then `disconnectUser` and the Slack bridge's `userChanged`; the refresh is `invalid_grant`. The write re-reads the user under a row lock (`users.lockById`: Postgres `FOR UPDATE`, so a restamp on another replica can't land between the read and the disable) and does nothing if their clock, issuer or subject changed or someone else disabled them since the check started, so a sign-in meanwhile wins. Anything else is transient: `auth.idp_check_failed {provider, error_class}` (warning; `timeout` after 3 s, inside hosted-core's 10 s refresh abort), and the user is backed off for five minutes (`TRANSIENT_BACKOFF_MS`): their checks answer transient without a call or a row until it lapses. The credential works while the clock is within `GRAYBOARD_IDP_RECHECK_MAX_STALE_HOURS` (default 72, at least the interval). Past it a refresh answers 503 `temporarily_unavailable` (`Retry-After: 60`) with the refresh token unspent, which the hosted adapters keep, and a CLI call answers 503 `temporarily_unavailable` (`Retry-After: 60`), which the CLI prints as the IdP being unreachable, not as signed out, and the auth gate doesn't charge as a refused token; either works again once the backoff lapses and the directory answers active. An error never disables.
- **Guards against a wrong directory.** A negative counts only from a provider that has answered active at least once in this process: one whose credential or subject mapping is wrong (answering "gone" for everyone) disables nobody; its negatives audit as `error_class: "unconfirmed_inactive"`. A breaker caps automatic disables at `GRAYBOARD_IDP_DISABLE_LIMIT` (default 5) in a sliding hour across providers; the next would-be disable trips it, audits `auth.idp_recheck_tripped {provider, limit}` (error) and logs once, and automatic disables stay off until restart: inactive answers are then transient, each audited `error_class: "breaker_tripped"`. A disable that turned out a no-op (the re-read found the user changed) isn't counted. One status call per user runs at a time in a process; a concurrent refresh or CLI use shares its answer. All three guards are per process: with several replicas each holds its own.
- **Google** (#930 A2b; `googleDirectoryStatus`, `src/server/idp_google_directory.ts`; the operator's steps in guide/server.md §Google directory check). With `GRAYBOARD_GOOGLE_DIRECTORY_KEY` (a service account's JSON key, or `…_KEY_FILE`) and optionally `GRAYBOARD_GOOGLE_DIRECTORY_ADMIN` (the admin it impersonates under domain-wide delegation), `status` signs a JWT-bearer assertion for the scope `admin.directory.user.readonly`, caches the access token until a minute before it expires (one mint at a time, shared; a 401 drops it), and calls Admin SDK Directory `users.get` on the subject with `fields=suspended,archived`. Suspended or archived is inactive; so is a 404. Everything else throws, named for `error_class`: `google_token_refused` (the token endpoint refused the key or delegation), `google_directory_refused` (401/403 from the Directory API: the role or scope is missing), `google_directory_error` (429, 5xx, a malformed body). `parseDirectoryKey` refuses at startup a key that isn't a service account's PKCS#8 RSA key (what jose's `importPKCS8` takes), an admin that isn't an address, an admin without a key, or a key with no `google` in `GRAYBOARD_IDPS`; no refusal, log line or audit row carries the key or a token. A subject that isn't all digits (Google's `sub` always is) throws without a request. The token request is shared by concurrent checks and runs on its own 10 s timeout, so one caller's 3 s abort stops only that caller's wait. Google's error text for a refused credential (token endpoint, or a 401/403 from the Directory API) is logged, each distinct text at most once in ten minutes, since the audit row carries only the class. **The subject is assumed to be the Directory user's `id`**: Google's OIDC `sub` is that id in practice, but neither that nor the 404 is documented, so the prior-positive guard is what keeps a mismatch from disabling anyone. A total mismatch (every lookup 404), like a refused key, leaves every Google user transient, and the stale bound runs from each person's `idp_checked_at`, which turning the key on doesn't reset: someone who last signed in more than `GRAYBOARD_IDP_RECHECK_MAX_STALE_HOURS` ago gets 503 at their first refresh or CLI call after the key goes on, while recent sign-ins keep working until their own bound. Each check audits `unconfirmed_inactive` (or the credential's class); removing the key and restarting puts everyone back on the §2 clock at once. The operator guide says to watch the first checks after turning it on. A keyless credential (Workload Identity or federation) is #1565.
- **Keycloak** (#1555; `keycloakDirectoryStatus`, `src/server/idp_keycloak_directory.ts`; the operator's realm steps in guide/server.md §Keycloak directory check). With `GRAYBOARD_KEYCLOAK_DIRECTORY_CLIENT_ID` and `…_CLIENT_SECRET` (or `…_SECRET_FILE`), the `oidc` provider (`defaultProviders`, `src/server/idp.ts`) gains `status`. `loadConfig` refuses half the pair, the pair (or `GRAYBOARD_KEYCLOAK_DIRECTORY_URL`) without `oidc` in `GRAYBOARD_IDPS`, an issuer that isn't `<base>/realms/<realm>` (`keycloakRealm`), and a `…_URL` that isn't a bare http(s) base. Requests go to `GRAYBOARD_KEYCLOAK_DIRECTORY_URL` when set (http allowed, for a deployment whose public hostname denies `/admin` and whose server reaches Keycloak in-cluster), else the issuer's base; Keycloak takes a token's `iss` and the admin API's audience from its frontend hostname whatever URL was asked, so minting and calling through one internal base agree. `status` mints a client-credentials token at `/realms/<realm>/protocol/openid-connect/token` (HTTP Basic, no `scope`: the client's default scopes, `kc-admin-api` among them, are what it carries; Keycloak 26.8's admin API refuses a token without that scope's audience), cached as Google's is (`tokenCache`, `src/server/idp_directory.ts`), then `GET /admin/realms/<realm>/users/<encoded subject>`. `enabled: true` is active. A 404 whose JSON `error` is `User not found` (Keycloak's own answer, for a caller with `view-users`) is inactive; any other 404 (a proxy, a wrong base or realm) throws. `enabled: false` with a `federationLink` throws `keycloak_federated_disabled`: `UserStorageManager.validateFederatedUser` reads every user of a switched-off storage provider as disabled (a read-only delegate), so a maintenance switch-off would otherwise answer inactive for all of them; telling the two apart needs `view-realm` on the provider's component, so a federated user is disabled here only by deletion (404). Otherwise `enabled: false` asks `GET …/attack-detection/brute-force/users/<id>`: `disabled: true` (a permanent lockout also clears `enabled`; the field is also true during a temporary lockout, so an admin-disabled user under attack stays transient until it lapses) throws `keycloak_locked_out`, otherwise inactive. A managed member of a disabled organization also reads disabled (`isReadOnlyOrganizationMember`) and is disabled here, as an admin action that already ends their Keycloak sign-in. A body whose `id` isn't the subject throws. Classes: `keycloak_token_refused` (token endpoint 400/401), `keycloak_directory_refused` (admin API 401/403: role, scope mapping or `kc-admin-api`; a 401 also drops the token), `keycloak_locked_out`, `keycloak_federated_disabled`, `keycloak_directory_error` (anything else, including a failed or redirected fetch; the caller's abort is rethrown as itself). Requests refuse redirects and bound the body at 256 KiB; a subject that is empty, `.`, `..` or over 255 characters throws without a request; any other is percent-encoded into one path segment (a federated user without import has an id `f:<provider>:<external id>`). **The subject is assumed to be the user's id**: Keycloak's ID token `sub` is (`TokenManager.generateIDToken`) unless a protocol mapper rewrites it, which would make every lookup miss; the prior-positive guard keeps that from disabling anyone, and the operator guide says not to rewrite `sub`. Refused-credential text is logged as Google's is; no refusal, log line or audit row carries the secret or a token.
- **Okta** (#1563; `oktaDirectoryStatus`, `src/server/idp_okta_directory.ts`; the operator's org steps in guide/server.md §Okta directory check). With `GRAYBOARD_OKTA_DIRECTORY_CLIENT_ID` and `GRAYBOARD_OKTA_DIRECTORY_KEY` (or `…_KEY_FILE`), optionally `…_KEY_ID` and `…_URL`, the `okta` provider gains `status`. `loadConfig` refuses half the pair, any of them without `okta` in `GRAYBOARD_IDPS`, a key `parseOktaDirectoryKey` can't sign with (a JWK with `d`, or any PEM private key, converted to PKCS#8; RSA signs RS256, EC ES256/384/512 by curve; a `…_KEY_ID` that differs from the JWK's `kid`), an RSA key under 2048 bits (jose won't sign with one), an issuer that isn't `https://<org>` or `https://<org>/oauth2/<id>` (`oktaOrgUrl`) when `…_URL` is unset, and a `…_URL` that isn't a bare https origin. Requests go to the org origin: the token endpoint is always the org authorization server's `/oauth2/v1/token`, since only it mints `okta.*` scopes, whichever authorization server signs people in; `…_URL` names the okta.com org for an issuer on a custom domain. `status` mints a client-credentials token for `okta.users.read` with `private_key_jwt` (the only client authentication Okta allows for its API scopes; iss = sub = client id, aud = the token URL, 300 s, a fresh `jti`, `kid` when known) and **always sends a DPoP proof** (RFC 9449, a per-process ES256 key): Okta turns on *Require DPoP* for new service apps. The first proof earns 400 `use_dpop_nonce`; one retry per mint signs a fresh assertion and proof with the nonce, which is kept for later mints. A `DPoP` token is presented as `Authorization: DPoP` with a proof carrying `ath`; a `Bearer` one without a proof. The token is cached as Google's is (`tokenCache`). Then `GET /api/v1/users/<subject>`: the subject must match `^00u[0-9A-Za-z]{1,252}$` or it throws without a request, because that path also resolves a login or its short name, and an email-shaped subject would name whoever holds that login; the body's `id` must equal the subject. Status `ACTIVE`, `LOCKED_OUT`, `RECOVERY` and `PASSWORD_EXPIRED` are active (a lockout or password chore isn't an offboarding); `SUSPENDED` and `DEPROVISIONED` are inactive, as is a 404 whose `errorCode` is `E0000007` (Okta's own not-found); any other 404 throws. Any other status (`STAGED`, `PROVISIONED`, where a reactivated user lands, or one Okta adds) throws `okta_status_unknown`. Classes: `okta_token_refused` (token endpoint 400/401/403: the app's id, key, grant or DPoP, a second `use_dpop_nonce` among them), `okta_directory_refused` (Users API 401/403: the admin role; a 401 also drops the token), `okta_status_unknown`, `okta_directory_error` (anything else). Redirects, the body bound, the abort and logged refusal text are as Keycloak's. **The role must be org-wide** (the guide says Read-only Administrator): a group-scoped admin may get 403 for a suspended or deprovisioned user, which never disables but means that user is never caught. **The subject is assumed to be the user's id**: Okta's ID token `sub` is reserved and is the `00u…` id on both the org and custom authorization servers. **Unconfirmed against a live org** (no Okta org has exercised this yet): whether Okta accepts a DPoP proof from an app with *Require DPoP* off (Bearer is then expected back), whether the assertion needs `kid`, which `aud` Okta expects when the org has a custom domain, and whether a deleted user answers 404 `E0000007`. The prior-positive guard keeps a wrong guess on the last from disabling anyone; the rest surface as `okta_token_refused` or `okta_directory_error`.
