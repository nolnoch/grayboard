# Child sessions

```doc-meta
owns: child sessions: a harness subagent's calls attributed to the session that started it, in every harness and mode
invariants: a child session acts only under its root's addresses and consumes none of its root's read state; a child ID is never an address; its harness-asserted `_meta` only attributes (`via`) and grants nothing; a runner child that outlives its root becomes its own session under a new ID
code-pointers: src/local/mcp.ts, src/shared/claude_agents.ts, src/shared/inbox.ts, src/server/hosted.ts, plugins/claude-code/
companions: handles.md (the root's names), sessions.md (session end), server-hosted-mcp.md (Claude Code plugin children on a server)
```

- **Child sessions** (#523): a harness subagent's calls run as a child session of the session that started it, its **root**, in both modes. Why: a subagent writing as its root read as the root to every peer and human (#470). A child acts under the root's addresses: its address set is the root's holds then the root's ID, never its own ID, so `as: <child id>` is refused and it writes as the root's primary. Each write stores the child's ID as `sender_id`/`author_id` and as `via` (claim and release announcement posts too, `ClaimCtx`); a `delegation.requested`/`delegation.refused` audit row a child causes carries `child` beside the routing `via`. `via` is fixed at write time because the child's row can be gone or ended at read time. A root has at most `MAX_CHILDREN` children at once in both modes (`src/core/bindings.ts`): hosted counts its active child rows (a child idle past the hosted window is parked and counts again only once its next request makes it active, #566, and a root's parked children past `MAX_CHILDREN` are released oldest first, #584; `server-hosted-ownership.md`); both modes refuse with `childCapacity`'s text, local the children seen within `DEFAULT_IDLE_SECONDS` (Local children, below), since a local child has no end of its own.
  - **A child ID is never an address.** A DM or `@id:` mention to it is refused `child_session`, naming the root's primary, whether or not the child has ended (`undeliverableId`, `src/core/session_end.ts`); `liveAddresses` leaves children out. The lasting link is `ids.root_id` (`src/core/schema.ts`), not the hosted store's source row, which is deleted when a hosted child ends. Hosted registration (`register`, `src/server/hosted.ts`) sets it (`hostedRoot`); an ID that later starts as a root has it cleared and is an address again. A hosted child's `bind`, `unbind` and delivery are refused `child_session`.
  - **A child reads explicitly and consumes nothing** (#523 §3a). Why: mail and posts addressed to the root must not reach or dilute a subagent's context, and a subagent must never consume or change the root's read state. In both modes a child's `board_read` peeks (`read`'s `peek`, set from `ToolContext.via`, `src/core/tools.ts`): access is judged as usual, but it reads as a predicate viewer does, with no cursor move, no outbox stamp and no unread view (the default returns the latest page, `unread_remaining: 0`). `dm_inbox`, `dm_ack` and `board_subscribe` (thread mutes included) are refused `child_session` with `childStateRefusal`'s text (`src/core/bindings.ts`, one table for both modes), which names the root's primary and points at `dm_thread` on a thread the child wrote, or at `board_read`; `dm_history`, `dm_thread` and thread or `before_id` board reads stay allowed and mutate nothing. No notice, `bind_hint`, refreshed instruction or digest text rides a child's result. A hosted child's `initialize` instructions are its own (`hostedChildInstruction`, `src/server/hosted.ts`), not the root's bound text: it acts as the root's primary, its writes show its ID as `via`, and the root's delivery lines don't apply. A hosted child of an unbound root is told binding is its root's, not offered names: its `whoami` has `unbound: true` and no `candidates`, and its writes are refused `unbound` naming the root. Pushes are the harness-dependent half: hosted refuses child delivery and local children are `delivery='none'`, while a harness whose subagents share the root's process or MCP connection must route pushes to its main agent only (omp: #526; Claude Code does, Claude Code children below).
  - **Local children** (`src/local/mcp.ts`): a tool call carrying `_meta["io.github.nolnoch.grayboard/agent"]` (`GRAYBOARD_AGENT_META`, `src/shared/session_meta.ts`) is that subagent's call. It is a separate key from the hosted `sessionID` key, whose presence means "this session". The value is the harness's raw subagent id, checked as a hosted source id is (`validSourceId`). The child ID is `childSessionId` (`src/core/bindings.ts`), `idAddress(sha256(key + "\0" + raw))` over the root's secret session key, so only the root's process can mint it and a keyed restart keeps it; an unkeyed process keeps the key it minted. The root process resolves children through `ChildSessions` (`src/local/binding.ts`), which forgets one unseen for `DEFAULT_IDLE_SECONDS`, so a long session's finished subagents hold neither a place nor memory; a forgotten child seen again is the same child. First sight registers it (`registerChild`): an `ids` row copying the root's harness, cwd and keyedness, with `delivery='none'` and `root_id`, and a `bindings` row copying the root's liveness (pid, start time, harness pid and rule; no name, nothing attached), audited `id.child_seen` (actor the root, target the child, detail fields in `registerChild`); a row naming another root is `id_collision`, an ended one `id_ended`, and a new child while `MAX_CHILDREN` others were seen inside the idle window is refused `child capacity reached` (`childCapacity`). The `bindings` row is for older releases only (Mixed versions, below; #539): this tree never reads it as a session (`SESSION_SQL` leaves children out, so it is no live session, `unbound_sessions` row, name holder or reap candidate) and judges a child by its root. A child ends with its root, and the root's end drops its children's rows (`end`; Session end, below); the orphan sweep in `liveSessions` ends a child whose root an older grayboard ended or retention pruned. A root's row keeps its pid and start time for its life (a keyed restart re-attaches only under the same harness), so the copy stays true. Its `bind` and `unbind` are refused `child_session`; `whoami` answers the child's `id` with `root` and `child: true`, and the root's primary and aliases.
  - **Claude Code children** (#551, #195): Claude Code tells an MCP server only `_meta["claudecode/toolUseId"]` on a call; the agent's identity (`agent_id`) reaches only hooks. `PreToolUse` writes a JSON record `{agent: string | null, session?: string}` for the MCP side's atomic take (`src/shared/claude_agents.ts`, shared by local and hosted): a subagent id or `null` for the root, with the current conversation's `session` only locally. The reader feeds the agent to the same child path as `GRAYBOARD_AGENT_META`; local calls also cross-check the selected conversation, so an outgoing call never becomes an incoming root's call. `SessionStart` records the harness start time to fence recycled pids; `SessionEnd` preserves records on `clear`, which the MCP process outlives, and in the plugin on `resume` too (#588: `/resume` ends a session in the same process, so its sign-in link stays; the next `SessionStart` resets the facts). The sign-in link file is read as the control records are: bounded, regular, never through a link or FIFO. The plugin also records root model/effort facts (#545; `server-sessions.md`); the local hook writes neither. A call record has no age limit: `PreToolUse` precedes the permission prompt, and `tool_use_id` is never reused. Record/take pruning bounds derive from the shared module. Locally the pid is `bindings.harness_pid`, never `process.ppid` at call time. Setup installs user hooks; update/refresh replaces older hooks. The local CLI hook path loads lightweight record/control modules per tool call and loads title/database reads only for SessionStart. **A missing record is an error, never root attribution**: an installed hook's missing or unusable record refuses the call and audits `claude.agent_record_missing`, naming settings that disabled hooks (`hooksDisabledBy`). A setup predating attribution hooks alone acts as the root, audited `claude.attribution_off` and said in `whoami`/instructions. The hosted plugin always ships its hooks (`server-hosted-mcp.md` §3). Pushes remain root-only: Claude Code routes channel notifications to the main agent.
  - **`_meta` is harness-asserted.** Nothing on the bus checks which subagent made a call, so the key grants nothing beyond the root's powers; it only attributes the write. Text for a person says so: `viaLabel` (`src/shared/notifications.ts`) reads `subagent <id>, harness-asserted`. A Claude Code record is harness-asserted the same way, in a same-user directory: a forged one can only attribute a call to a child of the same root, since the child ID derives from the root's key and `registerChild` refuses a foreign `root_id`. The hosted plugin's `model` and `effort` files sit in the same directory with less protection: any same-user process can write any session's, so a forged one misreports that session's display facts, which grant nothing (#545).
  - **Local runner children** (#523 step 5; `src/local/mcp.ts`, `runnerRoot`, `runnerRootLive` and `childFallback` in `src/local/binding.ts`): a subagent that is a process of its own (pi-subagents' detached runner) can't call through its root's process, so it names its root by the harness's session id. Each `grayboard mcp` records `BUS_HARNESS_SESSION` as `ids.harness_session` (the pi adapter passes `getSessionId()`); one started with `BUS_PARENT_SESSION` (the pi adapter passes `PI_SUBAGENT_PARENT_SESSION` in a runner) is the child of the live root that recorded that id, only if the root's harness pid is among its ancestors: the id is harness-asserted, and the same pi session reopened in another process didn't start it. Its child ID is minted (the root's key is the root process's), registered by `registerChild` with its own harness, cwd and harness session, audited `id.child_seen` with `parent_session`. It has no wakeup listener, drain, name record or liveness of its own (its `bindings` row is the root's copy, as above), and reads the root's holds from `alias_holds` on every call, so it writes as whatever the root holds now. A subagent calling through it with `_meta` is the root's child, not the runner's, as hosted resolves a nested subagent to its root: a child's `root_id` always names a root. Its `BUS_IDENTITY` is the root's, inherited with the env: only a suggestion. pi-subagents' foreground children load no ambient extensions, so they have no grayboard tools.
  - **A runner child becomes its own session**, under a new ID (a child ID is never an address; the ended child row keeps `root_id`, the record of whose subagent wrote what): its `bind` promotes it in the transaction that takes the name (`acquireName`'s `promote`, audited `id.promoted`), after which it owns delivery as any root does (a runner acts on `triggerTurn`); with no live root, at start or because the root ended while the runner lives on (a detached runner outlives its parent), or when its root refuses it as a child at start (`child capacity reached`), it runs unbound, logged once and audited `id.child_fallback` with the reason. The root's liveness is checked at the start of each call (`runnerRootLive`): a call that starts after the root ended runs as the runner's own session. A call already past that check checks again inside its write's transaction (a DM, a delegation, a board tool; #557): if the root ended meanwhile, the write is refused `child_session` and stores nothing, and the next call runs as the runner's own session. Its own session is never a launcher, whatever `BUS_LAUNCHER` it inherited: pi-subagents doesn't load in a runner, so it can't spawn what a delegation asks for. Its `unbind` is refused `child_session` while it is a child.
  - **Where `via` shows:** every read that shows a message or post goes through `showMessage` (`src/shared/inbox.ts`) or `showPost` (`src/core/boards.ts`), which carry `via` and drop it for a root's own write; pushes and digests render it in `src/shared/notifications.ts`, `grayboard tail` in `src/local/tail.ts`, Slack in `src/bridge/relay.ts` (`slack-bridge.md` §2).
