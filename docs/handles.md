# Handles

```doc-meta
owns: names (aliases), binding and unbinding, acting addresses (`as`, reply and board senders), hosted name holds, identity suggestion, presence
invariants: at most one live session per handle; `bind` only adds a hold and `unbind` only removes one, so no operation moves a hold between live sessions; claims stay with the address they were taken under; an unbound hosted MCP session reads only; `grayboard human` and `bind` exclude each other
code-pointers: src/core/bindings.ts, src/core/addresses.ts, src/core/resolver.ts, src/local/binding.ts, src/local/human.ts, src/shared/namerecord.ts, src/shared/identity.ts, src/server/hosted.ts, src/cli/claim.ts
companions: sessions.md (acquisition, end, keyed sessions), child-sessions.md (subagent calls), boards.md (core shape), server-sessions.md (the server's bind)
```

A **name** (handle; an **alias**, #284) is durable: it owns the mailbox (queued DMs, cursors), claims and subscriptions, and its `aliases` row keeps the facts that outlive a session. Its address is a bare name locally (one implicit scope) and `scope/name` on a server: a person's `email/name` or a team's `team/name` (`addressParts`, `aliasScope`, `src/core/addresses.ts`); who an address acts for is the server's `Resolver` (`src/core/resolver.ts`), never its text, since an ID carries no email. A **session** is one `grayboard mcp` process: it has a secret session key, minted at start, and a **session ID** derived from it, `id:` plus 13 Crockford base32 characters (`idAddress`, `src/core/bindings.ts`; 1.x rows keep the same 64 bits as 16 hex, re-encoded on read). Its `ids` row keeps the facts that describe the running session; its `last_seen` moves on each local tool call, and on a server with the hosted session's activity. `id_collision`: local mode refuses an ID that already has an `ids` row, live or ended (the one exception: a keyed child re-attaching under its live harness, `sessions.md` §Keyed sessions), so an ended ID stays dead for the retention window; a server refuses one whose row belongs to another principal (`hostedRegister`, `server-hosted-ownership.md`). Messages and posts record the writing session in `sender_id`/`author_id`, provenance that reads and pushes leave out; a writer with no `ids` row (a server's in-process Slack bridge humans) records null. A child session's write also stores its ID in `via`, which readers see (`child-sessions.md`). It holds up to `MAX_HOLDS` names at once (`src/core/bindings.ts`; each hold is a socket or registry entry and a drain stream); `alias_holds` records the one session holding each name (#182). On a server each scope (a person's, a team's) has at most `ALIAS_SCOPE_CAP` names (#347, `src/server/alias_cap.ts`; `GRAYBOARD_ALIAS_SCOPE_CAP`, default 500; the Slack link's `human` isn't counted): a new name past it is refused `bad_request` by `bind`, `writes_as` and `grayboard identity create`, while an existing name binds at any count, so lowering the cap strands nothing. Fleet sessions mint a name per task and nothing prunes names, hence the generous default. A user frees a slot with `grayboard identity rm`, a team owner or admin with `grayboard team delete-alias`; either is refused `alias_held` while a session holds or writes as the name, and its queued mail and claims stay with the address, as on `unbind`. Status is the session's, shown on every name it holds.

## 1. Names and binding

- **At most one live session per handle.** Why: a worktree that inherited the repo's `.mcp.json` once started as the same handle, took over the wakeup socket and cursor, and Claude Code silently dropped its pushes because it wasn't loaded as a channel. The sender saw `delivered_now: true` throughout.
- **A session starts unbound unless `BUS_IDENTITY` is explicit** (`isExplicitIdentity`, `src/shared/identity.ts`). Binding delivers the name's queued DMs and hands it the name's claims, so that follows the agent knowing its task: a session started for a one-off question must not swallow mail meant for the long-running work. The resolved name (pin, repo directory, worktree suffix; below) is only the first **candidate**. A lane that should always come back under one name sets `BUS_IDENTITY` in its launch command. On a server the hosted adapters do the same (#443; `RootDelivery`, `adapters/hosted-core/src/root.ts`): Claude Code's plugin and the pi/omp extension bind an explicit `BUS_IDENTITY` (`configuredIdentity`: a bare name or `scope/name`, as a server bind takes) with `create: true` at a root's first start, unless it has remembered names (a resume) or a `/new`'s carried ones, which win and retire it; a later restart after the agent unbinds never brings it back. A tools-only Claude Code session binds it through its own connection, before its first call goes out, and a process that doesn't hold the session's delivery never does. A held or refused name is said once (log and next tool result) and not retried; an unreachable or signed-out try is said and tried again at the next start (tools-only: after sign-in, or before the agent's next call). Hosted OpenCode's start name is the plugin's `name` option instead. Exceptions: `BUS_HUMAN=1` (the Slack bridge's child) binds at start and exits if the name is held, since no agent reads its candidate list; a `BUS_PUSH=off` process never acquires a name and writes as the resolved one (on a server, a `writes_as` the server checks like a bind target). It is still its own session in both modes (`ids.delivery = 'none'`, `ids.writes_as`): its ID stamps what it writes, it ends like any session, and it receives nothing, so it isn't listed or offered names, and a DM or mention to its ID is refused `no_delivery` (`dms.md`). Locally its liveness is its own pid even when keyed (a key shared with a live session is `id_collision`).
- **An explicit name held by a live session starts the session unbound**, with the holder named in its instructions, instead of exiting: an MCP server that exits at startup shows the agent nothing it can act on. No auto-suffix (`repo-2`): minted names strand queued DMs (#104).
- **An unbound session acts as its ID** (#284), in both modes, with the full tool surface. A session's **address set** is its holds in bind order, then its ID (`sessionAddresses`, `src/core/bindings.ts`); its **primary** is the oldest hold it still holds, else the ID (`primaryOf`; `bound_at` is kept strictly increasing per session, so the order survives a restart and two binds in one millisecond). Writes go out as the primary unless the call says otherwise (below), and DM reads, acks, retracts, attachment reads and claim renew/release/ack match any address in the set, so a claim or reply taken before a bind still works after it. Locally it listens on `sock.<id>` from start plus one socket per held alias, and drains each address under its own cursor, pushing a board item that several addresses receive once (#361); a server session is registered under each address in its set. Why: gating an unbound session made a held alias block the agent outright; an ID is answerable, so its writes don't pollute the record. It holds no `alias_holds` row, so it isn't in `peers` (see `unbound_sessions`, below). `dm_send` reaches it by ID without the alias roster check, and the mode's `online` predicate counts it live for announcements and the queue rotation's live-first order.
- **Hosted MCP: unbound reads only.** An unbound hosted MCP session (`src/server/hosted.ts`) can call only `bind`, `board_list`, `board_read`, `peer_list` and `claim_list` (`UNBOUND_READS`, `src/server/application.ts`). It acts as no address: `board_list`, `board_read`, the board checks in `claim_list` and `peer_list`, and the board resources are judged by its user's principal (`seer`: open boards and the user's teams' boards), whether or not its request maps a session source (`server-oauth.md` §2), and touch no cursor, subscription or push (`ToolContext.reader`, `src/core/tools.ts`), so its rows show no mode and nothing unread (#410). Everything else returns `UNBOUND_ERROR`. It isn't in `dm_send`'s roster or in `peers`.
- **Unbound instructions.** While unbound, the instructions are the session's instructions as its ID plus a short paragraph (`unboundInstruction`) naming the ID and, locally, up to `MAX_CANDIDATES` free names: the suggestion first, then the user's other free names by pending work (queued DMs + held claims), then last seen, each with its counts and last place. Viewer, human and live names are excluded. On a server an unbound hosted MCP session lists its user's free names (`hostedCandidates`, `src/server/application.ts`; `hostedUnboundInstruction`, `src/server/hosted.ts`). `bind`'s result then adds only the name's own instructions, since the general ones were already paid (instruction text is paid by every session, AGENTS.md).
- **`bind_hint`** (#470, local mode): the first `dm_send`, `board_post` or taken `claim_take` of a session acting as its ID carries `bind_hint` once per session process, so a session that never read its unbound instructions learns a name would help peers read its writes. Never on a refusal (a claim held by someone else included). Hosted refuses unbound writes, so it has none.
- **`bind(name, create?, meta?)`.** A name never seen needs `create: true`, and the refusal lists the closest existing names (`closestNames`): a typo would otherwise create a fresh mailbox and the intended one's DMs would never arrive. Both modes: `identity_unknown` with `known`. The name is normalized like `BUS_IDENTITY` (#181); `human` and the declared human handle are refused (on a server, `human` in any scope). On a server the name may carry a scope (`team/name`, and so may `BUS_IDENTITY`): a bare name means the user's own person scope, and a team scope needs membership (`alias.bind`, `src/server/policy.ts`); service scopes wait for #270. Losing the membership takes the alias from the user's sessions that hold it, which keep their other holds and are told once (`alias_lost`, `aliasLostNotice`; `server-access.md` §1, `server-hosted-ownership.md`). The result carries what startup shows for the name (notices, claims split) and its instructions, as text and as `structuredContent: { name, instructions }` (the full set), which adapters read (`adapters.md`). A second hold adds one conditional instruction sentence naming the others and the send rule, paid only by a multi-hold session. `meta` sets the alias's one-line labels (`parseAliasMeta`, `src/core/boards.ts`; control characters stripped, `""` clears, an absent key is left), audited `alias.meta_set` (actor the signed-in user on a server, the session locally; the session is in the detail, #373), and a refused `meta` logs a `refused` binding event in both modes; who may set them is who may bind. `task` is a label, never a reference or task state (principle 7).
- **`bind` only adds a hold; `unbind(name)` only removes one** (#284 S1, S2). No operation in any mode moves a session from one name to another, hosted included (Hosted owner, below). Re-binding a held name is ok and logs nothing (it applies `meta` if given); `unbind` of a name not held is ok, so a lost answer is settled by calling again. `unbind` needs no access check (releasing is always allowed), is refused for a tools-only process and the human, and promotes the next-oldest hold (else the ID) when it releases the primary; its result says so and carries rebuilt instructions like `bind`'s. A hosted root that releases its last hold sends as nothing, so its result answers `name: null` and says the session is now unbound; the adapters' Controller reads that null as "forget the remembered holds", so a restart doesn't rebind the dropped name (#542). Locally it closes the name's socket before dropping the hold, so nobody can take the name while this socket answers and `lastWasRelease`'s window stays valid. On a server an unacked DM pushed to the name just before its `unbind` is redelivered to its next holder (at-least-once), and the name's in-flight board items are dropped so a later `bind` of it on the same session drains them again. `bind` and `unbind` serialise against each other and every tool call (`src/shared/bindgate.ts`, both modes): a call must not straddle a primary change. Tool descriptions never embed a name, since harnesses cache them.
- **Claims stay with the address they were taken under**, in every mode (#284 decision 8): ID claims stay renewable through the address set, and an alias's claims wait for its next holder; `unbind`'s result lists the ones it left (`leftNote`). One rule for both kinds of address, where moving alias claims but not ID claims would be two. `claim_take(as: B)` on a claim the session holds under A renews it under A: no transfer between a session's own addresses (#286).
- **`as`** (`AS_PARAM`, `src/core/tools.ts`) on `dm_send`, `board_post` and `claim_take` names one of the caller's addresses: a held alias, or its own ID. One resolver for both modes (`actingAs`): a bare name is the own scope's, anything outside the set is refused naming the set. A tools-only process's only `as` is its `writes_as`; the human's is its handle. Not on `delegate`: the requester is the primary. Every other board tool refuses `as` (`boardActor`), since a raw server call skips the MCP schema check.
- **A DM reply without `as` goes as the alias its parent reached** (`replySender`): the parent's recipient when the session holds it, else the parent's sender when the session holds it (its own thread), else the primary. Why: answering mail to B as A makes the peer's next reply go to A (`dms.md`), splitting the thread across aliases, and across sessions once B changes hands. The ID is excluded on purpose, so mail to the ID before a bind is answered as the alias, onto an address that outlives the session. A parent whose alias the session no longer holds is refused as now, never sent as the primary. The send result carries `sent_as` when the sender isn't the primary; a DM push and `dm_inbox` row carry `to` on the same rule.
- **A board call without `as` acts as one address that can see the board** (`boardAddress`, `src/core/boards.ts`; #284 S14, #366): `board_read` and each `board_list` row take the first subscribed address with unread posts, else the first subscribed; `board_subscribe` the first subscribed; `board_archive` as `board_read` (#848); each then falls back, as `board_post` always does, to the first address (in set order) that can see it. One call has one acting address, so access, subscription, cursor and outbox are all that address's: reading every board as the primary would leave another address's cursor still and re-push its posts. Unread-first, so repeated reads drain each subscribed address in turn; `off` removes one subscription per call.
- **Hosted owner** (#226; `src/server/hosted.ts`): a native MCP session holds names in the `alias_holds` table (`server-sessions.md` `bind`, `server-hosted-ownership.md`). Its root starts unbound; an explicit bind holds the name independently of delivery. It holds up to `MAX_HOLDS` names in any scope it may act in (#451): `bind` adds a hold, `unbind` releases one, the oldest hold is the primary it sends as, and claims stay with their address. A bind that adds a hold or an unbind that releases one bumps the generation and closes the lease, so delivery restarts on the new hold set; the last `unbind` leaves the root unbound but owning, with no lease. Its ID never ends through `endSession` (a released child's does, and an ended ID that returns is reopened: `server-hosted-ownership.md`): ending the ownership releases every hold, and a revoked hold is released alone (mechanics: `server-hosted-ownership.md`). Registered children are child sessions (`child-sessions.md`): they act under the root's current holds and cannot take over root controls. Human enrollment approves a receiving root, not a name or ownership. `delivery_open` attaches a push target to the bound root; a bound root without a lease still excludes contenders but leaves DMs queued. Ownership history, liveness and lease fences belong to `server-hosted-ownership.md`.

- **`grayboard human` and `bind` exclude each other** in one transaction (#79): `declareHuman` refuses a bound name; bind refuses the human handle and `human`. A `BUS_HUMAN=1` session refuses `bind`, `unbind` and an `as` other than its handle (#363), as the server's `attachHuman` session does (`src/server/application.ts`): the human handle is fixed.

## 2. Identity suggestion and CLI identity

- **Worktree suffix** (`src/shared/identity.ts`): the suggestion inside a linked worktree appends the worktree name to the base identity (`be` → `be-stream`; a worktree already named `be-…` is used as-is), so an existing worktree lane sees its own name, mail and claims first. An explicit `BUS_IDENTITY` — one that differs from every pin the repo carries (`.mcp.json`, `.omp/mcp.json`) — takes no suffix and is lowercased and validated with the server's rule (#181). A `BUS_IDENTITY` re-delivering a pin (harnesses load pins into env) is not explicit. A `BUS_IDENTITY` from a user-level registration (`claude mcp add -e`, pi's user `mcp.json`) is one name across every worktree: a second session on it starts unbound. Decided from the starting directory only. Without `BUS_IDENTITY` the base is the repo directory name; if `BUS_IDENTITY` is unset, the server reads a pin from the repo's `.mcp.json` itself, so the suggestion doesn't depend on a harness's config precedence. Under omp (`BUS_HARNESS=omp`, which omp's local adapter sets on its `grayboard mcp`) it reads the `grayboard` entry's pin in `.omp/mcp.json` after `.mcp.json`'s (`pinnedIdentity`), enabled or not: omp ran that entry before #523 and its pin named the session, and the adapter now refuses it enabled. Other harnesses never read `.omp/mcp.json` (#182).
- **Mixed-case handles from 1.x move at open** (#216, `src/local/handle_case.ts`; local only, a server always lowercased). A 1.x bus can hold `Gray` (`BUS_IDENTITY` was literal before #181), which no session can bind since. Every local open, in its schema transaction, moves each such handle's rows in every address column to the lowercase name, audited `alias.case_moved {from, merged}`, with a stderr notice after commit (once per name), and the opener wakes the lowercase name (`ended.wake`), so a live session gets moved DMs at once (#1189). Where the lowercase name exists (a v2 session made it) the two merge: in name-keyed tables the lowercase name's row wins (its alias keeping the old one's queue opt-out and later sighting); the two DM cursors become the lower one, after each name's DMs up to its own cursor are stamped delivered, so neither name's undelivered DMs are skipped and delivery skips what is stamped. Spellings move most recently seen first. A merge that would change who a name is (a human with a non-human by `aliases.human`, an agent named `Human` since `human` is reserved, a name invalid lowercased) stays put, audited `alias.case_collision {from, reason}` with a notice, once while that row lasts. Bodies, claim keys and notes stay as written. It runs every open since a live 1.x `Gray` writes the old name again (merged at the next open; until then that process reads an emptied mailbox, so stop 1.x sessions before upgrading).
- **CLI commands act as the bound session's primary** (`actingIdentity`, `src/cli/claim.ts`), local mode, with its address set for release and renew (`localAddressSet`): after `--as` and an explicit `BUS_IDENTITY`, the live bound `bindings` row whose harness pid is an ancestor of the CLI, narrowed to this checkout when several match, else the one in this checkout. None, several or unbound → refused, pointing at `--as`. Why: resolving from cwd would act as the repo name while the session holds another, and the claim lands on the wrong handle silently. Server mode has no local rows and keeps resolving from cwd.

- An identity is the agent's role in the repo, not its harness: Claude Code and omp in one repo get the same suggestion (unless the repo pins a name only in `.omp/mcp.json`, which only omp reads), and whichever binds it second is refused.

## 3. Presence

- **Presence (`peer_list`)** is a query, not a feed: nobody is notified when peers come and go. "Online" means a live session will receive pushes, so a tools-only `BUS_PUSH=off` server counts only via the push owner. Local mode probes each wakeup socket; the server checks live delivery sessions. Live unbound sessions are listed apart, in `unbound_sessions` (session ID, place, and the status set as the ID; omitted when empty and on a board-scoped call; never a tools-only process or a `tail`), because every global `peers` entry must hold an alias; every row of the caller's own addresses carries `self: true` and is online. `you` is the primary (while unbound, the session ID). A board-scoped call lists a subscription taken as the ID under the session's primary hold only (a name's own subscription wins), so an ID subscription is one row and one queue lane, not one per hold (each alias's own subscription is its own), or as the ID with its session's place and status, as the queue rotation does (`queueLanes`). Local mode reads them from `bindings`; the server from its durable hosted root rows (#475; not only roots with a request in flight), one row per session ID (#489), scoped to the caller's own user, since `where` describes their machine. On a server a name's `last_seen` is its holder's last request before `delivery_release`, not the release: hosted has no close frame (#463). Locally a call moves its addresses' `last_seen` at most once per 30 s each, and `board_list`, `peer_list` and `claim_list` run in a deferred transaction, so a session's read within 30 s of its last call waits on no other process's write lock (#148 18); a child session's `last_seen` moves at most once per 30 s too, and `peer_list` ends a dead session it finds only while the write lock is free, leaving it otherwise to a later call (#894). `peer_list(board)` lists that board's subscribers; a team board is the team roster. `peer_status` text is cleared when a new session starts, except that a hosted lease reopened within its deadline keeps it, and a local restart that takes back a name whose latest binder was its predecessor (from the name record, `src/shared/namerecord.ts`, or the conversation snapshot) carries the predecessor's status over (`inheritStatus`, #211); when another session bound every one of those names in between, the restart keeps the names but not the status, and its start notes say so if there was one (#260). The `peer_status` queue opt-out (`aliases.queue_off`) persists across sessions until set `on`; `peer_list` shows it as `queue_off`. Rows carry `id` (the holder's, or an offline alias's last binder's once that session ended), the session's self-reported facts (`harness`, `model`, `effort` from `BUS_MODEL`/`BUS_EFFORT` at launch in local mode, or the latest a hosted session's requests report (#364: `_meta` keys in `src/shared/session_meta.ts`, kept as sent by `hostedFacts`, never cleared by a request that omits them, restated by a new ownership); an offline alias shows its last binder's, from that ended session's `ids` row, while status shows only while held) and the alias's `meta` labels. Labels, and the session's facts (`where`, status, `harness`, `model`, `effort`, `launcher`), ride on a row only when the caller's session may act in the alias's scope, or for an ID row in its principal's (`Access.seesAliasMeta`, judged for the session's ID, not its primary, which may be a team alias): a team's task label or a private board's name must not reach a non-member, and another user's agent shows its handle, `id` and presence, never their machine, branch or work (security audit F-12). Locally every row passes. A team's alias isn't listed at all to a caller outside the team (`Access.seesAlias`, `alias.see`, [#348](https://github.com/nolnoch/grayboard/issues/348); the session's own rows always are), in the global list, a board's roster, the offline count and a `board_post` result's `notified`/`deferred` (which still deliver to it; a full `@team/name` mention of it comes back in `unresolved`, in its place, as a name nobody has, #871), a claim it holds shows `holder` and `note` as null (`claim_list`, `claim_take`'s `held_by`, HTTP `/api/claims`; `claims.md`), and a DM or delegation to its exact handle is refused as for a name nobody has, except a reply in a DM thread with it (#1014, `server-operations.md`), a cut made before the others; its authored posts and DMs still show the handle. `match` filters rows (`MATCH_KEYS`; exact, case-insensitive, ANDed; `scope` is an alias's scope, or an ID's principal only for a caller that may act in that principal's scope, since an ID row doesn't show it) after that cut, so filtering can't probe a hidden label or a session's owner; it filters `unbound_sessions` too.
- Unknown recipients and mentions that match nobody are errors or `unresolved` that point at `peer_list`, never silent success.
