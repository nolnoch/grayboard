## 1. Embedded authorization boundary

`src/server/app.ts` mounts `src/server/oauth.ts` on the same listener before the retained HTTP router; only the new hosted MCP boundary adopts its OAuth principal. The CLI's API token stays independent of OAuth grants (it authenticates the retained HTTP API, never `/mcp`), though `grayboard login` obtains it through this AS (§2), so the server's IdPs are the only sign-in. An upstream IdP proves an account, never authorizes a downstream client: upstream state, PKCE and verified ID-token nonce are separate from downstream state, PKCE and explicit one-use consent. The upstream leg goes through the providers config lists (`defaultProviders`, `src/server/idp.ts`) or `OAuthOptions.providers` injects: a provider builds the authorize URL and returns an identity only after every check (architecture.md §3, Login), while `oauth.ts` keeps upstream state, PKCE, the nonce and the callbacks. Pending browser flows intentionally fail across process restart; issued codes and grants survive through `Repo.oauth`.

**Several providers** (#928). With one, authorize redirects upstream at once; with several and no browser session, a chooser links each, in config order, to `/oauth/upstream`, which finds the flow by the binding cookie and only then creates the upstream state, verifier and nonce; choosing again replaces them. Each provider has its own callback, `/oauth/<id>/callback` (Google's never moves: every deployment registers it), and the flow's upstream state records its provider: a callback on another provider's path is refused, its state spent, before any exchange. Per-provider redirect URIs and provider-bound state are the mix-up defence; a callback's `iss`, when present, must equal `provider.issuer` before state is spent (not relied on: Okta's discovery omits it). A browser session names a user, not a provider. Once the callback holds its flow, a refusal returns `access_denied` to the client with a fixed reason (`REFUSED`); a provider whose authorize URL fails (discovery) returns `temporarily_unavailable`. Audits `oauth.upstream_denied`, `_failed`, `_authenticated` and `oauth.domain_refused` carry `{provider}`; a failure logs only the error's class, naming the OIDC stage (`OidcError`'s subclasses). No upstream client is a downstream MCP client registration.

Public clients register through HTTPS Client ID Metadata Documents, but only the document URLs in `GRAYBOARD_OAUTH_CIMD_CLIENTS` (default OpenCode's alone; security audit F-16): any URL would otherwise be a client whose self-declared redirects receive authorize errors (an open redirector) and whose self-declared name heads the consent page. `resolveClient` refuses an unlisted URL before any DNS or fetch; consent for a metadata-document client is headed by the document's host, with its name quoted as a claim; operator registrations remain available for pinned public or confidential clients. `src/server/oauth-cimd.ts` validates the exact client ID, registered redirects and public-client authentication before consent. All DNS answers must be public unicast; the HTTPS connection pins one validated address while retaining TLS hostname verification. Redirects are not followed. Bounded fetches, coalescing, concurrency, positive/negative caches and the `/oauth/*` rate limits bound metadata abuse. Dynamic client registration is not exposed without a demonstrated supported-client requirement.

Redirects match their registration except ephemeral ports on registered HTTP loopback callbacks (not `grayboard-admin`'s); host, scheme, path and query remain exact, distinguishing localhost from literal addresses. Code redemption binds the actual selected redirect including its port. Confidential authentication does not waive PKCE. Protected-resource discovery advertises tools and delivery so one native grant can support both; scopes have no hierarchy. Missing resource selects the single configured resource server, but an explicitly wrong or empty resource fails, and code exchange and refresh preserve the original audience binding.

The configured public base is the exact issuer identifier, including any explicit default port; `iss` must never be URL-normalized. The resource identifier is separately URL-serialized to one canonical audience, so default-port spelling cannot fragment client resource bindings; alternate spellings are not additional audiences. Redirects, metadata and Origin checks derive from configuration; request Host and forwarding headers never select them. Prefix-preserving and prefix-stripping proxies can forward OAuth routes, but must also forward the RFC well-known path-insertion locations. Production requires HTTPS; the only HTTP issuer exemption is explicit loopback development. Opaque HttpOnly cookies are hash-only capabilities, not signed identity claims. Browser session rotation, request/browser/session binding, one-use CSRF and mandatory same-Origin consent precede atomic code issuance. The remote completion page is an ordinary registered HTTPS callback for full-URL paste, not an out-of-band grant, and never redeems codes; a CIMD client can't register a redirect on the AS's own origin, so only operator-registered clients use it.

OAuth extension parameters are ignored only after bounded syntax, encoding and duplicate checks; they never become stored bindings or redirect fields. Empty OAuth values are omitted only after duplicate checks; omitted scope never expands beyond persisted consent. Nonempty credentials and grant bindings still belong only in their prescribed locations; Basic authentication cannot be mixed with a nonempty body client ID. Authorization errors redirect with state and exact issuer only after an unambiguous registered client/redirect pair and valid state are established; malformed or untrusted requests stay local, and database exceptions never become client redirect errors.

Authorization codes and refresh tokens consume atomically with their successor records. Recognized code or refresh replay commits whole-family revocation; a concurrent loser can therefore invalidate the legitimate winner. Clients must single-flight refresh and reauthorize after ambiguous results, not retry old credentials. Stable grants retain original refresh permissions; each access token records its actual requested subset. Scope omission on refresh restores original permissions, not merely the previous access subset. IdP re-auth or re-check may refuse a refresh, unspent ([server-offboarding.md](server-offboarding.md)). Access revocation is individual; refresh revocation is family-wide; the retained `/api/auth/logout` touches no OAuth grant or browser session. Disable and admin all-session revocation invalidate OAuth grants so reenable cannot resurrect them; on Postgres a mint racing either is ordered by a lock on the user's row ([D3](future/postgres-server.md#d3-database-invariants-move-into-sql)). Lifetimes derive from `src/server/oauth-types.ts` (`OAUTH_TTL`); the input and entry checks, stored-field whitelists, the rotation clamp and the capacity limits from `src/server/oauth-rules.ts`, one copy all backends import. What reads rows stays in each backend's SQL: user, grant, token and secret liveness, the counts those limits bound, and a run token's expiry clamp, computed in its insert. Spent lineage outlives sliding expiry through the absolute family deadline.

Consumers must authenticate every HTTP method and revalidate the actual access hash and deadline, not only the grant ID, before dispatch and during long-lived delivery. `isAuthorized` covers individually revoked access as well as disabled users and revoked grants. Database failures propagate from authentication and become generic server errors on AS HTTP operations, never invalid-grant guesses or successful revocations. Closing this service clears its bounded ephemeral maps and housekeeping timer and closes the CIMD resolver (aborting in-flight fetches) only; server shutdown first cancels MCP exchanges and contexts, then closes OAuth before callers close the database. Rate limits key by the auth gate's client address (`src/server/client_addr.ts`, so a trusted proxy's `X-Forwarded-For` counts), check the address bucket before the global one, and spend neither until both pass, so one address can't drain the org-wide bucket. An IPv6 caller's address bucket (its /64) has a /48 sibling (#274, scope `site`, and `token_site` for token and revocation posts), `SITE_LIMIT_FACTOR` (4) times its size with its own 10,000-key cap, checked after it and before the global one and spent with it; a new /64 bucket is made only by a spend, which costs its /48 a token, so a prefix rotating its /64s holds a bounded number of buckets and can't fill the address cap. IPv4 has no /48 tier. Token and revocation posts have their own address bucket of the same size and spend it and its /48 sibling, and only those, when a request carrying grant material (a code, refresh token or revocation token, or an Authorization header) is refused with a 4xx (or, its listed client's document unavailable, a 503), except a service credential's `slow_down`: its secret checked, it is refused for its own mint bucket or cap, so it spends neither (#1244) and a fleet behind one NAT retrying through it can't block other users' refreshes from that address; they neither check nor spend the global bucket, so refused refreshes from a few addresses can't drain it and block every sign-in in the org, and a drained global bucket doesn't block token refresh (F-18, #931). Their org-wide bound is on their writes instead: a `token_refusal` bucket the size of the global one is spent at each refusal past grant material, a credential's `slow_down` streak's first included (its retries are not, below), never checked before the work, and while it's empty the refusal answers as usual but writes no `oauth.request_refused` row, nor its client's CIMD row (`oauth.cimd_refused`, `oauth.cimd_failed`; #933, which also charges an outage's post to its address); its streak's `oauth.rate_limited` and `oauth.rate_limit_ended` rows (scope `token_refusal`, `refused` counting the refusals that wrote no row) record the run. That holds past the address limiters' 10,000-key cap, where a new address is neither charged nor refused; a foreign Origin, a malformed request or one with no grant material fails before client authentication (so before any CIMD fetch), uncharged and unaudited, so a cross-site form post can't lock an address out of token refresh (#283). A browser-route GET (every `/oauth/*` GET) whose `Sec-Fetch-Mode` is present and isn't `navigate` (an `<img>` or a `no-cors` fetch another site's page makes a visitor's browser send) is refused 403 before the charge and before any client lookup, uncharged and unaudited, so such a page can't drain an address's bucket and block its sign-ins; a request with no `Sec-Fetch-Mode` (not a browser) is charged on entry as before (#404). Every other `/oauth/*` route spends on entry.

## 2. Clients and sources

**Source mapping** (#414). `oauth.authenticate` resolves the grant's client to one `_meta` source key, `OAuthPrincipal.sourceKey` (`sourceKeyFor`, `src/server/oauth-config.ts`): OpenCode's CIMD client maps `ai.opencode/sessionID`; the built-in clients (below) and an operator client (`GRAYBOARD_OAUTH_CLIENTS`) with `sessionSource: true` map `io.github.nolnoch.grayboard/sessionID`; every other client, every other CIMD client included, is unmapped and gets the unbound reads only. A mapped client ignores the other key; a missing or invalid value leaves the request unbound (reads still run), and `bind`/`delivery_open` refusals name the client's own key. `sourceContext` (`src/server/hosted.ts`) is the one mapping for `_meta`, child registration and the byte routes. Why opt-in: a CIMD client gets both scopes on user consent, so mapping every client would let a consent-phished client bind names, send DMs and take delivery as the victim; the operator config is the trust decision. `sessionSource` is refused on any `https:` client ID, OpenCode's included: CIMD resolves only `https:` IDs and a grant keeps only the client ID string, so a grant consented under a metadata document never turns write-capable because an operator later registers the same ID. It is also refused on a client ID over `SESSION_FACT_MAX` (`src/shared/protocol.ts`): `harnessFor` labels an operator client's sessions with its exact ID, and `registerId` would cut a longer one. Config is read at startup, which logs the opted-in IDs and the built-in ones. Removing `sessionSource` unmaps the client's requests after restart (writes stop; its tokens keep reads until they expire) but ends none of its hosted sessions: bound roots keep their names until the lease deadline, an idle probe or a competing bind, since `sweep` idle-ends only unnamed rows. To end them at once, revoke the grants or disable the user.

**Built-in clients** (#429). Public clients defined in code (`BUILTIN_CLIENTS`, `src/server/oauth-config.ts`), reserved as the constant IDs of the hosted adapters (#279, #280, #281). Each is `none`-auth with refresh and both scopes, redirects only to `/callback` on `127.0.0.1` or `[::1]` (not `localhost`) on any port (`matchesRedirect`, RFC 8252), maps the generic key, and takes its harness label from the same table. They join the AS client map ahead of operator clients, so the consent page shows no "Unverified client" line (the local-callback line still shows), and AS metadata lists their IDs as `grayboard_builtin_clients` (an RFC 8414 §2 extension) so an adapter can detect an older server before it opens a browser. Why in code: operator registration would be a manual step per server, and CIMD can't carry them: a CIMD ID must be the https URL of its own `application/json` document (`src/server/oauth-cimd.ts`), which raw.githubusercontent.com (`text/plain`) can't serve and this repo has no Pages site for. Trust matches OpenCode's CIMD client, whose document is loopback-only too: a consent-phished code lands on the victim's own machine, so exploiting it needs code already running there, including another local user on a multi-user host, since binding a loopback port needs no privilege (RFC 8252 §7.3, §8.1). Map membership is load-bearing: token refresh and revocation authenticate the client through the map (`clientAuth`, `src/server/oauth.ts`) and refresh needs its `allowRefresh`, while write capability and the harness label come from the code table (`sourceKeyFor`, `harnessFor`). The CIMD same-origin redirect check applies only to fetched clients. Built-ins can't be disabled per server: an operator entry reusing one of their IDs stops startup (`parseOAuthClients`). Before #429 an operator client could hold one of these IDs, and a grant keeps only the client ID, so its grants would become a built-in's (write-capable, refreshed with no secret). So the first start that knows the built-ins, once the config parses and before it serves, revokes every grant and drops every unredeemed code under their IDs, audits each grant as `oauth.builtin_client_grant_revoked`, and records the cutover in `server_state` (`revokePreBuiltinGrants`, `src/server/db.ts`). Later grants under these IDs are the built-ins' own; since it runs once per database, a downgrade that re-registers one of these IDs isn't caught on the next upgrade.

**CLI login** (#928). `grayboard-cli` (`CLI_CLIENT`, `src/server/oauth-config.ts`) is a public client with the built-ins' loopback redirects and PKCE, `allowRefresh: false` and the single scope `LOGIN_SCOPE` (`grayboard:login`), which redeems for an API token, not a grant. It is its own constant, not a `BUILTINS` row: no source key or harness, and metadata names it as `grayboard_cli_client`, not in `grayboard_builtin_clients`. **Invariant (R3): no client but `grayboard-cli` can obtain `grayboard:login`, and the scope never travels with another.** Likewise `grayboard:admin` for `grayboard-admin` (server-admin-dashboard.md §1). A built-in, CIMD or operator client holds only `OAUTH_SCOPES`, which never contains it, so `client.scopes` refuses it `invalid_scope` at authorize; `scopes()` admits it only alone, so `grayboard-cli` can't mix it or ask for anything else; an operator entry using the ID stops startup (`parseOAuthClients`); and neither `scopes_supported` nor protected-resource metadata advertise it. Why: the scope mints a CLI session for whoever approves, so a client that could add it to a grant would turn one consent into a long-lived API token. The CLI omits `resource`, and the code is stored with the MCP resource as every omitted resource is. The consent page shows "a grayboard CLI sign-in" in place of the resource line. The token endpoint sends a login code to `redeemLoginCode` (`src/server/db.ts`), which in one transaction checks it with the checks `redeemCode` shares (`presented`, `usable`: binding, PKCE, expiry, an active user), creates the session (labelled with the request's user agent) and stamps `oauth_codes.session_id`; the response is `{access_token: gbrd_v1_…, token_type, scope}`, no refresh or `expires_in`, since a CLI token expires only by idleness (architecture.md §3). It audits `oauth.session_issued {client_id, token_session}`. A spent login code is kept while its session lives (`cleanup`), so a replay finds it, revokes the session and audits `oauth.code_replay_revoked` (warning), as a grant code's replay revokes its grant. `redeemCode` refuses a row whose `session_id` is set or whose scopes include the login scope, and `redeemLoginCode` refuses a grant code, so neither kind redeems as the other. An earlier operator client may have held the ID, so a second once-per-database cutover under the `server_state` key `builtin_clients_cli` revokes its grants and unredeemed codes, as the built-ins' did. An old CLI (`/api/auth/exchange`) can't sign in here; this CLI refuses a server without `grayboard_cli_client` before opening a browser (#991). Each updates (principle 12).

**Service credentials** (#270 D2, D3). A service's non-interactive client: `svc_` and 32 hex digits, one `service_credentials` row, its own `oauth_grants` row (the service, the MCP resource, both `OAUTH_SCOPES`) whose `expires_at` is the credential's expiry (far-future when none), and up to two live secrets in `service_credential_secrets`, stored as SHA-256 only and shown once by the admin route (`server-access.md` §1). Why the expiry lives on the grant: the access cache checks `grantExpiresAt` and the generation triggers cover `oauth_grants`, never `service_credentials`. `resolveClient` reads a `svc_` ID from the store (one indexed read, before CIMD); `parseOAuthClients` refuses the prefix, since the startup map would shadow it. `clientAuth` takes its secret from the Basic header only and compares every live secret in constant time with no early exit; the match names the secret the token is minted under. `grant_type=client_credentials` is that client's only grant and no other client's (`unauthorized_client` both ways), and `/oauth/authorize` refuses it before the redirect check, so codes and refresh never reach it. The mint is one `INSERT … SELECT` (`mintServiceToken`, `src/server/db.ts`) that re-checks credential, grant, secret and service and holds the per-credential mint bucket (per minute) and the unexpired-token cap, so a revoke or disable between the secret's check and the insert still refuses (`testPause` `oauth:mint:before-write`). That is enough under SQLite's single writer only: on Postgres the mint, rotation's two-secret count and both revokes lock the credential row first (`future/postgres-server.md` D3), and `findActiveAccess` refuses a token whose secret is revoked; the row's expiry is `min(now + min(token_seconds, ceiling), grant expiry)`, the ceiling re-read at each mint. The answer is a bearer with no refresh token (RFC 6749 §4.4.3), audited `oauth.token_issued {client_id, secret_id, expires_at}`; capacity answers `slow_down` 429, a dead credential or secret `invalid_client` 401, both audited by the token route's rules (§1), and only `invalid_client` charged to the address (#1244). A credential's `slow_down` also holds it in memory (`mintBackoff`, by client ID) until one mint interval at the current rate has passed: its retries until then answer `slow_down` with no write transaction, and a streak, refusals no more than a minute past that time, writes one `oauth.request_refused` row and spends the `token_refusal` bucket once, so a valid-secret retry loop can't cost a write per post or drain the org's refusal rows (#1244 M-1). A success or the credential's own revoke ends the hold, since a revoke can free the cap; the map is per process. A held credential's first mint past its hold is a probe and is single-flighted (`probing`, #1282): a marker set before the store's write and cleared on every outcome makes requests that arrive during its round trip (network I/O on Postgres; SQLite has no such window) answer the hold's own uncharged, unaudited `slow_down`, the answer the probe most likely gives, so a coordinated burst at a hold's expiry costs one write and at most one row. A credential with no entry isn't single-flighted, so a fleet's concurrent first mints all reach the store; the first refusal among them sets the hold, and the rest of the wave, judged against it, write no row (#1287); the sweep drops an entry a minute past its hold, returning the credential to that state. Run tokens are ordinary access rows (`oauth_tokens.secret_id` names their secret) re-read on every call, so lifetime only bounds an unnoticed leak; revoking a secret revokes its tokens alone, revoking the credential revokes its grant and ends its sessions in that transaction (`revokeGrant`), and `cleanup` drops a revoked secret once its tokens are gone. A credential's `source` (`generic` or `opencode`), immutable like the principal's kind, rides the cached access read (`findActiveAccess` joins it), and `sourceKeyFor` and `harnessFor` take it in place of the client table: no query on the hot path. A `generic` one's session takes its harness label from the request's declared client (`server-sessions.md`, #1298). Two credentials of one service are two clients, so their session IDs are each other's `hosted.other_client`. Hosted `whoami` reports `principal_kind` (`user` or `service`, the authenticated principal's): OpenCode V2's static mode, which takes the run token as its native entry's bearer header from the launcher's environment, enrolls a root without a human only for `service` (`adapters-hosted-login.md` §OpenCode V2 static mode). `/oauth/revoke` takes a run token from its own credential's client (Basic auth, the same as the mint) and revokes that token alone, so a launcher ends a run's token when the run ends; another client's request is answered 200 and revokes nothing (RFC 7009), and the token's sessions are refused on their next call, since access is re-read on every call.

**Delivery declaration** (#429). A generic-key client may send `_meta["io.github.nolnoch.grayboard/delivery"] = {mode: "push" | "poll", source}` beside its session key on any native request (`deliveryDeclaration`, `src/server/hosted.ts`; `source` format: `DELIVERY_SOURCE`). It selects a bound session's `initialize` instructions (`hostedBoundInstruction`; an unbound session gets `hostedUnboundInstruction` whatever it declares) and the bind result text. `push`: the channel lines (`channelInstructions`, `src/core/tools.ts`) carry the declared `source`, the tag the client renders, and the bind result has no delivery note: a push client must open delivery right after bind and report its own failure. `poll`: `initialize` keeps the polling line, both texts add `POLL_NOTE`, and neither carries channel lines. Absent (any bound session that sends none, OpenCode's included): a bind result with `DEFAULT_CHANNEL_SOURCE` channel lines and the `delivery_open` note; the `initialize` text follows the ownership's lease (#531): open, those channel lines; none, the polling line and the same note. Why: a push client forwards the server's text verbatim, so the text must match the delivery the session actually has. A malformed declaration refuses the request (HTTP 400 `bad_request`) before admission, never falling back to text for the wrong delivery. Only a generic-key principal's declaration is read, so an OpenCode session always gets the absent text, and the subscriber role ignores it. It changes text only: it grants nothing, so nothing audits it. Local sessions pass `DEFAULT_CHANNEL_SOURCE` through `boundInstructions` (`src/core/bindings.ts`); it must equal the MCP entry name `grayboard setup` writes, since Claude Code sets a pushed tag's `source` from the server's configured name.
