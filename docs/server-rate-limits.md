# Rate limits

```doc-meta
owns: the server's rate limits: binds per user, authentication failures per client address and /48, the refused-token memo
invariants: authentication failures are limited per client address and charged only on a refused presented token or a sign-in call, so valid traffic never touches a bucket, and a refused token repeated on a path is answered from memory, uncharged, for 60s
code-pointers: src/server/rate_limit.ts, src/server/auth_gate.ts, src/server/client_addr.ts, src/server/http.ts (signInRoute, chargeRefusedToken, replayRefused)
companions: server-access.md (authorization), server-hosted-ownership.md (the hosted request buckets), server-sessions.md (bind)
```

- **Binds are rate-limited per user** (#210, `RateLimiter`, `src/server/rate_limit.ts`): a token bucket per user (sizes: `src/server/config.ts`, `GRAYBOARD_HELLO`, named from when a hello spent it too), spent by every `bind` and checked before anything reads or writes the database. Over it, a bind gets `rate_limited` with `retry_after_ms` (the wait until a token is back). Why: a bind creates its alias lazily, so a client looping on it could load the server and mint rows without bound. The Slack bridge's in-process connections are exempt. A run of refusals lasts until the user's bucket is full again, seen by the next bind or by the 30s limiter sweep (`sweepLimits`, `src/server/app.ts`, which drops refilled buckets); ending it at any accepted bind would let a loop just faster than the refill start a run, and an audit row, at every refusal. Each run logs one line and writes one audit row when it starts (`bind.rate_limited`, detail: the tripping session ID, the alias it bound, and `retry_after_ms`) and one of each with its count when it ends (`bind.rate_limit_ended`, detail `{refused}`). A hosted bind spends the bucket inside its transaction, which a refusal rolls back: the run's row is written there, where a committing bind keeps it, and again after a rollback through the session's `afterRollback` (#467), so each row is written once either way.
- **Authentication failures are rate-limited per client address** (#240, `AuthGate`, `src/server/auth_gate.ts`, on the same `RateLimiter`): every presented token the server refuses with 401 on the MCP, OAuth attachment byte (#401) or `handleHttp` path (the OAuth AS routes authenticate clients by secret, never a bearer, and answer before charging, under their own OAuth limiters: per address and global, with token and revocation posts per address only (`docs/server-oauth.md`)) and every call to a sign-in route (`signInRoute`, `src/server/http.ts`, one table that both dispatches and decides charging; charged on entry; a disabled route, such as dev-login with dev auth off, dispatches to 404 uncharged) spends a token from the address's bucket. An HTTP 401 is charged on the MCP, byte-route or `handleHttp` response when the request carried a bearer token (`chargeRefusedToken`), so a protected or unknown path with a bad token costs one, while the public routes, dispatched before `requireAuth`, cost nothing unless they are sign-in routes. A request with no token costs nothing: a web page can make a browser send one cross-origin (an `<img>`), but can't attach `Authorization` without a CORS preflight, so charging them would let any page lock out everyone behind its viewer's NAT. For the same reason a sign-in route takes only `Content-Type: application/json` (`isJsonRequest`) and answers anything else 415 `unsupported_media_type`, uncharged: a cross-origin form post needs no preflight, a JSON one does. While it's empty, `fetch` answers every request from the address, `/healthz` included, with 429 `{code: "rate_limited", message, retry_after_ms}` and `Retry-After` (whole seconds, at least 1), before anything reads the database. 403s, 404s and the 429s themselves cost nothing, and valid authenticated traffic never touches a bucket: a check allocates nothing, so the map holds only addresses that have failed, dropped by the 30s sweep once refilled, and capped at 10,000 (past the cap a new address is neither charged nor refused, with a log line and an `auth.rate_limit_full` row at most once a minute; a flood spread across addresses belongs at the network edge). Why failures only: a lookup that succeeds is bounded by legitimate use and the bind limit, and charging only failures keeps a stale-token client behind a shared NAT from blocking its neighbours until it fails the whole burst; hosted-core stops retrying a refused token, which keeps it from getting there. A client that keeps retrying anyway is answered from memory (#923): `chargeRefusedToken` keeps each 401 it sees for a presented token (status, headers and body, so `/mcp` keeps its `WWW-Authenticate`) for 60s, keyed by one SHA-256 of the path, query and `Authorization` header as sent (a fixed size whatever the client sends, and a token in another shape is another entry), at most 10,000 entries with the oldest forgotten and the expired dropped by the 30s sweep. The entry is stored before the body is read and a token already remembered isn't charged again, so requests in flight together cost one. `replayRefused`, first in `route` ahead of the limiter check, answers a remembered token with it, uncharged, with no database read, from a limited address too. So one stale token costs its address one token a minute per path and query, under the 0.1/s floor on the refill rate, while distinct bad tokens still drain the bucket. A refused token stays refused, save a disabled user's after an admin re-enables them, whose wait the 60s bounds. A valid token pays a SHA-256 and a map lookup. What stays open: tokenless requests and new sign-ins from an address another client's distinct bad tokens have limited are still refused. The address (`src/server/client_addr.ts`) is the peer, normalised (Bun reports an IPv4 peer as `::ffff:a.b.c.d`), or when the peer is in `GRAYBOARD_TRUSTED_PROXIES` (default loopback) the first untrusted `X-Forwarded-For` entry walking from the right, with a port or brackets stripped; a walk that runs out of entries, or meets one that doesn't parse, keys by the last address it trusted, and the first unparsable entry per process is logged, since it puts that proxy's clients in one bucket. A peer Bun can't report keys to the shared bucket `unknown`, never skipping the gate. IPv4 keys by address, IPv6 by /64, and an IPv6 request is also checked against, and charged to, its /48 (#274): a second limiter with its own 10,000-key cap and 4× the per-address limit (`SITE_LIMIT_FACTOR`), checked after the /64 so a request its own /64 refuses doesn't spend its /48. Since a new /64 bucket is created only by a charge, which spends the /48, a prefix rotating through its /64s holds at most about the /48's burst plus its refill over a sweep interval and a bucket's refill (240 + 4 × 31 ≈ 364 at the defaults), plus requests in flight (a refused token is charged when its response resolves, so fresh /64s whose requests overlap all pass the /48's check). So one /48 can't fill the cap and fail every later address open; about 28 /48s together can, and so can a flood that fills the /48 tier's own cap, which then charges no new /48: both are floods across prefixes, which belong at the network edge (#240 decision 6). A drained /48 refuses every /64 under it, valid tokens included, as a drained IPv4 address does its NAT, and the 429's message names the network (/48) rather than the address. A /48 is often more than one site (an ISP's /48 holds 256 customers' /56s), so a client failing from five or more /64s at once can drain it and lock out its neighbours; the refused-token memo keeps one stale-token loop from getting it there. The /48's rows are the same `auth.rate_limited`/`auth.rate_limit_ended` actions with the /48 as target; its cap row carries `tier: "site"`. The resolved address is also dev login's `auth.login` `ip`. A run of refusals has the bind limit's streak semantics, with `auth.rate_limited` (actor null, target the key; its detail carries the refused request's full address and `last_failure`, the charge that emptied the bucket, so a stale-token fleet reads differently from a scan) and `auth.rate_limit_ended` (`{refused}`) rows and a log line each. The start hook runs before the refusal is counted, so a failed audit write leaves no run without its row; `sweepLimits` (its own 30s timer in `startServer`) runs the hello, address and /48 limiters' sweeps, each catching per bucket.
