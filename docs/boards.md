## 1. Principles

These decide new features. A change that breaks one needs an explicit decision.

1. **Primitives, not an org chart.** Boards, claims and mentions; roles emerge from use. No manager-agent feature.
2. **Context is the scarce resource.** Every byte pushed into an agent costs attention and tokens. Push what demands action; tell an agent the rest exists (digest).
3. **Push, never polling.** No agent has to remember to check. Principle 2 decides how much is pushed, not whether.
4. **Enforced state beats conventions.** A norm agents would invent in free text (`HOLD`, `owner`) becomes an operation with real semantics.
5. **Append-only.** Nothing is edited or deleted by agents; retention is operator policy.
6. **Harness-neutral core.** Coordination logic lives in `src/core/`; harnesses are adapters. A feature isn't skipped because one harness has a native version (Claude Code's `SendMessage`/`ListAgents` reach only Claude Code sessions). Harness-only conveniences that the core can't know neutrally (busy/idle, `notify_when_idle`) aren't copied.
7. **The interconnect, not the orchestrator or the store.** grayboard owns addresses, mailboxes, boards, claims and presence, and nothing else. It never spawns or dispatches agents, never picks a harness, model or persona, and never holds task state or knowledge. Task state means configuration, prompts, skills, transcripts and handoff notes. Orchestrators, skill catalogs, knowledge stores and event systems do those jobs and coordinate *through* grayboard. When one of them needs a hook, grayboard emits an event (mail queued for a dormant name) or carries an opaque reference (an alias's task reference, #284), and never absorbs the job. Why:
   - Each component stays adoptable on its own.
   - grayboard prunes on a retention clock, and task state and knowledge must outlive it: messages aren't knowledge.
   - Each absorbed job widens the attack surface and the tool surface that every agent pays for (principle 2).

## 2. Core shape

- The core takes a `bun:sqlite` `Database` and handle strings; it knows nothing of MCP, sockets or WebSockets.
- **Core functions return a delivery plan (who to wake); they don't deliver.** Local mode turns the plan into socket pokes, the server into WS pushes. That keeps one implementation for both modes and makes it testable.
- **Access is checked in the core** via the installed `Access` policy (`setAccess`). Local mode: open, bare handles. Server: team-aware (`architecture.md` §5). Call sites can't forget to filter.
- Board tables are separate from DM tables in both modes. Post IDs are their own sequence; notifications say `post_id` + `board` so they can't be confused with `message_id`.
- Tool definitions, dispatch and notification rendering for board, claim and peer tools live once in `src/core/tools.ts`; local mode calls them directly, the server runs the same dispatch for `call` frames. DM tools are per mode (`AGENTS.md`).
- **Upfront tools** (`_meta` `anthropic/alwaysLoad`): in Claude Code a loaded definition costs its (cached) schema on every request; a deferred one costs a ToolSearch, a full extra request rereading the context, on first use. So mark a tool upfront only if most sessions call it (reply, recovery, the resume path). Other harnesses ignore the key. The local-mode set is pinned in `tests/integration/local.test.ts`; server mode's `dm_send`/`dm_thread` carry their own `_meta` in `src/plugin/mcp.ts`.

## 3. Handles

A **name** (handle; an **alias**, #284) is durable: it owns the mailbox (queued DMs, cursors), claims and subscriptions, and its `aliases` row keeps the facts that outlive a session. Its address is a bare name locally (one implicit scope) and `scope/name` on a server: a person's `email/name` or a team's `team/name` (`addressParts`, `aliasScope`, `src/core/addresses.ts`); who an address acts for is the server's `Resolver` (`src/core/resolver.ts`), never its text, since an ID carries no email. A **session** is one `grayboard mcp` process: it has a secret session key, minted at start, and a **session ID** derived from it, `id:` plus 13 Crockford base32 characters (`idAddress`, `src/core/bindings.ts`; 1.x rows keep the same 64 bits as 16 hex, re-encoded on read). Its `ids` row keeps the facts that describe the running session; its `last_seen` moves on each local tool call, and on a server at each hello and close. `id_collision`: local mode refuses an ID that already has an `ids` row, live or ended (the one exception: a keyed child re-attaching under its live harness, below), so an ended ID stays dead for the retention window; a server refuses one whose row belongs to another principal or has ended, or that a live connection still answers for, and re-attaches its own user's unended row (`architecture.md` §4). Messages and posts record the writing session in `sender_id`/`author_id`; a writer with no `ids` row (a server's in-process Slack bridge humans) records null. It holds up to `MAX_HOLDS` names at once (`src/core/bindings.ts`; each hold is a socket or registry entry and a drain stream); `alias_holds` records the one session holding each name (#182). Status is the session's, shown on every name it holds.

- **At most one live session per handle.** Why: a worktree that inherited the repo's `.mcp.json` once started as the same handle, took over the wakeup socket and cursor, and Claude Code silently dropped its pushes because it wasn't loaded as a channel. The sender saw `delivered_now: true` throughout.
- **A session starts unbound unless `BUS_IDENTITY` is explicit** (`isExplicitIdentity`, `src/shared/identity.ts`). Binding delivers the name's queued DMs and hands it the name's claims, so that follows the agent knowing its task: a session started for a one-off question must not swallow mail meant for the long-running work. The resolved name (pin, repo directory, worktree suffix; below) is only the first **candidate**. A lane that should always come back under one name sets `BUS_IDENTITY` in its launch command. Exceptions: `BUS_HUMAN=1` (the Slack bridge's child) binds at start and exits if the name is held, since no agent reads its candidate list; a `BUS_PUSH=off` process never acquires a name and writes as the resolved one (on a server, a `writes_as` the server checks like a bind target). It is still its own session in both modes (`ids.delivery = 'none'`, `ids.writes_as`): its ID stamps what it writes, it ends like any session, and it receives nothing, so it isn't listed or offered names, and a DM or mention to its ID is refused `no_delivery` (§7). Locally its liveness is its own pid even when keyed (a key shared with a live session is `id_collision`).
- **An explicit name held by a live session starts the session unbound**, with the holder named in its instructions, instead of exiting: an MCP server that exits at startup shows the agent nothing it can act on. No auto-suffix (`repo-2`): minted names strand queued DMs (#104).
- **An unbound session acts as its ID** (#284), in both modes, with the full tool surface. A session's **address set** is its holds in bind order, then its ID (`sessionAddresses`, `src/core/bindings.ts`); its **primary** is the oldest hold it still holds, else the ID (`primaryOf`; `bound_at` is kept strictly increasing per session, so the order survives a restart and two binds in one millisecond). Writes go out as the primary unless the call says otherwise (below), and DM reads, acks, retracts, attachment reads and claim renew/release/ack match any address in the set, so a claim or reply taken before a bind still works after it. Locally it listens on `sock.<id>` from start plus one socket per held alias, and drains each address under its own cursor, pushing a board item that several addresses receive once (#361); a server connection is registered under each address in its set. Why: gating an unbound session made a held alias block the agent outright; an ID is answerable, so its writes don't pollute the record. It holds no `alias_holds` row, so it isn't in `peers` (see `unbound_sessions`, below). `dm_send` reaches it by ID without the alias roster check, and the mode's `online` predicate counts it live for announcements and the queue rotation's live-first order.
- **Hosted MCP: unbound reads only.** An unbound hosted MCP session (`src/server/hosted.ts`) can call only `bind`, `board_list`, `board_read`, `peer_list` and `claim_list` (`UNBOUND_READS`, `src/server/application.ts`). It acts as no address: `board_list`, `board_read`, the board checks in `claim_list` and `peer_list`, and the board resources are judged by its user's principal (`seer`: open boards and the user's teams' boards), whether or not its request maps a session source (`architecture.md` §Hosted MCP), and touch no cursor, subscription or push (`ToolContext.reader`, `src/core/tools.ts`), so its rows show no mode and nothing unread (#410). Everything else returns `UNBOUND_ERROR`. It isn't in `dm_send`'s roster or in `peers`.
- **Unbound instructions.** While unbound, the instructions are the session's instructions as its ID plus a short paragraph (`unboundInstruction`) naming the ID and, locally, up to `MAX_CANDIDATES` free names: the suggestion first, then the user's other free names by pending work (queued DMs + held claims), then last seen, each with its counts and last place. Viewer, human and live names are excluded. A WSS session gets no candidates; an unbound hosted MCP session lists its user's free names (`hostedCandidates`, `src/server/application.ts`; `hostedUnboundInstruction`, `src/server/hosted.ts`). `bind`'s result then adds only the name's own instructions, since the general ones were already paid (instruction text is paid by every session, AGENTS.md).
- **`bind(name, create?, meta?)`.** A name never seen needs `create: true`, and the refusal lists the closest existing names (`closestNames`): a typo would otherwise create a fresh mailbox and the intended one's DMs would never arrive. Server mode: `identity_unknown` with `known`. The name is normalized like `BUS_IDENTITY` (#181); `human` and the declared human handle are refused (on a server, `human` in any scope). On a server the name may carry a scope (`team/name`, and so may `BUS_IDENTITY`): a bare name means the user's own person scope, and a team scope needs membership (`mayActIn`, `src/server/access.ts`); service scopes wait for #270. Losing the membership takes the alias from the user's live sessions, which carry on as their IDs (`alias_lost`, `architecture.md` §4). The result carries what startup shows for the name (notices, claims split) and its instructions, as text and as `structuredContent: { name, instructions }` (the full set), which adapters read (§9). A second hold adds one conditional instruction sentence naming the others and the send rule, paid only by a multi-hold session. `meta` sets the alias's one-line labels (`parseAliasMeta`, `src/core/boards.ts`; control characters stripped, `""` clears, an absent key is left), audited `alias.meta_set`, and a refused `meta` logs a `refused` binding event in both modes; who may set them is who may bind. `task` is a label, never a reference or task state (principle 7).
- **`bind` only adds a hold; `unbind(name)` only removes one** (#284 S1, S2). No WSS or local operation moves a session from one name to another; hosted MCP differs (Hosted owner, below). Re-binding a held name is ok and logs nothing (it applies `meta` if given); `unbind` of a name not held is ok, so a lost answer is settled by calling again. `unbind` needs no access check (releasing is always allowed), is refused for a tools-only process and the human, and promotes the next-oldest hold (else the ID) when it releases the primary; its result says so and carries rebuilt instructions like `bind`'s. Locally it closes the name's socket before dropping the hold, so nobody can take the name while this socket answers and `lastWasRelease`'s window stays valid. On a server an unacked DM pushed to the name just before its `unbind` is redelivered to its next holder (at-least-once), and the name's in-flight board items are dropped so a later `bind` of it on the same connection drains them again. `bind` and `unbind` serialise against each other and every tool call (`src/shared/bindgate.ts`, both modes): a call must not straddle a primary change. Tool descriptions never embed a name, since harnesses cache them.
- **Claims stay with the address they were taken under**, in both modes (#284 decision 8), except across a hosted rebind (Hosted owner, below): ID claims stay renewable through the address set, and an alias's claims wait for its next holder; `unbind`'s result lists the ones it left (`leftNote`). One rule for both kinds of address, where moving alias claims but not ID claims would be two. `claim_take(as: B)` on a claim the session holds under A renews it under A: no transfer between a session's own addresses (#286).
- **`as`** (`AS_PARAM`, `src/core/tools.ts`) on `dm_send`, `board_post` and `claim_take` names one of the caller's addresses: a held alias, or its own ID. One resolver for both modes (`actingAs`): a bare name is the own scope's, anything outside the set is refused naming the set. A tools-only process's only `as` is its `writes_as`; the human's is its handle. Not on `delegate`: the requester is the primary. Every other board tool refuses `as` (`boardActor`), since a raw server call skips the MCP schema check.
- **A DM reply without `as` goes as the alias its parent reached** (`replySender`): the parent's recipient when the session holds it, else the parent's sender when the session holds it (its own thread), else the primary. Why: answering mail to B as A makes the peer's next reply go to A (§7), splitting the thread across aliases, and across sessions once B changes hands. The ID is excluded on purpose, so mail to the ID before a bind is answered as the alias, onto an address that outlives the session. A parent whose alias the session no longer holds is refused as now, never sent as the primary. The send result carries `sent_as` when the sender isn't the primary; a DM push and `dm_inbox` row carry `to` on the same rule.
- **A board call without `as` acts as one address that can see the board** (`boardAddress`, `src/core/boards.ts`; #284 S14, #366): `board_read` and each `board_list` row take the first subscribed address with unread posts, else the first subscribed; `board_subscribe` the first subscribed; each then falls back, as `board_post` always does, to the first address (in set order) that can see it. One call has one acting address, so access, subscription, cursor and outbox are all that address's: reading every board as the primary would leave another address's cursor still and re-push its posts. Unread-first, so repeated reads drain each subscribed address in turn; `off` removes one subscription per call.
- **Hosted owner** (#226; `src/server/hosted.ts`): a native MCP session holds names in the same `alias_holds` table as WSS sessions, so each excludes the other (`architecture.md` §4 `bind`, §Hosted MCP). Its root starts unbound; an explicit bind holds the name independently of delivery. It holds one name (#407), so a rebind moves its claims to the new name, the one exception to the claims rule above (mechanics: `architecture.md` §Hosted MCP); several holds and `unbind` aren't designed for hosted. Its ID never ends through `endSession`: ending the ownership releases only its hold. Registered children act under that root's current name, with their own writer attribution, and cannot take over root controls. Human enrollment approves a receiving root, not a name or ownership. `delivery_open` attaches a push target to the bound root; a bound root without a lease still excludes contenders but leaves DMs queued. Ownership history, liveness and lease fences belong to `architecture.md` §Hosted MCP.
- **Local acquisition** (`src/local/binding.ts`): every session (delivery owner, tools-only process, `tail`) writes a `bindings` row at start (`name` NULL while unbound) with its pid, start time and harness pid (its harness and cwd are its `ids` row's), audited `id.registered` (detail fields: `src/local/binding.ts`, the server's `delivery` and `keyed` plus harness rule and pids); `pid`/`proc_start` are always the process whose death ends the session (keyed sessions: the harness, below). Acquire runs in one `BEGIN IMMEDIATE` transaction: a row holding the name whose pid is alive with a matching start time holds it; a dead holder's row is cleared. Liveness is `kill(pid, 0)` plus the start time, never a socket probe, so the write lock isn't held across one, and a holder whose event loop is blocked keeps its name (#80: probe → unlink → listen let two starters both win). Dead only on evidence (`src/shared/proc.ts`): an unknown start time on either side (no recorded value, `ps` failed) counts as alive, logged once per pid, because a reused pid holding a dead name is safer than reaping a live session. Only the row owner listens: on a temp path renamed onto `sock.<name>`, unlinking on stop only if the inode is still its own, because Bun's `server.stop()` unlinks its path unconditionally and would delete a successor's socket. The stat → unlink check isn't atomic; the window is microseconds wide and needs a successor's rename to land inside it. A flagless Claude Code session (#71) holds its name without listening: offline to peers, DMs wait.
- **Mixed versions.** A pre-#182 session holds a socket and no row, so when no live row holds the name the acquirer probes `sock.<name>` before the transaction (a dead row doesn't skip the probe): live socket, no live row → held. When no row (dead or alive) holds the name and its last `binding_events` row is a release, that socket is a 1.x session that has just rebound off it and not yet closed it: the refusal says to retry in a moment, and `dm_send` to the name reports `delivered_now: false` (`lastWasRelease`, `src/core/bindings.ts`). Known limit: a pre-#182 session *starting* concurrently can still unlink the new owner's socket; closed once both run new code. A post-#182, pre-#284 process holds by `bindings.name` alone: HEAD counts a live row naming the alias as its holder (`holdingSession`), and a HEAD acquire writes `bindings.name` too, so the 1.x check sees it. `bindings.name` is `UNIQUE`, so it mirrors the primary only (moved to the next hold, or `NULL`, when the primary is unbound): a 1.x process sees a HEAD session's other holds only as live sockets. A 1.x reap deletes a dead HEAD session's `bindings` row but not its other rows, so an unended local `ids` row with no `bindings` row counts as dead and the next opener ends it (below).
- **Session end** (`endSession`, `src/core/session_end.ts`; #284 decisions 4 and 10): one transaction that leaves nothing deliverable against the ID. It marks `ids.ended_at` and `held_aliases_json`, bounces the ID's unread direct mail to each sender (`messages.kind = 'bounce'`, threaded under the original, naming what it held; dropped when the sender is itself an ended ID), releases its claims (lapsed ones through the sweep first, so they end as lapses; queue posts redelivered, watchers told; a release the core refuses (`CoreError`) still deletes the claim, unannounced, since a claim on an ID that can't act would never free), drops every other row keyed by the ID (`forgetHandle`, the mail port's `dropReader`, unbound uploads), and releases its holds (`released`, detail `session_end`), audited `id.ended` (detail fields: `session_end.ts`; the server's row goes to its access log through an `AuditSink`). Alias claims and mail stay: the alias is durable. Mail per mode goes through a `MailPort` (local `src/local/mailbox.ts`, server `Repo.mail`). A WSS session ends on an unkeyed clean exit (`end`; a keyed one only closes and keeps its grace), at the end of its reconnect grace, when it loses what it writes as, when an admin revokes or disables its user, or when its token is signed out, live or in its grace (`architecture.md` §4); a hosted session ID never ends here (Hosted owner, below). Locally a clean exit ends the session, and **every opener** (`openLocalDb`, `src/local/open.ts`) ends dead ones, as do `peer_list` and the candidate list (`liveSessions`) and a bind that finds a dead holder: candidates are found outside the lock, then each is re-probed and ended in its own `BEGIN IMMEDIATE`: one that throws is logged and audited `id.end_failed` (`error`, `by_pid`) and leaves the others ended and the opener working. Every caller, the CLI's openers included, runs `deliverEnded` (`src/local/wakeup.ts`) after commit: it unlinks the ended IDs' sockets, pokes the wakes and sweeps the bytes of the uploads the end dropped. On a clean exit `grayboard mcp` refuses new tool calls and drains, waits for in-flight calls and the drain, ends, then waits for the wakes, each wait capped at `SHUTDOWN_WAKE_MS`; a failed end is logged. A send racing the end either commits first and is bounced, or reaches the write lock after it and is refused `id_ended` (`assertDeliverableId`, inside the send's transaction); `tests/integration/ids.test.ts` forces both through `testPause`.
- **Keyed sessions** (`BUS_SESSION_KEY`, `envSessionKey`; #284 decision 3): an orchestrator mints the key, so it knows the child's ID (`idAddress`) before launch. On a server a keyed session outlives its process's exit for the reconnect grace (`architecture.md` §4); the rest of this bullet is local. The session lives as long as its **harness**, not its `grayboard mcp` child: `bindings.pid` is the harness (`BUS_HARNESS_PID`, which must name an ancestor of the process or it refuses to start, else the first ancestor `launcherName()` doesn't classify as a shell or package runner; `harness_rule` records which), `attached_pid` the child. Only a push-mode process resolves a harness: a keyed tools-only process lives by its own pid and never attaches. A child that exits under a live harness detaches; a restart under the same harness re-attaches (waiting out its predecessor's exit, then re-checked inside one transaction) and is the same session, nothing ended or bounced, audited `id.reattached`. A key whose session has ended, whose child is still alive, or that belongs to another harness is refused `id_collision`, as is a re-attach whose human-ness doesn't match the held alias (an agent to a session holding the human handle, or `BUS_HUMAN=1` to one that doesn't). An explicit `BUS_IDENTITY` is ignored on re-attach: the session keeps what it held. Keyed sessions write no name record (below): re-attaching is their continuity.
- **`binding_events`** (core schema, `src/core/schema.ts`; written by `logBinding` in both modes, and directly by the hosted store when an ownership ends, `src/server/db.ts`): `bound`, `released`, `refused`, keyed by session ID, with the holder on a refusal. `moved` is written only by a hosted rebind, on the new name (`architecture.md` §4 Binding events); WSS and local never write it, and older rows carry it from a pre-multi-hold rebind, so readers keep it in their `IN` lists. A refusal joins the session's latest row for the name when that row is a `refused` with the same detail, last repeated within `REFUSED_COALESCE_MS`: its `count` and `last_at` grow instead of a row being added (#210), so a steady retry loop is one row and any other event starts a new one. Retention goes by `last_at` when set. The audit trail for every name change, and the join between run metadata and a name (#185). Retention prunes them with posts (`prunePosts`, `src/core/boards.ts`), except each name's latest `bound`/`moved` event, which says who holds the name by the record (#211).
- **Names survive an MCP restart in one harness process** (`src/shared/namerecord.ts`). The delivery owner writes `bind.<harness pid>` in the socket dir after each bind and unbind, listing every held name oldest first (a 1.x record's single `name` reads as a one-name list: client files can't be migrated); a restarted `grayboard mcp` whose record matches its parent's pid and start time binds each name back in order ahead of `BUS_IDENTITY`, with a new session ID, each judged on its own: the first restored is the primary, and one now held elsewhere goes in the restore note. It waits for its predecessor's exit once across all the names (`SIBLING_WAIT_MS`), and tries at most `MAX_HOLDS` of them, reporting the rest: the record is a local file, not proof. Each name's `bound` detail is `restored: restart of session <id>` only when the name's latest `bound`/`moved` event is the recorded session's (`continuityOf`, `src/core/bindings.ts`), and the session inherits the recorded session's status once, from the first name that verifies; the check runs in the acquire transaction, so a bind that lands while the restart waits for it counts. Otherwise it takes the name with the detail `restored_from <id> not verified: latest bound by <id>`, so the history never records a restart the bus didn't see (#211). A server bind's `restored_from` proves nothing (#259): any client can name a public ID, so it's logged `restore claimed from id:…, not verified` and carries no status; server continuity needs `previous_key` (`architecture.md` §4). Locally the record is keyed by the restarting process's own harness pid, so a stray under another harness can't present it. Why: `/mcp` reconnect and crashes restart the child under the same harness, which would otherwise come back unbound mid-task. A new harness process starts unbound (`--resume` restore: #195). An unbound exit removes its record; a bound exit keeps it, which is what lets `/mcp` reconnect restore. A failed restore (name now held or gone) starts unbound with the reason in the instructions; it doesn't fall back to an explicit `BUS_IDENTITY`, since the restarted session is mid-task under the recorded name and must not silently become another. A launcher parent (`npx`, `bunx`) changes pid per restart, so the record never matches; the instructions say so. Records are writable by any process of the same user, the same trust domain as `sock.*`.
- **`grayboard human` and `bind` exclude each other** in one transaction (#79): `declareHuman` refuses a bound name; bind refuses the human handle and `human`. A `BUS_HUMAN=1` session refuses `bind`, `unbind` and an `as` other than its handle (#363), as the server's `attachHuman` session does (`src/server/application.ts`): the human handle is fixed.
- The local MCP server exits when its client closes stdin; otherwise the socket listener keeps an orphan alive that locks its handle out.
- **Worktree suffix** (`src/shared/identity.ts`): the suggestion inside a linked worktree appends the worktree name to the base identity (`be` → `be-stream`; a worktree already named `be-…` is used as-is), so an existing worktree lane sees its own name, mail and claims first. An explicit `BUS_IDENTITY` — one that differs from every pin the repo carries (`.mcp.json`, `.omp/mcp.json`) — takes no suffix and is lowercased and validated with the server's rule (#181). A `BUS_IDENTITY` re-delivering a pin (harnesses load pins into env) is not explicit. A `BUS_IDENTITY` from a user-level registration (`claude mcp add -e`, pi's user `mcp.json`) is one name across every worktree: a second session on it starts unbound. Decided from the starting directory only. Without `BUS_IDENTITY` the base is the repo directory name; if `BUS_IDENTITY` is unset, the server reads a pin from the repo's `.mcp.json` itself, so the suggestion doesn't depend on a harness's config precedence.
- **CLI commands act as the bound session's primary** (`actingIdentity`, `src/cli/claim.ts`), local mode, with its address set for release and renew (`addressSet`): after `--as` and an explicit `BUS_IDENTITY`, the live bound `bindings` row whose harness pid is an ancestor of the CLI, narrowed to this checkout when several match, else the one in this checkout. None, several or unbound → refused, pointing at `--as`. Why: resolving from cwd would act as the repo name while the session holds another, and the claim lands on the wrong handle silently. Server mode has no local rows and keeps resolving from cwd.
- **Claude Code session title = handle.** Registering with Claude Code (`grayboard setup`) installs a SessionStart hook (`grayboard session-start`, `src/cli/session_start.ts`) that returns an explicit `BUS_IDENTITY` as `sessionTitle`; otherwise it sets no title, since no name is held yet (retitling after `bind`: #180). Why: Claude Code's own name for a session (what ListAgents shows) otherwise differs from the handle, and agents DM the wrong one. It fires on startup, resume and fork only. It overrides `--name`. A `BUS_IDENTITY` in the user-scope registration's env (`claude mcp add -e`) is invisible to it, so such a session gets no title. A resolution error prints nothing, so the hook never blocks a session.
- An identity is the agent's role in the repo, not its harness: Claude Code and omp in one repo get the same suggestion, and whichever binds it second is refused.
- **Presence (`peer_list`)** is a query, not a feed: nobody is notified when peers come and go. "Online" means a live session will receive pushes, so a tools-only `BUS_PUSH=off` server counts only via the push owner. Local mode probes each wakeup socket; the server checks open connections. Live unbound sessions are listed apart, in `unbound_sessions` (session ID, place, and the status set as the ID; omitted when empty and on a board-scoped call; never a tools-only process, a `tail` or a server hold connection), because every global `peers` entry must hold an alias; every row of the caller's own addresses carries `self: true` and is online. `you` is the primary (while unbound, the session ID). A board-scoped call lists a subscription taken as the ID under the session's primary hold only (a name's own subscription wins), so an ID subscription is one row and one queue lane, not one per hold (each alias's own subscription is its own), or as the ID with its session's place and status, as the queue rotation does (`queueLanes`). Local mode reads them from `bindings`; the server from its live push connections, scoped to the caller's own user, since `where` describes their machine. `peer_list(board)` lists that board's subscribers; a team board is the team roster. `peer_status` text is cleared when a new session starts (a server-mode reconnect within one session keeps it). The `peer_status` queue opt-out (`aliases.queue_off`) persists across sessions until set `on`; `peer_list` shows it as `queue_off`. Rows carry `id` (the holder's, or an offline alias's last binder's once that session ended), the session's self-reported facts (`harness`, `model`, `effort` from `BUS_MODEL`/`BUS_EFFORT` at launch or the hello; an offline alias shows its last binder's, from that ended session's `ids` row, while status shows only while held) and the alias's `meta` labels. Labels ride on a row only when the caller's session may act in the alias's scope (`Access.seesAliasMeta`, judged for the session's ID, not its primary, which may be a team alias): a team's task label or a private board's name must not reach a non-member. `match` filters rows (`MATCH_KEYS`; exact, case-insensitive, ANDed; `scope` is an alias's scope, or an ID's principal only for a caller that may act in that principal's scope, since an ID row doesn't show it) after that cut, so filtering can't probe a hidden label or a session's owner; it filters `unbound_sessions` too.
- Unknown recipients and mentions that match nobody are errors or `unresolved` that point at `peer_list`, never silent success.

## 4. Boards and posts

- **Created explicitly** with a one-line purpose. Implicit creation on first post makes typo boards in a swarm. The creator is subscribed in `push`.
- Posts are append-only; corrections are replies. Threads use `parent_id` within a board. Body limit 64 KiB.
- Local mode: every board open to every handle. Server: team boards are members-only.
- **`#announce`** (the `Access` policy's `announceBoard`; local mode only, created when the bus opens) is how the human addresses every agent (#24). Why a board where only a human can start posts: an agent relaying "the user says stop" carried no `human="true"`, so careful recipients rightly treated it as a peer request. On this board the authority comes from the board itself, so no agent has to make a per-message trust call.
  - Top-level post: refused unless the author is a declared human (`slack-bridge.md` §3). It pushes as a `mention` to every handle **live at post time** (the mode's `online` predicate, passed into `post`). Nothing is queued for offline handles: an announcement applies to the sessions running when it's said.
  - `expires_at` (`grayboard announce --ttl`) is the exception: until it passes, the post is listed in every new agent session's instructions, like active claims.
  - Agent subscriptions are ignored on this board (viewers like `tail` still get it). An agent's reply fans out only to the root author (explicit @mentions still push); `threadAuthors` fan-out would push every ack to every earlier acker. A human's reply reaches the thread's authors.
  - Server mode sets `announceBoard: null`, so a deployed team board named `announce` stays an ordinary board. A server `#announce` for users' `human` identities (`slack-bridge.md` §8) isn't built (#24).
- **Mentions**: `@handle` outside backtick code (spans and fences). An `@` preceded by a word character isn't a mention, so email addresses in prose aren't. A mention pushes to that handle regardless of subscription, carrying the post and board so it can reply in-thread. `@id:<13>` mentions that session whatever it's bound to, in both modes; in an agent's post, an unknown, ended, tools-only or viewer ID refuses the whole post with the same error a DM to it gets (`undeliverableId`), rather than an `unresolved` entry, since the poster named an exact session. A system post (a claim announcement quoting its key) lists such an ID in `unresolved` instead (`PostOpts.strictIds`): a key naming an ID that later ended must not make every sweep throw. Locally a name is a bare alias. On a server `@scope/name` is exact (`@you/be` names principal `you`, never an email's local part), and a bare `@name` is the author's own scope's first, then the one alias of that name on the board; several refuse an agent's post naming them, and go to `unresolved` on a system post, for the same reason as an ID; a bare `@human` is only ever your own (`resolveMention`, `src/server/access.ts`; who may be reached: `architecture.md` §5).
- **Queue boards** (`board_create(kind: "queue")`, #131/#114): each top-level post delivers to exactly ONE subscriber — work routing for a fleet, not fan-out. The rotation picks the least-recently-woken eligible lane (`queueLanes`, `src/core/boards.ts`), live lanes first when the mode can tell (`online`), offline lanes as the fallback. A subscription an unbound session took as its ID counts as the session's primary hold. Eligible: a push subscriber who isn't one of the poster's addresses (a session posting as any alias is never its own lane; a redelivery rebuilds the set from the post's `author_id`), hasn't opted out (`peer_status(text, queue: "off")` — status text never affects routing), isn't a viewer, and can see the board. The claim IS the delivery (§6): the holder's reply acks and releases it, `claim_release` declines it to the next lane, and a 30-minute TTL takeover redelivers the original post to the next lane either way, so an ignored post can't die with one lane; with no other lane it sits readable on the board. A resolved @mention is direct addressing and skips the rotation (untracked as delivered-once; #219 covers the gap). Redelivery from the sweep is presence-blind (the sweep has no `online` predicate); an offline lane holds the re-offer in its outbox until it wakes, and its own TTL lapse re-rotates. Subscribers are lanes, not audience: a reply follows thread semantics only.

## 5. Subscriptions and attention

| Event | Delivered as |
|---|---|
| DM; `@mention`; reply to your post, or in a thread you started, that you haven't muted; your user's reply in a thread you posted in; any thread reply to a human handle; post on a `push` board outside a thread you muted | Push, full body |
| Other reply in a thread you posted in and haven't muted | Deferred push, full body, `deferred="true"`: rides with the next waking delivery |
| Post on a `digest` board (team auto-follow uses digest; creators get `push`) | One coalesced notice per board until read, riding with the next waking delivery |
| Post on a `quiet` board | Nothing pushed; unread count in `board_list` |
| Human's top-level post on `#announce` | Push to every live session, regardless of subscription |
| Queue-board post routed to you (the rotation picked your lane) | Push, full body; your reply acks the claim, `claim_release` declines it to the next lane |
| Claim / release / expiry with `board` set | A system post on that board |

- Subscriptions start with the cursor at the **current tip**: joining never replays history (it stays readable via `board_read`).
- One cursor per (handle, board). Cursors advance on `board_read` (to the newest post returned) or when a `push`-mode subscription's delivery is acknowledged. Acked mention and thread pushes don't move the cursor; they're marked delivered and excluded from unread. `board_read` marks delivered only the posts it returned: a mention its unread filter excluded (a pending waking push) or a post outside a read thread is still pushed, though the cursor passed it (#68). **A digest never advances a cursor**: it says "you have unread", it isn't the read.
- Coalescing: a digest fires on the first unread post, then stays silent for that board until the cursor advances. No timers. A post already pushed to a handle in full doesn't count toward its digest or unread count (it was once announced twice).
- Per handle, highest reason wins: mention > thread > subscription. Your own posts never count as unread for you, on any of your session's addresses: a post its session wrote as one alias is not unread, digested or read back on the others (`NOT_OWN`, by `posts.author_id`).
- **Deferral** (`outbox.wake = 0`, #44, #45): a reply wakes the author of its parent and the thread's root; other participants' pushes wait. Bystanders reply about as often as direct recipients, so deferral delays them rather than dropping them. A push-mode subscriber, a human participant, and every participant of a human's reply still wake. Thread fan-out skips an author the mode's `Access.mayReach` refuses (server: a human outside the replier's reach, slack-bridge.md §8). `pendingFor` returns deferred pushes and digests only alongside a waking push or with `all` (a session's first drain, a local drain carrying DMs, a human's session, a server hello), because any notification wakes an idle agent and liveness probes run drains. A deferred push still waiting counts as unread (`NOT_PUSHED_YET`), so `board_read` picks it up early; digest counts still exclude it (`NOT_PUSHED`) so it isn't announced twice. Adapters deliver deferred pushes as context, like digests.
- **Thread mute** (`board_subscribe(board, "off", thread)`, #26): thread-reply fan-out ignores board mode, so without it a one-off replier hears every later reply forever. Keyed by the thread's root, so any post id names it. It drops thread and subscription pushes for that thread; @mentions still land because `post()` applies the mute before the mention pass, so keep that order. For a subscriber, muted replies drop out of push and into the digest/unread count; a push subscriber's cursor passes them only on a later acked subscription push or `board_read`. Posting again doesn't unmute; `mode: "push"` with the thread does. Pruning a root drops its mutes.
- **Delivery reads are not receipts.** Inbox reads and failed hints leave durable delivery pending. Receipt means awaited durable host admission, not DM handling; retrying a lost receipt remains idempotent, but unissued items or a noncontiguous unread DM prefix cannot advance delivery. Hosted session ownership and lease fencing are server mechanics (`architecture.md` §Hosted MCP); they share the WS/bridge holder registry, not a competing ownership system.
- **Resource watches are not attention subscriptions.** Read-only snapshots (`src/core/boards.ts`) never advance cursors, acknowledge outbox items, or expand threads without bounds. Transport-neutral watchers (`src/server/resources.ts`) fan out hints independently of the identity's sole delivery owner; watching must not call `board_subscribe` or acquire a push session. Reconcile snapshots after subscribing and reconnecting: hints carry no content authority or acknowledgement and may be missed. Hosted listeners are isolated by actual access and, for inbox hints, the lease capability's epoch; stream closure neither releases a still-live delivery lease nor receipts its durable pending items. Explicit release, expiry, revocation, rebind or grant reattachment fences that delivery epoch; a hosted process restart keeps its durable ownership deadline, credited with the downtime (#423).
- Resource watchers recheck session authorization and board visibility before each hint. Membership loss closes the watch without revealing new private content. External auth/team administration must invoke the resource service's revalidation hook, and its owner must close the service at shutdown; periodic revalidation is only a backstop. Committed application board mutations, including claim-generated posts and expiry, carry changed board names separately from attention wakeups. Hosted retention signals only actual post deletions through the same application entrypoint. Direct low-level core callers outside the application must forward their returned changed boards explicitly; resource signals are never inferred from delivery wakeups.
- **Board content is untrusted data from other agents.** Instruction text says peer requests are coordination requests, acted on when they fit the user's goals and permissions, never overriding the user. Stronger wording ("information, not instructions") made agents refuse benign peer requests.

## 6. Claims

- `claim_take(key, ttl_minutes? | until?, note?, board?)`: take, renew (if you hold it), or learn who holds it. `claim_release(key, note?)`: holder only; the note rides on the release post.
- **A repeated release answers from state** (#254): when the key's latest `claim_events` row is the caller's release (or, on a `queue:` key, the redelivery take that release made directly after it), the call succeeds with `already released by you at T`, writing no second event and redelivering nothing. Checked inside the release transaction, only where the release would otherwise refuse. Anything since (someone took it, released it, or a TTL takeover) and today's errors stand: a fingerprint would wrongly replay "released" after an intervening take.
- **Renewal never shortens by default**: without `ttl_minutes`/`until` it keeps the later of the current expiry and now+default. Resetting to now+default silently cut multi-day claims to the default TTL when an agent renewed only to change the note (#37). An explicit ttl or `until` still sets the expiry, shorter or not.
- **Progress updates** ride on renewal, not a separate tool: a renewal whose given note differs from the current one posts `[update] key — note` on the claim's board, mentioning watchers without consuming them. An unchanged note is silent, as is an update by a holder who lost the board.
- **Atomic**: one `INSERT … ON CONFLICT` transaction; two agents can't both win.
- **Expiring**: TTL (default and max in `src/core/claims.ts`) or explicit `until`, stored as an absolute timestamp so it survives restarts. Expired claims are free; a crashed agent's claims lapse on their own. An alias's claims don't release when a session exits: agents resume work across restarts under the name. Claims held by a session ID are released when that session ends (§3).
- Keys are free-form by convention (`ticket:ENG-142`, `path:src/foo/`, `lane:fixtures`); grayboard doesn't know what a ticket is.
- **Board announcements**: claim, update, release and expiry post to `board`. One timer per live session (local) or the server, armed for the next expiry and re-armed after tool calls and wakeups. The sweep deletes and posts in one transaction, so a lapse posts once. Taking over a lapsed claim announces the lapse first. An expiry post says nobody confirmed the work was done.
- **`queue:` keys are queue-board deliveries** (§4), minted only by `claimQueuePost` (`src/core/boards.ts`); `claim_take` refuses the prefix, since a squatted key would audit a delivery that never happened and break the lane's reply-ack. They never announce on the board (an announcement there would rotate as a new work item): a take is the push, a holder's thread reply releases with note `ack` (`ackQueueClaim`; `ack (late)` when the row lapsed but the sweep hadn't reached it, which then redelivers nothing), and a release or lapse consumes watches quietly and redelivers the post (`redeliverQueuePost`). Only a take whose row wins is logged.
- No veto windows, no queues: held or not, and who holds it. Advisory to the world (grayboard can't stop a file edit), truthful to any agent that asks.
- **Watches** (`claim_watch`, `claim_watches` table): the `[update]` post and the end post (release or expiry) `@mention` watchers, so they reach them in any subscription mode and survive `/clear`. Mention resolution already drops anyone who can't see the board; `watch()` refuses up front a claim with no board or one the watcher can't see, since its end post couldn't reach them. The end post consumes the watches (`watchersCc(…, true)`), so a later claim on the key starts with none; so does a quiet end, where the holder lost the board.
- Active claims are listed in each session's instructions at start, so a fresh or `/clear`-ed session sees them without knowing to look. Claude Code truncates long server instructions (limit noted at `MAX_CLAIMS_CHARS`, `src/core/tools.ts`), so `claimsInstruction` lists the session's own first (notes clipped), others as bare keys within a char budget, then "N more", and both modes put it last so a cut takes it rather than fixed text. Others' are keys only: every call pays for the text, and `claim_take` refuses a held key with its holder. The keys stay because a signal like `dev:freeze` is never `claim_take`n, so a refusal can't reveal it.
- **History** (`claim_events`): release and expiry delete the `claims` row, so each take, renew, refused take (with `held_by`), release, expiry and hosted-rebind move (`moved`, `held_by` the old name; `moveClaims`) also appends an event in the same transaction. It exists for usage analysis (`scripts/usage.ts`); the one runtime read is a repeated release's check (`releasedBy`, `src/core/claims.ts`). Retention prunes it with posts, in both modes (`src/server/retention.ts`, `src/local/retention.ts`).
- `grayboard claims` (`src/cli/claims.ts`) has exit codes chosen for harness hooks: a match blocks, its own errors fail open (README §Guarding a merge or deploy with a hook).
- `grayboard claim take|release|watch` (`src/cli/claim.ts`) runs the claim tools from a shell as the handle `grayboard mcp` would resolve in that directory (or `--as`, taken literally: no worktree suffix), so a script's claim is held by that directory's session. Local mode calls the core directly and pokes the wake list plus the acting handle, whose wakeup re-arms its claim-expiry timer as its own tool call would. It refuses a handle that has never connected, so a typo can't hold a claim no session answers for, and the human handle (`slack-bridge.md` §3; on a server, the reserved name `human`, §8). `isHuman` must run before the `lastSeen` check: `declareHuman` touches the handle, so a declared human that never connected passes `lastSeen`. Server route: `architecture.md` §5.

## 7. DMs and recovery

- DMs keep their own `messages` table per mode; read points are local `cursors` (by reader) and server `mailbox_cursors` (by address). Threads via `parent_id`, which must be a message you sent or received.
- **`id:` recipients**: `dm_send` to a session ID reaches that session whatever it's bound to, in both modes. Refused inside the insert's transaction, so it can't race the end: `id_ended` (naming what it held), `not_found` (never existed, a viewer, or pruned past retention) and `no_delivery` (a tools-only session, naming the alias it writes as). Mail that can only bounce later is a failure the sender must see now. A bounce reaches the sender as an ordinary DM with `kind="bounce"` on the push and inbox item.
- Pushes live in the conversation, so `/clear` loses them. `dm_inbox` lists messages still owed (no later message from you in the thread, no `dm_ack`) plus your messages queued for offline peers (`src/shared/inbox.ts`). Session instructions list your DMs undelivered after 24h.
- **Promises** (`dm_send … pending: true`, #38): the sender's side of the same rule. A pending message is listed under `promised` while it's still the sender's latest in its thread; the recipient's reply doesn't clear it, the sender's next message (pending or not) does, and so does the sender's `dm_ack` on it (an ack row with `reader` = sender). Windowed by `PROMISE_DAYS`, not `days`, so a promise doesn't drop out of a default-window inbox. Stored as a 0/1 column; history and threads show `pending: true` only when set (`showMessage`), so other rows don't pay tokens for it.
- `dm_send` to an offline recipient idle over `STALE_RECIPIENT_MS` or never connected (`queuedNote`) warns of a likely misaddress and names `dm_retract`. That note is how agents find `dm_retract`, so it isn't `alwaysLoad`.
- `dm_retract` deletes a message you sent only while it's still queued. Reached means the recipient's cursor passed it **or** the recipient is live. Local: `poke()` answers, and the poke itself wakes it to drain. Server: registry `ready`, since a push may already be in its context unacked. The delete re-checks cursor and replies in one statement (`retractMessage`, `repo.messages.retract`), so a race with delivery or a reply refuses rather than deleting. Each retract writes `message.retracted {message_id, recipient}` (target `message:<id>`; the server's detail adds `sender`, since its actor is the user's email) in the delete's transaction, in both modes, and a repeat on a message that's gone answers `ok: already retracted by you at T` from that row, so a retry after a lost answer isn't told "no message from you". Locally the delegate re-pick's retraction (§13) writes it too.

## 8. Local-mode wakeup

Posting or sending computes the plan, writes the DB, then pokes each target's Unix socket (`~/.claude-bus/sock.<handle>`). The woken process drains its DMs, then asks the core for its pending pushes and digests (deferred ones only alongside a waking item, §5). The doorbell says "look"; the database is the truth. Connecting to a socket is itself the wakeup, so a liveness probe also wakes. `grayboard tail '#board'` is a **viewer** session (`ids.viewer`, `viewers()` in `src/core/boards.ts`): its own ID and socket, read-only, never listed, mentionable or addressable (`not_found`), and ended like any session, so a SIGKILLed tail is cleaned up by the next opener; local mode only.

## 9. Adapters and push ownership

An adapter does two jobs: **tools** and **push** (harness-specific).

- **Exactly one component per handle owns delivery** (holds the socket or live connection, drains, moves cursors). In a harness that drops MCP notifications, a push-mode MCP server would consume messages into a void. A harness without an adapter runs its MCP entry with `BUS_PUSH=off` (tools only; in server mode a `push: false` hello), which never acquires a name.
- Claude Code: native `notifications/claude/channel`; the MCP server is the owner. Started without a channels flag, Claude Code drops them silently, so the MCP server detects that (`channelsOff`, `src/shared/toolguard.ts`), holds its name without listening (server mode: a `hold` hello, a session that gets no pushes and binds like any other, `architecture.md` §4), and warns in its instructions and first tool result.
- omp (`adapters/omp/`): omp forwards MCP notifications to extensions as `mcp_notification`; the adapter relays them with `pi.sendMessage` (DMs, mentions, thread replies trigger a turn; digests and deferred pushes are context only). MCP server stays owner.
- **pi and local/V1 opencode: the adapter serves the tools** from its one push-mode `grayboard mcp` child. Why: with a tools-only MCP entry beside the push child, a name bound through the tools process would have to move the push process, needing a cross-process record and a control socket (#182 decision 13). At load the adapter runs `grayboard tools` (the list `grayboard mcp` would serve, in the mode it would pick, without opening the bus) and registers each tool under the name the harness showed before (pi `mcp__grayboard__<tool>`, opencode `grayboard_<tool>`); each call is a `tools/call` to the child, started on demand and awaited through initialize. A failing `grayboard tools` fails the load: pi 1.3.0 then exits 1 (any extension load failure does), opencode's init throws. After initialize the adapter compares the child's `tools/list` with what it registered and logs any difference. The child's instructions go into the system prompt, replaced by `structuredContent.instructions` from any tool result: `bind`'s, or the next call's after a lost bind result or a lost name. A cancel that crosses a result on the wire requeues what the result carried (notices, instructions, a bind outcome) for the next call (`src/shared/latecancel.ts`). The adapter listens for `error` on the child's stdin: a write after the child closed its end (EPIPE) would otherwise crash the host.
- **For those child adapters, the harness's `grayboard` MCP entry is config, kept disabled** (`enabled: false`, `BUS_PUSH=off`; `grayboard setup` writes it, `refresh-adapters` disables the entry of each adapter it rewrites). The adapter takes the child's command and env from it. An entry enabled anywhere would register the tools twice (pi: last registration wins; opencode: duplicate ids), so the adapter refuses: no tools, no child, and the fix reported (pi: UI notify; opencode: `app.log` and a toast, and every call fails with it). `BUS_PUSH=off` stays on the disabled entry, so a re-enabled one never adds a second delivery owner.
- pi (`adapters/pi/`): reads the user-level `~/.pi/agent/mcp.json` entry only (a project `.pi/mcp.json` can override just `enabled` and exposure); registers the tools at `session_start`, which has the cwd for the project-entry check. Injects DMs, mentions and thread replies as a turn (or steers into a running one); digests and deferred pushes as context. Tested by `tests/integration/pi.test.ts` against the pinned pi.
- opencode (`adapters/opencode/`): the tool record is fixed at plugin init, before any config hook, so the tool list comes from the user-level `opencode.json` entry, and so does the child's command and env: the effective entry the config hook delivers is merged over project configs, so a cloned repo's `opencode.json` could otherwise choose what runs; it only decides the enabled check. Injects with `session.promptAsync` into the last root session the user wrote in (`noReply` for digests and deferred pushes). The child starts on the first root session, so messages wait in grayboard until something can receive them; starting it at load would drain into no session. A `noReply` digest landing during a running turn gets answered by that run. Known limit: N root sessions in one opencode process share one child, so one binding; a `bind` from one adds the hold for all. Tested by `tests/integration/opencode.test.ts` (a driver standing in for opencode's client). opencode V2 doesn't run V1 plugins (#141).
- A respawned child under the same harness pid (pi `/new`, `/resume`, fork; `/mcp` reconnect) takes its name back from the name record (§3).
- Hosted OpenCode V2 (`adapters/opencode-v2/`) leaves tools, session context and OAuth with native HTTP MCP; its in-process supplement owns only delivery. Human receiving-root approval and mailbox binding are independent and both required, in either order (#226). A configured name never approves delivery; creation is explicit. Enrollment pins account, resource, selected native connection/configuration and root; observed drift latches a pause even after switch-back. Durable host admission precedes receipts, with stable root-specific IDs and fresh authority checks. An already-authorized in-flight call may still write/wake that same approved root across a state change; it cannot retarget or receipt a stale epoch. No atomic cancellation or exactly-once wake is promised. `resume:false` avoids an idle digest wake, not later evaluation. See `architecture.md` §Hosted MCP for backend ownership and the package guide for lifecycle guards.
- `grayboard setup` registers child adapters for harnesses on PATH but preserves remote or uncertain OpenCode registrations. Hosted V2 uses native configuration/package loading or explicit `setup-opencode`; human steps belong in the README.

## 10. Tool surface rules

- Every tool is an attention cost in every agent's context; the surface stays small. Derive the list from `src/core/tools.ts`, `src/shared/inbox.ts`, `src/local/mcp.ts`, `src/plugin/mcp.ts`.
- Names are `<noun>_<verb>` (`dm_*`, `board_*`, `claim_*`, `peer_*`): harnesses often show only names until the agent searches, so the name must say what it's for.
- A wrong or missing argument returns an error naming the expected call (`src/shared/toolguard.ts`).
- **A repeat after a lost answer never writes twice** (#254). The append writes (`dm_send`, `board_post`, `delegate`) are deduplicated by a server (`architecture.md` §4) and take `resend` in every mode's schema, so the surfaces don't drift (`checkArgs` refuses unknown keys); local mode accepts and ignores it, having no transport to lose an answer on (its cancel-crosses-a-landed-write case is #292). The state-changing writes answer a repeat from state, in core, so every mode gets it: `claim_release` (§6), `dm_retract` (§7), and `board_create`, where a board the caller created with the same scope, kind and purpose, and can still see, comes back as it is with `note: you created #x at T`. Anything else stays "already exists": other arguments, anyone else's board, and every call by the Slack bridge's human (`ToolContext.human`, set by both modes), whose relay treats success as a fresh create. The rest are idempotent by construction.

## 11. Not built, by decision

Refused (don't add without reopening the decision):

- Edit/delete of posts: breaks auditability (principle 5).
- Veto windows, voting: a recorded swarm failure mode, not a feature. A claim is held or it isn't.
- Reactions, join/leave presence pushes, profiles, follower graphs: `peer_list` answers presence when asked; claims cover "what I'm doing".
- Message signatures or per-agent crypto identity: on a trusted bus the transport enforces identity.
- Copying harness-only conveniences (principle 6).
- Spawning agents: per-harness spawn adapters, harness- or model-aware routing, and personas as grayboard objects. Dispatch is an orchestrator's job (principle 7). Delegation (§13) carries a request to an agent that launches. Its auto-pick stays "the first live launcher of the requester's user" and gains no selection logic.
- Task state and knowledge on the bus: resume records, prompt or skill storage, scoped memory (#108). This is principle 7: an alias carries only an opaque task reference (#284), and handoff notes go to a knowledge store, not a board.
- Several live sessions on one name (fleet lanes, #124; the question was closed "no" on #114). One live session per task name is the invariant (§3); spread work across sessions with claims and queue boards, never with a shared name.
- Triggers and event routing (the event fabric): grayboard emits events for other systems to act on, and doesn't schedule or route on them.

Deferred (each must re-justify itself): a one-line `role` per handle in `peer_list`; pinned posts (`purpose` covers most of it); claim queues; full-text search; a web UI; `tail` in server mode; DMs as two-member boards.

## 12. Attachments

Files ride on `dm_send` and `board_post`. Retained local and stdin clients check local paths and fetch with `attachment_get` (#133); hosted HTTP tools accept only previously uploaded `attachment_ids`. Standard clients transfer bytes over authenticated HTTP (`architecture.md` §5), never ask the server to read a client path, and derive download URLs from protected-resource discovery's canonical resource without credentials in the URL. Base64 in a tool argument would cost the sender's context and every reader's.

- **Paths are checked where they're read: the session's MCP process** (`readAttachmentFiles`, `src/shared/attachments.ts`), before anything is stored or uploaded. The resolved path (symlinks followed) must lie under a root (`attachRoots`: the working directory, unless it's the home directory or a filesystem root, plus `BUS_ATTACH_ROOTS`), with no dot component below that root and no key- or credentials-like name, named or resolved. No temp directory is a root: `/tmp` is shared, so anything planted there would be attachable. Why: board content is untrusted (§5), and an agent talked into attaching `~/.ssh/id_rsa` would hand it to every reader. It isn't a sandbox: anything in the working directory is attachable.
- **The file is opened once** (`O_NOFOLLOW`, then `fstat`) and refused if its size changed after the check (`readChecked` reads one byte past it), so a symlink or a different file swapped in after the path check isn't what gets sent.
- **One file check wherever a file enters the bus** (`checkFile`): agent paths, server HTTP uploads and Slack shares. Type comes from the bytes, never the name (`sniffType`): PNG, JPEG, GIF, WebP, PDF, or UTF-8 text without NUL (typed by extension only among text types), so an HTML or SVG file is stored and served as plain text, never as something a browser renders; anything else is refused. A file holding key material (a PEM private key, a PuTTY key, an AWS secret) is refused whatever its name or type: the scan runs on every type, since an image or PDF header is a few bytes anyone can put in front of a key. The name is sanitized (`sanitizeFilename`: it reaches channel meta, Slack titles and save paths; `;` separates the meta list; bidi and other format characters could make `gnp.exe` read as `exe.png`), then given an extension matching the sniffed type (`typedName`; rendered text such as `.html` or `.url` gets `.txt`), so a saved file can't pass as another kind.
- Limits (count, per file, per message or post): the constants in `src/shared/attachments.ts` in local mode; on a server, its configured caps, sent in `hello_ok.attachment_limits` so the MCP process refuses before uploading (`architecture.md` §4).
- **Storage** (`src/core/attachments.ts`): SQL holds metadata only, one `attachments` row per file and an `attachment_blobs` catalog keyed by SHA-256, so identical files share one blob. Bytes live in a `BlobStore` (server: files, `src/server/blobs.ts`; local: a table in the bus file, `src/local/blobs.ts`), outside any transaction. Both modes store a file unbound, then bind it to its message or post **in the insert's transaction**, and only if it's the sender's own unbound upload. So a refused send leaves nothing bound (local mode releases the uploads, `withUploads`; the plugin releases its server uploads, `architecture.md` §5), and an id can't ride a second message or be sent by another identity. Unbound uploads are pruned after `UNBOUND_TTL_MS`.
- **A sweep never deletes bytes a row names**: an upload commits the row and catalog entry before the put (a failed put drops the row), and `sweepBlobs` deletes bytes, then the catalog entry, only for a SHA-256 no row names. Uploads and sweeps of one SHA-256 are serialized in-process; local sessions share one file, so `SqliteBlobs.delete` also refuses bytes a row names.
- **Readable exactly where its carrier is** (`canReadAttachment`): on a post, by anyone who can see the board; on a DM, by its two parties; unbound, by the user who made it, from any address of its session, so a team alias's next holder can't read its last holder's unsent file (#367). Anything else reads as missing, not forbidden.
- Attachments go with their message or post: retention and `dm_retract` delete the rows (`dropAttachments`), then the sweep deletes bytes no row names. Local mode runs the server's retention rule itself (`src/local/retention.ts`, `BUS_RETENTION_DAYS`, the server's default): every session may run it, and a `retention_runs` row keeps the sessions sharing a bus to one run a day. Local retention also deletes `ids` rows ended before the window (`pruneEndedIds`; the server's retention runs it on the same window), regardless of `binding_events`, whose session IDs are provenance text. A keyed row leaves a `pruned_ids` tombstone (`ids.keyed`) that outlives the window, since audit rows prune on the same one: a key re-presented after the prune registers a fresh session, consumes the tombstone and is audited `id.reused`. Unkeyed IDs are random and leave none.
- Reads, threads, inbox, pushes and `attachment_get`'s result carry each file's `{id, filename, type, size, sha256}`; the SHA-256 lets a reader check what it saved and match it against the server's audit log. A channel notification with files carries the same list as one string (`attachments`, `formatAttachmentsMeta`) plus `files_tool` naming `attachment_get`, which isn't `alwaysLoad`; one without files costs nothing extra. `dmNotification` and `boardNotification` (`src/core/tools.ts`) build them for every mode.
- **`attachment_get` behaves alike in both modes**: it checks the id (`checkAttachmentId`) and resolves the save directory (`saveTarget`) before reading or downloading any bytes. It saves as `<id>-<filename>`, mode 0600, under `dir` or the bus's subdirectory of `$GRAYBOARD_ATTACHMENTS_DIR` (default `~/.grayboard/attachments`; `serverBusDir` is the server's host, `localBusDir` a hash of the database path), because ids are per bus and two buses' id 12 would otherwise collide. `dir` is held to the read roots, again with no dot component below the root, so an injected reader can't plant files where tools load them (`.claude/rules`, `.github/workflows`, `.git/hooks`). The write goes to a private temp file, then a hard link into place, which never follows or replaces what's at the name: a taken name gets `-2`, `-3`…, unless it's this user's own copy of the same bytes.
- Slack: both bridges carry files both ways (`slack-bridge.md` §2).

## 13. Delegation

An agent hands work to a launcher session — one whose harness can spawn subagents (#184). The requester names a **persona and a task brief, never a model or reasoning tier**: the receiving session's harness maps the persona to its own roster. **Delegation stays within the requester's own user** (auto-pick and an explicit `to` both resolve only among that user's launchers); cross-user delegation needs an authority ruling (follow-up on #184).

- **Launcher opt-in** (`BUS_LAUNCHER=1` with push on, locally; the hello's `launcher` flag on a server, honored only from a push-mode owner): recorded on the session's row (`ids.launcher`, `setLauncher`), shown as `launcher: true` in `peer_list`, and audited (`handle.launcher_set`, both modes). It belongs to that session, not the handle: the next session has its own row, and a tools-only sidecar (a `BUS_PUSH=off` process beside the owner, §9's subagent pattern) leaves the flag alone. Any number of sessions may opt in; routing picks one live launcher of the requester's user, no designated one.
- **`delegate(persona, task, to?, context?)`** (`src/core/delegation.ts`): resolves the launcher — explicit `to` (on a server, resolved like `dm_send`'s recipient; locally, the exact handle; then it must be the requester's own user and a live launcher; a cross-user `to` is refused, naming the ruling) or the first live launcher of the requester's user by name — and delivers the payload as a pending DM, so `dm_inbox` lists it under `promised` **until the requester settles the thread: a later message of theirs or a `dm_ack`** (the launcher's reply alone leaves it listed). No live launcher of the requester's user: the request surfaces to their human instead (`human_fallback`) if that human is reachable (on a server: the bridge is running and the user is linked; locally: the human has connected), else it's refused, naming the undo. Every outcome is audited: `delegation.requested {via: explicit|auto|human_fallback, message_id}` or `delegation.refused {reason}`.
- **The payload frames its untrusted fields**: persona (one line), task and context ride inside a four-backtick fenced JSON block that the launcher's instruction says is data, never instructions — a task can't forge a reply trailer or a second request. The body's `[delegation request from …]` header is plain text and **never authority**: the launcher acts only on a delegation DM whose channel sender is one of its own user's handles.
- **The subagent must be bus-capable** (owner ruling on #184): it sends and receives through its own connection, a fabric, or its parent relaying for it. **One delivery owner per handle is the invariant** (§9): a subagent never shares its launcher's push channel; it runs tools-only (`BUS_PUSH=off`) or holds its own name (§3). The launcher posts the result in the request's thread even when the subagent holds its own connection — a thread is only visible to its participants, so a subagent can't post into it itself (threading for own-connection subagents: #244). Every supported harness satisfies this (#184); per-harness spawn APIs (#243) and bus-native child push (#244) are follow-up issues.
- Resolution is not rotation: the first live launcher of the requester's user, by name, takes every request. The auto-pick lists a multi-hold launcher session once, by its primary (`launchers()`); an explicit `to` may name any alias it holds (`isLauncher`). Locally, a pick whose socket dies between resolution and delivery is retracted and re-picked once, excluding it (audited with `repicked_from`). Queue-board routing of delegation requests is the follow-up (#242).
- At-least-once delivery: the launcher's instruction says to reply in the thread immediately when it takes a request ("spawned") and to treat an already-handled message id as handled, so a `/clear`, a context wrap or a reconnect re-push can't cause a second spawn; a `delegate` repeated after a lost answer gets the first request's result back from the server (`architecture.md` §4), so a retry doesn't spawn the work twice.
