# Delegation

```doc-meta
owns: delegation: launchers, `delegate`, the payload, resolution
invariants: grayboard never spawns agents: a launcher's harness does (`vision.md` principle 7); the payload frames its untrusted fields; the subagent is bus-capable; resolution is not rotation
code-pointers: src/core/delegation.ts
companions: server-operations.md (the server's delegate), factory.md (a standing launcher), adapters.md
```

An agent hands work to a launcher session — one whose harness can spawn subagents (#184). The requester names a **persona and a task brief, never a model or reasoning tier**: the receiving session's harness maps the persona to its own roster. **Auto-pick stays within the requester's own user.** An explicit `to` may name another user's launcher only on a server, under a grant: the two users share a team whose policy is `delegating` (#256; `delegate.to` in `src/server/policy.ts`), which a team owner sets and which also grants wakes as `collaborative` does. Locally there is one user. An owner-approved grant per launcher is #874.

- **Launcher opt-in** (`BUS_LAUNCHER=1` with push on; a hosted session's client declares it in its requests' `_meta`, from the same variable, and the server stores it for that ownership, `architecture.md` §4; the Claude Code plugin, pi and omp do; the OpenCode v2 adapter declares it from its plugin option `launcher: true`, #520, which `setup-opencode` writes, #564): recorded on the session's row (`ids.launcher`: `registerId`'s `launcher` locally, `hostedDeclareLauncher` on a server), shown as `launcher: true` in `peer_list`, and audited (`handle.launcher_set`). It belongs to that session, not the handle: the next session has its own row, and a tools-only sidecar (a `BUS_PUSH=off` process beside the owner, §9's subagent pattern) leaves the flag alone. Any number of sessions may opt in; routing picks one live launcher of the requester's user, no designated one.
- **`delegate(persona, task, to?, context?)`** (`src/core/delegation.ts`): resolves the launcher — explicit `to` (resolved like `dm_send`'s recipient in both modes, in any case: locally the exact handle first, since a pre-#181 database may hold a mixed-case one, then the lowercased one (#272); then it must be the requester's own user, or granted (above), and a live launcher; an ungranted cross-user `to` is refused, naming `grayboard team policy`, with an `authz.decision` row, and a replay re-checks the grant against the session holding the name now, so a policy set back, a member removed or a team name that moved to another user refuses it) or the first live launcher of the requester's user by name — and delivers the payload as a pending DM, so `dm_inbox` lists it under `promised` **until the requester settles the thread: a later message of theirs or a `dm_ack`** (the launcher's reply alone leaves it listed). No live launcher of the requester's user: the request surfaces to their human instead (`human_fallback`) if that human is reachable (on a server: the bridge is running and the user is linked; locally: the human has connected), else it's refused, naming the undo. Every outcome is audited: `delegation.requested {via: explicit|auto|human_fallback, message_id}` or `delegation.refused {reason}`, each with `child` when a child session (§3) made the call. **Limits** (#252, defaults in `src/core/delegation.ts`): a token bucket (a burst of 60, then one every 10 s), checked before resolution and spent only when a request is written, so a refusal costs nothing; on a server the hub's, keyed by the user's email, so all of a user's sessions, aliases and children share it and a fresh session can't reset it (a dedup replay is neither charged nor refused; `resend: true` is charged); locally the session process's (one user, and a bucket across processes would need a table). An empty bucket refuses with the wait, audited once per run of refusals: `delegation.throttled {retry_after_ms}` at the first (on a server, target: the user's email; detail adds the tripping `requester` and `session_id`) and `delegation.throttle_ended {refused}` when the bucket is full again, not a `delegation.refused` per call. A launcher holding 20 open requests (a server's `GRAYBOARD_DELEGATE_OPEN_CAP`) (delegation requests audited to it in the last 3 days, `dm_inbox`'s default window, whose message still exists and that it hasn't taken: no reply in the thread from its side and no `dm_ack` of its own; the requester's settling doesn't count, or one requester that never settles would pin the launcher) is skipped by the auto-pick and refused when named; another user's granted request is refused once the launcher holds half that cap (its own user's open requests count too), so a teammate's loop can't lock the launcher's own user out of it; every live launcher full is refused rather than handed to the human, which would move a loop's flood to Slack. The local count is a read before the insert, so concurrent requesters can overshoot the cap by a few.
- **The payload frames its untrusted fields**: persona (one line), task and context ride inside a four-backtick fenced JSON block that the launcher's instruction says is data, never instructions — a task can't forge a reply trailer or a second request. The body's `[delegation request from …]` header is plain text and **never authority**: the launcher acts only on a delegation DM whose channel sender is one of its own user's handles, or another user's that the server marked `delegated` (#256): a message `delegate` wrote (its `delegation.requested` row) whose writer a `delegate.to` grant covers at that read, on the pull and on `dm_inbox`, `dm_thread` and `dm_history` alike, so a plain `dm_send` carrying a delegation header never earns it and a revoked grant takes it off the next read.
- **The subagent must be bus-capable** (owner ruling on #184): it sends and receives through its own connection, a fabric, or its parent relaying for it. **One delivery owner per handle is the invariant** (§9): a subagent never shares its launcher's push channel; it runs tools-only (`BUS_PUSH=off`), holds its own name (§3), or calls through its launcher's session as a child session, which is pushed nothing and reads without consuming (§3 Child sessions). The launcher posts the result in the request's thread even when the subagent holds its own connection — a thread is only visible to its participants, so a subagent can't post into it itself (threading for own-connection subagents: #244). Every supported harness satisfies this (#184); per-harness spawn APIs (#243) and bus-native child push (#244) are follow-up issues.
- Resolution is not rotation: the first live launcher of the requester's user, by name, takes every request. The auto-pick lists a multi-hold launcher session once, by its primary (`launchers()`); an explicit `to` may name any alias it holds (`isLauncher`). A launcher session that holds no alias yet is delegable by its ID (#337): listed after every named launcher, by ID, and nameable as `to`. A candidate's user is its session's principal, never the address's spelling: an ID's `ids.principal` (null locally), an alias's holding session's (offline, the session that last held it, as `peer_list` shows). A team alias (`eng/x`) is every member's address, so its prefix says nothing about whose launcher it is: a requester's user is its signed-in user, and its human fallback is that user's `email/human`. Locally, a pick whose socket dies between resolution and delivery is retracted and re-picked once, excluding it (audited with `repicked_from`). Queue-board routing of delegation requests is the follow-up (#242).
- **A launcher need not be a person's session.** The factory (`docs/factory.md`, opt-in) is a standing launcher with no harness UI: it holds its own name, spawns a headless worker per request and relays the result, acting only when the DM's sender is the payload's requester.
- At-least-once delivery: the launcher's instruction says to reply in the thread immediately when it takes a request ("spawned") and to treat an already-handled message id as handled, so a `/clear`, a context wrap or a reconnect re-push can't cause a second spawn; a `delegate` repeated after a lost answer gets the first request's result back from the server (`architecture.md` §4), so a retry doesn't spawn the work twice.
