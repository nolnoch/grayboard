## Problem

The server runs on one SQLite file. The target platform runs on Kubernetes against managed Postgres (RDS), and a SQLite pod there needs a persistent volume plus replication work that RDS makes throwaway, so Postgres moves ahead of the pilot (#807).

Facts that set the port's shape, from an inventory of `origin/master` (be48f91):

- **`Repo` is not the whole seam.** `src/server/db.ts` runs most of the server's statements, but the raw `Database` also flows from `app.ts` into application, http, slack, teams, retention and the attachment modules, and they call the shared core (`src/core/`: boards, claims, bindings, session_end, delegation, attachments) on it directly. This contradicts `../architecture.md` §4 ("`Repo` is the only server-side store interface"), which holds only for the server's own tables.
- **The core calls back into the server synchronously.** `src/core/boards.ts` keeps a `WeakMap<Database, Access>`; core statements call the server's `Access`, which reads through `Repo`. An async server core forces an async `Access`.
- **Correctness leans on a blocking transaction.** `repo.atomic` is `BEGIN IMMEDIATE` with a synchronous callback (`Sync<T>` makes a promise a type error). A hosted tool call is one such transaction (`hosted.ts` run). While it runs, nothing else in the process runs, so a transaction may read in-memory state (registry liveness, busy and inflight maps, delivery leases, BindGate, limiters, a session's `holds`) and nothing can change it before commit. Several sites (the `no await since` comments among them) depend on this.
- **Read-then-write invariants rely on the single writer.** At least: alias takeover in `holdAlias`, `bindNow`'s exclusivity check against another user's tools-only `writes_as` (`aliasUser`), the alias cap (`alias_cap.ts` says so), `teams.create`, the last-owner checks (`revokeBinding`: a team's, #927, and a service's, #270), OAuth `redeemCode` and `rotateRefresh` replay detection, the `createRequest` capacity count, the attachment quota, `dedupWrite`, `claim()` (`core/claims.ts`), and the hosted `full()` capacity check. Postgres's default READ COMMITTED serializes none of them.
- **`afterCommit` and the auth cache are SQLite mechanisms.** `afterCommit` monkey-patches `db.transaction`; the auth cache is keyed on TEMP triggers plus `PRAGMA data_version`, which also sees another connection's commits (an operator's `sqlite3`, `scripts/loadtest.ts` seeding users and tokens), and `authRead` pins one generation in a single `pinned` variable that assumes one auth read at a time (#881).
- **The driver.** `Bun.SQL` (built in; no dependency) speaks Postgres. Probed on Bun 1.4.4 against `postgres:18`: `int8` returns as a string (or `BigInt` with `bigint: true`; no per-type parser, and `BigInt` breaks `JSON.stringify`); SQLSTATE is in the error's `errno` (`40001`, `23505`), not `code`; `sql.begin(...)` gives a transaction handle; `RETURNING` and `ON CONFLICT ... DO NOTHING` behave as in Postgres.

## Decisions

### D1. Fork the server core; local keeps its own (maintainer, 2026-11-14)

The server gets its own async core on Postgres under `src/server/store/`. `src/core/` stays synchronous SQLite for local mode and loses its server callers. Drift between the two is caught by a black-box conformance suite on the tool surface run against both modes, not by sharing code. The server's copies of board, claim, binding, session-end, delegation and attachment logic are ports, so a later fix to one side names the other in its PR (the conformance suite is the backstop).

### D2. Transactions are explicit values

- `type Read` is a statement handle (the pool, or a transaction); `type Tx extends Read` adds `afterCommit(fn)`, `savepoint(fn)` and `beforeCommit(key, fn)` (a hook on the root Tx after the body fulfils and before `COMMIT`, P3 A7g). Every store function that writes takes a `Tx`; one that only reads takes a `Read`. No module holds an ambient pool it can query behind a caller's transaction: a stray pool query inside a transaction runs outside it, and at pool exhaustion it deadlocks against the transaction holding the last connection.
- `write(fn)` opens a transaction through the write queue and passes the `Tx`. Inside one, `write` refuses; nesting goes through `tx.savepoint`, whose body writes on the savepoint's own Tx (`Repo.atomic` is gone, #807 P3 A1).
- `afterCommit` callbacks live on the `Tx` and run in registration order after `COMMIT` resolves, never on rollback, and the synchronous part of each runs before the write queue (D4) is released. So the next queued transaction sees every in-memory effect of the last, as it does today when effects flush before anything else runs. This replaces the `db.transaction` monkey-patch.
- The handle types and the backend-neutral half of this contract (liveness, the savepoint template, `beforeCommit` key bookkeeping, `isTx`/`afterCommitOf` dispatch) live once in `src/server/store/tx_base.ts`, which imports nothing at runtime so a `pg/` module can build on it; a backend supplies only a savepoint frame's statements, where an effect waits for the commit, and a `settled` hook that moves or drops a settled savepoint's effects. A savepoint's Tx closes as its body settles and its parent stays blocked until the frame has, so an un-awaited task can't use either while an async `RELEASE` or `ROLLBACK TO` is in flight. The template awaits a frame's commit or rollback only when it returns a promise, so a SQLite savepoint still settles in the same turn as its body.
- On Postgres (`src/server/store/pg/tx.ts`) a savepoint is raw `SAVEPOINT`/`RELEASE`/`ROLLBACK TO` with a frame stack per transaction, never Bun's `tx.savepoint`: Bun releases an outer savepoint while an un-awaited inner one is open, then commits the inner one's rows although its body threw. The stack carries weight there: `ROLLBACK TO a` destroys `b` and `RELEASE a` releases it, and a later statement naming `b` fails 3B001 and aborts the whole transaction, so a frame an enclosing statement or the transaction's end already ended sends nothing. A savepoint's effects and `beforeCommit` keys move to its parent only after its `RELEASE` succeeds; a `RELEASE` that fails 25P02 (its body swallowed a statement error) is undone with `ROLLBACK TO` and rejects `TxAborted` (D6), and the parent goes on. The root's effects flush after `begin` fulfils (after `COMMIT`), still before the queue's next body. Postgres has no synchronous body: every commit is async, so `post` always returns false, and a post from the queue's holder (its `committed`, its effects) queues behind the bodies already waiting, where SQLite's commits before the next body. Only posted rows see that order, and none feeds in-memory state; the Slack bridge's seq-guarded posts queue FIFO, so the latest `seq` commits last and `done` reads after the progress writes queued before it (C7).
- `Access` (the authorization seam) becomes async and takes the caller's `Read`, so a policy read inside a transaction sees that transaction. This lands with the core's server-side ports (P3): until then the server still calls the synchronous `src/core/`, whose statements call `Access` synchronously.

### D3. Database invariants move into SQL

Each read-then-write invariant becomes one statement or a lock on a row the invariant hangs off, so it holds at any isolation level and on any number of pods:

| Invariant | Form |
|---|---|
| OAuth code single use; refresh-token rotation replay; a consent request bound to one browser session and decided once | a code is spent when its `grant_id` or `session_id` is set: `UPDATE oauth_codes SET grant_id = $g WHERE hash = $h AND grant_id IS NULL AND session_id IS NULL RETURNING ...`, and rotation the same on the refresh token's spent marker, after locking its grant `FOR NO KEY UPDATE` so a grant revoke serializes with it and a replay's revoke never upgrades a shared lock (#1066); zero rows means replay, and the replay path revokes the grant. The request binds with `UPDATE … WHERE coalesce(data->>'consentSessionHash', $s) = $s` and is consumed by `DELETE … RETURNING`. On Postgres the loser's statement waits on the winner's row lock and matches nothing after its commit; its re-read is a new statement that sees the winner's row. No lock is added |
| An alias's hold (`repo.bindings.take`; core's `holdAlias` locally), `claim()` | `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE <the takeover is allowed> RETURNING ...`: zero rows means held. For a hold the takeover allowed is the same ID's re-take: no other ID ever takes a held alias (a hosted bind ends a stale contender first). Before the upsert a take locks the alias (`aliases.lock` "use", below) and the taking ID's `ids` row `FOR KEY SHARE`, unended (E4): an end's `FOR UPDATE` makes it wait and then return null (`src/server/store/pg/bindings.ts` `lockLive`; the server's claim take locks the acting ID the same way and refuses an ended one, `src/server/claims.ts`). So the session end must never lock an `aliases` row `FOR (NO KEY) UPDATE` after an `ids` row `FOR UPDATE`, or a bind that ends a stale holder and then takes deadlocks against a plain take. A claim's release, a queue reply's ack, the sweep's expiry and the take of its watchers are each one conditional `DELETE … RETURNING` (`src/server/store/pg/claims.ts`), so the ack deletes only a row its lane still holds; a watch reads the live claim `FOR SHARE`, so a release waits for it and tells the watcher, or the watch finds no claim |
| An alias is held or written as by one user (`bindNow`'s `aliasUser` check; a tools-only root registering `writes_as`), and a deleted alias is held by no one (`identityDelete`, `teamDeleteAlias`, `adminServiceDeleteAlias`, the Slack unlink: the `aliasUser` check, then the delete) | each path locks the alias row through the aliases store's `aliases.lock` before checking the other: `FOR NO KEY UPDATE` for a take and a `writes_as` registration (two of them serialize: `bindings.take`, and `hostedWritesAs`' create path through `lockedUserOf`, `src/server/alias_use.ts`), `FOR UPDATE` for a delete. No table has a foreign key to `aliases`, so no FK check's `KEY SHARE` meets either; `aliasUser`'s tiebreak (`started_at`, then `rowid`) is `ids.seq` on Postgres |
| Write dedup (`dedupWrite`) | insert the receipt first (`ON CONFLICT DO NOTHING RETURNING`); zero rows means a duplicate. A duplicate reads the stored result, unless its message was retracted (#306): then a conditional `UPDATE` on that receipt replaces it, the write goes out fresh and `request.receipt_stale` is audited, as today. `resend: true` skips the receipt check, as today. On Postgres the claim's loser waits on the winner's uncommitted receipt, and a winner whose write throws frees it at the savepoint's `ROLLBACK TO`. A replay whose message a retract removes before it answers is accepted: it wrote only its `request.replayed` row, as the serial order replay-then-retract would |
| Principal names unique across users, teams and services (`teams.create`) | `principals.name` is already `UNIQUE`; the store relies on it and on `teams.name` (a team's name is a principal's too, and its insert runs first) instead of a prior read, and `23505` on either constraint maps to `PrincipalTaken` |
| A team's board is its own (`teamCreate`, #1069) | team create inserts the team and its board in one savepoint and refuses when the board insert (`ON CONFLICT (name) DO NOTHING`) wrote nothing: a `board_create` of the name that committed after the create's board check would otherwise leave the team a board it doesn't scope. The insert waits on an uncommitted board row of the name, so the refusal sees it; the 409 is the check's, and the savepoint rolls the team back (`tests/integration/pg_team_board_race.pg.test.ts`; on SQLite a trigger lands the board in the gap) |
| Count caps: alias cap per scope, attachment quota per user, hosted `full()`, a launcher's open delegations | The alias cap: a transaction-scoped advisory lock per scope (`ALIAS_CAP_LOCK`, `hashtext(kind:ref)`, `src/server/store/pg/aliases.ts`), taken in `aliasCapRefusal` before its count, which re-finds the name after the lock; not the scope's parent row, since a scope's parent spans three tables (user, team, service) and `FOR UPDATE` on a missing row locks nothing. The attachment quota: a transaction-scoped advisory lock per uploader principal (`ATTACH_QUOTA_LOCK`, `hashtext(principal)`, `src/server/store/pg/attachments.ts`), taken first in `insertUpload`; not the `users` row, since an uploader principal isn't always one (a service) and `FOR UPDATE` on it would block every insert whose foreign key names the user. A launcher's open cap (`DELEGATE_OPEN_CAP`): `delegation.facts`, on the delegate's savepoint, takes one advisory lock per target core could pick (the named target, or each launcher of the requester's user, re-read after the lock; `DELEGATE_CAP_LOCK`, `hashtext(target)`, one statement in key order, `src/server/store/pg/delegation.ts`) before its counts, so two delegations at cap-1 count in turn; not the launcher's `ids` row, since the count is keyed by `access_log.target` (possibly an alias) and that row is the end's and every send's lock. Hosted `full()` has no parent row: one transaction-scoped advisory lock for every user (`HOSTED_CAP_LOCK`, `src/server/store/pg/hosted.ts`), taken in `admit` before its counts; a creating request re-reads its row after it |
| The OAuth caps: consent requests per browser and in all, live browser sessions, a service credential's mint bucket and unexpired-token cap, its two live secrets and its last live one (`createRequest`, `createBrowserSession`, `mintServiceToken`, `rotateServiceCredential`, `revokeServiceSecret`, #270) | `pg_advisory_xact_lock(class, key)` before the count, one named class per cap (`src/server/store/pg/oauth.ts`): the requests' two caps share one global key (the total's count serializes every creator, so a per-browser key would add nothing), browser sessions one global key, and a credential's secrets and its mints each a key on `hashtext(client_id)`. Taken at the method's top and never inside a savepoint (`ROLLBACK TO` frees it). `findActiveAccess` also refuses a token whose `secret_id` is revoked, so a mint that slips past a secret's revoke (its `UPDATE` can't see a token committed after it) mints nothing usable. `revokeServiceCredential` takes no advisory lock: it reads the credential's grant `FOR NO KEY UPDATE OF g`, so a second concurrent revoke waits, re-checks the grant after the first commits and answers `not_found` as on SQLite (one revoke, one audit row); the revoked grant is what every mint and use checks |
| A user's revoke-all catches every grant, code, CLI session and service credential minted for them, and every browser session (a live one consents without the IdP, #1552); a per-grant revoke (`revokeUserGrant`, `sessions.revokeOwn`) also ends the browser sessions and unspent codes under the same users-row lock, and a locked `decideRequest` re-reads its browser session after the user's `FOR SHARE`, so it either commits first and loses its code or waits and finds no session (`users.setDisabled`, `sessions.revokeAllForUser` against `redeemCode`, `redeemLoginCode`, `decideRequest`, `createBrowserSession`, `addServiceCredential`) | each mint reads the user `SELECT … FOR SHARE OF u` (`activeUser` with its lock, `src/server/store/pg/oauth.ts`); `setDisabled`'s `UPDATE users` and `revokeAllForUser`'s `SELECT … FOR NO KEY UPDATE` take the row first (`src/server/store/pg/identity.ts`). A mint holding the share makes the revoke wait and then see its rows; a mint after the revoke waits and finds the user disabled. A plain FK insert takes only `KEY SHARE`, which neither conflicts with. A revoked grant's hosted sessions end in the same transaction through a port the store is given (`src/server/store/pg/hosted_port.ts`), always after the grant revoke: `revokeGrant` and the user-wide end both take the grant row before any hosted row, so a token revoke racing a disable can't deadlock |
| The boot cutover of pre-built-in OAuth grants runs once across pods (`revokePreBuiltinGrants`) | claim the `server_state` key first, `INSERT … ON CONFLICT (key) DO NOTHING RETURNING`, and act only if it inserted: a second boot waits on the uncommitted key, then returns 0 without revoking or auditing. Its count is what its `UPDATE … RETURNING` revoked |
| A team keeps an owner (the last-owner check (`revokeBinding`, #927)) | every role-binding and membership writer (`roles.grant`, `roles.revoke`, `teams.addMember`, `teams.removeMember`) first takes one transaction-scoped advisory lock (`ROLE_WRITE_LOCK`, `src/server/store/pg/identity.ts`), outside the store's own savepoints (`ROLLBACK TO` frees a lock taken inside one), then deletes and counts owners. `addMember` takes it so a last-owner revoke counts the member it adds: without it, an owner adding a member while an admin revokes that owner leaves two members and no owner. `removeMember` takes it unconditionally: revoke returns early for a non-owner, which is exactly the member a concurrent `team_owner` grant is making an owner. One lock, so one lock order and no deadlock; role writes serialize server-wide, which their rate allows |
| A service keeps an owner (`revokeBinding`'s `service_owner` count, #270) | the same role-write lock, then count owners |
| A grant or revoke re-checks its granter's authority in its own statement (`authoritySql`, #927) | the same role-write lock: under READ COMMITTED two org admins revoking each other both see the other's binding still present and leave none, which no serial order reaches. Revocation is strict: a grant or a membership change whose actor's authority is being revoked commits before the revoke or not at all. `addMember` re-checks the authority in its `INSERT … SELECT … WHERE`; `removeMember` reads it once under the lock before any write, since its own revoke may delete the binding it rests on (an owner removing themselves); either refuses with `AuthorityLost` (403) |
| A refusal thrown after a write (`LastOwner` after the revoke's `DELETE`, `upsertUser`'s `PrincipalTaken` after its rename) | the store function runs in its own `tx.savepoint`, so a caller that catches the refusal and commits keeps none of the refused call's writes: `revokeRole`, `teamLeave` and member removal catch `LastOwner` and commit the 409. No caller catches `PrincipalTaken` today (dev login and the sign-in propagate it); for it the savepoint is the store's guarantee. So does every statement whose `23505` is control flow (`teams.create`, `services.create`, the sign-in link), since an error caught without one aborts the transaction |
| An ID ends once, and a send to it either lands in the end's bounces or is refused (`repo.sessionEnd.end`, `repo.sessionEnd.refusal`) | the end first `SELECT ... The end then locks its unended children's rows `FOR UPDATE` before any other row it touches, and takes the rest in one order (`src/server/session_end.ts`'s header: unread mail, claims and their posts in post id order, forget's outbox then subscriptions, holds); it takes nothing `SKIP LOCKED`, so a hosted child's end through `PgSessionEndPort` may wait on an in-flight write, bounded by `lock_timeout` |
| A lazily created alias exists once (`aliases.create` from a bind, a delegation, a `writes_as`), and a session ID registers once | insert-if-absent: `INSERT … ON CONFLICT (address) DO NOTHING RETURNING`; zero rows means it exists, and the second creator waits on the first's uncommitted row instead of failing `23505` and aborting its body. | A retract deletes only a message nobody has read or replied to, and leaves no ack behind (`messages.retract`, `ack`, `markDelivered`) | retract locks the message `FOR UPDATE`, reads `delivered_at` from the locked row, then reads the cursor and the reply check in a later statement (a new snapshot), so a reply or a delivery stamp committed while it waited answers `replied` or `read`, and an ack committed first is deleted with the message (`retracted`); an ack inserts `… SELECT … FROM messages m WHERE m.id = $1 FOR KEY SHARE OF m ON CONFLICT DO NOTHING`, so it lands before the retract's ack delete or finds no message (`dm_acks` has no FK). One order: grant, root, child, then capacity; under capacity (the nested sweep) the target and its dependent rows are taken `SKIP LOCKED`, and a busy one waits for the next tick |

`MAX_HOLDS` counts a session's in-memory `holds`, so the write queue covers it until Stage 4 moves holds out of process.

These forms also run on SQLite except `FOR UPDATE`, which SQLite's single writer makes unnecessary. The server-only sites without a lock (OAuth, `dedupWrite`, `teams.create`) take them before Postgres does (P2 below); the count caps and the last-owner check (`revokeBinding`, #927), whose forms need `FOR UPDATE`, an advisory lock or the role-write lock, take theirs in P3. Claims already run theirs in core (`takeClaim`'s conditional upsert, `releaseClaim`'s conditional delete, `src/core/claims.ts`), so both modes share the form; their Postgres statements order handles and keys with `COLLATE "C"`, matching SQLite's byte order, since a default collation such as `en_US` ignores `-` and `_`. The other shared-core sites (`holdAlias`, the attachment quota) take theirs in the server's ports (P3), so local mode's core is untouched there.

Isolation stays READ COMMITTED. SERIALIZABLE everywhere would turn every conflict into a retry of a whole tool call, whose in-memory side effects then need making re-runnable, for no gain at one pod.

### D4. In-memory state: the write scheduler until Stage 4

Stage 3 is one server pod. Once statements are awaited, other requests run between them, so a transaction that reads the registry, a lease map, BindGate or a limiter can see it change before commit. SERIALIZABLE does not cover memory, and an advisory lock helps only if every in-memory mutator takes it.

- Every write transaction runs through one in-process scheduler (`store/queue.ts`, #1510). A body is exclusive (`write`, `post`) or keyed (`writeKeyed(keys, fn)`): an exclusive body conflicts with every body, a keyed one only with exclusive bodies and keyed ones sharing a key. Conflicting bodies start in arrival order, so a stream of keyed bodies never starves an exclusive one, and at most W run at once. A body's slot is released only after its effects and `committed` (or its rejection) have run. Deciding what starts next walks no waiters: an arrival list, a FIFO per key and one of exclusive waiters, and a heap of keyed waiters that head every key they hold (#1520 L3). Exclusive is the default; the rest of D4 holds for every exclusive body, and a caller becomes keyed only once its body is shown not to read state another keyed body changes, nor to depend on commit order (below).
- **Keyed callers.** Each writes only rows no keyed body of another key writes, takes its locks in one order (below), reads no in-memory state another keyed body changes, queues no change notice or effect (renew and receipt opt in to theirs, below), and touches no auth table, so keyed bodies can't deadlock each other, and every other writer of their rows is exclusive and never overlaps them. Lock order for every keyed body: the grant `FOR SHARE`, then a root's `hosted_sessions` row, then a child's, then an `ids` row; an UPDATE locks only the row it writes, after any lock above it. Keyed bodies take only share locks on grants, and those don't conflict with each other.
  - The hosted gate's fast path (`hosted.ts` `keyedBody`), keyed `root:<root id>` from the pool's read of the row, for a request whose row exists and isn't parked: its authorization read in the body (`authorized(p, tx)`, uncached there: the auth cache's `ownsTx`), the grant `FOR SHARE` (`grantLive`), then settle and rowFor (the root's and row's `FOR UPDATE`, the `ids` row's `FOR NO KEY UPDATE` for facts) inside a read-only probe (`Repo.readsOnly`), then the touch. Anything settle or rowFor would write (an end, a park or eviction, an unpark, a creation, a facts or launcher change, an audit or refusal row, the capacity lock) refuses `ProbeWrite` before its statement is sent; so does an `ApplicationError` there, or a row under another root. Each is a miss: the body has written nothing, its refusal rows are dropped, and the exclusive gate body runs as it would have, so miss-then-exclusive writes what the exclusive body alone writes. The probe guards SQL only: an in-memory write settle or rowFor made before their first SQL write would run twice on a miss (none does: `countRefusal` and `sweptAt` come after the capacity lock). The launcher declaration reads before it writes (`store/pg/hosted.ts` `declareLauncher`), so only an ownership's first declaring request misses. A refusal of the authorization or the grant, before the probe, is the request's, as the exclusive body's would be. Postgres only: `readsOnly` is absent on SQLite. The exclusive writers of these rows (revoke, disable, bind, end, park, sweep) never overlap it on one process; a revoke or disable that committed before the body began is what its authorization reads (READ COMMITTED reads each statement's snapshot), and across processes a grant's revoke waits on the share lock and the rest on the rows' locks. A first-contact request (one that may create its row) that reads no row while another of this process is creating that ID (an MCP client's second wire, opened at once) waits once for the creator's exclusive body (`withGate`'s `creating`, #1537a) and reads again, so it runs keyed instead of a second exclusive body. Only such requests register or wait; the creator releases its entry when its exclusive body settles, before the request's own work runs, and on every exit including a throw before the body. The wait is advisory: afterwards the request takes any later request's path (a refused create is refused again by its own exclusive body; another user's row is a miss into the refusal and its `authz.decision` row), one still reading no row runs its own exclusive body without a second wait, and an abort while waiting rejects `RequestAbortedError` at once, having written nothing. Postgres only, like the fast path.
  - The prior's touch (`hosted.ts` `withPrior`), keyed `root:<root id>`: authorization in the body, the grant `FOR SHARE`, plain reads compared with the exchange's selection, then the touch; a difference is a miss into the full gate. So is a request whose model, effort or launcher declaration differs from the stored one (`priorWouldWrite`): rowFor writes those only on a change, and a request built before a switch that commits after it (a lease op with the old facts) reverts them, so this request must write its own (#364). A subscriber's second gate body takes the exchange's verdict too (#1537 C5, C7): `control`'s renew, receipt and pending and `owning`'s open and bind run the prior instead of a full gate, open and bind as a writer on the BindGate (`bind`, not `call`), so a bind or an end never interleaves them, and a miss runs the full gate as they did before, outside that BindGate callback. A stale verdict (an end, a rebind, a park, a lapse) is a miss, so its refusal, refusal row and audit are the full gate's. A revoke or disable is refused inside the prior's body instead: on Postgres it reads authorization in its transaction always, and on SQLite as the gate's exclusive body does (again when the body waited in the queue or anything committed since its pool check), so a body that waited behind the revoke refuses `unauthenticated` with no row, as the full gate's waited body does, and never reaches renew's lease check, which would answer `not_found` and audit a stale capability. `hosted.pg.test.ts` compares both arms' outcome, leases and every non-OAuth table for end, rebind, grant revoke, token revoke and disable (rebind and grant revoke also by an outside writer); `hosted.test.ts` compares outcome, audits and the row's state for the #907 windows and a revoke while the body waits in the queue. Renew and receipt keep their own probe's ownership check (above): the prior is checked before their body, not inside it. Release and unbind keep the full gate. Skipping the second body outright isn't parity-preserving: the gate's settle ends a lapsed or disabled root, its rowFor admits and audits a new ownership, and its authorization refuses `unauthenticated` where renew's lease check would answer `not_found` with a stale-capability audit.
  - The end-of-call touch (`hosted.ts` `touchAfter`), keyed `root:<root session id>`: reads, then `last_seen_at` of the root's row and then the calling row (the root or one of its children). A root's children share its key, so two calls under one root touch one at a time; touches of different roots write disjoint rows.
  - A close's last-seen touch (`application.ts` `close`), keyed by the writer's hosted root (its own ID outside hosted) and `id:<writer>`: one `ids.last_seen` UPDATE, a column no key, foreign key or trigger covers. The root alone doesn't exclude every other writer of the row (#1527 L1): it is fixed when the session is built, so two sessions of one writer ID can carry different roots, and their touches would commit out of order and move `last_seen` back; the ID key starts them in arrival order, each stamping the clock as it runs. A keyed gate body may hold the row for its facts read and writes no `last_seen`; the one-statement touch waits on it and on nothing after, so no cycle forms. Close's human release row stays exclusive.
  - A posted audit (`audit.ts` `writeAudit` outside a body, `Repo.postKeyed`), keyed by its subject, `audit:t:<target>` (`audit:a:<actor>` without a target): one `access_log` INSERT, a table with no foreign key or unique column beyond its identity. A subject's rows commit in posting order, so its history reads in order by id and `audit.last` (a pair's newest by time, then id) never takes an older row as newest; rows of different subjects overlap and may commit out of posting order, which nothing depends on.
  - Delivery's renew (`delivery.ts`, #1510 chunk 4), keyed `root:<root id>` (the gate's row: `control` admits only a root): in a probe, the root's `FOR UPDATE`, a comparison with the gate's row (session, root, ownership, bind generation, grant) and the lease check (`get`: the lease map, its match with the locked row, the token's authorization on the body's Tx); then the root's `lease_deadline` and `last_seen_at` (`hosted.update`), whose notice's facts read runs in a `beforeCommit` hook on the body's Tx (`hosted.ts` `readHolder`: the row, its `alias_holds`, and on a holder mismatch the full `hostedBuildFacts`, all reads), and the lease map again. The update's change notice is load-bearing: it hands delivery's listener the row whose deadline `deliver()` judges, and the streams' stamps their recheck time, so a renew without it would stop waking its lease a TTL after open. It is the one notice a keyed body queues: renew opts in to `hosted.update`'s (`Repo.writeKeyedEffects`, below), for its own root's row only, and `committed` (the lease's `expiresAt` and hooks) runs as an exclusive body's does. The notice's listeners and `committed` run after `COMMIT`, after the body's open transaction is dropped (`store.open.delete`), so `inTransaction`, the pool-read refusal and the auth cache's `ownsTx` answer as outside any body. The listeners are every hosted observer, run synchronously as under the exclusive renew: hosted's `reconcile`/`applyNamed` for this root (which may close and rebuild its holder session, touching `hub.registry` for its addresses), delivery's listener (this root's leases), `mcp.ts`'s, which judges every rowless live stream of any session against its stamp, and application's ended-children observer (empty at a renew's flush: its queue fills after an end's commit). No keyed body of another root reads what these write mid-body: they're synchronous, so another body sees them only between its own awaits, as it would see an exclusive renew's; the root's own keyed and exclusive bodies wait for the slot, released after them.
  - Delivery's receipt, keyed `root:<root id>`: in a probe, the root's `FOR UPDATE`, the same comparison, every check the exclusive body makes (the lease, each id's issue and fence, each board's visibility, the directs' order against `pending`'s unread), and each push's board kind; then the session's own rows: each direct message's `delivered_at` and then its address's `mailbox_cursors` row, message by message in id order (`handleAck` sorts the ids, scope pair 4: message 1, cursor X, message 2, …), then each board item's `outbox` row and, for a push subscription, its `subscriptions` row, per address. Its afterCommit effects (`receiptBoards`: the session's `inflight` and `boardDrain`) and `committed` (the lease's issued and acknowledged maps) are this root's session's and lease's alone. No notice: none of these writes queues one.
  - **Renew's and receipt's misses.** Before any write: a row other than the gate's root, or one whose ownership, generation, grant or root changed since the gate read it (renew and receipt never extend or acknowledge for another ownership); a stale capability or any other `ApplicationError` (the exclusive body then refuses it and `refused` audits it once, outside the body); a push on a queue board (its first acknowledge credits the take, a `claim_events` UPDATE); and anything the reads would write (`pending`'s lost-ack repair of a push its reader can no longer see, or `valid`'s terminate). After the first write, a renew whose lease was finished meanwhile and an `ApplicationError` from the writes (a session closed meanwhile) miss too: the body throws, so its writes roll back and its effects never run. On a miss the exclusive body runs as it would have (`miss-then-exclusive writes the same rows`, `hosted.pg.test.ts`). `valid`'s terminate is unreachable keyed on one process: the lease check's authorization reads the user active on the body's Tx, and a disable is exclusive. A disable another process (or `psql`) commits between those two reads does reach it inside the receipt's probe: terminate's in-memory close runs and its row write refuses, so `terminate` tells the transport in a `finally` (its lease finishes, as the exclusive body's terminate finishes it) and the exclusive body then refuses the stale capability. Neither renew nor receipt grows past its own session's rows without the store refusing: a notice other than `hosted.update` of the body's own root refuses, and so does the queue credit (`boards.acknowledge`), a backstop for the probe's board check.
  - **Pair 5 (receipt against a session end): ends stay exclusive.** On one process an end never runs beside a keyed receipt, so receipt's order (messages and cursors, then outbox and subscriptions) never meets end's (outbox, then subscriptions, then cursors). Across processes (#808) both take the root's `hosted_sessions` row `FOR UPDATE` before any of those tables (an end through the hosted store locks it first), so they serialize there; reordering receipt would buy nothing while ends are exclusive. Pair 6 (`acknowledge` against `board_read`'s multi-row outbox UPDATE) never overlaps on one process either: `board_read` runs in the exclusive tool body, not under the root's key, until a later chunk keys tool bodies.
  - **Lock order, per pair** (tables each body locks or writes, in order; `=` a shared key, so the two never overlap): gate: grant `FOR SHARE`, root and row `hosted_sessions` `FOR UPDATE`, the `ids` row `FOR NO KEY UPDATE`, their `hosted_sessions` touches. Prior: grant `FOR SHARE`, the `hosted_sessions` touch. Touch: root's, then the row's `hosted_sessions`. Close touch: one `ids` row. Audit: one `access_log` INSERT. Renew: root `hosted_sessions` `FOR UPDATE`, then its UPDATE. Receipt: root `hosted_sessions` `FOR UPDATE`, then per direct message in id order its `messages` row and its address's `mailbox_cursors` row (interleaved), then `outbox` and `subscriptions`. Renew's notice adds reads only (its facts hook).
    - Renew or receipt against gate, prior, touch, renew or receipt of the same root: `=`. Of different roots: no row in common (each root's `hosted_sessions` rows; receipt's messages, cursors, outbox and subscriptions rows are its own addresses', each a hold of one session). That disjointness, not the sort, is what rules out a cycle between receipts of different roots: a lease session's addresses are its holds and its root ID, a hold belongs to one alias, and a hold that moves bumps or ends the losing root on one process, so its lease turns stale before two sessions could share an address. If two receipts ever shared one, the interleaved cursor rows would deadlock them despite the sorted ids (A: message 1, cursor X; B: message 2, waits on cursor X; A: message 2), which Postgres reports as 40P01.
    - Renew or receipt against a close touch: no table in common (`ids`; receipt's `messages` UPDATE changes no key column, so it takes no lock on `ids`). Against a posted audit: none (`access_log`; a refusal's audit is posted after the body).
    - Against every exclusive body (sends, posts, retract, prune, end, bind, revoke, sweep): never overlapping on one process. Across processes (#808): a send inserts its message and takes `ids` `FOR KEY SHARE`, which no keyed body holds against it; a post inserts its post and outbox rows, never receipt's existing ones; a retract locks one message, then deletes, holding nothing receipt wants first; a prune locks its batch by id and receipt marks by id (pair 4); an end, a bind and a sweep lock the root's `hosted_sessions` row first, as renew and receipt do; a revoke holds the grant, then waits on the root row, and renew and receipt hold the root row and take no grant lock.
- **The store refuses what a keyed body must not do** (Postgres; SQLite's one writer has no overlap to guard). A keyed body's transaction carries its keys, savepoints included (`store/pg/tx.ts` `refuseKeyed`). Ids commit in allocation order only among bodies that exclude each other on a stream, so `messages.insert` and `messages.bounce` refuse a keyed body that lacks `dm:<recipient>`, and `boards.insertPost` one that lacks `board:<name>`; no caller holds those keys yet. `hosted.lockCapacity` refuses every keyed body: admission and its nested sweep stay exclusive. So does every `claim_events` insert (`recentEvents` reads them newest by id), every change notice (`store/notices.ts`: `marks` and `change` refuse before the wrapped write runs, `pg_repo.ts` wires `refuseKeyed`), every `afterCommit` effect and `beforeCommit` hook, and a `committed` callback, which `writeKeyed` and `postKeyed` refuse before the body runs: each runs other code at the commit, in the body's context, while other keyed bodies run (#1527 L2), and a hook registered in a probe would run after it, unchecked. `PgTransactions.writeKeyed`'s `{ effects: true }` lifts the effect, hook and `committed` refusals for a reviewed caller, and its `notices` names the change notices (by wrapped op, `hosted.update`) that caller may queue, each only for a row whose `root:<id>` the body holds (`store/pg/tx.ts` `refuseKeyedNotice`); every other notice still refuses. The Repo's `writeKeyed` takes no options (`pg_repo.ts`), so no Repo caller can pass them; `Repo.writeKeyedEffects(keys, notices, fn, committed)`, Postgres only, is the named opt-in, called only by the reviewed callers above (renew with `["hosted.update"]`, receipt with none). The ops it accepts are fixed in `pg_repo.ts` (`KEYED_NOTICE_OPS`: `hosted.update`), so a caller can't widen them; it rejects any other name before the body runs. A keyed body that set `gb.auth_touched` (D5) throws before `COMMIT` and rolls back, since the generation bump must land before the next body and auth writers are exclusive. Each refusal names the operation and the body's keys, so a misclassified body fails in the first test that reaches it. Inside a `readsOnly` probe (`store/pg/tx.ts`) a store's refusal is the probe's `ProbeWrite`, and so is any statement whose text isn't a `SELECT` or names an advisory lock (a `sql.fragment` counts as its own text, so a read that opens with a `SELECT` fragment passes), and any notice, effect or hook, opted in or not; the probe rejects with the first one even when the probed code caught it.
- **A synchronous fan-out from inside a body** (a notice's listeners, run at commit) runs other requests' listeners in that body's async context (#1520 L5). Under overlap it errs toward refusal (a pool read refused as inside a body), never toward an auth-cache hit, since the cache's `ownsTx` answers for the body's own token. The store refuses a keyed body's notices and effects (above); a keyed caller that needs one moves its fan-out out of the body's context before it opts in. In-memory state a transaction reads is mutated only inside a queued transaction or its `afterCommit`, with one exception: a session's close (a request's end, the Slack bridge's detach, a revalidate's terminate) changes the registry and the session at once, so a body reads that state again after an await where it matters (P3 A7f2). That restores today's guarantee, "nothing else writes while I'm in a transaction", without depending on the event loop being blocked.
- A transaction body awaits only its own statements: no network, no blob I/O, no timers, no hooks (except `beforeCommit` hooks, D2, which run only statements on the Tx). A blob `put` already happens outside the row's transaction (`core/attachments.ts`) and stays that way. The queue enforces what it can see, on both backends (`store/tx.contract.ts`): a write a body leaves running after it settles is refused, and a timer it starts, firing while it's suspended, inherits its queue ownership, so a write, a post or the store's Read from it refuses (#1054). Ownership is per body: each started body gets its own token in an `AsyncLocalStorage`, and Postgres keys a body's open transaction on it, so `inTransaction`, the pool-read refusal and the auth cache's `ownsTx` answer for the calling body, never for whichever body is open. A continuation a body leaves running past its release (an async `afterCommit` effect's tail) holds a dead token and counts as outside every body. The change notices' pending facts are per transaction for the same reason (`store/notices.ts`). The one way left in is the body's `Tx`, captured by name: a reviewable capture, whose row commits or rolls back with the body. Nothing stops a body from awaiting a timer; that, and a captured `Tx`, are review's.
- **Abandoned bodies (#1535).** A write queued inside `abandonable(signal, …)` (`store/queue.ts`) whose signal fires before the body starts never runs: its caller rejects `RequestAbortedError` at the abort, and the scheduler drops the waiter when it heads the arrival list, the exclusive FIFO or the ready heap (the abort queues a pump), taking no slot or key; a dead exclusive waiter stops holding back keyed ones behind it. A body that started is never cut short. A body opts in only when a request handler queues it for that request's own answer and skipping it equals the body failing before its first statement, which every caller already handles: the hosted gate (exclusive and keyed; a skip is not a miss, so no exclusive fallback), the prior's touch, the native tool body, and native bind and unbind (`owning`; the subscriber role's bind and unbind, `mcp-resources.ts`, pass no signal, so only their selection is skippable), each with the HTTP request's signal passed explicitly from `mcp.ts`, never read from an ambient store (a commit's fan-out runs other requests' listeners in the committing body's context, above). Never skipped: an ending call's gate and body (`session_end`, `delivery_release`; `select` still refuses the call itself once its client aborted, as before), the end-of-call touch, refusal-row flushes, close touches, ends, sweeps, heartbeats, posted audits, delivery's open, renew, receipt and pending bodies. The mark is cleared inside every body, so a write a marked body, its effects or its `committed` queue is unmarked. Both stores, since both run every write through `WriteQueue`.
- Reads run concurrently on the pool, outside the queue.
- A body runs in the async context of the task that queued it (`AsyncLocalStorage` stores: its hosted exchange, its request origin), whether it started at once or waited: the queue snapshots a waiter's context at `run()` and starts it inside that snapshot, with its own holder token on top (#1408). Started from `release()` without it, a waiter inherits the releasing holder's context and judges its work as that other request's: a hosted resource read refused as another exchange's principal, an audit row carrying another request's origin (#1042).
- On Postgres writes have a pool of their own, W connections (`GRAYBOARD_DATABASE_WRITERS`, the scheduler's cap; default 8, `store/queue.ts` `DEFAULT_DATABASE_WRITERS`: with renew and receipt keyed, the 300-session localhost loadtest meets the bar at W = 8, 100% of tools ≤ 100 ms, and misses at W = 4, 98.2%): Bun's pool serves its callers FIFO, and a plain query queued behind as many waiting `begin`s as the pool has connections isn't served, so on one pool reads would wait behind writers (Bun's `src/js/internal/sql/pool.ts`). A transaction's connection goes back before its `begin` settles and the body's slot after that, so a started body never waits for a connection. The scheduler's writer ownership rests on the connections, not a per-statement check: no shared writer connection exists, both pools are read-only (`default_transaction_read_only`, so a pool write fails 25006) with `read write` on each `BEGIN`, a `Tx` dies with its body, and the statement handle a store function gets (`pgOf`) has no `begin`, `reserve` or `savepoint`. SQL text can still change a pooled session's settings (`SET`, `set_config`) or open a transaction: review catches that, nothing enforces it. The pools' `lock_timeout` is 5 s: an outside writer (`psql`, seeding) holding a row lock would otherwise stall an exclusive body, and every write behind it, without bound, as SQLite's `busy_timeout` bounds the same wait. A 55P03 rejects the write and releases the queue.
- The database can be ahead of memory on Postgres: once `COMMIT` lands, a pool read elsewhere in the process can see the rows before the commit's effects flush (the ack takes a round trip). The effects still come before the next queued transaction, which is all D2 promises; code that pairs a pool read with in-memory state tolerates the gap. A `COMMIT` whose connection drops before the ack is in doubt: the write rejects, logged `commit outcome unknown`, its effects don't run, and the rows may be committed (P4 decides recovery). That log and a failed post's carry a Postgres error as its class, code and SQLSTATE only: its detail quotes row values.
- The queue is measured (#1510): `grayboard_write_queue_{wait,hold}_seconds` by calling site, `_bodies_total`, `_keyed_bodies_total` and `_skipped_bodies_total` (abandoned, above) by site, `_depth` at enqueue, `_waiters` and `_running` now, and `grayboard_hosted_gate_bodies_total` by site (gate, prior, renew, receipt), the call the gate served (`method`: for the gate site an exchange's selection, a tool call's own gate, `control`'s renew, receipt, pending and release, `owning`'s open, bind and unbind, and the rest by name, so the subscriber calls' second gate body is told from the selection's, #1537; for the prior site the call that reused the verdict: a tool, renew, receipt, pending, open or bind) and outcome (keyed, miss, skipped: no attempt) (`src/server/metrics.ts`). On Postgres `grayboard_write_queue_statements` and `_round_trips` are per-body histograms by site (#1537): every statement the body's transaction sent, BEGIN, its COMMIT or ROLLBACK and the auth-mark read included, counted where they're sent (`store/pg/tx.ts` `counted`), and the round trips among them, where a statement sent while another of the body's is in flight (a SAVEPOINT, an eager audit insert) rides that flight. Round trips are the code's flights, assuming Bun pipelines what is sent un-awaited; pool reads outside a body aren't counted, and SQLite records neither. Statements × round-trip time is the floor of a body's hold, so a cut in framing or reads shows as a drop in its site's mean, and the keyed gate's count is pinned in `hosted.pg.test.ts`. The site is a literal the caller sets around its `write` (`atSite`, `store/queue.ts`): the hosted gate, `withPrior`, the native tool body, renew, receipt, the touches and posted audits have their own, everything else is `other`. A body inherits its enqueuer's site, so a write a body starts without one counts under the body's. Hold over wall time is the queue's busy fraction, the number that says when one queue stops being enough. `_world_stop_seconds_total` counts the time in which an exclusive body waited or ran (its drain of the keyed bodies ahead of it, then its hold): the time every keyed body arriving waits, and what keying more callers shrinks. `scripts/loadtest.ts` reports these per window and over the steady period, and `--pg-latency <ms>` puts a delay proxy (`tests/support/delay_proxy.ts`) between the server and Postgres, adding that much each way, to see how hold scales with round-trip time. `--gate pilot` judges a run by the pilot gate instead of the exit bar's 100 ms target (#1537): "doesn't fall over, with headroom" at an Aurora-like round trip (`--sessions 300 --period 6 --pg-latency 0.25`, W = 8), because at that RTT the lost DMs and lapsed leases were symptoms of saturation, not of latency. Every exit-bar check stays (connect, lost and misdelivered DMs, leases held each steady window, refusals, client errors, ops throughput, driver saturation, drain); each 99%-at-100-ms check becomes p99 ≤ 1 s on the same histogram, and the steady world stop must be ≤ 70%. Lapsed leases count from the drivers too (a lease op answering LeaseUnavailable outside churn and close): the per-window lease gauge misses a lease that lapses and is replaced within one window, and the server has no lapse metric. The 100 ms bar and the 1,000-session target stay for post-pilot tuning (#808).
- Granularity is measured, not guessed: the vertical slice (P4) runs `scripts/loadtest.ts` against Postgres, and #1510 keys bodies only because one queue's hold missed the 300-session bar. Exclusive bodies rule out deadlocks among the server's own transactions; keyed ones that overlap can deadlock in the database, which is the keyed caller's to rule out.
- Hosted's `inflight` call counts and `sweptAt` stay in process: the idle sweep's `busy` check (a session with a call running is never idle-ended or parked) is Stage 4's.
- Stage 4 (#808) externalizes this state (leases, issued sets, wake fan-out); the queue is the thing it replaces, which is why D3 does not lean on it. The cursor model (`id > read point`) and the drain gate assume ids allocate in commit order, which exclusive bodies give and overlapping keyed ones don't.

### D5. Hot reads stay in process

`authRead` runs per tool call and once a second per open stream: at the Stage 1 load about 1,000 checks a second, which as round trips would dominate. Principle 11 still binds: no cache outlives a revocation.

- **The generation.** An in-process counter that only grows (`src/server/store/pg/auth_generation.ts`). Statement triggers with transition tables on every table a cached answer reads, `oauth_tokens`, `oauth_grants`, `users`, `service_credential_secrets`, `service_credentials` and `principals` (and TRUNCATE; `ENABLE ALWAYS`, so replica-mode writes fire them too) mark the transaction (`gb.auth_touched`) and issue `NOTIFY gb_auth`; the write path (`store/pg/tx.ts`) reads the mark before COMMIT and bumps after it, before the queue's next body. A statement that changes no row (the OAuth cleanup's) marks nothing. A secret's revoke whose token `UPDATE` missed a racing mint changes only the secret, which `findActiveAccess` joins; the last two never change once written, but an operator's edit could (`0001_init.sql` lists why). Writers outside the process exist (an operator's `psql` disable, `scripts/loadtest.ts` seeding a live server), so the server's `LISTEN` connection bumps the counter on each notification, its own included (one extra clear per auth write). An outside write takes effect when its notification arrives, after commit; the process's own writes take effect before the next queued transaction.
- **A fill can't race a bump.** A cache entry (`src/server/store/auth_cache.ts`, over a per-backend generation source) records the generation read before its database read, and is stored only if the generation is unchanged after the read resolves. A read that straddles a bump returns its result uncached.
- **No shared pin.** Each `authRead` carries its generation in its own scope, not in one module variable (`pinned`, #881), because async auth reads overlap.
- **The hosted gate's stamp.** The hosted gate checks the token outside its transaction and skips the in-transaction check when the generation it checked under is unchanged just before its body starts (`withGate`, `src/server/hosted.ts`; #807 P3 A7d2b). That reads equal generations as "no commit to the auth tables between them", which holds on SQLite, where every commit moves the generation synchronously, but not for an outside write whose notification hasn't arrived yet. So the gate compares its own signal, `Repo.commitGeneration()`, not `authGeneration()`: the Postgres store keeps its counter for the caches and the stream timer but returns undefined from `commitGeneration()`, so the gate checks again in every body and the stamp is a SQLite saving only.
- If the `LISTEN` connection drops, the cache is disabled (every check reads the database) from its `onclose` until it re-listens (a bump comes with it), so a lost notification can't leave a revoked token cached; a heartbeat through the pool every 5 s turns it off when the last one never arrived, so a silent drop is bounded at 10 s; the first `LISTEN` is retried by the server (Bun retries only after a connection it had), and so is a re-`LISTEN` after a drop that is still unacknowledged after a full heartbeat interval (no heartbeat is sent while off, so nothing else would notice it). The `LISTEN` has a `Bun.SQL` instance of its own: `onclose` is per instance, so on the store's pool an idle read connection's close would look the same.

- **No store bumps it itself.** A Postgres store group's writes to those tables (the OAuth store's, `setDisabled`'s) add no hook: the triggers mark the transaction and `store/pg/tx.ts` reads the mark, for every group alike, so a group ported before C9 needs no change after it.

Stage 4 keeps this shape across pods: every pod listens.

### D6. Types and SQL

- Timestamps stay integer milliseconds in `int8` (`bigint`); ids are `int8 GENERATED ALWAYS AS IDENTITY`. Row mappers in the store convert `int8` strings to `number` (every value is below 2^53); nothing above the store sees a string id or time.
- Booleans become `boolean`: `hosted_alias_lost.was_primary`, `messages.pending`, `ids.launcher`, `ids.viewer`, `ids.keyed`, `ids.local_resume`, `aliases.human`, `aliases.queue_off`, `outbox.wake`; their queries change `= 1` to the bare column and `SUM` over one to `count(*) FILTER (WHERE …)`. JSON columns queried by path or parsed on read become `jsonb`: the `data` of `oauth_requests`, `oauth_browsers`, `oauth_codes` and `oauth_grants`, `access_log.detail`, `ids.held_aliases_json`, `slack_progress.progress`; `json_each`/`json_extract` become `= ANY($1)` over an array or `jsonb_array_elements`, and `->>`. `write_receipts.result_json` stays `text`: an in-flight write's placeholder is `''`, not valid `jsonb`, and a replay re-sends the stored bytes, which `jsonb` would reorder. `oauth_tokens.access_scopes` stays `text` (`JSON.stringify` of the scopes, parsed on read): nothing queries it by path, and its SQL NULL means a pre-downscope row whose scopes are the grant's, which a `jsonb` column would have to keep distinct from JSON `null`. The OAuth `data` writes pass the object.
- Every `text` column is `COLLATE "C"`. SQLite compares BINARY everywhere, so one uniform rule mirrors it (the cluster default, `en_US.utf8` in the docker image, orders `a_b` before `aB`), and a btree index can serve `LIKE 'prefix%'`. Picking columns by `ORDER BY` would need an audit of every query at every port.
- Postgres refuses NUL: U+0000 in `text` (22021) and `\u0000` in `jsonb` (22P05). SQLite stores both. A message or post body with NUL is refused in core `checkBody`, in both modes (#807 P3 C5), as are a claim key and note (`validKey`, `validNote`); a body the system composes (a claim's announcement) replaces any NUL with U+FFFD instead (`systemBody`), since an older row may hold one; a status line can't carry one (`oneLine` strips control characters); the messages store relies on that and passes bodies through, its other text columns being validated addresses; each other store port decides whether its inputs refuse or strip it. `jsonb` also refuses a lone surrogate (22P02): audit rows and Slack progress store NUL and lone surrogates as U+FFFD (`jsonSafe`), since refusing would fail the audited action.
- The two queries that tiebreak on SQLite's `rowid` (`aliasUser`'s `ORDER BY …, started_at, rowid` in core/bindings.ts and `hosted_alias_lost`'s `ORDER BY at, rowid` in db.ts) read a `seq int8 GENERATED ALWAYS AS IDENTITY UNIQUE` column instead, on `ids` and `hosted_alias_lost`.
- SQLite forms map: `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`; `INSERT OR REPLACE` → `ON CONFLICT ... DO UPDATE`; two-argument scalar `MAX` → `GREATEST`; `IS NOT ?` → `IS DISTINCT FROM`; `rowid`, `last_insert_rowid`, `.changes` → `RETURNING` and the result count (a DELETE's is `.count`; its row list is empty); `?N` → `$N` (tagged templates); `CROSS JOIN … ON` is SQLite-only (42601 on Postgres: an inner `JOIN` or an `EXISTS`); a parameter used only in `$n IS NULL` has no inferable type (42P18) and takes a cast (`$n::text`). `+col` planner hints and the `EXPLAIN QUERY PLAN` pins in `db.test.ts` don't carry over; plan pins that matter are rewritten against `EXPLAIN (FORMAT JSON)`.
- SQLite's integer truth in a `WHERE` (`AND 1`, `kind IN ()` written `0`) fails 42804 on Postgres: write `TRUE`/`FALSE`, and `= ANY($array)` for a list, which an empty array makes match nothing. `json_group_array(… ORDER BY …)` becomes `ARRAY(SELECT … ORDER BY …)`, which Bun.SQL returns as a JS array. A `jsonb` parameter takes the object (`JsonParam`, `src/server/store/pg/sql.ts`), never its `JSON.stringify`. An order a caller relies on is an explicit `ORDER BY` on both backends: Postgres's plan promises none, and an `UPDATE` moves a row to the end of the heap.
- Errors are classified by `errno` (SQLSTATE) in one place, `src/server/store/pg/errors.ts`: `23505` with its `constraint` to the domain refusal it means; `40001`/`40P01` cannot arise at READ COMMITTED without explicit locks out of order, and are treated as server errors if they do. Bun.SQL's `code` is its own class (`ERR_POSTGRES_SERVER_ERROR`), not the SQLSTATE, so nothing reads it but for the two failures that carry no SQLSTATE: a rolled-back COMMIT, and a connection that never opened (`ERR_POSTGRES_CONNECTION_*`, which the startup wait `transientConnectFailure` retries with 57P03, 53300 and class 08; `src/server/store/pg/connect.ts`, #1418). An error a transaction body catches without a savepoint aborts the transaction: the next statement fails `25P02`. The write then rejects `TxAborted` (`src/server/store/pg/tx.ts`), cause the `25P02` or Bun's rolled-back `COMMIT` (`ERR_POSTGRES_COMMIT_ROLLED_BACK`, no SQLSTATE), naming the fix: a statement that may fail as part of normal control flow (`23505` on a create) runs in `tx.savepoint`. When the failure was a statement sent without await (an audit row, `src/server/store/pg/audit.ts`), the rejection names it as `first`, with its SQLSTATE in the message and `errno`, unless a savepoint it was sent in rolled it back (#1302). Every `BEGIN` pins `isolation level read committed, read write`: a bare one inherits the database default, which a parameter group can set to serializable. Bun queries are lazy, and an `await` alone sends one a microtask later, after a `SAVEPOINT` a sibling task opened meanwhile, so a parent's statement would roll back with that savepoint. `pgOf`'s handle sends each statement as it's built, so statements reach the connection in the order the code builds them, as SQLite's run; every one is still awaited for its error. No retries: a retry re-runs a body whose in-memory reads have moved on, and an in-doubt `COMMIT` makes even a safe-looking one double-apply.
- The driver is Bun.SQL (`src/server/store/pg/sql.ts`): no dependency in a signed, compiled release. It has no per-type parsers, so `int8` arrives as a string and goes through the mappers. A string bound to a `jsonb` parameter is stored as a JSON string scalar, not parsed: pass the value, never `JSON.stringify` of it.

### D7. Schema and migrations

- The Postgres schema is new DDL, not a translation of `CREATE TABLE IF NOT EXISTS` plus guarded `ALTER`s. Not carried over: the legacy tables (`identities`, `cursors`, `handles`); `audit_log`, which only local mode writes (the server audits to `access_log`); `hosted_sessions.name` (vestigial since #451) and `ids.token_session` (unused since #282). `src/server/store/pg/schema-parity.test.ts` compares `0001_init.sql` with a SQLite server database and lists every difference, so a SQLite column added without its Postgres twin fails it.
- Migrations are numbered SQL files in `src/server/store/pg/migrations/`, embedded in the binary and applied at boot by `migrate.ts` in one transaction under `pg_advisory_xact_lock`, recorded in `schema_migrations` with a sha256 checksum. The lock is transaction-scoped because COMMIT or ROLLBACK releases it whatever the body did; a session lock on a pooled connection could outlive an error path. The record table's own `CREATE TABLE IF NOT EXISTS` races without the lock (two fresh boots fail `23505`). A boot refuses a recorded migration whose checksum differs from its file, and runs on recorded versions it doesn't know (a newer release migrated; N-1 must run). `0001_init.sql` is edited in place only while no kept database has applied it: the first database that is kept (a pilot run under `GRAYBOARD_UNRELEASED_POSTGRES=1`, or the first release that runs a server on Postgres, P5, whichever comes first) records its checksum, an in-place edit after that stops the server's boot, and every later schema change goes in `0002` onward. From then on files are append-only. Changes follow expand/contract: a release adds (columns, tables, dual writes), a later release removes once no running version reads the old shape. This replaces "schema changes are additive" for the server; local mode keeps that rule.
- Open-time data steps that are migrations in all but name (`migrateHostedHolds`, `seedSchema`, `sweepStaleLaunchers`, the attachment backfill) are not ported: the import (D8) starts from a database HEAD already opened, and on Postgres a hosted end clears its launcher flag, so no stale mark arises.

### D8. Landing and cutover

Master stays releasable throughout; the released server stays SQLite until the cutover release.

2. **P2, the server-only invariants into SQL (D3)** on SQLite. SQLite serializes these transactions, so where a slice can, it adds a test that lands the other caller's write between this caller's read and its write with a SQLite trigger, the one interleaving a single writer allows; the two-transaction test on Postgres comes with P3. **P2-1** OAuth single use: `redeemCode` and `redeemLoginCode` insert what they mint (the grant or the session, which `oauth_codes.grant_id` and `session_id` reference), then spend the code with `UPDATE oauth_codes SET grant_id|session_id = ? WHERE hash = ? AND kind = 'refresh' AND spent_at IS NULL AND revoked_at IS NULL AND expires_at > ? RETURNING hash`. Zero rows means another caller spent it first: the loser deletes the rows it inserted in its own transaction (no rollback sentinel, since nothing else saw them) and re-reads the code or token, which on Postgres's READ COMMITTED shows the winner's commit, then answers as the replay path always has, or `not_found` when the code or the winner's grant is gone (revoke what the winner minted, audit `oauth.code_replay_revoked` or `oauth.refresh_replay_revoked`); a token the re-read finds revoked or expired, not spent, answers invalid. RETURNING` (zero rows: `not_found`) and `bindRequestSession` binds with an `UPDATE` conditioned on the request being unbound or bound to the same browser session (zero rows: `not_found`); no SQLite write lands between their read and write, so their race tests come with P3. **P2-2** `dedupWrite` claims the receipt before the write: `writeReceipts.claim` inserts a placeholder (`ref_id` 0, empty result) with `ON CONFLICT(session, sender, fp) DO NOTHING RETURNING`, and the write's `upsert` fills it in the same transaction. RETURNING` on the stale row, then `request.receipt_stale` is audited and the call writes fresh. A lost reclaim reads again, so it replays the call that replaced it; three passes bound the loop (a pass that neither claims nor answers needs another transaction's commit in between, which SQLite never allows). `resend: true` skips the claim and upserts, as before. ### D9. Tests

- **Isolation by template database** (`tests/support/pg.ts`). `bun test --parallel` runs files in worker processes, so there is no suite-level setup: the first process to need it builds `gb_tpl_<hash of the migrations>` under a cross-process advisory lock, renames it into place only when complete and marks it non-connectable (a connected template refuses `CREATE DATABASE … TEMPLATE`). The hash lets several checkouts share one cluster. Each test gets `CREATE DATABASE … TEMPLATE` it, dropped after; a later run drops a killed run's per-test databases (`gbt_*`) once they are 6 hours old. Each process that uses a template stamps it (`COMMENT ON DATABASE`, epoch ms), and the sweep drops another migration set's template whose stamp is over 7 days old; an unstamped one (built before stamps) is stamped on first sight and ages from there. Another checkout may still use a recent one, and one coming back to an aged-out one rebuilds it in about a second. `GRAYBOARD_TEST_PG_URL` names the cluster. `GRAYBOARD_TEST_BACKEND=pg` puts each `TestServer` (`TestServer.open`) on a database of its own cloned from the template, kept across `restart()` and dropped by its final stop; a server given a `dbPath` stays on that SQLite file, and tests SQLite by nature (a second connection to the file, the `sync_access` oracle) skip there through `describeSqlite`/`testSqlite`. `ServerProcess` takes `{ url }` (the gate and a blob directory set for it); release binaries stay SQLite. Postgres-backed tests skip when the variable is unset, and the SQLite store keeps the suite's coverage. `GRAYBOARD_TEST_PG_REQUIRED=1` with the variable unset fails instead of skipping, so a lost service can't turn the server tests silently green. CI's `test` job runs a `postgres:18.7` service container (pinned by digest, default settings) and sets both (`.github/workflows/test.yml`); the hosted e2e suites stay SQLite until P5.
- **Helpers go through the store.** `hostedRowCount`, `accessAudits`, `busRows`-style readers become async store reads, so tests stop issuing SQL. Test files that run SQL directly are ported with the module they test, not up front.
- **Conformance suite (D1)**: tool-surface scenarios (DM, board, claim, bind, delegate, attachments, session end) run against local mode and the hosted server; it starts small in P3 and grows with each port.
- **One transaction contract, run per backend.** `src/server/store/tx.contract.ts` holds the portable tests of D2's handles and the write path (`write`, `post`, the queue) over a harness each backend supplies: SQLite runs it from `store/tx.test.ts` and `store/queue.test.ts`, Postgres from `store/pg/tx.pg.test.ts` beside the Postgres-only cases (aborted transactions, commit-time failures, a killed connection, the read-only pool, `lock_timeout`, and the two-store race template D3's tests copy: two stores on one database are two pools and two queues). A backend declares what legitimately differs (`post`'s result for a body that finishes synchronously); synchronous-only paths and per-backend handle checks stay in each backend's own tests. The identity groups do the same (`src/server/store/identity.contract.ts`, from `src/server/db.test.ts` and `src/server/store/pg/identity.contract.pg.test.ts`), and their races are Postgres-only tests in `src/server/store/pg/identity.pg.test.ts`, each in T-P12's two-store shape and asserting the end state the race would break. The OAuth store the same: `src/server/store/oauth.contract.ts` (from `src/server/oauth-store.test.ts` and `src/server/store/pg/oauth.contract.pg.test.ts`), races in `src/server/store/pg/oauth.pg.test.ts`. The aliases and messages groups the same: `src/server/store/aliases.contract.ts` and `src/server/store/messages.contract.ts` (from `src/server/db.test.ts`, `src/server/store/pg/aliases.contract.pg.test.ts` and `src/server/store/pg/messages.contract.pg.test.ts`), races in `src/server/store/pg/aliases.pg.test.ts` and `src/server/store/pg/messages.pg.test.ts`. The cursors, write receipts, audit and Slack groups the same: `src/server/store/{cursors,write_receipts,audit,slack}.contract.ts`, from `src/server/db.test.ts` and `src/server/store/pg/*.contract.pg.test.ts`, races in `src/server/store/pg/{cursors,write_receipts,audit,slack}.pg.test.ts`. The hosted group the same: `src/server/store/hosted.contract.ts`, races in `src/server/store/pg/hosted.pg.test.ts`. ## Open questions

- **Postgres major.** The RDS major the platform runs; CI and local tests pin the same image. `postgres:18` until the platform answers.
- **Pool size.** `Bun.SQL` defaults to 10, and the read pool keeps it; writes take W more (D4), and D5's `LISTEN` one more of its own. Each pool dials to its size on first use. Size them from P4's measurements, against the RDS instance's `max_connections`.
- **Inspector and usage scripts.** `scripts/inspect.ts` (a released binary) and `scripts/usage.ts` read a server's SQLite file. At P5 they either read Postgres or drop their server views; decide before the cutover release.
- **Import window.** P5's import is offline: the team server is down for the copy. The live database is small, but measure it before choosing offline over dual-write.

## Not in scope

HA, multiple pods, blobs in object storage, and externalized hub state are Stage 4 (#808). This design keeps them possible: D3's invariants hold across pods, D4 names exactly what Stage 4 replaces, and D5's notifications already reach every pod.
