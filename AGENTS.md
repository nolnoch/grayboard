# grayboard — agent instructions

Durable coordination bus for coding agents (boards, claims, DMs) across harnesses. Bun + TypeScript, SQLite. Two modes behind one tool surface: local (same machine, Unix-socket wakeup) and distributed (central server, WSS). Design docs: `docs/`, governed by [`docs/CONTRACT.md`](docs/CONTRACT.md) — read it before editing any doc.

## Commands

- Install deps: `bun install`
- Typecheck: `bun run typecheck` (covers `src/`, `adapters/pi/` and `adapters/opencode/`; see gotchas)
- Test: `bun run test` (root/backend suite; `tests/integration/` starts real servers and MCP children). One file: `bun test <path>`. Hosted OpenCode is an independent package: `bun run test:opencode` installs its own frozen lockfile, strictly typechecks, tests and builds it; root install/typecheck does not cover it.
- Test helpers live in `tests/support/`: `until()` (poll a condition; no fixed sleeps), `localSession()`/`mcpSession()` (a `grayboard mcp` child in an isolated env), `TestServer` (in-process server; `srv.session()` for server-mode children), `ServerProcess` (a compiled server as its own process), `runCli()` (kills its process group on timeout), `releaseBinaries()` (a release's binaries, digest-checked and cached in `.e2e-cache/`), `ReleaseServer` (a stand-in releases origin for `update`/`install.sh`), `buildCli()` (this tree compiled, optionally under another version or, with `keys`, trusting test keys), `tests/support/release_keys.ts` (openssl-made test keys and signed `SHA256SUMS`), `piScenario()` (a real pi session woken through the bus), `keep()` (copy evidence into the e2e run dir; a no-op under plain `bun test`). Use them rather than a per-file copy. A race a test must force goes through a `testPause` point (`src/shared/testpause.ts`, set by `BUS_TEST_PAUSE`/`BUS_TEST_PAUSE_FILE`), never a sleep.
- E2E suites: `scripts/e2e.sh <suite>` (suites: its usage line), the one entry point for CI and by hand. Files named `*.e2e.ts` (`tests/e2e/`) are outside `bun test`'s discovery, so root `bun run test` does not run them. Hosted suites are separate CI jobs and release gates; merge enforcement also requires their aggregate status in the repository ruleset. The pre-push hook also runs strict package, normal host and helper config acceptance. Each run writes a run dir (`.e2e-runs/`, gitignored; CI retains evidence for 7 days). Hosted uploads contain only constructed metadata; raw diagnostics remain private. `.github/workflows/e2e.yml` runs the nightly suites and is called by `release.yml`; a nightly failure opens or comments on a "Nightly e2e failing: <suite>" issue.
- Build binaries: `bun run build` → `dist/grayboard`, `dist/grayboard-server`
- Run from source: `bun src/cli/main.ts <cmd>`; server: `bun src/server/main.ts`
- Manual distributed smoke: `GRAYBOARD_DEV_AUTH=1 GRAYBOARD_DB_PATH=/tmp/gb.db GRAYBOARD_PUBLIC_URL=http://localhost:8080 bun src/server/main.ts`, then `bun src/cli/main.ts login --dev you@example.com --server http://localhost:8080`, then `BUS_IDENTITY=fe bun src/cli/main.ts mcp --mode server`. `tests/integration/ws.test.ts` covers the same path over real WebSockets.

## Git hooks

Install once per clone: `git config core.hooksPath scripts/hooks`. `scripts/hooks/pre-push` runs:

1. Per pushed ref, the docs gate (`scripts/docs_gate.sh <sha>`): refuses a push whose commits since the `docs-baseline` tag change anything other than docs (`docs/`, any `*.md`), tests (`tests/`, `*.test.ts`), `scripts/`, `assets/` and `.claude/`, until the docs are reconciled. Bypass for deliberate WIP: `DOCS_GATE_BYPASS=1 git push …`, and tell the user. Inert until the tag exists; fails open on its own errors.
2. Once, with Bun 1.4.4: root typecheck/tests, then independent hosted package strict/unit/build, normal actual-backend host and helper-generated config gates.

`docs-baseline` is a local tag (never pushed); a fresh clone's gate is inert until its first reconcile. Reconcile: follow `.claude/commands/reconcile-docs.md` (Claude Code: `/reconcile-docs`). The tag moves only through `scripts/advance_docs_baseline.sh`. CI (`.github/workflows/test.yml`) is the universal gate; the hook is local protection.

## Contributions

- Commits are signed — `commit.gpgsign` is on in these checkouts; unsigned commits don't merge.
- GitHub Actions are pinned by full commit SHA with the release in a trailing comment (`@<sha> # vX.Y.Z`, the commit an annotated tag points to, not the tag object); the repo's `sha_pinning_required` setting fails any run that uses a tag. Dependabot (`.github/dependabot.yml`) opens the bump PRs.
- Commit and PR subjects carry the issue key; conventional prefixes (`feat:`, `fix:`, `chore:`…) on commits and PR titles.
- Issues and PRs open with the concise front — the problem, the value of solving it, the proposed solution — 2–5 bullets each; verbose detail after, for agents. Templates live in `.github/`; the filer applies the surface label (server, local, core, cli, adapters, bridge, ci).
- Reviews block on medium-and-up findings; file lower ones as `follow-up` issues rather than chasing them in review rounds. A PR merges when each in-scope item is fixed or deferred to a filed issue.
- Issues with a human audience get a Jira render, generated with `scripts/jira-format.mjs` from the issue's spec; the Jira ticket is a render, not the spec — the GitHub issue stays the source of truth.
- Jira tickets lead with the same concise front — the problem, the value, the solution — 2–5 bullets each; verbose detail after.

## Load-bearing gotchas

- **Public repo.** Don't name employers, clients or private projects (repos, ticket prefixes, people) in committed files. Use stand-ins: `ticket:ENG-142`, `#e2e`, `be`/`fe`/`sim`, `you@example.com`. Grep the staged diff before every commit.
- **Bugs and feature requests are GitHub issues** (`gh issue create`), not doc sections or TODO lists.
- **Two modes, one tool surface.** Board, claim and peer tools are defined once in `src/core/tools.ts`. DM tools are implemented per surface: `src/local/mcp.ts`, `src/plugin/mcp.ts` (+ `src/server/application.ts`) and hosted HTTP `src/server/mcp.ts` (over the same application). Change every surface or they drift.
- **Every instruction sentence costs every session.** MCP instruction text (`src/core/tools.ts`, `src/shared/inbox.ts`, `src/local/mcp.ts`, `src/plugin/mcp.ts`) is paid in tokens by every agent on every start. Add a sentence only when it's conditional on state that makes it relevant (human handles, team membership, notices).
- **Exactly one delivery owner per handle.** A retained child-adapter harness that drops MCP notifications (pi, local/V1 opencode) gets one push-mode `grayboard mcp` from its adapter, which serves the tools itself; the harness's `grayboard` MCP entry stays `enabled: false` with `BUS_PUSH=off` and is only the adapter's config. A push-mode server whose notifications go nowhere consumes messages into a void. See `docs/boards.md` §9.
- **`bun:sqlite` isolation.** `src/server/db.test.ts` fails if anything outside `src/server/db.ts`, `src/core/`, `src/local/`, `src/bridge/` imports `bun:sqlite`. That keeps the server's `Repo` facade the Postgres seam. Server data goes through `Repo`.
- **The human handle is a declaration (`grayboard human`), not a session flag.** `BUS_HUMAN=1` only asserts it; `src/local/mcp.ts` refuses a session where the two disagree. Don't make anything an agent can reach set `aliases.human` or start `#announce` posts: that board's authority depends on it. See `docs/slack-bridge.md` §3. On a server the name `human` is reserved for the Slack bridge's in-process connections (`src/server/application.ts` `attachHuman`); don't open a client path to it (§8).
- **Logout truncates the credentials file; it must not delete it.** `busMode()` (`src/cli/api.ts`) picks server mode when the file exists, so an empty file makes `grayboard mcp` fail with "signed out" instead of silently switching the user to local mode.
- **Upgrade support floor: v1.0.0.** Every database a v1.0.0-or-later release wrote must open under HEAD. `tests/integration/upgrade.test.ts` checks the latest release per push, and `scripts/e2e.sh upgrade-matrix` checks every v1.x release. So `bun test` (and the pre-push hook) needs network: the upgrade tests list releases from the GitHub API on every run and download a release's binaries once (cached in `.e2e-cache/`). Set `GITHUB_TOKEN` if you hit the API's anonymous rate limit; `GRAYBOARD_UPGRADE_FROM=<tag>` picks the release.
- **Schema changes are additive.** No migration tool: every open runs `CREATE TABLE IF NOT EXISTS` (`src/server/db.ts`, `src/core/schema.ts`, `src/local/open.ts`); new columns go in as a guarded `ALTER TABLE … ADD COLUMN` (pattern in `src/core/schema.ts`). Deployed databases must open under the new code. Every opener goes through `openSqlite` (`src/core/sqlite.ts`), which runs the schema step in one `BEGIN IMMEDIATE` transaction: processes open one file at once (a session and the Slack bridge), and a guarded ALTER outside that transaction races (#170).
- **The omp adapter is outside `tsconfig.json`** (it imports harness-only types). `bun run typecheck` doesn't see it; typecheck in a scratch dir against the harness's own `node_modules`, or test in the harness. The pi and local/V1 opencode adapters typecheck against their pinned devDependencies. Hosted V2 uses native tools/OAuth plus its independent in-process subscriber, not a CLI child; `setup-opencode` requires an explicit HTTPS URL/config and full Git revision (or installed-directory fallback), and ordinary setup/refresh preserves hosted or uncertain registrations.
- **The factory module is isolated.** `adapters/factory/` (opt-in, #293) imports only `src/plugin/client.ts` and `src/shared/protocol.ts` from `src/`, and nothing in `src/` imports it. `scripts/check_factory_isolation.ts` enforces both directions under `bun test`. Orchestration code goes in the factory, never in `src/`.
- **Fleet sessions bind task names, not directories.** A session starts unbound and calls `bind` with a task name (`research-1`, `auth-refactor`); one that must come back under a name sets `BUS_IDENTITY` in its launch command. A second session on a live name starts unbound, naming the holder. N sessions share one checkout freely on the bus; writers still take worktrees — two writers share `.git/index`, which is git's constraint, not the bus's. Claims partition work across all of them; they never substitute for index isolation.
- **`tests/integration/pi.test.ts` runs the real pi CLI** (pinned devDependency) and needs Node ≥ 22.19 on PATH.
- **Markdown is soft-wrapped**: one line per paragraph or bullet.

## Releasing

Releases are cut from `master` by tag. Assets and targets come from `.github/workflows/release.yml` (CLI and server binaries per target, `install.sh`, the `deploy-*` files `install.sh` places on a server, `SHA256SUMS` and `SHA256SUMS.sig`); read it rather than trusting a count here.

1. Bump `version` in `package.json` on the release branch and merge to `master`. A release that needs words the generated notes can't give (the first signed release, #322) gets `.github/release-notes/vX.Y.Z.md` in the same merge; the release job puts it above the generated notes. The workflow's first job refuses a tag that isn't `v<package.json version>`, because `grayboard update` checks that the downloaded binary reports the tag's version. So a pre-release tag (`v1.3.0-rc1`) needs the matching pre-release version.
2. `git tag vX.Y.Z && git push origin vX.Y.Z`. The workflow runs root tests and independent hosted gates → cross-compile (Linux runners, every target) → the binaries suite per target it runs on, while the upgrade matrix and the `hosted-network` suite (`hosted-live` + `hosted-public`, both via `e2e.yml`) run from the start and also gate the release job. Then the `release` job waits for the maintainer's approval (environment `release`, `v*` tags only; it alone holds `RELEASE_SIGNING_KEY`), signs `SHA256SUMS`, verifies the signature against `assets/release-keys/`, attests provenance and publishes. The gate is one account, not two-person control: the maintainer is the only reviewer, may approve their own run, and as an admin can bypass it. Publishing creates a draft, uploads the assets, then publishes it: a failure before the draft leaves no release, and a failed upload leaves a draft (step 4). There's no manual trigger: a branch run must never reach the key.
3. Verify: `gh release view vX.Y.Z` lists every asset including `SHA256SUMS` and `SHA256SUMS.sig`; `gh release view vX.Y.Z --json isImmutable` says `true` (the only proof the setting applied); `gh attestation verify <asset> -R nolnoch/grayboard`; the release workflow's post-release `hosted-live` and `hosted-public` verification of that same published tag commit both pass; `grayboard update` locally (it prints the key it verified), then `grayboard --version`; after updating a server, `scripts/deploy_check.sh <server url> vX.Y.Z`.
4. Immutable releases is on for this repo (Settings → General), so a published release can't be edited, and a deleted one's tag can never be reused. A run that failed before publish left no release, or only a draft: delete any draft (`gh release delete vX.Y.Z`, which a draft allows), then the tag (`git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z`), fix and re-tag. A bad published release is superseded by the next patch version.

**Release signing key (#162).** ECDSA P-256. The public half is `assets/release-keys/<key id>.pem`; `bun scripts/release_keys.ts sync` regenerates `src/shared/release_keys.ts` and install.sh's key block from that directory, and a test fails if they differ. The private half lives only in the `release` environment secret (write-only: GitHub never returns it) and one offline backup the maintainer keeps; no one cutting a release handles it. Release authority is the environment's reviewer list: add a reviewer there, never share the key. New key: `bun scripts/release_keys.ts keygen <path outside the repo>`, then `gh secret set RELEASE_SIGNING_KEY --env release < <path>`, back it up, delete the file. Rotation: a release signed by the old key ships the new key's file; the next release is signed with the new key; a later one drops the old file. Loss of every listed private key means no installed binary can `update` again; recovery is a new key in a new release that users install by re-running `install.sh`.

A release that changes server behavior needs the server updated too (README §Updating the server).
